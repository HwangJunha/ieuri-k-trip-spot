> 설계 문서: `problem/SPEC-0010-client.md` · 수용 기준: `Specs/SPEC-0010/spec.md` (R1~R25)
> Stitch 프로젝트: `projects/8651053354437738829` (K-Trip Spot Design System)
> 디자인 시스템: `assets/073fee5b990e4b1eb2c918d7e9de2d8f`

이 문서는 **레이아웃·컴포넌트 분해 참조**다. 수용 기준과 어긋나면 스펙이 이긴다.

목업의 샘플 콘텐츠(닉네임·본문·spot 이름)는 디자인 확인용이며 실제 데이터는 라이브 API다.

## 1. 커뮤니티 탭 (R7, R8, R10, R11)

> Stitch 화면: `Community — Spot Talk` — `screens/aa677bb553d24e99921c4caa142486d8`

하단 탭으로 진입하는 화면. 라우트 `/community` 와 탭 라벨 `navCommunity` 는 SPEC-0008 이
이미 만들어 두었으므로 **탭을 새로 만들지 않고 스텁 내용만 바꾼다** (설계 문서 §1).

```
Scaffold (하단 플로팅 내비 유지, Community 탭 활성)
├── AppBar               title "Spot Talk", 뒤로가기 없음
├── 스크롤 본문
│   ├── DiscoveryTileGrid       2열 그리드, 타일 높이 ~110
│   ├── TopicChipRow            가로 스크롤 한 줄
│   └── 지역 피드 섹션 "Nearby"
│       └── PostCard × N        커서 페이지네이션
└── FAB                  compose 아이콘, primary — 글 작성 진입
```

**필터 UI 는 태그 칩 한 줄이 전부다.** 정렬 선택도, 추가 필터도, 상단 탭도, 검색창도 두지
않는다 (설계 문서 §3). 상태는 "선택된 topic (없을 수 있음)" 하나뿐이다.

### 컴포넌트

| 컴포넌트 | 역할 | 비고 |
|---|---|---|
| `DiscoveryTileGrid` | `DiscoveryTile` 2열 그리드 | 타일 제목은 **서버 문자열 그대로** 표시 (§4) |
| `DiscoveryTileCard` | 사진 + 하단 그라디언트 + 흰 제목 | 탭 → 해당 topic 필터로 진입 (R11) |
| `TopicChipRow` | 주제 태그 칩 한 줄, 단일 선택 | 표시 문자열은 **클라이언트 l10n 매핑** (§4) |
| `PostCard` | 피드 항목 | 아래 분해 참조 |
| `PostSpotChip` | 위치 핀 + spot 이름 pill, secondary 톤 | 탭 → spot 상세 |
| `PostActionBar` | 하트+좋아요 수, 말풍선+댓글 수 | 각각 ≥48dp |

### PostCard 분해

```
PostCard
├── 헤더 행    아바타 · 닉네임 · middot · 상대시각 · [⋮ 오버플로]
├── PostSpotChip
├── 본문       2~3줄, 넘치면 ellipsis
├── 사진       0장(없으면 미렌더) / 1장 와이드 / N장 썸네일 행
├── 주제 태그 pill   저강조
└── PostActionBar
```

- 작성자를 눌러도 **이동할 곳이 없다** — 프로필 화면이 비범위 (설계 문서 §6). 닉네임과
  프로필 이미지는 표시만 한다.
- 사진이 없으면 자리를 비워두지 않고 **영역 자체를 렌더하지 않는다.**
- 댓글 수는 서버 `commentCount` 를 그대로 쓴다 — 목록 길이로 계산하지 않는다 (설계 문서 §3).

### 타일 → 필터 반영 (R11-3)

타일에서 진입해도 **같은 상태에 반영**되어 상단 칩이 그 태그로 선택된 것처럼 보인다.
타일 진입과 칩 선택이 서로 다른 화면 상태를 만들지 않는다.

### 상태

| 상태 | 화면 |
|---|---|
| 로딩 | 피드 자리 로딩 인디케이터 |
| 빈 피드 | "아직 글이 없다" 안내 |
| **위치 권한 없음 / 좌표 실패** | 지역 피드를 비우고 **그 사유**를 표시 — 빈 피드와 다른 상태다 (설계 문서 §3) |
| 추가 로딩 | 목록 하단 인디케이터 |

**Stitch 목업에는 정상 상태만 있다.** 위 상태 화면은 목업 없이 구현한다.

### 목업이 스펙과 어긋나는 지점 — 목업을 따르지 않는다

생성된 목업에 아래가 섞여 있다. **스펙이 이긴다**(문서 머리말).

| 목업 | 실제 구현 |
|---|---|
| 하단 내비가 5탭(Home·Map·Discover·Events·Chat), **Home 활성** | SPEC-0008 이 만든 현재 탭 구성을 그대로 쓰고 **Community 탭이 활성**이다. 목업의 탭 구성은 DESIGN.md §8 의 옛 5탭이라 이미 낡았다 |
| 앱바에 하트 아이콘 | 스펙에 없다. 두지 않는다 |
| 두 번째 카드 사진이 세로 스택 / `+2` 인디케이터 | 배치는 미확정(§10). `+N` 는 스펙에 없는 발명이므로 근거로 삼지 않는다 |
| 주제 태그가 `#Photo` 처럼 해시태그 표기 | 표시 문자열은 **l10n 매핑**이다(§8). `#` 접두사는 목업의 장식이며, 4개 언어 문자열에 `#` 를 넣지 않는다 |

## 2. spot 상세 안의 피드 (R6)

> Stitch 화면: `Spot Detail — Posts Section`

SPEC-0003 의 상세 화면(`Spot Detail`) 하단에 섹션으로 끼워 넣는다.

```
… 기존 상세 섹션들 (Overview / Contact) …
└── 게시글 섹션
    ├── 섹션 헤더 "Posts" + 우측 "Write" 텍스트 버튼
    ├── PostCard × N       해당 spot 의 글만, 최신순
    └── 더 보기
```

- **태그 필터를 두지 않는다.** 한 spot 의 글은 애초에 많지 않고, 필터가 하나 더 늘면
  "빼기" 원칙에 어긋난다 (설계 문서 §3).
- 카드 안의 `PostSpotChip` 은 **생략한다** — 이미 그 spot 의 화면이다.
- 여기서 "Write" 로 진입하면 spot 이 이미 정해진 컴포저가 열린다 (§3).

이 화면에서 spot 쪽이 커뮤니티 provider 를 직접 참조하는데, **이는 의도된 결합**이다
(설계 문서 §1) — "커뮤니티는 spot 으로 되돌리는 구조"라는 전제가 화면 구조에 그대로 나타난다.

## 3. 글 작성 (R1~R4, R3, R25)

> Stitch 화면: `Post Composer`

진입 경로가 둘이고, **차이는 spot 을 어떻게 정하느냐뿐이다** (설계 문서 §3).

| 진입 | spot 선택 단계 |
|---|---|
| spot 상세에서 | 없음 — spot 이 정해진 채로 열린다 |
| 커뮤니티 탭에서 | 있음 — 최근 본 spot·좋아요한 spot 이 먼저, 검색은 그다음 |

```
Scaffold
├── AppBar    "New Post" · 닫기(X) · 우측 [Post] 액션(비활성 가능)
└── 본문
    ├── SpotPickerField     선택됨: PostSpotChip + 변경
    │                       미선택: "Select a spot" → 선택 시트
    ├── 본문 TextField      멀티라인, 힌트 표시
    ├── CharacterCounter    "123 / 500" 잔여 표시, 초과 시 강조
    ├── PhotoStrip          썸네일 + [+] 추가 (최대 5장)
    └── TopicChipRow        단일 선택, 미선택 상태로 시작
```

### 등록 버튼 (R1-1)

**본문·spot·태그가 모두 갖춰지기 전까지 비활성.** 서버 검증을 기다렸다가 에러를 보여주는
방식이 아니다 — 화면이 애초에 잘못된 상태를 만들지 못하게 한다 (설계 문서 §3).

### 본문 길이 (R4)

잔여 글자 수로 보여준다. **500자를 넘으면 입력이 막히는 것이 아니라 등록이 막히고 초과분이
드러난다.** 입력을 자르면 붙여넣기한 유저가 무엇이 사라졌는지 모른다 (설계 문서 §3).

### 사진 첨부 (R3, R18, R25)

업로드는 세 단계이고 **유저에게는 한 단계로 보여야 한다** (설계 문서 §3).

| 썸네일 상태 | 표시 |
|---|---|
| 업로드 중 | 로컬 썸네일 + 진행 오버레이 |
| 완료 | 썸네일 + 제거(×) |
| 실패 | 오류 오버레이 + **재시도** / **제거** — 사진 한 장 때문에 글 전체를 다시 쓰지 않는다 |

- 업로드 중에도 **본문을 계속 쓸 수 있다.** 업로드가 등록을 막지 않되, 등록 시점에 아직
  끝나지 않은 업로드가 있으면 기다린다.
- presigned URL 5분 만료 (R18) → PUT 실패 시 URL 을 재발급받아 재시도.
- 지원 형식 JPEG·PNG·WebP (R25) — **사진 선택 단계에서 거른다.** 고르고 나서 거부당하는
  것보다 애초에 고를 수 없는 편이 낫다. iOS HEIC 변환 필요.

> Stitch 화면: `Post Detail`

```
Scaffold
├── AppBar    뒤로가기 · 우측 [⋮ 오버플로]
├── 스크롤 본문
```

**댓글은 1단계만.** 답글 버튼도, 들여쓰기도 두지 않는다.

## 5. 신고·차단 (R15, R16, R22)

> Stitch 화면: `Report & Block Sheets`

글·댓글의 **오버플로 메뉴**에서 신고와 차단에 닿는다.

```
오버플로 메뉴 (bottom sheet)
├── Report post/comment
└── Block this user
```

### 신고 시트 (R16)

```
ReportSheet
├── 제목 "Report"
├── 사유 라디오 4종 (고정)
├── 상세 TextField   — "기타" 선택 시에만 노출, 이때 필수 (R16-3)
└── [Submit] (사유 미선택 시 비활성)
```

신고 후에는 **접수되었다는 사실만** 알린다. 처리 결과나 예상 시점을 약속하지 않는다 —
사용자 대상 신고는 기록만 되고 자동 조치가 없으며 (R22), 글·댓글도 5명이 모여야 숨겨진다.
**신고 직후 무언가 일어난 것처럼 보이는 문구를 쓰면 실제 동작과 어긋난다** (설계 문서 §3).

### 차단 확인 (R15)

확인 단계를 둔다 — **양방향이라 되돌리기 전까지 서로 안 보이게 되며, 유저가 그 결과를 알고
눌러야 한다.** 확인 문구에 양방향임을 명시한다.

차단 직후 피드는 **다시 불러온다.** 서버가 필터링하므로 로컬에서 지우는 것이 아니라
재조회가 정답이다 (설계 문서 §3).

### 차단 목록 화면

```
Scaffold
├── AppBar "Blocked users"
└── 리스트: 아바타 · 닉네임 · [Unblock]
```

비어 있으면 빈 상태 안내. 진입 지점은 설정/프로필 쪽 (이 스펙 범위 밖의 기존 경로).

## 6. 좋아요 낙관적 갱신 (R12)

`PostActionBar` 의 하트는 **낙관적으로 반영하고 실패 시 되돌린다** (설계 문서 §5).

1. 탭 즉시 `likeCount` 와 눌림 상태 갱신
2. 뮤테이션 발사
3. **실패 시 이전 값으로 롤백**

댓글 작성과 글 등록은 낙관적으로 처리하지 **않는다** — 서버가 거부할 사유(길이, 미업로드 키)가
실재하고, 등록된 것처럼 보였다가 사라지는 편이 잠깐 기다리는 것보다 나쁘다.

`likedByViewer` 는 미인증일 때 false 로 오므로 (R17-5) 별도 분기가 필요 없다.

## 7. 미인증 상태 (R17)

**피드는 로그인 없이 보인다.** 쓰기·좋아요·신고·차단을 시도하는 순간 로그인으로 유도한다.

**버튼을 감추지 않고 눌렀을 때 유도하는 쪽을 택한다** — 감추면 기능이 없는 것처럼 보인다
(설계 문서 §3). FAB 도, 하트도, 오버플로 메뉴도 미인증 상태에서 그대로 보인다.

로그인 유도 경로는 SPEC-0005 의 세션 게이트를 재사용한다.

## 9. 비범위 — 화면에 흔적을 남기지 않는다

리포스트, 팔로우, 알림, DM, 프로필 꾸미기, 글 수정, 대댓글, 게시글 검색.

**비활성 버튼이나 "준비 중" 표시도 두지 않는다** (설계 문서 §6). 목업에 이런 요소가
들어갔다면 그것은 생성 노이즈이며 구현하지 않는다.

## 10. 갭 / 미확정

- 탐색 타일의 개수·행 수는 서버가 내려주는 만큼 — 목업의 4개는 예시다
- 사진 N장 배치(그리드 vs 가로 스크롤)는 목업의 제안일 뿐, 확정 아님
- 차단 목록 진입 지점은 기존 설정 화면 구조에 맞춰 구현 시 결정

### 목업이 아직 없는 화면

커뮤니티 탭(§1)만 Stitch 목업이 있다. **§2~§5(spot 상세 내 피드, 글 작성, 글 상세,
신고·차단 시트)는 목업 없이** 이 문서의 분해만으로 구현한다 — 각 절의 구조·상태·금지사항은
스펙에서 직접 도출한 것이라 목업이 없어도 구현 가능하다.

목업이 필요하다고 판단되면 커뮤니티 탭과 같은 프로젝트·디자인 시스템으로 추가 생성한다.
