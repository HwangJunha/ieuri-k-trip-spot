## 0. 벤치마크 — 당근마켓 동네생활 (2026-08 개정)

**커뮤니티 화면의 레퍼런스는 당근마켓 동네생활이다.** Stitch 목업(§1)이 만든 배치는
소셜 피드에 가까웠는데, 이 기능의 성격 — 장소에 매인 짧은 글, 게시판 성격의 태그,
가벼운 상호작용 — 은 당근 쪽에 훨씬 가깝다. 그래서 아래 다섯 가지를 당근에 맞춰
바꿨고, **§1의 옛 배치는 이 절이 대체한다.**

| 당근 요소 | 이 앱에서의 대응 |
|---|---|
| 상단 카테고리 줄 (아이콘+라벨, 원형) | `TopicChipRow` — 얇은 아웃라인 칩 → **원형 아이콘 + 라벨** |
| 카드 맨 위의 게시판 이름 ("동네질문") | 주제 태그를 **카드 최상단**으로 올리고 저강조 처리 |
| 굵은 제목 한 줄 + 그 아래 본문 | 본문 첫 문장을 제목 자리에 (→ §11 갭 B) |
| 좌하단의 동 이름 ("신림동") | **spot 이름** (`PostTarget.title`) + 상대 시각 |
| 우하단의 공감·댓글 수 | 좋아요 수 + 댓글 수 |
| 카드 우상단 ⋮ | **차단·신고·삭제 시트** (§5) |
| 납작한 카드, 얇은 구분선 | `Card`/elevation 없음. 항목 사이 `Divider(thickness: 0.5)` |
| 게시판 먼저 고르는 작성 화면 | 컴포저가 **주제 → 장소 → 본문** 순 (§3) |

**두 가지는 서버가 막고 있어 오늘 만들 수 없다** — 카테고리 필터와 제목 필드다.
§11에 갭으로 적었고, 현재 계약으로 도는 대역을 함께 기록했다.

## 1. 커뮤니티 탭 (R7, R8, R10, R11)

> Stitch 화면: `Community — Spot Talk` — `screens/e46fdc51b6114fbfa2ac4f025c332105`

하단 탭으로 진입하는 화면. 라우트 `/community` 와 탭 라벨 `navCommunity` 는 SPEC-0008 이
이미 만들어 두었으므로 **탭을 새로 만들지 않고 스텁 내용만 바꾼다** (설계 문서 §1).

```
Scaffold (하단 플로팅 내비 유지, Community 탭 활성)
├── AppBar               title "Spot Talk", 뒤로가기 없음
├── 본문
│   ├── DiscoveryTileGrid       2열 그리드, 타일 높이 ~110
│   ├── TopicChipRow            카테고리 줄 (아이콘+라벨, 높이 88)
│   └── 지역 피드 섹션 "Nearby"
│       └── PostCard × N        커서 페이지네이션, 사이에 얇은 Divider
└── FAB                  compose 아이콘, primary — 글 작성 진입 (§3)
```

**필터 UI 는 카테고리 줄 하나가 전부다.** 정렬 선택도, 추가 필터도, 상단 탭도, 검색창도
두지 않는다 (설계 문서 §3). 상태는 "선택된 topic (없을 수 있음)" 하나뿐이다.

### 컴포넌트

| 컴포넌트 | 역할 | 비고 |
|---|---|---|
| `DiscoveryTileGrid` | `DiscoveryTile` 2열 그리드 | 타일 제목은 **서버 문자열 그대로** 표시 (§4) |
| `DiscoveryTileCard` | 사진 + 하단 그라디언트 + 흰 제목 | 탭 → 해당 topic 필터로 진입 (R11) |
| `TopicChipRow` | **카테고리 줄** — 원형 아이콘(44) + 라벨, 단일 선택 | 표시 문자열은 **클라이언트 l10n 매핑** (§4). 데이터 출처 교체 지점 (§11 갭 A) |
| `PostCard` | 피드 항목 | 아래 분해 참조 |
| `showPostModerationSheet` | 오버플로 시트 (차단·신고·삭제) | §5 |
| `showReportSheet` | 사유 라디오 + 조건부 상세 | §5 |

`PostSpotChip`(위치 pill)과 `PostActionBar`는 **없앴다.** 당근 카드는 pill 을 쓰지 않고
장소를 하단 텍스트로 두며, 좋아요·댓글도 별도 액션 바가 아니라 같은 하단 행의 우측에
붙는다. 두 파일은 삭제했다 (죽은 코드를 남기지 않는다, CLAUDE.md §9).

### PostCard 분해 (당근 배치)

```
PostCard                                       ← 그림자 없음, 상하 여백 넉넉히
├── 상단 행    [주제 태그 · 저강조]        [⋮ 오버플로]
├── (숨김 배지)                              ← hidden: true 일 때만
├── 제목 줄     본문 첫 문장, titleMedium + w700, 최대 2줄
├── 본문        나머지, bodyMedium/onSurfaceVariant, **2줄** + ellipsis
├── 사진        0장(미렌더) / 1장 와이드 16:9 / N장 가로 스크롤
└── 하단 행     [spot 이름 · 상대시각]      [♡ 12] [💬 4]
```

- **작성자를 목록에 표시하지 않는다.** 프로필 화면이 비범위라 닉네임을 눌러도 갈 곳이
  없고 (설계 문서 §6), 당근도 목록 카드에 작성자를 두지 않는다. 아바타·닉네임 헤더를
  제거했다 — 차단 확인 문구에서만 닉네임을 쓴다.
- 사진이 없으면 자리를 비워두지 않고 **영역 자체를 렌더하지 않는다.**
- 댓글 수는 서버 `commentCount` 를 그대로 쓴다 — 목록 길이로 계산하지 않는다 (설계 문서 §3).
- **개발 시드의 photoKey 는 404 가 정상**이므로 (가이드 §3) 항상 플레이스홀더를 깔고 그
  위에 이미지를 그린다. 실패해도 레이아웃이 무너지지 않는다.
- `expanded: true`(상세)에서는 **제목/본문으로 가르지 않는다** — 본문을 자르지 않으므로
  원문 그대로 읽히는 편이 낫다.

### 타일 → 필터 반영 (R11-3)

타일에서 진입해도 **같은 상태에 반영**되어 상단 칩이 그 태그로 선택된 것처럼 보인다.
타일 진입과 칩 선택이 서로 다른 화면 상태를 만들지 않는다.

### 상태

| 상태 | 화면 |
|---|---|
| 로딩 | 피드 자리 로딩 인디케이터 |
| 빈 피드 | "아직 글이 없다" 안내 |
| **위치 권한 없음 / 좌표 실패** | 지역 피드를 비우고 **그 사유**를 표시 — 빈 피드와 다른 상태다 (설계 문서 §3) |
| 추가 로딩 | 목록 하단 인디케이터 |

**Stitch 목업에는 정상 상태만 있다.** 위 상태 화면은 목업 없이 구현한다.

### 목업이 스펙과 어긋나는 지점 — 목업을 따르지 않는다

생성된 목업에 아래가 섞여 있다. **스펙이 이긴다**(문서 머리말).

| 목업 | 실제 구현 |
|---|---|
| 하단 내비가 5탭(Home·Map·Discover·Events·Chat), **Home 활성** | SPEC-0008 이 만든 현재 탭 구성을 그대로 쓰고 **Community 탭이 활성**이다. 목업의 탭 구성은 DESIGN.md §8 의 옛 5탭이라 이미 낡았다 |
| 앱바 우측 프로필 아바타 | 스펙에 없다. 두지 않는다 |
| 두 번째 카드 사진에 `+2` 인디케이터 | 배치는 미확정(§10). `+N` 는 스펙에 없는 발명이므로 근거로 삼지 않는다 |

목업에서 **맞게 나온 것**(그대로 따른다): 2열 타일 그리드 4개, 칩 한 줄에 `All` 만 채워진
선택 상태, `Nearby` 라벨, 카드 3장의 사진 변주(1장 / 여러 장 / 없음), 우하단 작성 FAB,
위치 pill 의 secondary 톤.

## 2. spot 상세 안의 피드 (R6)

> Stitch 화면: `Spot Detail — Posts Section`

SPEC-0003 의 상세 화면(`Spot Detail`) 하단에 섹션으로 끼워 넣는다.

```
… 기존 상세 섹션들 (Overview / Contact) …
└── 게시글 섹션
    ├── 섹션 헤더 "Posts" + 우측 "Write" 텍스트 버튼
    ├── PostCard × N       해당 spot 의 글만, 최신순
    └── 더 보기
```

- **태그 필터를 두지 않는다.** 한 spot 의 글은 애초에 많지 않고, 필터가 하나 더 늘면
  "빼기" 원칙에 어긋난다 (설계 문서 §3).
- 카드 안의 `PostSpotChip` 은 **생략한다** — 이미 그 spot 의 화면이다.
- 여기서 "Write" 로 진입하면 spot 이 이미 정해진 컴포저가 열린다 (§3).

이 화면에서 spot 쪽이 커뮤니티 provider 를 직접 참조하는데, **이는 의도된 결합**이다
(설계 문서 §1) — "커뮤니티는 spot 으로 되돌리는 구조"라는 전제가 화면 구조에 그대로 나타난다.

## 3. 글 작성 (R1~R4, R3, R25)

> Stitch 화면: `Post Composer`

진입 경로가 둘이고, **차이는 spot 을 어떻게 정하느냐뿐이다** (설계 문서 §3).

| 진입 | spot 선택 단계 |
|---|---|
| spot 상세에서 | 없음 — spot 이 정해진 채로 열린다 |
| 커뮤니티 탭에서 | 있음 — 최근 본 spot·좋아요한 spot 이 먼저, 검색은 그다음 |

**순서는 당근 컴포저를 따른다 — 게시판(주제)을 먼저 고른다.** 무엇을 쓸지가 정해져야
본문이 나오기 때문이고, 등록 조건 중 가장 잊기 쉬운 것이 태그라 맨 위에 두면 비활성
버튼의 이유가 바로 보인다.

```
Scaffold
├── AppBar    "New post" · 닫기(X) · 우측 [Post] 액션(비활성 가능)
└── 본문 (ListView)
    ├── "Choose a board"    ChoiceChip Wrap, 단일 선택, 미선택으로 시작
    ├── "Where"             선택됨: 장소 이름 / 미선택: "Select a spot" → 선택 시트
    │                       상세에서 진입했으면 고정 (탭 불가, suffix 아이콘 없음)
    ├── 본문 TextField      멀티라인(5~8줄), 힌트. **maxLength 없음**
    └── 카운터              "123 / 500" · 초과 시 "3 characters over the limit." (error 색)
```

### 장소 선택 시트

목록은 **주변 글들의 `PostTarget` 을 중복 없이 모은 것**이다 (`composerTargets` provider).
관광지 검색은 `domain/spot` 에 있는데 커뮤니티가 그것을 import 하면 기능 간 의존이
생기고 (CLAUDE.md §3), 둘이 공유할 만큼도 아니라 공용으로 올리지 않았다.

**한계를 그대로 적어 둔다: 글이 하나도 없는 장소는 고를 수 없다.** 지금 서버는 커넥션
조회가 깨져 있어 (§12) 이 목록도 비고, 그때 시트는 빈 화면이 아니라 **사유**를 보여준다.
관광지 검색이 필요해지면 그 시점에 `common/` 으로 올릴 대상을 정하는 것이 순서다.

### 사진 첨부 — 이번 범위 밖

업로드가 3단계(서명 발급 → R2 직접 PUT → 확인)라 손이 크고, **가이드 §17 의 권장 순서도
"사진 없이 먼저"** 다. 지금 컴포저는 `photoKeys: []` 로 등록한다. 아래 §3 의 사진 절은
붙일 때의 설계로 남겨 둔다.

### 등록 버튼 (R1-1)

**본문·spot·태그가 모두 갖춰지기 전까지 비활성.** 서버 검증을 기다렸다가 에러를 보여주는
방식이 아니다 — 화면이 애초에 잘못된 상태를 만들지 못하게 한다 (설계 문서 §3).

### 본문 길이 (R4)

잔여 글자 수로 보여준다. **500자를 넘으면 입력이 막히는 것이 아니라 등록이 막히고 초과분이
드러난다.** 입력을 자르면 붙여넣기한 유저가 무엇이 사라졌는지 모른다 (설계 문서 §3).

### 사진 첨부 (R3, R18, R25)

업로드는 세 단계이고 **유저에게는 한 단계로 보여야 한다** (설계 문서 §3).

| 썸네일 상태 | 표시 |
|---|---|
| 업로드 중 | 로컬 썸네일 + 진행 오버레이 |
| 완료 | 썸네일 + 제거(×) |
| 실패 | 오류 오버레이 + **재시도** / **제거** — 사진 한 장 때문에 글 전체를 다시 쓰지 않는다 |

- 업로드 중에도 **본문을 계속 쓸 수 있다.** 업로드가 등록을 막지 않되, 등록 시점에 아직
  끝나지 않은 업로드가 있으면 기다린다.
- presigned URL 5분 만료 (R18) → PUT 실패 시 URL 을 재발급받아 재시도.
- 지원 형식 JPEG·PNG·WebP (R25) — **사진 선택 단계에서 거른다.** 고르고 나서 거부당하는
  것보다 애초에 고를 수 없는 편이 낫다. iOS HEIC 변환 필요.

## 4. 글 상세 (R13, R23)

> Stitch 화면: `Post Detail`

```
Scaffold
├── AppBar    뒤로가기 · 우측 [⋮ 오버플로]
├── 스크롤 본문
│   ├── PostCard 전체 형태 (본문 미절단, 사진 전체)
│   ├── 구분선 + "Comments · 12"     서버 commentCount 그대로
│   └── CommentTile × N              1단계만, 최신순
└── CommentComposerBar   하단 고정: 입력 + 전송
```

| 컴포넌트 | 역할 | 비고 |
|---|---|---|
| `CommentTile` | 아바타·닉네임·상대시각·본문·[⋮] | **대댓글 입력 수단 없음** (설계 문서 §3) |
| `CommentComposerBar` | 하단 고정 입력 | 낙관적 처리 **안 함** (§5) |

**댓글은 1단계만.** 답글 버튼도, 들여쓰기도 두지 않는다.

## 5. 신고·차단 (R15, R16, R22)

> Stitch 화면: `Report & Block Sheets`

**카드 우상단의 ⋮ 와 글 상세 앱바의 ⋮** 에서 신고와 차단에 닿는다. 두 진입은 같은
흐름(`runPostModerationFlow`)을 쓴다 — 같은 순서를 두 번 적으면 "차단은 양방향임을
명시한다"나 "`ALREADY_REPORTED` 를 오류로 띄우지 않는다" 같은 규약이 한쪽만 고쳐진다.

```
오버플로 메뉴 (bottom sheet)
├── Block this user     → 확인 다이얼로그 → blockUser
├── Report              → 사유 시트 → reportContent
└── Delete post         → 확인 다이얼로그 → deletePost   ← ownedByViewer 일 때만
```

**미인증이어도 항목을 감추지 않는다** (가이드 §13, §7). 시트를 열고 실행까지 간 뒤 서버가
`UNAUTHENTICATED` 를 주면 그때 안내 + 로그인 화면으로 보낸다. 감추는 것은 삭제 하나뿐이고,
그것도 "내 글이 아니면 의미가 없어서"이지 인증 때문이 아니다.

성공 후 처리:

| 동작 | 성공하면 |
|---|---|
| 차단 | 피드 **재조회** (서버가 필터링한다 — 로컬에서 지우지 않는다). 상세에서는 화면을 닫는다 |
| 삭제 | 위와 같음 |
| 신고 | 목록은 그대로. 접수 안내만 |

### 신고 시트 (R16)

```
ReportSheet
├── 제목 "Report"
├── 사유 라디오 4종 — 서버 `ReportReason` 와 1:1
│     SPAM / ABUSE / INAPPROPRIATE_CONTENT / OTHER
├── 상세 TextField   — OTHER 선택 시에만 노출, 이때 **필수** (R16-3)
└── [Submit] — 사유 미선택 또는 (OTHER인데 상세 공백)이면 비활성
```

- 사유의 표시 문자열은 **클라이언트 l10n 매핑**이다 (`PostTopic` 과 같은 방식, POL-023).
- `OTHER` 인데 상세가 비면 서버가 `REPORT_DETAIL_REQUIRED` 로 거부하는데, **왕복해서
  거절당하는 것보다 애초에 누를 수 없는 편이 낫다** — 제출을 클라이언트에서 막는다.
- 라디오는 `RadioGroup` 조상으로 값을 관리한다 (개별 타일의 `groupValue`/`onChanged` 는
  Flutter 3.32 에서 deprecated).
- **`ALREADY_REPORTED` 는 오류가 아니라 안내다.** "이미 신고했습니다" 로 접고 오류
  토스트를 띄우지 않는다 — 재신고는 서버가 막는 정상 흐름이라 오류로 보이면 사용자는
  무언가 고장난 줄 안다.

신고 후에는 **접수되었다는 사실만** 알린다. 처리 결과나 예상 시점을 약속하지 않는다 —
사용자 대상 신고는 기록만 되고 자동 조치가 없으며 (R22), 글·댓글도 5명이 모여야 숨겨진다.
**신고 직후 무언가 일어난 것처럼 보이는 문구를 쓰면 실제 동작과 어긋난다** (설계 문서 §3).

### 차단 확인 (R15)

확인 단계를 둔다 — **양방향이라 되돌리기 전까지 서로 안 보이게 되며, 유저가 그 결과를 알고
눌러야 한다.** 확인 문구에 양방향임을 명시한다.

차단 직후 피드는 **다시 불러온다.** 서버가 필터링하므로 로컬에서 지우는 것이 아니라
재조회가 정답이다 (설계 문서 §3).

### 차단 목록 화면

```
Scaffold
├── AppBar "Blocked users"
└── 리스트: 아바타 · 닉네임 · [Unblock]
```

비어 있으면 빈 상태 안내. 진입 지점은 설정/프로필 쪽 (이 스펙 범위 밖의 기존 경로).

## 6. 좋아요 낙관적 갱신 (R12)

`PostActionBar` 의 하트는 **낙관적으로 반영하고 실패 시 되돌린다** (설계 문서 §5).

1. 탭 즉시 `likeCount` 와 눌림 상태 갱신
2. 뮤테이션 발사
3. **실패 시 이전 값으로 롤백**

댓글 작성과 글 등록은 낙관적으로 처리하지 **않는다** — 서버가 거부할 사유(길이, 미업로드 키)가
실재하고, 등록된 것처럼 보였다가 사라지는 편이 잠깐 기다리는 것보다 나쁘다.

`likedByViewer` 는 미인증일 때 false 로 오므로 (R17-5) 별도 분기가 필요 없다.

## 7. 미인증 상태 (R17)

**피드는 로그인 없이 보인다.** 쓰기·좋아요·신고·차단을 시도하는 순간 로그인으로 유도한다.

**버튼을 감추지 않고 눌렀을 때 유도하는 쪽을 택한다** — 감추면 기능이 없는 것처럼 보인다
(설계 문서 §3). FAB 도, 하트도, 오버플로 메뉴도 미인증 상태에서 그대로 보인다.

로그인 유도 경로는 SPEC-0005 의 세션 게이트를 재사용한다.

## 10. 갭 / 미확정

- 탐색 타일의 개수·행 수는 서버가 내려주는 만큼 — 목업의 4개는 예시다
- 사진 N장 배치(그리드 vs 가로 스크롤)는 목업의 제안일 뿐, 확정 아님
- 차단 목록 진입 지점은 기존 설정 화면 구조에 맞춰 구현 시 결정

### 목업이 아직 없는 화면

커뮤니티 탭(§1)만 Stitch 목업이 있다. **§2~§5(spot 상세 내 피드, 글 작성, 글 상세,
신고·차단 시트)는 목업 없이** 이 문서의 분해만으로 구현한다 — 각 절의 구조·상태·금지사항은
스펙에서 직접 도출한 것이라 목업이 없어도 구현 가능하다.

`Post Detail` 과 `Post Composer` 는 2026-08-05 에 4회 시도했으나 모두 생성되지 않았다
(프롬프트 길이·모델을 바꿔도 동일, 회당 8~12분 대기 후 확인). 커뮤니티 탭은 같은 조건에서
생성됐으므로 프롬프트 문제가 아니라 그 시점 생성 계통의 문제로 보인다. **나중에 다시 시도할
때는 이 문서의 §3·§4 를 그대로 프롬프트로 쓰면 된다** — 목업이 생기면 화면 id 를 각 절
머리말에 채우고, 커뮤니티 탭처럼 "목업이 스펙과 어긋나는 지점" 표를 함께 남긴다.

## 11. 서버가 막고 있는 갭 — [AMEND] 대상

당근 배치(§0) 중 **두 가지는 현재 계약으로 만들 수 없다.** 클라이언트에서 흉내 내는
대신 갭으로 적고, 오늘 도는 대역과 서버가 열렸을 때의 교체 지점을 함께 남긴다.

### 갭 A — 카테고리 필터 (사용자 요청: "SpotCategory 줄")

**요청:** 상단 줄을 주제(topic)가 아니라 **`SpotCategory`** 로 채운다.

**막힌 이유:** 서버 피드는 `topic: PostTopic` 만 받는다.

```graphql
nearbyPosts(latitude:, longitude:, radiusMeters:, topic: PostTopic, first:, after:)
targetPosts(targetType:, targetId:, topic: PostTopic, first:, after:)
```

`nearbyPosts`/`targetPosts` 에 **category 인자가 없고**, `Post` 에도 category 필드가
없다 (라이브 introspection 으로 확인). `SpotCategory` 는 spot 도메인의 다른 enum이라
클라이언트가 매핑할 대상 자체가 없다 — 받은 목록을 클라이언트에서 거르면 페이지네이션이
깨지고 (한 페이지에서 몇 건이 사라진 채로 커서가 진행된다) 개수도 맞지 않는다.

**필요한 서버 작업:** 두 피드 쿼리에 `category: SpotCategory` 인자 추가 + `Post` 에
대상의 카테고리 노출.

**오늘의 대역:** 같은 자리를 **`PostTopic` 으로 채우되 모양은 당근식**으로 만들었다
(원형 아이콘 + 라벨). 항목 생성이 `TopicChipRow` 안에 갇혀 있어 **서버가 열리면 그
파일 하나의 `_entries` 부분만** 바꾸면 된다.

### 갭 B — 제목 필드 (사용자 요청: "굵은 제목 + 본문")

**요청:** 카드에 굵은 제목 한 줄과 그 아래 본문.

**막힌 이유:** `Post` 에 **`body: String!` 만 있고 `title` 이 없다** (라이브 introspection
으로 확인). `CreatePostInput` 에도 없다.

**필요한 서버 작업:** `Post.title` + `CreatePostInput.title` 추가 (nullable 로 시작해
기존 글을 깨뜨리지 않는 편이 안전하다).

**오늘의 대역:** `model/post_body_split.dart` 의 `splitPostBody()` 가 본문을 제목 줄과
나머지로 가른다. 규칙은 넷이고 첫 성공에서 멈춘다:

1. 개행이 있으면 첫 줄이 제목 (사용자가 스스로 나눈 경계라 가장 믿을 만하다)
2. 없으면 첫 문장이 제목 (종결부호 `.!?。！？` + 뒤에 공백/끝. 소수점 "3.5달러" 는 안 걸린다)
3. 종결부호도 없으면 **첫 이모지가 경계** — 앞뒤가 공백일 때만. 캐주얼한 한국어 글에서
   이모지가 마침표 노릇을 한다 ("청계천 야경 🌃 여름 밤에…")
4. 제목이 40 코드포인트를 넘거나 나머지가 비면 **제목 없이 본문만** (한 문장짜리 글에서
   제목만 있고 본문이 빈 카드가 되면 위계가 오히려 어색하다)

**규칙 3 은 실제 데이터를 보고 넣었다.** 라이브 시드 9건 중 4건이 종결부호 없이
이모지로만 끊긴다 — 규칙 2까지만 두면 그 글들은 제목 없이 본문만 나온다. 지금은 9건
모두 사람이 읽기에 자연스러운 자리에서 갈린다.

순수 함수로 **모델 계층에** 두었고 단위 테스트 16개가 붙어 있다 — `Post.title` 이 오면
그 파일과 테스트를 통째로 지우고 `PostCard` 의 두 줄을 `post.title`/`post.body` 로
바꾸면 끝난다. 위젯에 흩어 두면 지울 때 찾아다녀야 한다.

## 12. 지금 서버 상태 — 화면이 견뎌야 하는 것

**모든 커뮤니티 Connection 필드가 깨져 있다.** `nearbyPosts`·`targetPosts`·`post.comments`
가 HTTP 200 과 함께 최상위 오류를 준다:

```
No ConnectionAdapter for: ...PostConnectionResponse
```

`post(id:)` 와 `discoveryTiles` 는 정상이다 (id 15~22 확인).

이 상태에서 화면이 지켜야 하는 것:

| 자리 | 지금 보이는 것 |
|---|---|
| 탐색 타일 | **정상** — 피드와 다른 provider 라 함께 죽지 않는다 |
| 카테고리 줄 | **정상** — 태그를 옮겨 다닐 수 있다 |
| 지역 피드 | 사유 + **재시도 버튼**. 빈 화면도 무한 스피너도 아니다 |
| 글 상세 | 본문은 뜨고 댓글 자리만 "불러오지 못했다" — repository 가 댓글 없이 한 번 더 조회한다 |
| 컴포저의 장소 시트 | 사유 표시 (목록 출처가 피드라 함께 막힌다, §3) |

**이 graceful degradation 은 서버가 고쳐져도 유지한다** — 네트워크가 끊긴 경우와 같은
경로이기 때문이다.

## 13. 실제 구현된 배치 (2026-08-06 서버 계약 기준)

§1~§12 를 대체하는 절이다. 벤치마크는 그대로 **당근마켓 동네생활**이고, 서버가 제목·
카테고리·태그를 내려주게 되면서 §11 의 대역(본문에서 제목을 잘라내던 `splitPostBody`)이
사라졌다.

### PostCard — 사용자가 지정한 배치

```
┌────────────────────────────────────────────────┐
│ 카테고리(저강조)                          [⋮] │  ← 좌상단 카테고리 / 우상단 메뉴
│ ┌────┐  제목 (titleMedium, w700, 2줄)          │
│ │사진│  본문 (bodyMedium, 2줄 + ellipsis)      │  ← 사진은 **좌측 1장만**
│ └────┘                                         │
│              장소명 · #태그 · 3시간 전  💬4 ♡12 │  ← 전부 우측 정렬
└────────────────────────────────────────────────┘
```

- **사진은 `photoKeys.first` 한 장만**, 84×84. 없으면 `Row` 자체를 쓰지 않고 텍스트만
  그린다 — 빈 상자를 남기면 사진 있는 카드와 없는 카드의 제목 시작점이 어긋난다
- **장소는 `spot != null` 일 때만** 그린다 (장소 없는 글이 허용된다, 가이드 §5)
- 태그는 `#야경` 형태로 **원문 그대로**. 번역 대상이 아니다 (가이드 §9)
- `hidden: true` → "신고 누적으로 숨겨졌다" 배지 / `edited: true` → 제목 옆 "수정됨"
- 상세(`expanded: true`)에서는 본문을 자르지 않고 사진을 가로 스크롤로 전부 보여준다.
  사진을 탭하면 전체 화면 뷰어(`PostPhotoViewer`, 여러 장이면 스와이프)

**조회수는 없다.** 사용자가 요청했지만 서버 `Post` 에 조회수 필드가 없어 자리를 비웠다 —
§14 참조.

### ⋮ 메뉴 (가이드 §5 와 1:1)

| 항목 | 노출 조건 |
|---|---|
| 이 글 신고하기 | `!ownedByViewer` |
| 이 사용자 차단하기 | `!ownedByViewer` |
| 글 수정하기 | `ownedByViewer` — **`hidden` 이면 비활성 + 사유 표시** |
| 글 삭제하기 | `ownedByViewer` |

### 컴포넌트

| 컴포넌트 | 역할 |
|---|---|
| `CategoryChipRow` | 상단 칩 — **구성은 `communityChips` 가 정하고 표시 문구만 앱이 매핑**. 빈 목록이면 줄 자체를 안 그린다 |
| `PostCard` | 위 배치 |
| `PostPhoto` / `PostPhotoViewer` | 키 → CDN URL 조합, 404 를 견디는 플레이스홀더, 전체 화면 뷰어 |
| `CommentTile` | 아바타·닉네임·상대시각·본문·[⋮] (삭제/신고) |
| `showPostModerationSheet` / `showCommentModerationSheet` / `showReportSheet` | 모더레이션 시트 |
| `community_labels.dart` | `TargetCategory`·`ReportReason`·상대시각의 l10n 매핑 |

`DiscoveryTileGrid`·`TopicChipRow`·`PostSpotChip`·`PostActionBar` 는 **삭제했다** — 서버에
`discoveryTiles`·`PostTopic` 이 없어졌다.

### 화면

| 화면 | 구성 |
|---|---|
| 커뮤니티 탭 | 칩 줄 + 피드(`PaginationListView`) + 작성 FAB + 앱바의 차단목록 진입 |
| 글 상세 | 글 카드(expanded) + 댓글 헤더 + 댓글 목록(커서 페이징) + 하단 고정 입력 |
| 컴포저 | 카테고리(필수) → 제목(50cp) → 본문(500cp) → 태그(최대 5) → 장소(선택) → 사진(최대 5) |
| 컴포저(수정) | 제목·본문·사진만. **카테고리·태그·장소 입력을 숨긴다** — 서버가 받지 않는다 |
| 차단 목록 | 아바타·닉네임·[해제] + "내가 건 차단만 보인다" 안내 |

### 상태 구분 (§1 의 원칙을 그대로 잇는다)

- 칩 줄과 피드가 **다른 provider** 다 — 한쪽이 실패해도 다른 쪽은 보인다
- 글과 댓글도 **다른 provider** 다 — 댓글 조회가 실패해도 글 본문은 남는다
- 위치 실패는 빈 피드와 **다른 문구**를 쓴다
- 칩 빈 목록·차단 목록 빈 상태는 **오류가 아니다**

## 14. 서버에 요청해야 할 것

### 조회수 (`Post.viewCount`)

사용자가 카드 하단에 **조회수**를 요청했으나 서버 `Post` 타입에 해당 필드가 없다.
클라이언트가 셀 수 있는 값이 아니므로(각 기기가 자기 조회만 안다) **지어내지 않고
비워 두었다.** 서버가 `viewCount: Int!` 를 열면 `PostCard` 의 `_FooterRow` 에 댓글 수
옆으로 한 칸 붙이면 된다.

### 사진 선택 수단

업로드 4단계(발급 → PUT → 확인 → 글 붙이기)는 repository·provider 에 전부 구현했고
테스트도 붙어 있다. 다만 **기기에서 사진을 고르는 UI 는 플랫폼 채널이 필요해
pubspec 에 패키지가 없다.** 새 의존을 임의로 들이지 않고 `photoPickerProvider` 라는
이음매만 두었다 — 그 provider 를 실제 picker 로 override 하면 그날부터 첨부가 돈다.
