이 문서는 **레이아웃·컴포넌트 분해 참조**다. 수용 기준과 어긋나면 스펙이 이긴다.

실제 데이터는 라이브 API다.

## 0. 벤치마크 — 당근마켓 동네생활

사용자가 지정한 기준이다. 초안의 소셜 피드형 배치가 "좁고 올드하다"는 지적을 받아
전면 재설계했다.

| 당근 | 이 앱 |
|---|---|
| 동네 이름(신림동) | **장소(spot)** — 없는 글도 허용된다 |
| 게시판 카테고리 | `TargetCategory` — 서버 `communityChips`가 구성을 정한다 |
| 납작한 목록(그림자 없음, 얇은 구분선) | 그대로 |
| 굵은 제목 + 본문 미리보기 | 그대로 |
| 카드 우상단 ⋮ | 신고·차단·숨기기·수정·삭제 |

**카드에 그림자를 쓰지 않는다.** 당근 동네생활은 Material 카드가 아니라 구분선으로만
항목을 나누고 세로 여백이 넉넉하다.

## 1. 커뮤니티 탭

```
┌──────────────────────────────────────────┐
│ 스팟 톡                      [👁] [🚫]   │  ← 숨긴 글 / 차단 목록
├──────────────────────────────────────────┤
│ [전체][맛집][축제·행사][관광지][문화시설]…│  ← communityChips (가로 스크롤)
│ ( 최신순 | 거리순 )                       │  ← 정렬 토글 (작게)
├──────────────────────────────────────────┤
│  PostCard                                │
│  ────────────────────────────────────    │  ← 얇은 구분선
│  PostCard                                │
│                                    [✏]  │  ← 작성 FAB
└──────────────────────────────────────────┘
```

**FAB은 하단 내비 바 위로 띄운다.** 셸이 `extendBody: true`라 탭 화면의 body가 떠 있는
내비 바 아래까지 그려져, 기본 위치의 FAB은 바에 가린다. `FloatingBottomNavScaffold.barExtent`
상수를 읽어 그만큼 + 27px 올린다. **값을 화면에 복사하지 않는 이유**는 바 높이가 바뀔 때
보정이 저절로 따라오게 하기 위해서다. 피드의 하단 여백도 같은 상수를 쓴다.

### PostCard — 사용자가 지정한 배치

```
┌────────────────────────────────────────────────┐
│ 카테고리(저강조) · 닉네임                  [⋮] │  ← 좌상단 / 우상단 메뉴
│ ┌────┐  제목 (titleMedium, w700, 2줄)          │
│ │사진│  본문 (bodyMedium, 2줄 + ellipsis)      │  ← 사진은 **좌측 1장만**
│ └────┘                                         │
│         장소명 · #태그 · 3시간 전  👁12 💬4 ♡8 │  ← 전부 우측 정렬
└────────────────────────────────────────────────┘
```

- **사진은 `photoKeys.first` 한 장만**, 84×84. 없으면 `Row` 자체를 쓰지 않고 텍스트만
  그린다 — 빈 상자를 남기면 사진 있는 카드와 없는 카드의 제목 시작점이 어긋난다
- **장소는 `spot != null`일 때만** 그린다 (장소 없는 글이 허용된다, 가이드 §5)
- 태그는 `#야경` 형태로 **원문 그대로**. 번역 대상이 아니다 (가이드 §9)
- 조회수·댓글 수·좋아요 수를 함께 그린다. `commentCount`는 **서버 값을 그대로** 쓴다 —
  차단 때문에 목록이 더 짧아도 다시 계산하지 않는다 (가이드 §6)
- `hidden: true` → "신고 누적으로 숨겨졌다" 배지 / `edited: true` → 제목 옆 "수정됨"
- **개발 시드의 photoKey는 404가 정상**이므로 항상 플레이스홀더를 깔고 그 위에 이미지를
  그린다. 실패해도 레이아웃이 무너지지 않는다
- 상세(`expanded: true`)에서는 본문을 자르지 않고 사진을 가로 스크롤로 전부 보여준다.
  사진을 탭하면 전체 화면 뷰어(`PostPhotoViewer`, 여러 장이면 스와이프)

### 상대 시각

사용자가 지정한 구간이다. 판정은 순수 함수(`relativeTimeSince`)가 하고 문구는 위젯이
l10n으로 고른다 — 모델은 번역을 알지 못한다(CLAUDE.md §3).

| 경과 | 표시 |
|---|---|
| 1분 미만 | 방금 |
| 1시간 미만 | 분 |
| 24시간 미만 | 시간 |
| 30일 미만 | 일 |
| 1년 미만 | 개월 |
| 1년 이상 | 년 |

미래 시각은 "방금"으로 접는다 — 서버 시계가 앞서도 "-3분 전"을 보여주지 않는다.

### 정렬 토글

`최신순`(기본) / `거리순`. 칩 줄 **아래**에 작게 둔다 — 칩과 같은 크기면 필터와 정렬
두 축이 섞여 보인다.

**정렬은 피드 provider의 family 인자다.** 값이 바뀌면 다른 인스턴스가 커서 없이 첫
페이지부터 받는다 — 두 정렬은 커서 형식이 달라 재사용하면 `INVALID_INPUT`이다(2차 §3).

거리순은 **장소 없는 글이 빠진다**(거리가 없어 순서를 정할 수 없다). 좌표가 없으면
거리순도 최신순처럼 동작하며 오류가 아니다.

## 2. 글 작성·수정 (컴포저)

초안의 테두리 있는 짧은 입력칸이 "좁고 올드하다"는 지적을 받아 **화면을 가득 쓰는
배치**로 바꿨다.

```
┌─────────────────────────┐
│ ✕   새 글          [등록] │
├─────────────────────────┤
│ [관광지][맛집][숙박]…     │  ← 카테고리 (필수, 한 줄 칩)
│                         │
│ 제목을 입력하세요          │  ← 테두리 없음, 굵게
│ ─────────────────────── │  ← 얇은 구분선만
│ 자유롭게 이야기해 보세요    │  ← 테두리 없음
│                         │
│         (남은 공간 전부)   │  ← expands: true
├─────────────────────────┤
│ 🏷 태그  📍 장소  📷 사진  │  ← 하단 액션 바
└─────────────────────────┘
```

- **본문이 남은 세로 공간을 전부 채운다**(`expands: true`) — 이것이 재설계의 요지다
- 카운터는 **한계 90%부터** 드러난다. 세는 단위는 **코드포인트**다(가이드 §8) —
  `String.length`(UTF-16)로 세면 이모지가 든 글에서 서버와 숫자가 어긋난다
- 길이를 넘겨도 **입력을 자르지 않는다.** 등록이 막히고 초과분이 드러난다 —
  붙여넣기한 사용자가 무엇이 사라졌는지 모르면 안 된다
- 등록 조건: 카테고리 + 제목 + 본문. **장소는 조건이 아니다**(선택 항목)

**수정 모드도 같은 입력을 전부 준다.** 서버 `EditPostInput`이 `category`·`changeSpot`·
`spotId`·`tags`를 받기 시작하면서 열렸다. 진입 시 `post(id:)`로 제목·본문·사진·카테고리·
태그·장소를 **함께 받아 채운다** — 빈 채로 열면 저장할 때 원래 값이 날아간다.

`changeSpot`은 `spotId: null`이 "떼라"와 "건드리지 마라" 둘 다로 읽히기 때문에 있는
플래그다. 씨앗 값과 지금 값을 비교해 **바뀐 경우에만** true를 보낸다.

### 사진 — 등록을 누를 때 올린다

**고르는 즉시 올리지 않는다.** 글을 쓰지 않고 나간 사용자의 사진이 스토리지에 고아로
남고, 골랐다 뺐다를 반복하면 그만큼 쌓인다 — 실제 저장 비용이다.

```
고를 때   → 메모리에 담고 로컬 미리보기(Image.memory). 통신 0회
등록할 때 → 발급 → PUT → 확인 → createPost(photoKeys:)
```

- `ComposerPhoto`는 sealed다 — **이미 올라간 것(`RemotePhoto`)과 방금 고른 것
  (`LocalPhoto`)이 한 목록에 순서대로 섞인다**. 수정 화면에서 둘이 공존한다
- 5장 상한은 **두 종류를 합쳐** 센다
- **업로드가 실패해도 글은 올린다.** 5장 중 1장이 실패하면 나머지로 등록하고 실패한
  장만 알린다 — 사용자가 쓴 글을 사진 때문에 날리지 않는다. 서버 3단계가 장별로
  갈리는 구조(가이드 §4)와도 맞는다
- 10 MiB·형식 검사는 **고를 때** 한다. 큰 사진을 글 다 쓴 뒤에 알려 주면 늦다
- 등록이 거부돼 다시 누르면 **이미 올라간 장은 다시 올리지 않는다**
- 수정 중 사진을 빼도 `deletePostImage`를 부르지 않는다 — 저장 전에 지우면 사용자가
  취소하고 나갔을 때 원래 글의 사진이 깨진다

### 장소 선택 시트

```
┌─────────────────────────┐
│ 주변 장소                 │
│ ( 주변 | 좋아요한 장소 )   │  ← 두 출처
│ [전체][관광지][맛집]…      │  ← availableSpotCategories
│                         │  ← 16px
│ 🔍 결과 내 재검색          │
├─────────────────────────┤
│ 서울갤러리          16m   │
│ 서울어텀페스타       41m   │
└─────────────────────────┘
```

- **서버 `spots`는 좌표 기반이고 이름 검색이 없다.** 그래서 상단 텍스트 상자는
  "결과 내 재검색"이고, 이미 받아 둔 목록만 좁힌다. 진짜 검색은 서버가
  `spots(keyword:)`를 열면 그 자리에 붙인다
- **카테고리 칩은 서버가 정한다**(`availableSpotCategories`). **언어마다 다르다** —
  국문은 여행코스, 외국어는 교통이 온다. 하드코딩하지 않는다
- 카테고리는 **서버가 거르는 진짜 필터**다(음식점 선택 시 3386 → 777건). 두 탭에
  함께 걸린다 — 탭마다 필터가 다르면 왜 결과가 달라졌는지 알 수 없다
- 좋아요한 장소는 **커서 페이징**이고 주변 장소는 **오프셋**이다. 거리 값이 없어
  대신 주소를 그린다
- 반경 5km, 한 번에 50건
- 위치를 못 얻어도 **장소 없이 등록하는 길은 열려 있다**

## 3. 글 상세

```
┌─────────────────────────┐
│ ←  글                [⋮] │
├─────────────────────────┤
│ PostCard (expanded)      │
├─────────────────────────┤
│ 댓글 · 6                 │
│ 홍길동   경복궁 좋네요     │
│                 [답글]   │
│    └ 김철수  저도요!      │  ← replies (40px 들여쓰기)
│    └ 이영희  언제 가셨어요?│
├─────────────────────────┤
│ [댓글을 입력하세요]   [전송]│  ← 하단 고정
└─────────────────────────┘
```

- **댓글은 루트 쿼리**(`comments(postId:)`)다. 글과 다른 provider라 **댓글 조회가
  실패해도 글 본문은 남는다**
- **대댓글은 깊이 2단계**다. `replies`는 **오래된 순**이라 뒤집지 않는다(대화 흐름).
  최상위 목록은 최신순
- **[답글 달기]는 최상위에만** 둔다 — 답글에 단 답글은 서버가 최상위로 눕혀서 넘긴
  값과 응답의 `parentCommentId`가 달라진다(2차 §1)
- 답글 모드일 때 입력줄 위에 "○○님에게 답글"과 취소를 띄운다 — 보이지 않으면 일반
  댓글을 달려던 사용자가 엉뚱한 곳에 단다
- 삭제된 부모의 답글도 그린다
- **완료 안내(스낵바)는 floating이어야 한다.** 기본값은 Scaffold 바닥에 붙는데 그
  자리가 곧 댓글 입력줄이라 입력창을 덮는다. 입력줄 높이를 실측해 그만큼 띄운다 —
  답글 모드에서는 높이가 달라지므로 상수로 적지 않는다

## 4. 모더레이션

세 가지가 **서로 다른 축**이다(2차 §2).

| | 대상 | 효과 | 되돌리기 |
|---|---|---|---|
| 숨기기 | 글 하나 | **내 화면에서만** 사라짐 | 가능 |
| 차단 | 사람 | 그 사람 글·댓글 전부(양방향) | 가능 |
| 신고 | 글·댓글·사람 | 운영 조치 요청 | 불가 |

### ⋮ 메뉴

| 항목 | 노출 조건 |
|---|---|
| 글 수정하기 | `ownedByViewer` — **`hidden`이면 비활성 + 사유 표시** |
| 글 삭제하기 | `ownedByViewer` |
| 이 글 숨기기 | `!ownedByViewer` |
| 이 사용자 차단하기 | `!ownedByViewer` |
| 이 글 신고하기 | `!ownedByViewer` |

**숨기기가 `!ownedByViewer`인 것은 2차 가이드 표(「항상」)와 다르다.** 내 글은 삭제가
있으니 내게서만 감출 이유가 없다는 사용자 판단이다. 2차 가이드 §2 본문도 이 기능을
"남의 글을 안 보기 위한 것"으로 설명한다.

### `Post.hidden`과 "숨기기"는 다른 값이다

- `Post.hidden` — 신고 5건 누적으로 **모두에게** 감춰짐. 작성자에게만 보이고 배지가 붙는다
- `hiddenByViewer` — 내가 나에게만 감춤

이름이 비슷해 섞기 쉬우니 모델·UI에서 갈라 둔다.

### 신고 시트

`OTHER`를 고르면 상세가 **필수**가 된다 — 폼에서 미리 막는다. 같은 대상 재신고
(`ALREADY_REPORTED`)는 오류로 터뜨리지 않고 "이미 신고했다"로 접는다. **회원 신고는
기록만 된다** — "접수되었다" 이상을 약속하지 않는다.

### 차단 확인

차단은 **양방향**임을 확인 문구에 밝힌다. 성공 후에는 로컬에서 지우는 것이 아니라
**피드를 다시 불러온다** — 필터링은 서버가 한다.

### 목록 화면

`/blocked-users`(차단한 사람) · `/hidden-posts`(숨긴 글). 둘 다 앱바에서 들어간다.
숨긴 글 목록은 카드가 아니라 제목·시각·[해제] 한 줄이다 — 거기서 할 일은 읽기가
아니라 되돌리기다. 좌표·카테고리 필터를 걸지 않는다(다른 도시에서 숨긴 글을 못 푼다).
차단 목록에는 "내가 건 차단만 보인다"는 안내를 둔다(가이드 §6). **빈 목록은 오류가
아니다.**

## 5. 상태 구분

- 칩 줄과 피드가 **다른 provider**다 — 한쪽이 실패해도 다른 쪽은 보인다
- 글과 댓글도 **다른 provider**다
- 위치 실패는 빈 피드와 **다른 문구**를 쓴다 — 사용자가 할 일이 다르다
- 칩 빈 목록·차단 목록 빈 상태는 **오류가 아니다**
- 조회 실패에는 재시도를 준다. 다만 차단·숨김으로 `post(id:)`가 null이면 재시도를
  주지 않는다 — 다시 조회해도 결과가 같다
- **당겨서 새로고침**은 공용 `PaginationListView`의 선택 인자다. 피드·차단 목록·
  글 상세에 붙어 있다. 새 값을 **await**해야 스피너가 제때 걷힌다

## 6. 좋아요 낙관적 갱신

탭 즉시 반영하고, **응답의 `likeCount`로 되맞춘다** — 서버 값이 정본이다(가이드 §7).
멱등이라 이미 좋아요한 글에 다시 눌러도 성공이다. 실패는 컨트롤러가 롤백한다.

## 7. 다국어 (POL-022, POL-023)

- **`TargetCategory`·`SpotCategory`·`ReportReason`은 앱이 매핑한다.** 서버는 enum 값만 준다
- 커뮤니티는 **자기 l10n 키**를 쓴다(`communityCategory*`). 값이 `SpotCategory`와 같아도
  spot 도메인의 라벨 함수를 부르지 않는다 — 기능 간 import가 되고, 두 도메인의 문구가
  갈릴 자유도 사라진다. 실제로 커뮤니티는 "맛집", 관광 목록은 "음식점"이 자연스럽다
- **태그는 번역 대상이 아니다** — 사용자 입력 원문 그대로
- `PostSpot`의 제목·썸네일은 `Accept-Language`를 따른다

## 9. 이 문서가 초안에서 달라진 이유

서버 계약이 두 차례 구조적으로 바뀌었다. 초안의 필드·컴포넌트 이름은 남아 있지 않다.

**1차 (2026-08-06)** — `nearbyPosts`/`targetPosts`/`discoveryTiles`/`PostTopic`/
`PostTargetType`이 전부 사라지고 피드가 `posts(...)` 하나로 합쳐졌다. `Post`에 `title`·
`tags`·`category`·`edited`가 생겼고 `spot`은 nullable이 됐다. 댓글은 루트 쿼리가 됐다.
→ `DiscoveryTileGrid`·`TopicChipRow`·`PostSpotChip`·`PostActionBar` 삭제, 본문에서
제목을 잘라 쓰던 대역(`splitPostBody`) 삭제.

**2차 (2026-08-07)** — 대댓글·게시물 숨기기·거리순 정렬·조회수 추가. `editPost`가
카테고리·장소·태그를 받기 시작.

**해소된 갭.** 초안이 [AMEND] 대상으로 적었던 것이 전부 서버에서 열렸다 — 카테고리
필터, 제목 필드, 조회수. 사진 선택 수단도 `image_picker`로 구현됐다.

**초안에서 뒤집은 판단 두 가지.**
- 목록 카드에 **작성자를 표시한다.** 초안은 프로필 화면이 비범위라 뺐지만, 누가 쓴
  글인지 모르는 피드가 더 어색하다는 사용자 판단으로 되돌렸다
- 정렬 선택을 **둔다.** 초안은 "필터는 카테고리 줄 하나가 전부"였으나 서버가 거리순을
  열면서 토글이 생겼다

## 10. 남은 갭

- **장소 이름 검색이 없다.** `spots`가 좌표 기반이라 반경 밖 장소는 이름을 알아도 못
  찾는다. 서버가 `spots(keyword:)`를 열면 "결과 내 재검색" 자리를 진짜 검색으로 바꾼다
- **장소 없이 쓴 글은 거리순 피드에 안 나온다.** 계약대로지만 "내가 쓴 글이 안 보인다"는
  문의로 이어질 수 있다. 최신순에서는 보인다
- **알림·대댓글 3단계·본문 검색·수정 이력**은 비범위다(가이드 §11)
- **Stitch 목업은 갱신하지 않았다.** 서버 계약이 두 번 바뀌면서 초안 목업의 화면
  구성이 실제와 어긋난다 — 이 문서가 정본이다
