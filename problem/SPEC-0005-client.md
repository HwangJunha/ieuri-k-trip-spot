# SPEC-0005 — 클라이언트 설계

요구사항과 수용 기준은 스펙이 정본이다. 이 문서는 그것을 다시 적지 않고 번호로 인용하며, 이 레포에서의
설계 결정만 다룬다. SDL 표면은 변경되지 않으므로 새로 생성할 GraphQL 연산 문서도 없다.

관련 이슈: #22 · 브랜치 `feature/SPEC-0005-auth-session-gate` (`dev`에서 분기)

> **v1.2 개정** — R15(인증 실패는 항상 최상위 `errors[]`)와 R16(낙관적 반응 재전송)이 신설되었다.
> R15는 **서버에서 해결한다**(`ieuri-server#32`). 이 문서에서 바뀌는 것은 §4가 새로 생긴 것과,
> §3의 "갱신은 링크 계층과 부팅 복원 경로에서만"이 유지된다는 점을 명시한 것이다.
> 클라이언트에 `userErrors` 판별 분기를 추가하지 않는다.

---

## 1. 현재 구조와 결함 위치

세 지점이 각각 독립적으로 고장나 있으며, 셋을 모두 고쳐야 R1~R13이 성립한다.

### 1.1 `lib/common/network/graphql_client.dart` — `_RefreshLink`

`_isAuthError()`가 `extensions['code'] == 'UNAUTHENTICATED'`를 검사한다. 서버는 그 형태를 방출하지
않으므로(스펙 「계약 요약」 E1) 이 조건은 성립할 수 없고, 자동 갱신이 한 번도 트리거되지 않는다. 링크의 재시도
골격 자체는 이미 있으므로 판별식 교체가 핵심이다.

동시성 처리도 없다. 요청별로 독립 재시도하므로 동시 만료 시 갱신이 중복 실행된다(R8).

### 1.2 `lib/router/app_router.dart` — `redirect`

인증 상태가 `AsyncValue.loading`인 동안 `null`을 반환해 리다이렉트를 포기한다. 주석에 의도가 명시되어
있으나("Auth state is async on first build; while it resolves, don't redirect"), 이 구간에 보호 대상
화면이 렌더링되고 provider가 발화한다(R1, R2).

`_authPaths` 목록 자체는 올바르므로 유지한다(AC-9).

### 1.3 `lib/domain/auth/repository/auth_repository_impl.dart` — `_run()`

최상위 `errors[]`가 채워져 있으면 무조건 `AuthFailure.networkFailure`를 던진다. 이 때문에 "서버가
refreshToken을 거부함"과 "네트워크가 끊김"이 repository 계층에서 같은 값으로 뭉개진다. R9와 R10이
정반대의 처리를 요구하므로(세션 종료 vs 세션 유지) 이 분류를 나누지 않으면 두 요구사항 중 하나는
반드시 위반된다.

## 2. 설계 결정

### 2.1 인증 실패 판별을 한 곳으로 모은다

판별 규칙(스펙 「계약 요약」 E1~E5)을 `lib/common/network` 아래 단일 함수로 두고, `_RefreshLink`와
`AuthRepositoryImpl`이 같은 함수를 쓴다. 두 곳에 문자열 매칭을 흩어 두면 서버가 형태를 바꿀 때 한쪽만
고쳐지고 증상은 지금 버그와 동일하게 나타난다.

판별 순서는 E2를 먼저 본다. `errorType == "UNAUTHENTICATED"`이면 message를 보지 않고 확정하고(AC-15),
아니면 `INTERNAL` + message 매칭으로 내려간다(AC-14). 서버가 정리되면 아래 분기만 지우면 되도록
순서를 잡는다.

`extensions`나 `errorType`이 없는 응답에서 예외가 나지 않아야 한다(AC-17). null 안전하게 접근한다.

### 2.2 실패 분류를 세 갈래로 나눈다

`_run()`이 던지는 값을 다음으로 구분한다. R9와 R10의 분기가 여기서 결정된다.

| 분류 | 조건 | 상위 처리 |
|---|---|---|
| 인증 실패 | E1 / E2 | 갱신 트리거 (R4·R5) |
| 갱신 거부 | E3 / E4 | 토큰 제거, 세션 종료 (R9·R11) |
| 전송 실패 | E5 — `linkException` 존재, `errors[]` 없음 | 토큰 유지, 오류만 전파 (R10) |

기존 `AuthFailure`에 갱신 거부와 전송 실패를 구분하는 케이스를 둔다. 이름은 구현 시 정하되, "네트워크"
하나로 뭉뚱그리는 현재 형태를 유지하면 안 된다.

E4(재사용 감지)는 E3와 동일하게 세션 종료로 처리한다. 사용자에게 다른 안내를 하지 않는 것은 의도된
선택이며 스펙 「미결 사항」에 기록되어 있다.

### 2.3 갱신을 단일 실행으로 만든다 (R8)

진행 중인 갱신의 `Future`를 보관하고, 갱신이 필요한 후속 요청은 새로 시작하지 않고 그 `Future`를
기다린다. 완료되면 참조를 비운다.

이게 없으면 서버 refresh가 1회용 회전이므로, 두 번째 갱신이 방금 폐기된 jti를 제시해
`TokenReuseDetectedException` → 회원 전체 세션 폐기 → 모든 기기 로그아웃으로 이어진다(AC-22). 탭 셸
화면들이 동시에 provider를 발화시키는 구조라 실제 발생 가능성이 낮지 않다.

대기 중이던 요청들은 갱신 성공 시 **새 accessToken으로** 재시도해야 한다(AC-21). 갱신 시작 시점에
읽어둔 토큰이 아니라 갱신 완료 후의 토큰을 읽는다.

### 2.3.1 갱신 실패 후 억제 (R14)

갱신이 실패하면 억제 플래그를 세우고, 억제 중에는 인증 실패가 와도 갱신을 시도하지 않고 오류를 그대로
전달한다(AC-37). 2.3의 단일 실행은 동시 요청을 합칠 뿐 순차 재발화를 막지 못하므로, R10 경로에서 세션이
유지된 채 사용자가 화면을 오가면 전환마다 갱신이 나간다. 그걸 막는 장치다(AC-36).

해제 계기는 명시적인 것만 인정한다 — 사용자의 재시도 동작, 또는 앱 재시작(AC-38). **시간 기반 쿨다운을
두지 않는다.** POL-029(응답 시간 목표)가 `[TBD]`인 이상 어떤 대기 시간을 적어도 근거 없는 수치가 된다.

갱신이 성공하면 억제는 당연히 해제된다. 억제는 실패 상태에만 존재한다.

### 2.4 요청당 갱신 1회 (R7)

재시도한 요청이 다시 인증 실패로 끝나면 두 번째 갱신을 시도하지 않는다(AC-19). 요청 단위로 재시도
여부를 표시해 전달한다.

호출 반복을 막는 장치가 셋이며 서로 겹치지 않는다. 셋 다 필요하다.

| 장치 | 막는 것 | 근거 |
|---|---|---|
| 2.3 단일 실행 | 동시 요청 **간** 중복 갱신 | R8 |
| 2.4 요청당 1회 | 한 요청 **내** 갱신 반복 | R7 |
| 2.3.1 실패 후 억제 | 실패 후 순차 재발화에 의한 반복 | R14 |

### 2.5 라우터 게이트를 세 상태로 다시 만든다 (R1·R2·R3·R13)

인증 상태를 `loading` / `authenticated` / `unauthenticated` 세 갈래로 다루고, `loading`에서 보호 대상
경로 진입 시 리다이렉트를 포기하는 대신 **대기 화면을 렌더링한다**. 보호 대상 화면 자체를 그리지 않으므로
provider가 발화하지 않는다(AC-1, AC-4).

대기 화면은 빈 화면이나 에러 화면이 아니어야 한다(AC-2). 스플래시 유지가 자연스럽다.

`spots`가 토큰 없이도 200에 데이터를 반환하므로(스펙 「미결 사항」 서버 측 후속 작업 3), 게이트가 새면 화면이 정상처럼 채워져
결함이 눈에 띄지 않는다. 이 스펙에서 서버를 고치지 않기로 했으므로 클라이언트 게이트가 유일한 방어선이다.

### 2.6 부팅 시 갱신 선행 (R13)

`AuthController._restoreSession()`의 기존 흐름(`me` 시도 → 실패 시 `refresh()` 1회)은 방향이 맞다.
다만 이 경로의 실패도 2.2 분류를 따라야 한다. 부팅 중 네트워크가 끊겨 있으면 토큰을 지우지 않고 유지한
채(R10) 미인증으로 두며, 복구 후 재시도 시 보관된 refreshToken으로 갱신이 성공해야 한다(AC-29).

accessToken만 만료된 경우 갱신이 선행되어 로그인 화면을 거치지 않아야 한다(AC-34). 상태를
`unauthenticated`로 잠깐이라도 넘기면 라우터가 `/login`으로 보내므로, 갱신 시도가 끝나기 전에는
`loading`을 유지한다.

### 2.7 토큰 저장 (R12)

갱신 성공 시 accessToken과 refreshToken을 함께 기록하고 이전 값을 남기지 않는다(AC-30). 저장이 끝난 뒤에
대기 중인 요청을 풀어야 이후 요청이 새 토큰을 담는다(AC-32).

`success: true`인데 `accessToken`이 null인 응답은 실패로 간주하고 R9를 따른다(AC-31). 스키마상
`accessToken`이 nullable이므로 가능한 상태다. **이는 계약이 보장하는 동작이 아니라 우회이며**, 서버
하네스에 확인이 필요한 사항으로 스펙 「미결 사항」에 기록되어 있다.

## 3. 계층 경계

- 생성된 GraphQL 타입은 repository 밖으로 나가지 않는다(POL-020). 갱신 경로도 예외가 아니며, 판별
  함수는 `graphql_flutter`의 응답 형태까지만 알고 도메인 계층은 `AuthFailure`만 본다.
- `_RefreshLink`가 provider를 직접 참조하지 않도록 현재의 bridge 구조를 유지한다. 순환 참조를 피하려는
  기존 의도가 맞다.
- 라우터는 인증 상태를 읽기만 하고 갱신을 트리거하지 않는다. 갱신은 링크 계층과 부팅 복원 경로에서만
  일어난다. **이 경계는 v1.2에서도 유지된다** — 아래 참조.

> **v1.2 — 이 경계를 바꾸지 않기로 한 결정.** `k-trip-spot#22` `[AMEND]`는 `reactToSpot`이 인증 실패를
> payload `userErrors[]`로 반환해 링크 계층이 보지 못하는 문제를 보고했다. 해결안 두 가지를 검토했다.
>
> | 안 | 결과 |
> |---|---|
> | 클라이언트가 `userErrors`도 판별 | repository가 갱신을 트리거해야 함 → 이 경계가 무너짐 |
> | **서버가 최상위 `errors[]`로 통일** | 경계 유지. 기존 판별 규칙(E1~E5)이 그대로 성립 |
>
> **후자를 택했다**(스펙 R15, `ieuri-server#32`). `userErrors`는 `response.data` 안에 있어 링크 계층이
> 읽으려면 연산별 payload 구조를 알아야 하고, 이는 바로 위 POL-020 항목과 정면으로 충돌한다.
> 인증 실패는 연산과 무관한 전역 신호이므로 전역 계층에서 처리하는 것이 옳다.
>
> 따라서 **`_RefreshLink`에 `userErrors` 분기를 추가하지 않는다.** 2.1의 판별 함수도 그대로 두며,
> 서버 변경 후 기존 규칙만으로 이 경로가 동작한다(AC-40).
- **서버 원본 message를 밖으로 흘리지 않는다(POL-013).** 판별 함수는 message를 읽지만, 그 문자열이
  로그·크래시 리포팅·사용자 노출로 나가서는 안 된다. 읽는 것과 남기는 것은 다르다. 원본 message에는
  서버 패키지 경로와 예외 클래스명이 그대로 들어 있다
  (`org.around.ieuri.common.security.UnauthorizedException: ...`). 밖으로 나가는 값은 분류 결과
  (`AuthFailure`)까지이며, 디버그 로그에 남길 때도 원본이 아니라 분류 결과를 남긴다.

## 4. 낙관적 반응의 재전송 (R16, v1.2)

### 4.1 대부분은 이미 성립한다 — 새 큐를 만들지 않는다

R15가 적용되면 `reactToSpot`의 인증 실패는 최상위 `errors[]`로 오고, `_RefreshLink`가 이를 판별해
갱신 후 **원 요청을 그대로 재시도한다**(2.1·R4). 재시도는 링크 계층에서 일어나므로
`_record()`의 `await`는 그동안 그냥 대기하며, 성공하면 정상 반환된다.

즉 **AC-43의 "재전송"은 링크 계층의 기존 재시도가 그대로 수행한다.** 반응을 따로 보관했다가 다시
보내는 큐를 새로 만들지 않는다. 낙관적으로 카드를 이미 제거했다는 사실은 재시도와 무관하다 — 재시도
대상은 UI 상태가 아니라 in-flight 요청이기 때문이다.

이 설계를 명시적으로 적는 이유는, `[AMEND]` 보고가 "갱신 성공 시점엔 카드가 이미 넘어간 뒤"라는 점을
근거로 별도의 재전송 장치를 검토했기 때문이다. **불필요하다.** 카드가 넘어간 것과 요청이 재시도되는
것은 서로 독립적이며, 사용자에게는 요청이 성공한 것으로 보인다(오류 노출 없음, AC-43).

### 4.2 실패 시 카드를 되돌리지 않는다 (AC-44)

갱신 자체가 실패하면(R9 세션 종료 / R10 세션 유지) 재시도가 성립하지 않고 `_record()`가 예외를 받는다.
현재 동작 — 조용히 로깅하고 카드를 복원하지 않는다(`swipe_providers.dart` `_record`) — 을 유지한다.

R9라면 세션이 종료되어 로그인 화면으로 이동하므로(R11) 카드 복원은 의미가 없다. R10이라면 세션은
유지되지만 이미 다음 카드가 화면에 있고, 되돌리면 사용자가 방금 넘긴 카드가 다시 나타난다 — 사용자가
분명히 반응한 카드를 되묻는 것이므로 하지 않는다. 이 반응은 유실된다.

**유실을 허용하는 것은 의도된 선택이다.** 좋아요/싫어요는 비치명적이며(§5 기존 방침), 오프라인 큐잉은
SPEC-0005 범위 밖이다.

### 4.3 재전송이 다시 실패해도 반복하지 않는다 (AC-45)

2.4(요청당 갱신 1회)와 2.3.1(실패 후 억제)이 그대로 적용된다. R16이 새 반복 경로를 만들지 않으므로
추가 장치가 필요하지 않다 — 재시도는 링크 계층에서 일어나고 그 계층의 기존 제한을 받는다.

### 4.4 상세 화면도 동일하다

상세 화면의 반응은 롤백이 있는 낙관적 업데이트지만, 재시도가 링크 계층에서 일어나는 것은 같다.
갱신 성공 시 요청이 성공하므로 롤백이 발동하지 않는다. 갱신 실패 시에만 기존 롤백이 그대로 동작한다.

## 5. 검증

수용 기준 중 자동화가 어려운 것과 쉬운 것을 나눈다. v1.2에서 AC-39~AC-45가 추가되었으며, AC-39·AC-41·
AC-42는 서버 소관이므로(`problem/SPEC-0005-server.md` §4) 아래에서 다루지 않는다.

**단위 테스트로 닫을 수 있는 것** — 판별 함수(AC-14~AC-17), 실패 분류(AC-25·AC-27), 단일 실행
(AC-21·AC-23), 재시도 1회 제한(AC-19·AC-20), 실패 후 억제(AC-36~AC-38), 토큰 저장(AC-30~AC-32).
서버를 띄우지 않고 응답 형태를 직접 만들어 검증한다.

**실기기·에뮬레이터 확인이 필요한 것** — 렌더링 차단(AC-1·AC-2·AC-35)과 부팅 경로(AC-33·AC-34).
"한 프레임도 렌더링되지 않는다"는 조건은 위젯 테스트로 프레임 단위 확인이 가능하나, 스플래시 전환과
함께 육안 확인을 권한다.

**AC-22(전체 세션 폐기 미발생)** 는 단일 실행이 성립하면 따라오는 결과다. 직접 재현하려면 서버에서
동일 refreshToken을 두 번 제시해야 하므로, 2.3의 단위 테스트로 갈음한다.

**v1.2 추가분(AC-40·AC-43~AC-45).** §4에 적은 대로 R16은 새 장치를 만들지 않고 링크 계층의 기존
재시도에 의존하므로, 검증도 기존 항목에 흡수된다.

| 기준 | 방법 |
|---|---|
| AC-43 (재전송 성공, 오류 미노출) | 단위 테스트 — `reactToSpot`이 인증 실패 응답 후 갱신·재시도로 성공하고 `_record()`가 예외 없이 끝나는지. AC-18과 같은 구조다 |
| AC-44 (갱신 실패 시 카드 미복원) | 단위 테스트 — 갱신 실패 시 `_record()`가 예외를 삼키고 큐 상태가 변하지 않는지 |
| AC-45 (재전송 반복 없음) | 2.4·2.3.1의 기존 테스트가 그대로 커버한다. 새 테스트 불필요 |
| AC-40 (서버 변경 후 갱신 트리거) | **단위 테스트.** 아래 참조 |

**AC-40은 실기기 확인으로 미루지 않는다.** 이 기준의 검증 가능한 핵심은 "최상위 `errors[]`에 인증 실패가
담긴 `reactToSpot` 응답을 받으면 갱신이 트리거되고 재시도된다"이며, 이는 응답을 직접 만들어 링크 계층에
넣으면 서버 없이 확인된다. 2.1의 판별 함수 테스트(AC-14·AC-15)와 재시도 테스트(AC-10)가 이미 쓰는
방식이고, 달라지는 것은 대상 연산이 `reactToSpot`이라는 것뿐이다.

`userErrors`가 비어 있고 최상위 `errors[]`에 인증 실패가 있는 `reactToSpot` 응답을 스텁으로 만들어,
갱신이 1회 트리거되고 재시도된 요청이 성공하는지 단언한다. 서버를 띄우지 않는다.

**서버가 실제로 그 형태를 내보내는지는 AC-39이며 서버 소관이다.** 클라이언트 테스트는 "그 형태가 오면
동작한다"까지만 책임진다. 두 기준을 한 실기기 확인으로 뭉뚱그리면 어느 쪽이 깨졌는지 구분되지 않는다.

실기기 확인은 배포 후 통합 확인으로 별도 수행한다 — 로그인 상태로 5분 이상 대기 후 좋아요를 눌러
`[AMEND]`의 재현 절차가 더 이상 재현되지 않음을 본다. 이는 수용 기준의 검증 수단이 아니라 배포 검증이다.

## 6. 알려진 부채

AC-14의 판별은 서버가 예외 클래스명을 message에 노출한다는 사실에 의존한다. 이는 운영 배포 전 차단되어야
할 정보 노출이며(`ieuri-server` #19), 차단되면 AC-14가 깨진다. AC-15가 안전망이지만 서버가 message만
막고 `errorType`을 `INTERNAL`로 둔 채 배포하면 이 버그가 그대로 재발한다.

**서버 측에서 `UnauthorizedException` → `errorType: UNAUTHENTICATED` 매핑과 message 차단은 반드시 함께
처리되어야 한다.** `ieuri-server#26`으로 개설되어 있으며, 쪼개서 처리되는 것을 막기 위해 두 작업을 한
이슈로 묶었다. 스펙 「미결 사항」 서버 측 후속 작업 1·2 참조.

`ieuri-server#26`이 닫히면 2.1의 AC-14 분기(`INTERNAL` + message 매칭)를 제거할 수 있다. 그 전까지는
남겨둔다.

### v1.2 추가 — 서버 배포에 대한 의존

**이 스펙의 R15·R16은 클라이언트만 배포해서는 성립하지 않는다.** `ieuri-server#32`가 배포되기 전까지
`reactToSpot` 인증 실패는 여전히 `userErrors`로 오고, 좋아요/싫어요의 자동 갱신은 계속 동작하지 않는다.
클라이언트에는 이를 우회할 장치가 없으며, 의도적으로 넣지 않았다(§3 v1.2 결정).

배포 순서는 다음과 같다.

1. `ieuri-server#32` — 인증 실패를 최상위 `errors[]`로 이동. 이 시점부터 AC-40이 성립한다
   (`errorType: INTERNAL`이므로 E1 문자열 매칭 경로로 판별된다)
2. `ieuri-server#26` — `errorType: UNAUTHENTICATED` 매핑 + message 노출 차단. 이후 E2 경로로 판별된다

**1번 없이 2번만 배포되면 안 된다.** message가 차단되면 E1이 깨지는데, `reactToSpot`은 아직
`userErrors`로 오므로 E2도 타지 않는다 — 좋아요/싫어요의 갱신이 계속 죽어 있고, 나아가 다른 연산의
E1 경로까지 함께 깨진다. 이 의존은 두 이슈 양쪽에 기록되어 있다.
