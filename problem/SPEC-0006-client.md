# SPEC-0006 — 클라이언트 설계

## 1. 이 저장소의 범위

12개 요구사항 중 **10건이 클라이언트 단독**이다(R1~R8, R11, R12). R9·R10은 서버의 nullability
완화(`ieuri-server` #34)에 의존하며, 이 문서는 그 응답을 어떻게 해석·표현하는지를 다룬다.

`spot` 도메인(`lib/domain/spot/`)과 공통 계층(`lib/common/`), 라우터에 걸친다.

## 2. 재시도 상한 (R1~R5)

### 2.1 현재 구조와 폭주의 원인

`SwipeController.build()`가 `ref.watch(currentCoordinatesProvider.future)`로 좌표 provider를
watch 한다. watch이므로 좌표 provider가 무효화되면 `build()`가 재실행되고, 그때마다
`fetchSpotPage`가 다시 호출된다. 실패 상태에서도 마찬가지다.

시도 횟수를 세는 지점이 코드 어디에도 없다. `reload()`도 호출될 때마다 무조건 재조회한다.
`_maybePrefetch()`는 실패를 조용히 로깅만 하고 백오프 없이 다음 스와이프에서 다시 시도한다.

SPEC-0005의 `TokenRefreshBridge.suppressed`는 **토큰 갱신 전용**이라 일반 조회 실패에는 관여하지
않는다. 즉 이 폭주를 막는 장치가 현재 없다.

### 2.2 시도 횟수를 어디에 두는가

**controller 인스턴스가 아니라 controller 바깥에 둔다.** provider가 재빌드되면 controller
인스턴스의 필드는 초기화되므로, 인스턴스 필드에 카운터를 두면 R4(리빌드 우회 금지)를 만족할 수
없다 — 바로 그 재빌드가 폭주의 경로이기 때문이다.

카운터는 재빌드를 넘어 살아남는 위치에 두고, `SwipeController`/`SpotDetailController`의 조회 진입
지점에서 상한을 확인한다. 상한 소진 상태면 **repository를 호출하지 않고** 종료 상태를 그대로
반환한다.

카운터의 생명주기는 **카테고리별 컨트롤러 인스턴스와 같은 축**을 따른다. 카테고리를 바꾸면 다른
컨트롤러를 보게 되고 상한도 새로 시작된다 — 이는 우회가 아니라 확정된 정상 동작이다(AC-4).

### 2.3 무엇을 시도로 계상하는가

| 실패 | 계상 | 근거 |
|---|---|---|
| 네트워크 오류·타임아웃 | 계상 | 일반 실패 |
| 서버 오류(`errors[]` 루트) | 계상 | 일반 실패 |
| 인증 실패(`UNAUTHENTICATED`) | **계상하지 않음** | SPEC-0005 갱신 경로 소관 (R5, AC-14) |
| 위치 권한 거부 | 계상하지 않음 | 재시도로 해결되지 않는 상태. SPEC-0001 안내 경로 |
| 하위 필드 부분 실패 | 계상하지 않음 | 상세 본문은 성공했으므로 조회 실패가 아니다 (R9) |

인증 실패 판별은 기존 `classifyGraphqlErrors`/`_isAuthError` 경로를 재사용한다. 새 판별 로직을
만들지 않는다.

### 2.4 종료 상태 (R2)

상한 도달은 **일반 오류와 구분되는 별도 상태**여야 한다(AC-5·AC-6). 오류 상태 하나에 재시도
버튼만 두는 현재 `_ErrorState` 구조로는 두 상태를 구분할 수 없다.

`discover_swipe_view.dart`와 `spot_detail_view.dart`에 각각 있는 `_ErrorState`를 공통 컴포넌트로
올려 재시도 가능/종료 두 형태를 갖게 한다. `k-trip-spot` #24(토큰 갱신 억제 해제 UI)가 같은
컴포넌트를 쓰게 되므로 `lib/common` 쪽에 두는 편이 자연스럽다 — 다만 #24의 요구사항 자체는 이
스펙이 흡수하지 않는다.

신규 문구는 POL-022에 따라 EN/KO/JA/ZH 4개 언어 키가 필요하다(AC-7).

### 2.5 명시적 재시도 (R3)

사용자의 재시도는 상한을 무시하고 1회 시도한다(AC-8·AC-13). 성공하면 카운터를 0으로 초기화해
이후 실패 시 다시 2회까지 자동 재시도가 가능해진다(AC-9). 실패하면 종료 상태를 유지하고 자동
재시도를 이어서 발생시키지 않는다(AC-10).

## 3. 화면 전환 (R6, R7)

`lib/router/routes.dart`의 `/spot/:id`는 현재 `pageBuilder` 없는 `GoRoute`라 플랫폼 기본 전환
(좌우 슬라이드)을 받는다. `CustomTransitionPage`를 지정해 아래→위 진입, 위→아래 종료로 바꾼다
(AC-17·AC-20).

이 라우트가 탭 셸 밖 루트 내비게이터에 있는 현재 구조는 **유지한다.** 하단 탭 바 위에 덮이고
스와이프 스택 상태가 보존되는 기존 성질이 R6/R12에도 그대로 필요하다(AC-19).

시스템 뒤로가기와 명시적 닫기가 같은 전환을 쓰도록 한다(AC-22). 곡선·지속시간 수치는 수용 기준에
넣지 않았으므로 구현 재량이다.

## 4. 썸네일 연속성 (R8)

현재 `SwipeCard`의 `_CardImage`와 상세 화면이 각각 독립적으로 `Image.network`를 만든다. 같은
`thumbnailImageUrl`이라도 상세 진입 시 다시 로드되어 깜빡인다.

리스트가 이미 가진 썸네일 URL을 상세로 **넘겨준다.** 라우트는 이미 `category`를 쿼리 파라미터로
넘기고 있으므로(`routes.dart` 주석 참조) 같은 방식으로 확장할 수 있다.

상세는 본문 조회가 끝나기 전에도 넘겨받은 썸네일로 첫 이미지 자리를 채운다(AC-24). 본문 조회가
완료되면 응답의 `thumbnailImageUrl`이 최종 값이 된다(AC-26). 넘겨받은 값이 없는 직접 진입에서는
조회 결과로 대체하며 오류로 처리하지 않는다(AC-25).

이미지 캐시가 같은 URL에 대해 재요청하지 않도록 하는 것이 목적이므로, URL이 동일하다는 사실만으로
충분한지 구현 시 확인한다. 필요하면 precache 계열 수단을 쓴다.

## 5. 부분 실패 표현 (R9, R10)

### 5.1 판별은 repository 안에서

`gallery`/`infoItems`가 nullable이 되면 생성 타입의 형이 바뀐다. POL-020에 따라 그 변화는
**repository 매핑 계층에서 흡수**하고 도메인 모델 밖으로 내보내지 않는다.

응답 해석 규칙:

- `data.spotDetail`이 null → 전체 실패. 오류 상태 (AC-30)
- `data.spotDetail`이 채워짐 → 부분 실패 가능. 본문은 정상 렌더 (AC-27·AC-28)
- `errors[]`가 비어있지 않다는 사실만으로 전체 실패를 단정하지 않는다. `path`로 범위를 판별한다
  (AC-29)

### 5.2 표현

| 상태 | 화면 |
|---|---|
| `gallery`가 null (조회 실패) | 썸네일 1장 (AC-31) |
| `gallery`가 빈 배열 (이미지 없음) | 썸네일 1장 — null과 동일 (AC-32) |
| `infoItems`가 null | 이용안내 섹션 숨김. 오류 문구 표시하지 않음 (AC-33) |
| `intro`가 null | 기존 SPEC-0003 동작 유지 (섹션 숨김) |
| 둘 다 null | 본문 + 썸네일 1장, 정상 상태 유지 (AC-34) |

**null과 빈 배열을 구분하는 분기를 만들지 않는다.** 두 경우의 화면 결과가 같으므로 도메인 모델에서
하나로 접어도 된다. 구분이 필요해 보이면 그것은 스펙과의 불일치이므로 `[AMEND]`로 보고한다.

## 6. 복귀와 전진 (R11, R12)

`spot_detail_view.dart`는 **이미** 반응 시 `consume(contentId)`를 호출하고 pop 한다. R11은 신규
로직이 아니라 기존 동작의 명문화이며, `SwipeController.consume`이 스택 중간 카드도 제거하고 없는
id는 무시하는 성질(AC-37)도 이미 갖춰져 있다.

실제 결함은 R12다 — 복귀 시 다음 카드로 넘어가는 것이 시각적으로 드러나지 않는다. 상세가 닫히는
동안 리스트는 이미 카드가 제거된 상태로 그려져, 사용자 입장에서는 전진이 일어난 순간이 보이지
않는다.

수용 기준은 "관찰 가능한 상태 변화로 드러난다"(AC-38)까지만 요구하고 구체적 연출을 규정하지 않는다.
반응한 카드가 맨 위에 남아 있지 않을 것(AC-39), 마지막 카드였다면 소진 상태가 정상 표시될 것
(AC-40)이 경계 조건이다.

## 7. 테스트

provider/notifier와 도메인 모델 수준의 단위 테스트로 다룬다. repository는 스텁한다.

| 단위 | 검증 | 대응 AC |
|---|---|---|
| `SwipeController` | 실패 시 자동 재시도가 정확히 1회 더 발생하고 총 2회에서 멈춘다 | AC-1·AC-2 |
| `SwipeController` | 최초 성공 시 재시도가 발생하지 않는다 | AC-3 |
| `SwipeController` | 상한 소진 후 재빌드·무효화가 반복돼도 repository 호출이 늘지 않는다 | AC-11·AC-12 |
| `SwipeController` | 상한 소진 상태에서 명시적 재시도는 조회를 발생시킨다 | AC-13 |
| `SwipeController` | 명시적 재시도 성공 시 카운터가 초기화된다 | AC-9 |
| `SwipeController` | 명시적 재시도 실패 시 종료 상태가 유지된다 | AC-10 |
| `SwipeController` | 인증 실패는 시도 횟수에 계상되지 않는다 | AC-14·AC-15 |
| `SwipeController` | 인증 외 실패는 계상된다 | AC-16 |
| 상태 모델 | 상한 도달 상태와 일반 오류 상태가 구분된다 | AC-5·AC-6 |
| 카테고리별 인스턴스 | 카테고리 변경 시 카운터가 독립적으로 시작된다 | AC-4 |
| `SpotDetailController` | 본문 성공 + 갤러리 null이면 본문이 채워진 상태로 노출된다 | AC-27 |
| `SpotDetailController` | 본문 성공 + 이용안내 null이면 오류 상태로 전환되지 않는다 | AC-28 |
| `SpotDetailController` | 본문 null이면 전체 실패로 분류된다 | AC-30 |
| repository 매핑 | 주어진 `path` 값에 대해 부분 실패와 전체 실패로 올바르게 분기한다 | AC-29 (분기 로직 한정 — 아래 참조) |
| repository 매핑 | `gallery`의 null과 빈 배열이 동일한 도메인 상태로 매핑된다 | AC-31·AC-32 |
| `SpotDetailController` | 넘겨받은 썸네일이 없으면 조회 결과로 대체되고 오류가 아니다 | AC-25 |
| `SpotDetailController` | 본문 조회 완료 후 조회 결과의 썸네일이 최종 값이 된다 | AC-26 |
| `SwipeController.consume` | 반응한 카드가 스택에서 제거된다 | AC-35·AC-36 |
| `SwipeController.consume` | 스택에 없는 id는 스택을 변경하지 않는다 | AC-37 |
| `SwipeController` | 마지막 카드 소비 후 소진 상태가 된다 | AC-40 |

### 단위 테스트로 명세하지 않는 것

- **전환 방향·곡선·지속시간**(AC-17·AC-18·AC-20·AC-21·AC-22) — 라우트 설정값과 렌더 결과로,
  위젯 테스트 없이는 관찰되지 않는다. 이 플랫폼의 테스트 범위 밖이라 **명세하지 않고 남긴다.**
  라우트 정의에 전환이 지정되어 있는지는 코드 리뷰로 확인한다.
- **깜빡임의 부재**(AC-23·AC-24의 시각적 측면) — 이미지 캐시 적중은 렌더 계층 사건이다. URL이
  동일하게 전달되는지까지만 단위 테스트로 확인하고, 깜빡임 자체는 실기기 육안 확인으로 남긴다.
- **전진 표현의 시각적 드러남**(AC-38) — 상태 변화(카드 제거, 다음 카드가 맨 위)는 테스트하되
  연출은 테스트하지 않는다.
- **4개 언어 문구의 존재**(AC-7) — l10n 키 존재 확인은 빌드·생성 단계에서 드러난다.
- **`errors[].path`의 실제 형태**(AC-29의 전송 계층 측면) — 위 표의 repository 매핑 테스트는
  **테스트 작성자가 넣어준 `path` 값에 대한 분기 로직만** 검증한다. DGS가 중첩 필드 실패에 대해
  실제로 `["spotDetail","gallery"]` 형태를 내려주는지는 GraphQL 전송 계층을 세워야 관찰되므로
  이 범위 밖이다. 서버 설계문서 §7도 같은 이유로 이 부분을 명세하지 않고 남긴다.

  **따라서 이 계약은 양쪽 어느 단위 테스트로도 검증되지 않는다.** 구현 시 실제 응답을 한 번
  육안으로 확인하고, 가정한 형태와 다르면 `[AMEND]`로 보고한다. 이것이 R9/R10에서 가장 얇은
  지점이다.
