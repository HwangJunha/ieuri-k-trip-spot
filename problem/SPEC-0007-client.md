# SPEC-0007 · 축제 정보 적재 — 클라이언트 설계

요구사항과 인수 기준은 스펙 문서에 있다. 이 문서는 그것을 되풀이하지 않고 **이 레포에서 어떻게 실현하는지**만
다룬다. 요구사항은 번호로 인용한다.

---

## 0. 선행 조건 — 서버가 먼저다

**이 작업은 서버 작업(`HwangJunha/ieuri#35`)이 완료된 뒤에 시작한다.**

이 스펙에서 클라이언트가 담당하는 것은 R-12 하나뿐이며, 그것은 서버가 만들어내는 상황에 대한 **반응**이다.
서버가 종료 축제 삭제를 구현하기 전에는 그 상황 자체가 발생하지 않으므로, 대응을 만들어도 검증할 대상이 없다.

**다만 "어떤 오류가 어디로 오는지"는 이미 확정되어 있다**(§1 참조). 기존 코드에 구현된 동작이므로 서버 작업을
기다려 확인할 사항이 아니며, §4의 설계는 지금 확정 가능하다. 서버 작업 후 재검토할 것은 설계가 아니라
**삭제가 실제로 일어나는 빈도와 규모**다(§6).

운영 환경에 배포되지 않은 상태이므로 하위 호환을 지킬 필요가 없다. 필요하면 과감하게 바꾼다.

## 1. 무엇이 바뀌는가

> **v1.1에서 개정.** 1.0은 "스키마는 바뀌지 않는다 · codegen 재생성 불필요"라고 적었다.
> 서버 PR #37이 머지되면서 **절반은 틀린 말이 됐다.** 아래 §1.0을 먼저 읽는다.

### 1.0 식별자가 바뀐다 (v1.1 신설 · R-13)

**`Spot.id`가 담는 값의 의미가 바뀌었다.** 타입 표기는 `ID!` 그대로다.

| 대상 | 이전 | 이후 |
|---|---|---|
| `Spot.id` | TourAPI contentId (언어별로 다름) | 서버가 부여한 `spot.id` (여전히 언어별) |
| `SpotDetail.id` | 동일 | 동일 |
| `ReactToSpotInput.spotId` | contentId | `spot.id` |
| `verificationId` (auth) | `ID!` | `String!` — 타입 표기 정정, 값은 그대로 UUID |

이 레포가 해야 할 일은 네 가지다.

1. **저장된 옛 id는 전부 무효다.** 스와이프 세션 캐시·즐겨찾기 등에 `spotId`를 들고 있다면 비우고
   목록을 다시 받는다. 옛 contentId를 그대로 보내면 `SPOT_NOT_FOUND`가 온다.
2. **언어 전환 시 반드시 목록을 재조회한다**(R-14). 서버가 요청 언어와 spot의 언어를 대조해 거부하므로,
   이전 언어의 id로 `spotDetail`을 호출하면 **최상위 `errors[]`** 로, `reactToSpot`은 **`userErrors[]`** 로
   `SPOT_NOT_FOUND`가 온다. 표면화 위치는 §4.2·§4.3의 기존 처리와 같다.
3. **codegen 재생성은 id 3건 때문에는 필요 없다.** `ID!` shape이 그대로이기 때문이다.
   서버의 `typeMapping = "ID" to "kotlin.Long"`은 **Kotlin 생성 타입에만 적용되며 SDL에 나타나지 않는다** —
   Dart 측에 도달하지 않는다. **다만 `verificationId`는 실제 SDL 변경이므로**, auth 흐름에서 이 필드를
   쓰고 있다면 그것 때문에 재생성이 필요하다.
4. **숫자가 아닌 id는 "없는 id"와 동일하게 `SPOT_NOT_FOUND`로 처리된다**(AC-49). 신규 오류 코드가 아니므로
   분기를 새로 만들지 않는다.

**§1.1 이하의 서술은 축제 삭제(R-8)에 관한 것이며 v1.0 그대로 유효하다.**

### 1.1 결과가 바뀐다 (v1.0)

**축제 삭제에 관한 한 스키마는 바뀌지 않는다.** 이 절의 세 오퍼레이션은 새로 쓸 쿼리가 없다.

바뀌는 것은 **기존 오퍼레이션의 결과**다.

| 오퍼레이션 | 이후 동작 | 표면화 위치 |
|---|---|---|
| `Query.spots(category: FESTIVAL_EVENT)` | 종료된 축제가 결과에서 사라진다. 목록이 시간에 따라 줄어든다 | — |
| `Query.spotDetail(id:)` | 종료된 축제의 `id`가 `SPOT_NOT_FOUND`를 발생시킨다 | **최상위 `errors[]`** |
| `Mutation.reactToSpot` | 종료되어 삭제된 축제에는 `success: false` | **payload의 `userErrors[]`** |

**두 오퍼레이션의 표면화 위치가 다르다. 이것이 이 작업의 핵심이다.**

- `spotDetail(id: ID!): SpotDetail!` 는 **non-null 반환**이다. 해소 실패는 null이 아니라 최상위 GraphQL
  오류로 온다. 따라서 "null이면 없는 것" 식의 처리는 성립하지 않는다.
- `reactToSpot(input:): ReactToSpotPayload!` 는 `success: Boolean!`과 `userErrors: [UserError!]!`를 갖는다.
  실패해도 **전송 자체는 성공**하며 오류는 payload 안에 있다.

**이것은 이 스펙이 정하는 것이 아니라 이미 구현된 기존 동작이다**(SPEC-0005 R15 규약,
`ReactToSpotResolver`·`TourismGraphqlErrorSupport`). POL-016의 확정 하위 규약과도 일치한다 — 인증 실패만
최상위 `errors[]`이고 도메인 규칙 위반은 `userErrors[]`이며, `SPOT_NOT_FOUND`는 후자다.
**서버 작업을 기다려 확인할 사항이 아니다.**

`SPOT_NOT_FOUND`는 **신규 코드가 아니라 기존 코드**이며 발생 빈도만 올라간다. 즉 이 작업은 새 오류를
처리하는 것이 아니라, **이미 처리하고 있어야 했던 오류가 실제로 발생하기 시작하는 것**에 대비하는 일이다.

## 2. 영향 범위

축제 카테고리는 죽은 코드가 아니다. 아래가 실제로 연결되어 있다.

- `lib/domain/spot/component/spot_display.dart` — `discoverCategoryFestivalEvent` l10n 라벨,
  Discover 화면의 선택 가능한 필터 칩
- `lib/domain/spot/repository/spot_repository_impl.dart` — `Enum$SpotCategory.FESTIVAL_EVENT` ↔
  도메인 `SpotCategory.festivalEvent` 양방향 매핑
- `lib/domain/spot/view/discover_swipe_view.dart` — 스와이프 세션

따라서 대응 지점은 **Discover 스와이프 흐름**과 **상세 조회**, **반응 전송** 세 곳이다.

`lib/domain/event/`(홈 화면의 mock `TourEvent`)는 **이 작업과 무관하다.** 서버 계약과 연결되어 있지 않은
클라이언트 전용 mock이며, 이번 스펙은 그것을 건드리지 않는다. 이름이 비슷하다는 이유로 함께 고치지 않는다.

## 3. 책임 분담

CLAUDE.md의 분담표를 따른다. 이 작업에서 갈리는 지점만 적는다.

| 관심사 | 소유 |
|---|---|
| 어떤 축제가 유효한가 | **서버.** 클라이언트는 종료일을 받지 못하며 판정하지 않는다 |
| 종료된 축제를 목록에서 빼는 것 | **서버.** 클라이언트는 목록을 그대로 보여준다 |
| 사라진 항목을 만났을 때의 화면 처리 | **클라이언트** (R-12) |
| 낙관적 갱신과 롤백 | **클라이언트** |
| 오류를 사용자에게 어떻게 보일지 | **클라이언트** |

**클라이언트는 축제 종료 여부를 스스로 판정하지 않는다.** 종료일 필드가 계약에 없고(비범위), 있더라도
판정을 두 곳에 두면 서버와 어긋난다. 목록에 없으면 없는 것이다.

## 4. 대응 설계

### 4.1 목록이 줄어드는 것은 정상 상태다 (AC-42)

축제 카테고리로 필터한 목록을 갱신했을 때 이전보다 항목이 적게 오는 것은 **오류가 아니다.**

notifier가 "이전보다 적음"을 실패 신호로 해석하는 로직이 있다면 제거한다. 빈 목록도 오류 상태가 아니라
**정상적인 빈 상태**로 표시한다 — 진행 중인 축제가 하나도 없는 시기가 실제로 존재한다.

### 4.2 스와이프 세션 중 카드가 사라지는 경우 (AC-43)

가장 현실적인 경로다. 목록을 받아 카드를 쌓아둔 뒤, 사용자가 스와이프하는 도중에 배치가 돌아 그 축제가
삭제될 수 있다.

- 상세 조회가 **최상위 오류**로 `SPOT_NOT_FOUND`를 돌려주면 **그 카드를 건너뛰고 세션을 계속한다.**
  반환 타입이 non-null이므로 "결과가 null인 경우"로는 잡히지 않는다.
- 세션 전체를 실패로 만들거나 사용자를 이전 화면으로 되돌리지 않는다.
- 건너뛴 사실을 오류 배너로 알리지 않는다. 사용자가 한 행동의 결과가 아니기 때문이다.

건너뛴 카드는 현재 세션의 카드 목록에서 제거해 다시 나타나지 않게 한다.

### 4.3 삭제된 축제에 대한 반응 (AC-44)

사용자가 좋아요/싫어요를 보낸 대상이 이미 삭제된 경우다. 낙관적 갱신이 먼저 적용된 뒤 실패가 돌아온다.

응답은 `success: false`이고 `userErrors`에 `SPOT_NOT_FOUND`가 담긴다. **최상위 `errors[]`가 아니므로
전송 오류 처리 경로로는 잡히지 않는다** — payload를 직접 봐야 한다.

- 낙관적 갱신을 롤백하되, **치명적 오류로 표시하지 않는다.**
- 해당 항목을 목록에서 제거한다 — 이미 존재하지 않는 대상이므로 되돌려 놓으면 다음 조회에서 또 실패한다.
- 재시도 큐에 넣지 않는다. 재시도해도 결과가 같다.

인증 실패와 구분해야 한다. 인증 실패는 POL-016의 확정 하위 규약에 따라 최상위 `errors[]`로 오며 세션 전체
처리 대상이다. 여기서 다루는 것은 그것이 아니다.

### 4.4 캐시

`spotId`를 오래 들고 있는 경로가 있다면(딥링크, 저장된 목록) 그 값이 언제든 해석 불가가 될 수 있다는 전제로
다룬다. 캐시 무효화 전략을 새로 만들지는 않는다 — 조회 실패 시 §4.2와 같은 처리로 충분하다.

> **v1.1 — 이번 한 번은 명시적 무효화가 필요하다.** 위 문단은 정상 운영 중의 이야기다. 식별자 체계가
> 바뀌었으므로(§1.0) **저장된 옛 id는 전부 무효**이며, 이것은 "언젠가 해석 불가가 될 수 있다"가 아니라
> "지금 전부 해석 불가다"에 해당한다. 배포 전이라 마이그레이션 경로는 필요 없고, 들고 있는 값을 비우고
> 다시 받으면 된다.

### 4.5 언어 전환 (v1.1 신설 · R-14)

**언어를 전환하면 목록을 반드시 다시 받는다.** 이전 언어의 id를 그대로 들고 상세를 요청하면 서버가 거부한다.

- 이전에는 언어가 다르면 contentId도 달라 자연히 실패했으므로 이 규율이 암묵적으로 지켜졌다.
- 이제 `spot.id`는 타 언어에서도 **형식상 유효한 값**이라, 서버가 명시적으로 대조해 거부하지 않으면
  조용히 다른 언어의 콘텐츠가 나갔을 것이다. 서버가 거부하는 쪽을 택했다.
- 클라이언트 입장에서 이것은 **새 오류 처리가 아니라 재조회 규율**이다. 거부가 발생했다면 이미
  재조회를 빠뜨린 것이다. 거부 자체의 처리는 §4.2·§4.3과 같다.

언어 전환 시 스와이프 세션도 함께 초기화한다 — 쌓아둔 카드의 id가 전부 이전 언어의 것이기 때문이다.

## 5. 테스트가 붙는 단위

스펙의 인수 기준 중 클라이언트 소관은 **AC-42 ~ AC-44** 세 건이다.
**provider/notifier와 도메인 모델 계층만 테스트한다** — 위젯 테스트와 통합 테스트는 범위 밖이다.

| 단위 | 담당 기준 |
|---|---|
| 축제 목록 notifier (repository 스텁) | AC-42 |
| 스와이프 세션 notifier (repository 스텁) | AC-43 |
| 반응 notifier (repository 스텁) | AC-44 |

repository는 스텁으로 대체하고 `graphql_flutter` 전송이나 실제 서버를 세우지 않는다.
`SPOT_NOT_FOUND`는 스텁이 반환하는 도메인 오류로 표현한다 — 생성 타입은 repository 밖으로 나오지 않는다
(POL-020).

### 인프라로만 관찰 가능해 테스트하지 않는 것

- 실제 GraphQL 전송에서 오류 코드가 도메인 오류로 매핑되는지
- 화면에 배너가 뜨지 않는다는 시각적 사실
- 딥링크로 진입했을 때의 실제 라우팅

## 6. 남는 위험

1. **삭제 시점의 관측.** 오류 표면화 위치는 §1에서 확정했으므로 열린 질문이 아니다. 다만 종료 축제 삭제가
   실제로 얼마나 자주, 몇 건씩 일어나는지는 서버 첫 실행 전까지 알 수 없다. 삭제가 대량으로 몰리면 §4.2의
   "카드 건너뛰기"가 한 세션에서 여러 번 연속 발생할 수 있다 — 그 경우의 체감을 서버 작업 후 확인한다.
2. **빈 목록의 사용자 경험.** 진행 중인 축제가 0건인 시기에 Discover의 축제 필터가 빈 화면이 된다.
   AC-42는 "오류 상태가 아닐 것"만 요구하므로 빈 화면 자체는 기준을 만족한다. 빈 상태에 안내 문구를 넣을지는
   기획 판단이며 **이번 범위에서 해결하지 않는다** — 필요하면 별도 스펙으로 다룬다.
