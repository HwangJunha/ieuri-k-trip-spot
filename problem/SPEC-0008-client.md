# SPEC-0008 — 클라이언트 설계

요구사항·수용 기준·컨트랙트는 스펙이 authority다. 이 문서는 이 저장소의 설계 결정만 담는다.

담당 요구사항: **R-7 ~ R-14, R-18.**
관련 이슈: #30 (이 스펙) · #28 (SPEC-0006 R9·R10 이월, **#30이 흡수**).

---

## 1. 선행 조건

R-7 ~ R-9, R-11은 서버의 nullability 완화(HwangJunha/ieuri#39 §7 작업 1번)에 의존한다. 완화 전에
구현하면 codegen이 여전히 non-null 타입을 만들어 **부분 실패 매핑이 절대 실행되지 않는 죽은
코드**가 된다. #28이 이월된 사유가 정확히 이것이다.

- [ ] 서버 `SpotDetail.gallery` → `[SpotImage!]`, `infoItems` → `[SpotInfoItem!]`
- [ ] 서버 재기동 후 introspection 반영 확인
- [ ] codegen 재생성

**R-12 ~ R-14(하단 네비게이션)는 서버 의존이 없다.** 선행 조건과 무관하게 먼저 진행할 수 있으며,
§7의 작업 순서가 이를 반영한다.

---

## 2. 세 가지 상태를 하나로 접는다 (R-7 ~ R-9, R-11)

화면이 구분해야 하는 것은 **두 가지뿐**이다.

| 응답 | 상태 |
|---|---|
| `data.spotDetail`이 null | 전체 실패 — 오류 화면 (AC-24) |
| `data.spotDetail`이 채워짐 | 정상 — 본문 렌더 (AC-23) |

두 번째 경우 안에서 섹션별로 값이 없는 사유는 셋이다 — **조회 실패**(서버가 필드를 null로 내림),
**업스트림 부재**(상세 자체가 없음), **정상적으로 없음**(빈 배열). 화면 결과가 셋 다 "섹션을
숨긴다"로 같으므로 **도메인 모델에서 하나로 접는다.**

`gallery`의 null과 빈 배열을 구분하는 분기를 만들지 않는다(AC-28). 구분이 필요해 보이면 그것은
스펙과의 불일치이므로 `[AMEND]`로 보고한다.

이것은 SPEC-0006이 이미 내린 결정이며 이 스펙이 부재 케이스까지 같은 규칙으로 확장한 것이다.

### 2.1 판별은 repository 안에서 (POL-020)

생성 타입의 nullable 변화를 매핑 계층이 흡수하고 도메인 모델 밖으로 내보내지 않는다. 도메인
모델은 "갤러리에 보여줄 이미지 목록"만 알면 되고, 그것이 실패였는지 부재였는지 알 필요가 없다.

`errors[]`가 비어있지 않다는 사실만으로 전체 실패를 단정하지 않는다. **`path`로 범위를
판별한다**(AC-25) — `["spotDetail","gallery"]`는 부분 실패이지 전체 실패가 아니다.

### 2.2 표현

| 상태 | 화면 |
|---|---|
| `gallery`가 null (실패) | 목록 카드가 이미 보유한 썸네일 1장 (AC-26) |
| `gallery`가 빈 배열 (없음) | 동일 — 썸네일 1장 (AC-27) |
| `infoItems`가 null 또는 빈 배열 | 이용안내 섹션 숨김, 오류 문구 없음 (AC-29) |
| `intro`가 null | 운영정보 섹션 숨김 (AC-30) |
| 전부 null | 본문 + 썸네일 1장, 정상 상태 유지 (AC-31) |
| `overview`까지 null | **축약 화면** — §3 (AC-34) |

## 3. 축약 화면 (R-11) — 이 스펙의 새 영역

SPEC-0006은 하위 섹션의 *실패*만 다뤘다. 이 스펙은 **본문까지 없는 경우**를 더한다.

`overview`가 null이고 갤러리·운영정보·이용안내가 전부 비어있으면, 남는 것은 목록이 이미 준
값들뿐이다 — 제목·썸네일·주소·카테고리. 이 상태를 **오류가 아닌 정상 상태**로 렌더한다(AC-35).

### 3.1 왜 오류 화면이 아닌가

사용자는 스와이프 카드에서 그 spot을 이미 보았다. 카드에는 사진과 제목이 떠 있었다. 탭해서
들어왔더니 "불러올 수 없습니다"가 나오면, 방금 본 것과 모순된다. 실제로는 실패한 것이 없다 —
보여줄 추가 정보가 없을 뿐이다.

축약 화면은 카드에서 본 것을 그대로 크게 보여주고, 좋아요·싫어요를 할 수 있게 한다. 그것이
이 화면이 원래 하던 일의 최소 형태다.

### 3.2 반응은 그대로 동작한다

축약 상태에서도 `reactToSpot`은 정상 호출되며, 반응 후 리스트 복귀와 다음 카드 전환은 기존
동작과 동일하다(AC-36 · AC-37). SPEC-0006의 R11·R12로 이미 구현된 경로를 그대로 탄다 —
새로 만들지 않는다.

`likeCount`는 non-null이 유지되므로 축약 화면에서도 표시할 수 있다.

### 3.3 목록에서 거르지 않는다 (R-10)

상세가 없다는 이유로 카드를 목록에서 제외하지 않는다(AC-32). 애초에 **목록 응답은 상세 보유
여부를 알려주지 않으며**(`spots`는 무변경), 알 필요도 없다. 거르는 분기 자체가 존재하지 않아야
한다(AC-33).

## 4. 하단 네비게이션 (R-12 ~ R-14)

현재 5탭 구조 — Home / Map / Discover / Events / Chat. `common/widget/floating_bottom_nav_scaffold.dart`가
셸 크롬을 담당하며, Discover가 가운데(index 2) 강조 위치다.

| 탭 | 현재 | 변경 후 |
|---|---|---|
| 0 · 1 · 2 | Home · Map · Discover | 무변경 |
| 3 | Events | **좋아요 목록** (R-12) |
| 4 | Chat | **커뮤니티** (R-13) |

탭 수는 5개로 유지되고 Discover의 가운데 강조도 유지된다(AC-40). 셸 구조(`StatefulShellRoute.indexedStack`)
자체는 바뀌지 않으며, 브랜치의 목적지와 라벨만 교체된다.

### 4.1 커뮤니티는 껍데기만

**라벨·아이콘·라우트 이름만 바꾸고 화면 내용은 손대지 않는다**(AC-42). 게시글·댓글·신고 등
커뮤니티 기능은 이 스펙의 비스코프이며 별도 스펙에서 `domain: community`로 열린다.

이 스펙은 GraphQL에 `Community` 타입을 만들지 않는다.

### 4.2 행사 탭은 내리되 코드는 남긴다

행사 화면은 도달 경로가 사라진다(AC-39). 다만 `lib/domain/event/`의 목업 코드
(`TourEvent`·`EventCategory`)를 **삭제하지 않는다** — 비스코프로 명시했다.

행사는 기능이 없어지는 것이 아니다. Discover의 카테고리 필터 `FESTIVAL_EVENT`로 여전히 찾을 수
있으며(`discoverCategoryFestivalEvent` 라벨, `spot_repository_impl.dart`의 enum 매핑), 그것이
탭을 내리는 근거다.

> SPEC-0007이 `Event`·`TourEvent`를 서버측 예약 금지 이름으로 기록해 두었다. 목업 코드가 남는
> 동안 그 제약은 유효하다.

### 4.3 i18n (R-14)

신규·변경 라벨은 EN/KO/JA/ZH 4개 언어 전부에 값이 있어야 한다(AC-43 · POL-022). 현재
`navEvents`·`navChat` 키가 네 `.arb` 파일에 모두 있으므로, 대체 키도 동일하게 넷을 채운다.

사용되지 않게 된 키는 남기지 않는다(AC-44).

## 5. 좋아요 목록 (R-18)

### 5.1 상세 화면을 새로 만들지 않는다

목록 항목을 선택하면 **기존 `/spot/:id` 경로**로 진입한다(AC-54). `SpotDetailView.routeName`이
이미 있고 `LikedSpot.id`가 그대로 `spotDetail(id:)`에 들어가는 같은 식별자다.

선택한 spot의 상세가 부재하면 §3의 축약 화면이 뜬다(AC-55). 좋아요 목록에서 들어오든 스와이프에서
들어오든 같은 화면·같은 규칙이다.

### 5.2 목록 자체

`likedSpots` 커서 페이징을 따른다. 생성 타입(`LikedSpot`·`LikedSpotConnection`·`LikedSpotEdge`)은
repository 밖으로 누출하지 않으며 도메인 모델로 매핑한다(POL-020).

`likedAt`은 엣지에 있다. 도메인 모델이 이 값을 보유할지는 화면이 좋아요 시각을 표시하는지에
달렸다 — 요구사항에 표시 요건이 없으므로 **표시하지 않는 것을 기본으로 하고**, 정렬은 서버가
보장하므로 클라이언트가 재정렬하지 않는다.

미인증 시 `UNAUTHENTICATED`는 SPEC-0005의 세션 갱신 경로를 탄다. 이 스펙이 별도 처리를
추가하지 않는다.

### 5.3 이 스펙이 다루지 않는 것

정렬 옵션·검색·좋아요 해제 UI는 비스코프다. 목록 표시와 상세 진입만 구현한다. 좋아요 해제는
상세 화면의 기존 반응 경로로 가능하다.

## 6. 테스트가 실릴 단위

provider/notifier 및 도메인 모델 계층 단위 테스트. 위젯·통합 테스트는 범위 밖이다.

| 단위 | 검증 |
|---|---|
| 상세 repository 매핑 | AC-23 ~ AC-31 (nullable 흡수, null/빈 배열 접기, `path` 기반 범위 판별) |
| 상세 notifier/provider | AC-34 · AC-35 (축약 상태 계산), AC-36 · AC-37 (축약 상태의 반응) |
| 스와이프 목록 notifier | AC-32 · AC-33 (상세 보유 여부로 거르지 않음) |
| 좋아요 목록 notifier | 커서 페이징 상태 전이, 미인증 처리 |
| 라우팅·라벨 | AC-38 ~ AC-42 (탭 목적지·라벨), AC-43 · AC-44 (i18n 키 4개 언어) |

AC-43·AC-44는 `.arb` 키 존재 검사로 충족한다 — 위젯을 세울 필요가 없다.

**AC-18(서버측 `errors[].path` 형태)은 이 저장소에서도 단위 테스트로 검증되지 않는다**
(`[TBD-3]`). §8을 볼 것.

테스트 인프라·픽스처·목 서버 구성은 이 문서가 규정하지 않는다.

---

## 7. 작업 순서

1. **하단 네비게이션 재구성 (R-12 ~ R-14)** — 서버 의존이 없다. 좋아요 목록 화면은 이 단계에서
   빈 껍데기로 두고 3번에서 채운다.
2. **부분 실패·축약 표현 (R-7 ~ R-11)** — §1의 선행 조건 충족 후. codegen 재생성이 먼저다.
3. **좋아요 목록 (R-18)** — 서버 `likedSpots` 배포 후.

1번을 먼저 두는 이유는 서버를 기다리지 않기 때문이다. 2·3번은 서버 작업 순서(#39 §7)에 맞춰
따라간다.

## 8. 가장 얇은 지점 — 반드시 육안 확인할 것

`errors[].path`의 **실제 형태는 양쪽 저장소 어느 단위 테스트로도 검증되지 않는다.** DGS가 중첩
필드 실패에 `["spotDetail","gallery"]` 형태를 실제로 내려주는지는 GraphQL 전송 계층을 세워야
관찰되며, 이는 이 스펙의 테스트 범위 밖이다.

§2.1의 `path` 기반 판별 전체가 이 가정 위에 서 있다. 가정이 틀리면 부분 실패가 전체 실패로
오판되어 R-7이 무너진다.

**구현 시 실제 응답을 한 번 육안으로 확인하고, 가정한 형태와 다르면 `[AMEND]`로 보고할 것.**
이는 SPEC-0006에서 이월된 미결 사항이며(`[TBD-3]`), #28이 같은 문구로 남겨 둔 항목이다.
