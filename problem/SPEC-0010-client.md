# SPEC-0010 클라이언트 설계 — 커뮤니티 Spot Talk

요구사항과 인수 조건은 스펙이 정본이다. 이 문서는 요구사항을 다시 쓰지 않고 번호로 인용한다.

## 1. 디렉터리 배치

feature-first 구조에 `lib/domain/community/` 를 새로 연다.

```
lib/domain/community/
  component/     피드 카드, spot 칩, 주제 태그 칩, 탐색 타일, 댓글 항목, 신고 시트
  model/         Post, Comment, PostAuthor, PostSpot, PostTopic, DiscoveryTile, ReportReason
  provider/      피드·작성·댓글·차단 notifier
  repository/    GraphQL 호출과 도메인 모델 매핑
  view/          커뮤니티 탭, 글 작성, 글 상세, 차단 목록
```

SPEC-0008 이 만들어 둔 `lib/domain/spot/view/community_screen.dart` 스텁을 이곳으로 옮긴다.
현재 `Center(child: Text(l10n.comingSoon))` 하나뿐인 화면이고, 라우트 `/community` 와 하단 탭
라벨 `navCommunity` 는 이미 자리를 잡고 있으므로 **탭을 새로 만들지 않는다.** 스텁의 내용만
바꾼다.

spot 상세 안의 글 피드(R6)는 `lib/domain/spot/` 쪽 상세 화면에 커뮤니티 컴포넌트를 끼워 넣는
형태가 된다. 이때 spot 화면이 커뮤니티의 provider 를 직접 참조하게 되는데, 이는 의도된 결합이다 —
"커뮤니티는 spot 으로 되돌리는 구조"라는 전제가 화면 구조에도 그대로 나타난다.

## 2. 생성 타입 격리 (POL-020)

`graphql_codegen` 이 만든 타입은 `repository/` 밖으로 나가지 않는다. repository 가 도메인 모델로
매핑하고, provider 와 view 는 도메인 모델만 본다.

매핑 지점은 다음과 같다.

| 생성 타입 | 도메인 모델 |
|---|---|
| `Query$SpotPosts$spotPosts$edges$node` | `Post` |
| `...$comments$edges$node` | `Comment` |
| `...$author` | `PostAuthor` |
| `...$spot` | `PostSpot` |
| `Enum$PostTopic` | `PostTopic` (클라이언트 enum) |
| `Query$DiscoveryTiles$discoveryTiles` | `DiscoveryTile` |

`PostTopic` 을 클라이언트 enum 으로 다시 정의하는 이유는 표시 문자열 매핑이 클라이언트 몫이기
때문이다(§4). 생성 enum 을 그대로 쓰면 매핑 코드가 repository 밖으로 새어 나간다.

## 3. 화면과 상태 전이

### 커뮤니티 탭 (R7, R8, R10, R11)

위에서부터 탐색 타일 그리드, 주제 태그 칩 한 줄, 지역 피드다.

필터 UI 는 태그 칩 한 줄이 전부다. 정렬 선택도, 추가 필터도 만들지 않는다 — 초기 버전의 원칙은
빼기다. 상태는 "선택된 topic (없을 수 있음)" 하나뿐이며, 타일에서 진입해도 같은 상태에 반영되어
상단 칩이 그 태그로 선택된 것처럼 보인다 (R11-3).

좌표는 이미 앱이 쓰고 있는 위치 흐름을 그대로 쓴다. 이 스펙이 새로 수집하는 항목은 없다.
위치 권한이 없거나 좌표를 얻지 못하면 지역 피드를 비우고 그 사유를 보여준다 — 빈 피드와
권한 없음은 다른 상태다.

### spot 상세 안의 피드 (R6)

해당 spot 의 글만 최신순으로. 여기에는 태그 필터를 두지 않는다. 한 spot 의 글은 애초에 많지 않고,
필터가 하나 더 늘면 "빼기" 원칙에 어긋난다.

### 글 작성 (R1~R4)

두 경로가 있고, 차이는 spot 을 어떻게 정하느냐뿐이다.

- **spot 상세에서 진입** — spot 이 이미 정해진 상태로 컴포저가 열린다. 유저가 할 일은 본문과
  태그뿐이다.
- **커뮤니티 탭에서 진입** — spot 선택 단계가 하나 더 있다. 최근 본 spot 과 좋아요한 spot 이
  먼저 뜬다. 처음부터 검색을 요구하지 않는다.

등록 버튼은 본문·spot·태그가 모두 갖춰지기 전까지 비활성이다 (R1-1). 서버 검증을 기다렸다가
에러를 보여주는 방식이 아니다 — 화면이 애초에 잘못된 상태를 만들지 못하게 한다.

본문 길이는 잔여 글자 수로 보여준다 (R4). 500자를 넘으면 입력이 막히는 것이 아니라 등록이
막히고 초과분이 드러나야 한다. 입력을 자르면 붙여넣기한 유저가 무엇이 사라졌는지 모른다.

### 사진 첨부 (R3)

업로드는 세 단계이고, 유저에게는 한 단계로 보여야 한다.

1. 사진을 고르면 즉시 로컬 썸네일을 보여주고 업로드를 시작한다.
2. 장당 `createPostImageUploadUrl` 로 URL 을 받아 R2 에 직접 PUT 한다. GraphQL 을 거치지 않는
   유일한 통신이다.
3. 업로드가 끝난 키만 모아 `createPost` 에 넘긴다.

업로드 중에도 본문을 계속 쓸 수 있어야 한다. 업로드가 등록을 막지 않되, 등록 시점에 아직
끝나지 않은 업로드가 있으면 기다린다. 실패한 사진은 개별로 재시도하거나 뺄 수 있다 —
사진 한 장 때문에 글 전체를 다시 쓰게 만들지 않는다.

presigned URL 은 5분 만료다 (R18). 만료된 상태로 PUT 하면 실패하므로, 실패 시 URL 을 다시
발급받아 재시도한다. 이는 재시도·오프라인 큐잉이 클라이언트 책임이라는 책임 분리표에 따른다.

지원 형식은 JPEG·PNG·WebP 다 (R25). 사진 선택 단계에서 걸러 `UNSUPPORTED_CONTENT_TYPE` 이
돌아오지 않게 한다. 서버 검증은 최종 방어선이지 1차 관문이 아니다 — 고르고 나서 거부당하는
것보다 애초에 고를 수 없는 편이 낫다. HEIC 로 촬영하는 iOS 기기가 흔하므로 변환이 필요하다.

### 댓글 (R13, R23)

1단계만. 대댓글 입력 수단을 만들지 않는다. 최신순.

댓글 수는 서버가 준 `commentCount` 를 그대로 쓴다. 숨겨진 댓글이 제외된 값이므로 (R23) 목록
길이와 맞아떨어진다. 클라이언트가 목록을 세어 따로 계산하지 않는다 — 페이지네이션 중에는 받아온
만큼만 세게 되어 숫자가 틀린다.

### 신고·차단 (R15, R16)

글·댓글의 오버플로 메뉴에서 신고와 차단에 닿는다. 신고 사유는 고정 4종이고 `기타` 를 고르면
상세 입력이 필수가 된다 (R16-3).

신고 후에는 접수되었다는 사실만 알린다. 처리 결과나 예상 시점을 약속하지 않는다 — 사용자 대상
신고는 기록만 되고 자동 조치가 없으며 (R22), 글·댓글도 5명이 모여야 숨겨진다. 신고 직후 무언가
일어난 것처럼 보이는 문구를 쓰면 실제 동작과 어긋난다.

차단은 확인 단계를 둔다 — 양방향이라 되돌리기 전까지 서로 안 보이게 되며, 유저가 그 결과를
알고 눌러야 한다. 차단 목록 화면에서 해제할 수 있다.

차단 직후 피드는 다시 불러온다. 서버가 필터링하므로 로컬에서 지우는 것이 아니라 재조회가
정답이다.

### 미인증 상태 (R17)

피드는 로그인 없이 보인다. 쓰기·좋아요·신고·차단을 시도하는 순간 로그인으로 유도한다.
버튼을 감추지 않고 눌렀을 때 유도하는 쪽을 택한다 — 감추면 기능이 없는 것처럼 보인다.

`likedByViewer` 는 미인증일 때 false 로 오므로 (R17-5) 별도 분기가 필요 없다.

## 4. 다국어 (POL-022, POL-023)

주제 태그의 표시 문자열은 **클라이언트가 매핑한다.** enum 값을 키로 EN/KO/JA/ZH 문자열을
l10n 에 둔다. `SpotCategory` 가 이미 같은 방식이므로 선례를 따르는 것이고, 서버에 표시 필드를
두지 않는 이유이기도 하다.

탐색 타일 제목은 반대다. 서버가 이미 언어에 맞는 문자열을 내려주므로 클라이언트는 그대로
표시한다. 매핑하려 들면 안 된다 — 운영자가 시즌마다 바꾸는 문구라 클라이언트가 알 수 없다.

UI 는 영어 우선이며, 이는 외국인 관광객이 1차 사용자이기 때문이다.

## 5. 낙관적 업데이트 (R12)

좋아요는 낙관적으로 반영하고 실패 시 되돌린다. 좋아요 수와 눌림 상태를 즉시 바꾸고,
뮤테이션이 실패하면 이전 값으로 롤백한다.

댓글 작성과 글 등록은 낙관적으로 처리하지 않는다. 서버가 거부할 사유(길이, 미업로드 키)가
실재하고, 등록된 것처럼 보였다가 사라지는 편이 잠깐 기다리는 것보다 나쁘다.

## 6. 비범위

리포스트, 팔로우, 알림, DM, 프로필 꾸미기, 글 수정, 대댓글, 게시글 검색. 초기 버전에서
의도적으로 뺀 것이며, 화면에 흔적을 남기지 않는다 — 비활성 버튼이나 "준비 중" 표시도 두지 않는다.

프로필 화면이 없으므로 작성자를 눌러도 이동할 곳이 없다. 닉네임과 프로필 이미지는 표시만 한다.

## 7. 테스트

provider/notifier 와 도메인 모델 로직의 단위 테스트만. 위젯·통합 테스트는 요구하지 않는다.

| 단위 | 검증 대상 |
|---|---|
| 글 작성 notifier | R1-1 등록 가능 여부 판정(본문·spot·태그 조합), R4 길이 경계와 잔여 글자 수 |
| 사진 업로드 notifier | R3 5장 상한, 개별 실패·재시도, 업로드 미완 상태에서의 등록 대기, R25 미지원 형식의 선택 단계 차단 |
| 피드 notifier | R8 태그 필터 상태 전이, R11 타일 진입 시 필터 반영, 커서 페이지네이션 상태 |
| 좋아요 notifier | R12 낙관적 반영과 실패 롤백 |
| 차단 notifier | R15 차단 후 피드 재조회 요청 |
| 신고 notifier | R16 기타 사유 선택 시 상세 필수 판정 |
| `PostTopic` 매핑 | 4개 언어 모두 문자열이 존재하고 누락된 값이 없음 |
| repository 매핑 | 생성 타입 → 도메인 모델 변환. 생성 타입이 밖으로 새지 않음 |

미인증 상태의 로그인 유도(R17)는 SPEC-0005 의 세션 게이트가 이미 담당하는 경로다. 이 스펙에서
다시 테스트하지 않고 재사용한다.
