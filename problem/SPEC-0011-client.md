# SPEC-0011 클라이언트 설계 — 설정 및 마이페이지

요구사항과 인수 기준은 스펙이 권위를 가진다. 이 문서는 클라이언트가 화면과 상태를 어떻게 구성하는지만 다룬다.

## 1. 기능 배치

`lib/domain/settings/`를 신설한다. 프로필·약관·앱 설정이 한 화면 계층에 모이고, 기존 `auth` 기능은 로그인·가입 흐름을 계속 갖는다.

| 위치 | 담당 |
|---|---|
| `domain/settings/` | 설정 홈, 마이페이지, 프로필 수정, 약관 관리, 앱 설정 (R1·R3~R14·R16) |
| `domain/auth/` | 로그아웃 로직 이동 (R15), 가입 폼 보정 (R18·R19) |
| `domain/community/` | 차단 목록 진입점 제거 (R2) |
| `common/storage/` | 반경 설정 저장 (R13) |

차단 목록 화면(`BlockedUsersScreen`) 자체는 `community`에 그대로 둔다. 옮기는 것은 진입점뿐이며, 화면을 이동시키면 `community` 리포지토리 의존이 `settings`로 끌려 들어온다.

## 2. 진입점과 라우팅 (R1·R2)

하단 탭 5개는 SPEC-0008에서 고정됐다. 설정은 탭이 아니라 **홈 화면 우상단**에서 들어간다. 현재 그 자리에는 `LogoutButton`과 비활성 `favorite_border` 아이콘이 있다. 로그아웃은 설정 안으로 들어가므로(R15) 우상단에서 제거하고, 그 자리를 설정 진입점이 대신한다.

커뮤니티 우상단에서는 차단 목록 아이콘만 제거한다. **숨긴 글 아이콘은 남는다** — 스펙의 결정이다. SPEC-0010 구현이 "둘 다 내가 안 보이게 한 것을 되돌리는 화면이라 같은 자리에 있어야 한다"는 근거로 둘을 묶어 놨으므로, 그 근거가 깨진다는 점을 코드 주석에 남긴다.

라우트는 설정 홈 아래에 중첩한다. 뒤로 가기가 설정 홈을 거쳐 진입 직전 화면으로 돌아가야 한다(R1 세 번째 기준).

```
/settings
/settings/my-posts          내가 쓴 글 (R3)
/settings/profile           프로필 수정 (R4·R5·R6)
/settings/profile/email     이메일 변경 (R7·R8)
/settings/terms             약관 동의 관리 (R9·R10)
/settings/preferences       반경·언어 (R13·R14)
/blocked-users              기존 유지, 설정에서 진입 (R2)
```

## 3. 필수 약관 게이트 (R11·R12)

가장 주의할 부분이다. 게이트는 라우터 리다이렉트로 구현하며 기존 세션 게이트(SPEC-0005)와 **같은 리다이렉트 경로에서 판정**해야 한다. 두 게이트가 각자 리다이렉트하면 서로를 되돌리는 순환이 생긴다.

판정 순서는 인증 → 필수 약관 → 목적지다. 미인증이면 로그인으로, 인증됐지만 미동의 필수 약관이 있으면 동의 안내로 보낸다.

동의 안내 상태에서 허용되는 목적지는 **설정 화면 계열과 동의 화면뿐**이다(R11 네 번째 기준). 홈·탐색·커뮤니티는 전부 막힌다.

동의 상태는 `agreements` 쿼리로 읽고 provider로 캐싱한다. 매 라우팅마다 조회하면 화면 전환이 네트워크에 묶인다. `agreeToRequiredTerms` 성공 시 반환된 상태로 갱신하면 재조회 없이 게이트가 풀린다(R12 첫 기준).

게이트 해제 후에는 **원래 가려던 목적지로 복귀**한다. 진입 시점의 목적지를 보관해야 한다.

## 4. 프로필 수정 (R4~R8)

### 닉네임 (R5)

제출 전 형식만 검사하고, 중복은 서버 판정을 받는다. `NICKNAME_ALREADY_TAKEN`을 입력란 오류로 표시한다. 클라이언트가 미리 중복을 조회하면 조회와 제출 사이에 선점당할 수 있어 어차피 서버 오류를 처리해야 한다.

### 프로필 이미지 (R6)

업로드는 3단계다 — URL 발급 → 스토리지 직접 PUT → 확정. 선언한 `contentType`과 `contentLength`가 실제 PUT 요청과 정확히 일치해야 서명이 유효하다. 파일을 읽어 실제 크기를 구한 뒤 발급을 요청한다.

중간 단계 실패가 남긴 임시 키를 정리한다. 확정 전에 화면을 벗어나면 키가 떠돈다.

제거는 별도 동작이다(`removeProfileImage`). 이미지 교체와 제거를 한 화면에서 구분해 보여준다.

### 이메일 변경 (R7·R8)

두 단계 화면이다 — 새 주소 입력 → 코드 입력. 코드 화면은 기존 `EmailVerificationScreen`과 형태가 같지만 **다른 뮤테이션**(`confirmEmailChange`)을 쓴다. 컴포넌트를 재사용하되 호출부는 분리한다.

검증 전까지 프로필의 이메일은 기존 값이다(R7 첫 기준). 변경 대기 중임을 화면에 드러내지 않으면 사용자가 실패로 오해한다.

재발송 쿨다운 60초는 남은 시간을 카운트다운으로 보여준다. `RESEND_COOLDOWN_ACTIVE`를 받고 나서 알리는 것보다 미리 막는 편이 낫다. 서버 오류는 여전히 처리한다.

`failureReason`별 문구를 구분한다 — `CODE_MISMATCH`는 재입력, `EXPIRED`는 재발송, `MAX_ATTEMPTS_EXCEEDED`는 처음부터. 셋을 같은 문구로 묶으면 사용자가 다음 행동을 모른다.

## 5. 약관 관리 (R9·R10)

한 화면에서 필수와 선택을 함께 보여준다. 필수 항목은 읽기 전용으로 표시하고 토글하지 않는다 — 철회 경로가 없다.

선택 항목(위치·마케팅)만 토글한다. 낙관적 업데이트를 적용하고 실패 시 되돌린다(CLAUDE.md 책임 분리표 — 낙관적 갱신과 롤백은 클라이언트).

`TermsCode`는 식별자이며 화면 문구가 아니다(POL-023). 표시 문자열은 l10n 키로 매핑한다.

## 6. 반경과 언어 (R13·R14)

### 반경 (R13)

서버 상태가 아니다. 기존 `AppPreferences` 로컬 저장을 쓴다. 0~100km 연속 슬라이더이며 기본값 20km다.

0km가 유효값이다(R13 네 번째 기준). 슬라이더 최솟값을 0으로 두되, 0이 "현재 위치만"을 뜻한다는 것을 화면에 드러낸다.

이 값을 실제 조회에 반영하는 것은 이 스펙의 인수 기준에 없다. 저장과 복원까지가 범위이며, 소비처 연결은 값이 있어야 가능하므로 순서상 다음 작업이다.

### 언어 (R14)

이미 동작한다. `LocaleController`가 선택값을 로컬 저장하고 `Accept-Language`로 매 요청 전송한다. **설정 화면에 선택 UI만 붙이면 된다** — 새 상태 관리를 만들지 않는다.

## 7. 로그아웃과 탈퇴 (R15·R16)

로그아웃은 기존 `LogoutButton`의 로직을 그대로 쓰되 위치를 설정으로 옮긴다. 서버 호출이 실패해도 로컬 토큰을 지우고 로그인 화면으로 보낸다(R15 세 번째 기준) — 실패로 사용자를 로그인 상태에 가두면 안 된다.

탈퇴는 확인 단계를 반드시 거친다(R16). 되돌릴 수 없다는 것과 삭제되는 대상(작성한 글·댓글·좋아요)을 명시한다. 취소가 기본 동작이 되도록 배치한다.

탈퇴 성공 후에는 로그아웃과 같은 정리를 한다. 계정이 사라졌으므로 토큰 갱신 시도가 남아 있으면 안 된다.

## 8. 가입 폼 보정 (R18·R19)

기존 `SignUpScreen`·`SnsSignUpScreen`은 이미 구현돼 있고 요구사항과 대체로 일치한다. 이 스펙에서 새로 만들지 않는다.

확인할 것:

- SNS 가입에서 provider 이메일 프리필과 수정 가능 여부 (R18 첫 기준) — 구현돼 있음
- provider가 이메일을 주지 않은 경우의 안내 (R18 두 번째 기준) — `snsEmailPrefillHint`로 구현돼 있음
- 필수 약관 미체크 시 제출 비활성 (R19 첫 기준) — `_agreements.requiredSatisfied`로 구현돼 있음
- 연령 확인 미체크 시 제출 비활성 (R19 두 번째 기준) — **확인 필요.** 현재 제출 게이트는 `requiredSatisfied`만 보고 `ageVerified`는 제출 시점에 값으로만 전달된다. 연령 확인이 게이트에 포함되는지 확인하고, 아니면 보정한다

R20(닉네임 자동 생성)은 서버 동작이며 클라이언트 작업이 없다.

## 9. 단위 테스트 대상

provider/notifier와 도메인 모델 로직만. 위젯·통합 테스트는 범위 밖이다(CLAUDE.md 테스트 범위표).

| 단위 | 검증 |
|---|---|
| 약관 게이트 판정 로직 | 미동의 시 차단, 설정 계열 허용, 동의 후 해제 (R11·R12) |
| 게이트 목적지 보관 | 해제 후 원래 목적지 복귀 (R12) |
| 프로필 수정 notifier | 닉네임 성공·중복·형식 오류 상태 (R5) |
| 프로필 이미지 notifier | 3단계 진행, 중간 실패 시 정리, 제거 (R6) |
| 이메일 변경 notifier | 단계 전환, `failureReason`별 상태, 쿨다운 (R7) |
| 약관 notifier | 낙관적 토글과 실패 롤백 (R10) |
| 내 글 목록 notifier | 첫 페이지·다음 페이지·빈 상태 (R3) |
| 반경 설정 저장·복원 | 기본값, 저장 후 복원, 0 허용 (R13) |
| 언어 선택 | 기기 언어 기본, 선택 저장, 미지원 언어 시 영어 (R14) |
| 로그아웃 | 서버 실패 시에도 로컬 정리 (R15) |
| 탈퇴 notifier | 확인 전 미실행, 성공 후 토큰 정리 (R16) |
| 가입 폼 제출 게이트 | 필수 약관·연령 미충족 시 비활성 (R19) |

화면 전환 자체는 라우터 설정이라 상태 판정 로직을 분리해 테스트한다. 리다이렉트가 실제로 일어나는지는 위젯 테스트 영역이며 범위 밖이다.

## 10. 계약 소비

생성 GraphQL 타입은 repository 레이어를 넘지 않는다. `AgreementStatus`·`PostConnection` 등은 전부 도메인 모델로 매핑한다.

`myPosts`는 `PostConnection`을 반환하므로 커뮤니티의 기존 `Post` 도메인 모델을 재사용한다. 마이페이지용 모델을 따로 만들지 않는다.

## 11. 확인 사항

- 홈 우상단의 비활성 `favorite_border` 아이콘을 설정 진입점으로 교체할지, 별도 아이콘을 추가할지
- 가입 폼의 제출 게이트에 연령 확인이 포함되는지 (R19)
