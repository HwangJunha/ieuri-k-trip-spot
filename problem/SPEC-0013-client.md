# SPEC-0013 클라이언트 설계

요구사항과 수용 기준은 스펙이 소유한다. 이 문서는 클라이언트가 그것을 어떻게 표현하는지만 다루며,
요구사항을 번호로 인용한다.

## 0. 구현 현황 — 전 요구 구현 완료

서버 배포를 사이에 두고 두 단계로 나눠 진행했다. **1차**(서버 미배포 시점)에는 서버에 의존하지
않는 것만 했고 — 별점·혼잡도 제거, 홈 목 데이터 제거, Near you 실데이터 전환, 검색 페이지 골격,
최근 검색어 — 신규 쿼리 4개가 배포된 뒤 **2차**에서 나머지를 채웠다.

나눈 이유는 CLAUDE.md §13이다: 제안(`contract.graphql`)이 아니라 **라이브 스냅샷** 기준으로
오퍼레이션을 쓴다. 착수 시점에는 `searchSpots`·`spotSearchSuggestions`·`ongoingFestivals`·
`popularSpots`가 서버에 하나도 없었으므로, 없는 스키마에 대고 오퍼레이션을 지어내지 않았다.

### 라이브 스키마가 제안과 다른 점

introspection으로 확인한 실제 계약이 초안과 **두 곳 어긋난다**:

- `FestivalConnection`과 `PopularSpotConnection`에 **`totalCount`가 없다**(제안에는 있었다).
  `SpotSearchConnection`에만 있다. 홈 섹션은 건수를 표시하지 않으므로 영향이 없다.
- **`searchSpots`가 오프셋 페이징이다**(`page`/`size` + `items`/`page`/`hasNext`).
  제안과 스펙 §8.1은 커서를 요구했으나 — BM25 점수 동점이 흔해 offset이면 페이지 사이에서
  순서가 흔들린다는 이유였다 — **서버 구현에서 커서 방식이 정확히 동작하지 않아 전환됐다.**
  `SpotSearchEdge`도 함께 사라졌다. `ongoingFestivals`·`popularSpots`는 커서 그대로다.

  그래서 **R7(중복·누락 없는 페이지네이션)의 보장 책임이 서버로 넘어갔다.** 클라이언트는
  받은 페이지를 순서대로 이어 붙일 뿐이고, 동점 정렬이 안정적인지는 서버가 책임진다.

커밋된 SDL 조각(`*_schema.graphql`)은 이 스냅샷을 따른다.

## 1. 화면과 라우트

| 화면 | 라우트 | 상태 |
|---|---|---|
| 검색 페이지 | `/search` | 신설 (R10, R11, R13) |
| 홈 | `/home` | 기존, 내용 교체 (R15–R20) |
| 커뮤니티 spot 피커 | 바텀시트 (라우트 없음) | 기존, 검색 방식 교체 (R14) |

`/search`는 탭 셸 **밖의** 최상위 라우트로 둔다. 검색은 탭 전환이 아니라 홈에서 밀고 올라오는
전체 화면 흐름이고, 루트 내비게이터에 푸시해야 하단 탭을 덮는다. 기존 라우트 관례를 따라
경로·이름은 kebab-case이며 화면은 `routeName`을 노출하고 이름으로 이동한다.

검색 페이지는 홈 외의 진입점(커뮤니티 등)이 생길 여지가 있으므로 라우트 이름 상수를
`lib/common/navigation/`에 두는 기존 패턴을 따른다.

> **구현에서 바꿨다.** 실제로 검색으로 보내는 곳은 홈 하나뿐이라 `SearchScreen.routeName`이
> 직접 소유한다 — 둘 이상이 쓰기 전에 공용으로 올리지 않는다(CLAUDE.md §4 "don't pre-share").
> 두 번째 진입점이 생기면 그때 `common/navigation/`으로 올리는 한 줄 변경이다.

디자인은 Google Stitch 산출물을 기준으로 한다. 화면 구성은 그쪽을 따르되, 서버에 근거가 없는
필드는 렌더링하지 않는다(§4).

## 2. 상태 모델

### 검색 페이지 (R11)

한 화면이 네 상태를 갖는다. 이 넷은 서로 배타적이며, 특히 **빈 결과와 실패를 같은 상태로 뭉치지
않는다** — AC-11.2와 AC-11.3이 이를 구분해 요구한다.

- 초기(질의 없음) — 최근 검색어를 보여준다
- 로딩 — 질의 전송 후 응답 전
- 결과 있음
- 결과 없음 — 정상 상태다. 실패 문구나 재시도 버튼을 쓰지 않는다
- 실패 — 재시도 수단을 제공한다

#### 최근 검색어를 여는 수단 (구현에서 추가)

설계상 최근 검색어는 "초기(질의 없음)" 상태의 화면이다. 그런데 그 상태로 돌아가는 길이
**빈 입력으로 엔터를 누르는 것뿐이었다** — 검색을 한 번 하고 나면 기록을 다시 볼 방법이 사실상
없었고, 빈 엔터가 초기 상태로 되돌리는 것은 의도한 진입점이 아니라 부수효과였다.

그래서 검색바 아래에 **최근 검색어 버튼**을 두고, 누르면 결과 위에 패널로 겹치게 했다.
닫기(X)와 배경 탭으로 닫힌다.

- **패널은 화면 로컬 상태다**(`_recentOpen`). 상태 기계에 여섯 번째 상태를 더하지 않았다 —
  §2의 다섯 상태는 *조회 결과*에 관한 것이고, 패널은 그 위에 잠깐 겹치는 표시일 뿐이라 닫으면
  보던 결과가 그대로 남아야 한다(그것이 겹치기를 택한 이유다).
- **버튼은 기록이 있을 때만 보인다.** 없으면 눌러도 빈 목록이 뜨는 버튼이 되고, 처음 쓰는
  사용자에게 의미 없는 자리를 차지한다. `select`로 목록의 비어 있음만 구독해, 항목이 바뀌어도
  개수가 그대로면 버튼은 다시 그리지 않는다.
- 초기 상태에서는 패널을 얹지 않는다 — 그때는 최근 검색어가 이미 본문이라 같은 목록이 두 번
  그려진다.

#### 카테고리 필터 (R5)

**한 번 빠뜨렸다가 뒤늦게 붙였다.** repository 서명에는 `category`가 있었는데 notifier가 그것을
넘기지 않아 항상 null로 나가고 있었다 — 서버는 지원하는데 클라이언트만 안 쓰는 상태였다.

- 선택은 **검색 전용 `SpotSearchCategory` provider**가 든다. Discover의 `SelectedSpotCategory`를
  같이 쓰면 Discover에서 고른 필터가 검색 결과까지 갈아치운다 — `CategoryBar`가 선택 상태를
  화면에서 받도록 만들어진 것도 같은 이유다.
- 카테고리는 **상태 기계에 넣지 않았다.** 그것은 *조회 조건*이지 결과가 아니라서, 다섯 상태
  전부에 실으면 같은 값이 다섯 번 복제된다.
- 필터를 바꾸면 `reapplyCategory()`가 **같은 질의로 0페이지부터** 다시 조회한다. 이어 붙이지
  않는 이유는 필터가 바뀌면 결과 집합 자체가 달라져 이전 페이지와 이어지지 않기 때문이다.
- 검색 전(초기 상태)에는 선택만 기억하고 조회하지 않는다 — 고를 질의가 없다.

커뮤니티 시트도 같이 걸었다(사용자 결정). 칩과 검색창이 한 시트에 있으니 둘이 함께 걸리는 것이
보이는 대로의 동작이다 — 스펙 R14는 카테고리를 언급하지 않지만 무시하는 쪽이 오히려 어긋난다.

> **Riverpod 함정**: 이 작업에서 `ref.watch`를 `await` **뒤**에 두어 카테고리가 계속 null로
> 나갔다. 비동기 gap 이후의 `watch`는 의존성으로 등록되지 않는다 — 디바운스가 있는 provider에서
> 특히 걸리기 쉽다. 자동완성 provider도 같은 문제(반경을 바꿔도 갱신 안 됨)가 있어 함께 고쳤다.

#### 결과 줄의 표시 (구현에서 조정)

**주소와 거리를 두 줄로 나눈다.** 처음에는 `주소 · 8.7km`처럼 한 줄에 이어 붙였는데, 실기기에서
주소가 긴 줄은 거리가 통째로 잘려 나갔다 — 정작 "얼마나 먼가"가 안 보였다. 같은 이유로 커뮤니티
시트도 고쳤다(그쪽은 거리가 있으면 주소를 아예 감추고 있었다 — 둘 다 고르는 데 필요한 정보다).

**질의와 일치한 글자를 굵게 그린다.** 제목에 질의가 없고 주소에만 있는 결과가 흔한데, 강조가
없으면 무관해 보인다. 매칭 구간은 `common/model/text_match.dart`의 순수 함수가 찾고, 굵게 그릴지는
`HighlightedText`가 정한다.

> **강조는 서버가 준 것이 아니라 클라이언트가 근사한 것이다.** 보이는 글자가 같은 곳만 굵어지므로
> **오타 허용(R3)이나 형태소 분석(R2)으로 걸린 결과는 강조가 없을 수 있다** — 틀린 것이 아니라
> 한계다. 정확히 하려면 서버가 매칭 위치를 함께 줘야 하는데, 그 필드는 계약에 없고 이 표시 하나를
> 위해 계약을 넓힐 일은 아니라고 봤다.

자동완성은 이 상태 기계와 **별개의** provider로 둔다. 입력 중 계속 갱신되므로 결과 상태 기계에
섞으면 로딩 표시가 요동친다.

디바운스는 스펙이 구현 재량으로 남겼고(§9.3), **250ms로 정했다** — 한 글자 더 치는 사이에는
나가지 않고 손을 멈추면 곧 뜨는 값이다. 질의를 provider family 인자로 받으므로, 대기 중에 질의가
바뀌면 그 provider가 폐기되어 호출 자체가 나가지 않는다.

로딩·실패를 화면에 드러내지 않는다 — 입력 보조 수단이라 타이핑 중에 스피너나 오류가 뜨면 방해가
된다. 제안이 없으면 아무것도 그리지 않고 사용자는 그대로 제출하면 된다.

### 홈 (R19, R20)

세 섹션은 **각각 독립된 provider**를 갖는다. 하나의 provider가 세 섹션을 함께 불러오면 한 섹션의
실패가 화면 전체를 무너뜨려 AC-19.1을 위반한다.

각 섹션이 로딩·결과·빈 상태·실패를 개별적으로 가지며, 재시도도 섹션 단위다(AC-20.1). 재시도가
다른 섹션의 provider를 무효화해서는 안 된다(AC-20.2).

**빈 상태가 일반적이라는 점을 설계에 반영한다.** 반경 안에 진행 중인 축제가 없거나, 좋아요 10개
이상인 spot이 없는 경우는 흔하다. 특히 초기 데이터 상황에서 Popular은 대부분 비어 있을 것으로
예상된다. 따라서:

- 빈 섹션은 이유를 알려주는 문구를 갖는다(예: 주변에 진행 중인 축제가 없음). 빈 공간을 그대로
  두지 않는다
- 세 섹션 중 둘이 비어도 화면이 성립해야 한다(AC-19.3) — 레이아웃이 세 섹션이 모두 찬다는 가정을
  하지 않는다

## 3. 저장소 계층

생성된 GraphQL 타입은 repository 밖으로 나가지 않는다(POL-020). repository가 도메인 모델로
매핑한다.

| 오퍼레이션 | 소비하는 곳 |
|---|---|
| `searchSpots` | 검색 페이지, 커뮤니티 spot 피커 (동일 오퍼레이션 재사용) |
| `spotSearchSuggestions` | 검색 페이지 자동완성 |
| `spots` (기존) | 홈 Near you |
| `ongoingFestivals` | 홈 Happening Now |
| `popularSpots` | 홈 Popular |

### 최근 검색어 (R12)

**클라이언트 로컬 저장 전용이다.** 서버에 저장하지 않으며 계약에 해당 필드가 없다. 토큰이 아닌
일반 설정 성격의 데이터이므로 `flutter_secure_storage`가 아니라 일반 로컬 저장소를 쓴다.

저장소는 provider 뒤에 두어 단위 테스트에서 교체 가능하게 한다. AC-12.2가 "앱 재시작 후 유지"를
요구하는데, 이를 위젯 재시작으로 검증하지 않고 저장소를 다시 읽는 것으로 검증한다.

**저장소는 `common/`이 아니라 `domain/spot/repository/`에 둔다.** 최근 *spot* 검색어를 쓰는 곳이
`domain/spot` 하나뿐이라 지금 공용으로 올릴 근거가 없다(CLAUDE.md §4 "don't pre-share"). 검색
라우트 이름도 같은 이유로 `SearchScreen.routeName`이 직접 소유한다 — 둘 다 두 번째 사용처가
생기면 그때 `common/`으로 올리는 한 줄 변경이다.

`SpotSearchResult`는 **`OffsetPage`를 감싸고 `totalCount`만 더한다.** 기능이 자기 페이지네이션을
새로 만들지 않는다(CLAUDE.md §4) — 목록도 공용 `PaginationListView`가 그린다. `totalCount`를
따로 두는 이유는 `OffsetPage.totalCount`가 nullable인데 검색 계약은 non-null이라, 화면이 null
분기를 하지 않도록 여기서 확정하기 위해서다.

**Happening Now의 모델을 교체했다.** 목 시절의 `TourEvent`(festival/live/art 카테고리)는 서버
`Festival`과 맞지 않아 지우고 새로 만들었다. 새 모델은 **카테고리와 저작권 유형을 담지 않는다** —
`ongoingFestivals`는 축제만 반환하므로 카테고리가 항상 같아 화면에 드러낼 정보가 못 되고, 두 값의
enum은 `domain/spot`이 소유해 여기서 쓰면 기능 간 의존이 생긴다. 그 자리를 실제로 다른 값인
**행사 기간**이 대신한다.

## 4. 제거 대상

다음 두 가지는 서버에 소스가 없는 클라이언트 측 허구다. 이번 작업에서 **대체가 아니라 삭제**한다.

- **별점** — `TouristSpot.rating`, 그리고 `spot_repository_impl.dart`의 4.8/4.6/4.5 리터럴,
  `popular_spot_card.dart`의 별 아이콘 표시. 서버에 rating 개념 자체가 없다
- **혼잡도** — `CongestionLevel`과 그 뱃지. `fromWire()` 파서가 있으나 서버에서 오는 값이 없어
  Discover는 항상 `low`로 하드코딩한다

AC-15.2와 AC-15.3이 이 필드들의 **부재**를 검증하므로, 화면에서 감추는 것으로는 부족하고 모델에서
제거해야 한다.

홈의 목 데이터 제공 경로(`fetchRecommendedSpots`, `fetchPopularSpots`, `EventRepositoryImpl`의
하드코딩 목록)도 함께 제거한다.

### 구현하며 함께 정리한 것

설계 당시에는 별점·혼잡도만 지목했으나, 실제로 지우고 보니 **`distanceKm`도 같은 성격**이었다 —
Home 목 카드 전용 필드이고 서버가 주는 값은 `distanceMeters`다. 두 개를 남겨 두면 어느 쪽이
진짜인지 다음 사람이 알 수 없으므로 함께 지우고 `distanceMeters` 하나로 모았다.

l10n 키도 같이 은퇴시킨다(`congestionLow/Moderate/High`, `distanceAway`). **문구가 남아 있으면
다음 사람이 "쓰던 게 있네" 하고 다시 붙인다** — `nav_arb_keys_test`의 은퇴 키 목록이 이를 막는다.

`homeSectionRecommended`("Recommended for You")도 `homeSectionNearYou`("Near You")로 교체했다.
R16이 요구하는 것은 거리순이지 취향 추론이 아니라서(스펙 §2 "개인화 추천은 범위 밖") 기존 이름이
실제 동작과 어긋나 있었다.

**두 카드는 합치지 않았다.** 필드를 지우고 나면 `SpotCard`와 `PopularSpotCard`가 거의 같아지지만,
전자는 가로 스크롤용 고정 폭이고 후자는 세로 리스트 행이라 배치가 다르다. Popular은 서버에서
`likeCount`(랭킹 근거)를 edge로 받게 되어 있어 그 자리가 이 행에만 생긴다 — 지금 합치면 그때 다시
갈라야 한다. 사용자 결정 사항이다.

## 5. 반경

세 홈 섹션과 검색 모두 기존 Discover의 반경 설정값(`search_radius_controller`)을 재사용한다.
반경 전용 설정을 새로 만들지 않는다. 설정이 바뀌면 다음 조회에 반영된다(AC-16.2).

위치 권한은 앱 전역에서 필수이므로 좌표가 없는 상태를 별도로 다루지 않는다.

## 6. 커뮤니티 spot 피커 (R14)

현재 구현은 `spots`로 목록을 받아 `title.contains()`로 클라이언트에서 거른다. 이를 서버
`searchSpots` 호출로 바꾼다. 제목만 검색되던 것이 주소까지 대상이 되고, 오타·형태소 일치가 생긴다.

지금은 질의가 입력되면 페이징이 꺼진다(`hasMore: query.isEmpty && ...`). 서버 검색은 페이지를
반환하므로 이 제약을 없앤다(AC-14.2).

질의를 지우면 기존의 좌표 기반 목록으로 되돌아간다(AC-14.3). 즉 피커는 질의 유무에 따라 두 소스를
오간다.

> 이 변경은 SPEC-0010이 명세한 피커 동작(목록 내 좁히기)을 대체한다. SPEC-0010은 수정하지 않으며,
> 이 스펙이 해당 부분을 갱신한 것으로 본다.

### 구현 결과

**시트 구조는 그대로 두고 검색만 얹었다.** 출처 탭(주변/좋아요한 장소)과 카테고리 칩은 원래대로
남고, 텍스트 칸이 "받아 둔 목록 좁히기"에서 **서버 검색**으로 바뀐 것이 이 스펙의 변경이다.

- **주변 탭에만 서버 검색이 걸린다.** 좋아요 탭은 클라이언트 필터를 유지한다 — `searchSpots`는
  좌표 기반 반경 검색이라 "내가 좋아요한 것 중에서"를 표현할 수 없고, 서버에 그 조합을 받는
  필드가 없다.
- 카테고리 칩은 주변 목록과 검색 **양쪽에** 걸린다. 칩과 검색 칸이 한 시트에 있으니 둘이 함께
  걸리는 것이 보이는 대로의 동작이다.
- **검색은 제출할 때만 나간다**(엔터 또는 키보드의 검색). 예전 텍스트 칸은 `onChanged`로 매 글자
  질의를 갱신했는데 그때는 이미 받아 둔 목록을 거르는 것이라 공짜였다 — 서버 검색이 된 뒤로는
  한 글자마다 호출이 나가므로 제출로 바꿨다. 지우는 것만 즉시 반영한다(서버를 부르지 않는
  방향이라, 비우면 곧바로 주변 목록으로 돌아온다 — AC-14.3).
- 그래서 **디바운스를 두지 않았다.** 제출 방식에는 억제할 대상이 없고, 디바운스가 있으면 결과만
  늦게 뜬다.

**오퍼레이션 이름은 `CommunitySearchSpots`로 갈랐다.** graphql_codegen이 모든 조각을 한
네임스페이스로 합치므로 spot 쪽 `SearchSpots`와 부딪힌다(`NearbySpots`·`CommunityLikedSpots`가
같은 이유로 개명한 전례를 따랐다). 스키마 조각에는 `searchSpots` 필드를 **다시 선언하지 않는다** —
spot 조각이 이미 `extend type Query`에 올렸고 중복 선언은 병합 시 충돌한다.

**질의는 provider family 인자로 받는다.** 질의가 바뀌면 Riverpod이 새 provider를 만들고 이전
것을 폐기하므로 이어 붙이던 페이지 번호가 자동으로 0으로 돌아간다. 질의를 상태로 들고 있으면 그
초기화를 손으로 해야 하고, 한 번 빠뜨리면 이전 질의의 다음 페이지를 새 질의 결과에 붙이게 된다.
디바운스는 350ms — 검색 페이지의 자동완성(250ms)보다 길게 잡았다. 이쪽은 제안이 아니라 본
조회라 한 번의 호출이 더 무겁다.

## 7. 테스트

provider/notifier와 도메인 모델 수준의 단위 테스트로 한정한다. 위젯·통합 테스트는 요구하지 않는다.

| 단위 | 담당 기준 |
|---|---|
| 검색 결과 notifier | AC-11.1~11.4, 13.2 |
| 최근 검색어 notifier + 저장소 | AC-12.1~12.4 |
| 홈 섹션별 notifier (3종) | AC-15.1, 16.1~16.3, 19.1~19.3, 20.1~20.2 |
| 피커 notifier | AC-14.1~14.3 |
| 홈 화면 모델 | AC-15.2, 15.3 (필드 부재) |

repository는 스텁한다. AC-10.1·10.2·13.1·14.4는 내비게이션과 위젯 상호작용이라 이 범위에서
검증하지 않는다 — 라우트 이름과 인자를 만드는 순수 함수 수준까지만 단위로 다루고, 실제 화면 전환은
수동 확인에 맡긴다.

### 구현에서 더한 것

이 표 밖에 두 가지를 추가했다. **repository 테스트**(모킹한 GraphQL 링크)로 AC-1.3(빈 결과)·
R8(`userErrors` 번역)·R9·R18·AC-17.5(날짜 파싱 실패 행 제외)를 잡는다 — 서버 응답을 도메인
모델로 옮기는 지점이라 여기서만 검증할 수 있다. **시트 위젯 테스트**는 이미 있던 것을 서버 검색
기준으로 고쳤다(클라이언트 필터를 검증하던 것이 R14로 거짓이 됐다).

**Riverpod 3에서 배운 것**: provider 실패는 `AsyncLoading(error: …)`로 오고 그때
`isLoading`이 **여전히 true다**. 실패를 `isLoading == false`로 기다리면 영원히 완결되지 않아
테스트가 30초 타임아웃까지 매달린다 — `hasError`로 판정해야 한다(실측 확인).
