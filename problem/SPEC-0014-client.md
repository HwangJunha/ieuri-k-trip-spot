# SPEC-0014 — 클라이언트 설계

요구사항·수용 기준·계약 초안은 spec에 있다. 여기에는 클라이언트 쪽 설계 판단만 적는다.

관련 이슈: `HwangJunha/ieuri-k-trip-spot#42`
브랜치: `feature/SPEC-0014-map-realtime-congestion` (`dev`에서 분기)

---

## 1. 구조

기존 feature-first 규약을 따라 `lib/domain/map/`을 신설한다.

```
lib/domain/map/
  component/   지도 위 오버레이 위젯 — 마커, 폴리곤, 안내 배너, 출처 표기
  model/       도메인 모델 — 뷰포트, 마커, 구역 혼잡도, 경계
  provider/    Riverpod — 뷰포트 상태, 조회, 경계 캐시
  repository/  GraphQL 연산 + 도메인 모델 매핑
  view/        지도 화면
```

기존 `lib/common/location/`(`location_service` · `coordinates` · `location_providers`)이
이미 있다. 좌표 타입을 새로 만들지 않고 `coordinates`를 재사용한다.

**생성 타입은 repository 밖으로 나가지 않는다**(POL-020). `graphql_codegen`이 만든 타입은
repository에서 도메인 모델로 매핑한다.

## 2. 지도 SDK

`kakao_map_sdk: ^1.2.6`을 추가한다.

- 네이티브 키 설정이 필요하다(Android `AndroidManifest.xml` / iOS `Info.plist`). 키는 커밋하지
  않는다.
- SDK 용어의 **"카메라"는 기기 카메라가 아니라 지도가 보여주는 화면 영역**이다. 본 문서와
  코드에서는 혼동을 피해 **뷰포트(viewport)**로 부른다. 카메라 권한과 무관하다.
- 뷰포트를 계약의 `MapBoundsInput`(minLat/minLng/maxLat/maxLng)으로 변환하는 책임은
  repository가 아니라 **model**에 둔다. 순수 계산이라 단위 테스트가 쉽다.

### 2.1 SDK는 뷰포트 경계를 직접 주지 않는다 — 구현 중 확인

설계 초안은 "SDK가 주는 뷰포트 경계를 변환한다"고 적었으나, **1.2.6의 실제 API에는 그런 값이
없다.** 확인된 것은 다음과 같다:

- `CameraPosition`이 담는 것은 **중심 좌표(`LatLng`)와 정수 줌(`zoomLevel`)뿐**이다.
  `LatLngBounds`에 해당하는 타입 자체가 패키지에 없다.
- 대신 `KakaoMapController.fromScreenPoint(x, y)`가 화면 좌표를 위경도로 되돌린다.

따라서 bbox는 **화면의 두 모서리(좌상·우하)를 `fromScreenPoint`로 변환해 만든다.** 이 변환은
컨트롤러를 거치므로 비동기이고 뷰 크기에 의존한다 — 순수 계산이 아니다.

경계 산출(SDK 왕복)과 경계 가공(확장·포함 판정)을 **분리한다**: 산출은 화면이, 가공은 model이
맡는다. model은 `MapBounds` 네 값을 입력으로 받는 순수 함수로 유지되어 그대로 테스트된다.

정수 줌이라는 점도 함께 기록한다. 줌 게이트(§5.1)와 클러스터 판정 임계값은 정수 비교이며,
소수 줌을 전제한 계산을 넣지 않는다.

**`newCenterPosition`에는 줌을 반드시 함께 넘긴다.** `zoomLevel`의 기본값이 `-1`이고 그 값이
네이티브까지 그대로 전달돼, 생략하면 좌표는 맞게 가지만 전국이 보일 만큼 축소된다. 현재 위치
버튼에서 실제로 그렇게 났다(2026-08-10, 사용자 발견). 위치 버튼은 **위치만 옮기는 것이 맞아**
`getCameraPosition()`으로 현재 줌을 읽어 그대로 넘긴다 — 배율까지 바꾸면 보던 맥락이 날아간다.

### 2.2 앱 키를 읽는 위치

`KAKAO_NATIVE_APP_KEY`는 현재 `domain/auth/repository/sns_config.dart`가 읽고 있다.
`map`이 이 파일을 import하면 **도메인 경계를 넘는다**(CLAUDE.md §3 — 교차 feature import 금지).

키 상수를 `common/config/kakao_config.dart`로 옮기고 `SnsConfig`가 그것을 참조하게 한다.
두 도메인이 같은 값을 쓰므로 `common/`이 맞는 자리다(§4 — 둘 이상이 쓰면 common).

초기화 실패 방침은 `SnsInitializer`를 그대로 따른다 — 키가 비면 SDK 초기화를 건너뛰고 지도
화면이 안내를 표시하며, **앱 기동을 실패시키지 않는다.**

**SDK 초기화기도 `common/config/`에 둔다** — 처음에는 `domain/map/repository/`에 뒀는데
계층 훅이 막았다. 지도 화면이 "SDK가 준비됐는가"를 읽어야 하는데, `view`가 `repository`를
import하는 것은 금지돼 있다(CLAUDE.md §3). 초기화는 데이터 접근이 아니라 **앱 부트스트랩**이라
애초에 repository가 아니었다. 로그인의 `SnsInitializer`가 auth 도메인 안에 있는 것은 화면이
그 상태를 읽지 않기 때문이며, 지도는 사정이 다르다.

### 2.2.1 SDK 오버레이는 **지우지 말고 재사용한다**

kakao_map_sdk 1.2.6의 `removePolygonShape`·`Poi.remove()`는 **Dart 목록에서만 지우고
네이티브에는 남긴다.** 실측으로 확정했다 — "4/4개 제거" 로그 뒤 3개만 그렸는데도 화면은
계속 진해졌고, 마커도 "10개 등록 완료"인데 이전 것이 그대로 남아 새것을 가렸다.

반투명 폴리곤은 겹칠수록 어두워져 지도가 안 보이게 되고, 마커는 쌓여서 최근 것을 덮는다.

그래서 만든 오버레이를 **풀에 두고 갈아 끼운다**:

| | 재사용 API | 남는 것 |
|---|---|---|
| 폴리곤 | `changePosition` · `changeStyle` | `hide()` |
| 마커 | `move` · `changeStyles` · `onClick` 재할당 | `hide()` |

`hide()`는 네이티브에서 정상 동작한다. 겹쳐 호출될 때를 대비해 그리기마다 세대 토큰을 둔다.

**SDK 자체를 고치는 길(vendor + `dependency_overrides`)은 택하지 않았다.** 업스트림이
고쳐질 때까지 SDK 사본을 우리가 관리해야 하고, 빌드마다 패치본을 받아야 하며 버전을 올릴
때마다 패치를 다시 얹어야 한다. 그 비용이 이 문제에 비해 크다.

같은 이유로 `PolygonStyle`은 **단계별로 하나만 만들어 재사용한다.** 폴리곤마다 새로 넘겼더니
SDK가 그때마다 스타일을 새로 등록했고, 도형을 지워도 등록된 스타일은 지워지지 않아 쌓였다.

### 2.2.2 `PolygonStyle.strokeWidth`는 iOS에서 앱을 죽인다

iOS 플러그인이 payload의 숫자를 `v as! UInt`로 강제 캐스팅하는데(`PrimitiveTypeConverter`),
`strokeWidth`는 Dart 타입이 `double`이라 NSNumber(double)로 건너간다:

```
Foundation/NSNumber.swift: Fatal error: Unable to bridge NSNumber to UInt
```

**값과 무관하다** — `2`를 넘겨도 Dart에서 `2.0`이 된다. `PolygonStyle`을 상속해
`toMessageable()`에서 그 값만 정수로 바꿔 피한다(`_IntStrokePolygonStyle`).

### 2.3 네이티브 앱 키의 성격

카카오 네이티브 앱 키는 **숨길 수 있는 값이 아니다.** SDK 규약상 Android 매니페스트에
`kakao{앱키}` 스킴으로 박혀야 하고 APK를 열면 읽힌다. 보호는 은닉이 아니라 **키 해시·번들
id 플랫폼 등록**이 담당한다 — 카카오 서버가 등록된 앱 서명에서 온 요청만 받는다.

그럼에도 Dart 코드에 하드코딩하지 않는 이유는 노출 지점을 늘리지 않기 위해서이자, 키를
교체할 때 고칠 자리가 갈리지 않게 하기 위해서다. 매니페스트에 이미 박힌 것은 불가피해
그대로 둔다(§10).

## 3. 뷰포트 조회 흐름

### 3.1 유휴 판정 (R19)

지도 이동·확대 중에는 조회하지 않는다. 멈춘 뒤 디바운스를 거쳐 1회만 조회한다.

```
지도 이동 시작 → (조회 없음)
지도 멈춤       → 디바운스 타이머 시작
  타이머 만료 전 다시 움직임 → 이전 타이머 취소
  타이머 만료                → 조회 1회
```

디바운스 시간은 `[TBD]`(spec §8 6번). 실기기에서 정한다.

**타이머는 provider가 소유하고 dispose 시 반드시 취소한다.** 화면을 벗어난 뒤 타이머가 살아
있으면 폐기된 provider에 결과가 도착한다.

### 3.2 확장 조회 (R20)

화면 bbox를 그대로 보내지 않고 일정 배율로 넓혀 조회한다. 배율은 `[TBD]`(spec §8 7번).

새 뷰포트가 **직전 조회 영역 안에 완전히 포함되면 재조회하지 않는다.** 이 판정을 model의
순수 함수로 두면 그대로 테스트할 수 있다(R20).

넓히는 만큼 결과 수가 늘어 상한에 더 빨리 닿는다는 점은 감수한다 — 재조회 빈도를 줄이는
쪽이 체감 품질에 유리하다.

### 3.3 조회 취소

뷰포트가 바뀌면 진행 중인 이전 조회 결과는 버린다. 늦게 도착한 응답이 현재 뷰포트를
덮어쓰지 않도록, 응답에 요청 시점의 뷰포트를 함께 들고 비교한다.

## 4. 마커

### 4.1 동반 표시 (R21)

spot 마커와 문화행사 마커를 **항상 함께** 표시한다. 토글 필터를 두지 않는다.

**사진 썸네일 마커를 쓴다**(구현 중 변경, 2026-08-10). 처음에는 단색 점으로 그렸는데,
카카오 지도가 기본으로 찍는 POI(약국·은행 아이콘 등)와 섞여 **무엇이 이 앱의 데이터인지
구분되지 않았다.** 사진이 들어가면 한눈에 갈리고, 확대하지 않아도 어떤 장소인지 짐작된다.

종류 구분은 **아래 꼬리 색**이 맡는다 — 사진이 주인공이라 도형을 바꾸면 사진이 잘린다.

아이콘은 캔버스로 그리되 **화면 밀도만큼 촘촘히** 그린다. 논리 크기로 만들었더니 3배
해상도 기기에서 늘려 그려져 사진이 눈에 띄게 흐렸다.

### 4.2 클러스터 — **서버가 제거했다**

계약 초안에는 저줌에서 서버가 묶어 주는 `clusters`가 있었으나, **라이브 스키마에서
`SpotCluster` 타입과 `MapViewportResult.clusters`가 모두 사라졌다**(2026-08-10 확인).
없는 필드를 요청하면 `mapViewport`가 통째로 실패해 마커가 하나도 오지 않는다.

저줌에서 마커가 몰리는 문제는 **클라이언트의 격자 솎아내기**가 맡는다
(`marker_thinning.dart`) — 화면을 4×4로 나눠 칸마다 하나만 남기고, 화면에 최대 10개를
그린다. 서버는 상한까지(관측상 500건) 주므로 그대로 찍으면 지도가 마커로 뒤덮인다.

R22(클러스터 탭 확대)는 따라서 해당 없음이 됐다.

### 4.3 잘림 안내 (R23) — **두지 않는다**

서버는 뷰포트에 걸리는 spot을 상한까지 주므로 도심에서는 `truncated`가 거의 항상 참이고,
클라이언트는 그와 별개로 10개만 그린다. 어느 기준으로 판정해도 배너가 상시 떠 있어 안내가
아니라 방해물이 됐다(사용자 결정, 2026-08-10).

"더 있으니 확대하라"는 정보 자체가 이 화면에서 쓸모가 적다 — 확대하면 자연히 주변 것이
보이고 사용자는 그걸 이미 안다.

### 4.4 갱신 시점 — "이 지역 재검색"

**지도를 멈출 때마다 자동으로 조회하지 않는다**(사용자 요청). 조금만 움직여도 마커가 바뀌어
보고 있던 장소가 사라지고 화면이 흔들렸다. 우상단 새로고침 버튼을 눌렀을 때만 새로 받는다 —
카카오맵·구글맵이 쓰는 방식이다.

버튼이 뜨는 계기는 둘이다: 이전 조회 영역을 벗어났을 때, 그리고 같은 자리에 3초 이상
머물렀을 때.

**화면이 비면 예외로 자동 조회한다.** 버튼의 취지는 "보고 있던 마커가 갑자기 바뀌는 것"을
막는 것이라, 보이는 게 없으면 그 취지가 성립하지 않는다 — 멀리 이동했을 때 지도가 텅 빈 채
남으면 기능이 죽은 것처럼 보인다.

**재검색은 후보를 섞는다.** 서버가 관련도 순으로 늘 같은 결과를 주고 격자도 칸마다 첫 번째를
고르므로, 섞지 않으면 같은 자리에서 다시 눌러도 화면이 그대로다.

### 4.5 마커는 provider가 소유한다

조회 결과로 통째로 갈아 끼우지 않고 **보탠다**(`MapMarkerController`). 지도를 옮겨도 이전
마커가 살아남아 화면이 깜빡이지 않는다. 화면 밖으로 나간 것도 버리지 않는다 — 축소하면 다시
보여야 한다(보관 상한 60개).

**provider는 `keepAlive`다.** autoDispose로 두었더니 검색 화면으로 넘어가는 동안 폐기되어
마커가 통째로 비워졌다.

`truncated`가 참이면 확대를 유도하는 배너를 띄운다. 마커를 지우거나 지도를 막지 않는다 —
보이는 것은 유효한 결과다.

## 4.6 검색으로 지도 이동 (spec 범위 밖, 사용자 요청)

지도 상단에 검색창을 두고, 누르면 **기존 검색 화면**(`/search`, SPEC-0013)을 연다. 결과를
고르면 상세로 가지 않고 그 장소를 돌려주며, 지도가 그 좌표로 이동하고 **마커를 찍는다.**

**카카오 장소 검색(REST)을 새로 붙이지 않았다.** 앱에 이미 `searchSpots`가 있어 두 검색이
서로 다른 결과를 주면 사용자가 혼란스럽고, REST 키 관리와 일일 쿼터가 새로 생긴다.

### SPEC-0013 쪽에 더한 것

- `searchSpots` 오퍼레이션에 `mapX`·`mapY`를 추가했다. 서버 `Spot` 타입에는 원래 있었고
  요청만 안 하고 있었다. **`mapX`가 경도, `mapY`가 위도다** — 이름이 직관과 반대라 매핑
  검증 테스트를 함께 뒀다.
- `TouristSpot`에 `coordinates`를 추가했다. 기존 `location`은 "서울 종로구" 같은 표시용
  문자열이라 지도 이동에 쓸 수 없다.
- `SearchScreen`에 `returnsPickedSpot` 모드를 뒀다. 지도에서 열 때만 참이며, 라우트
  쿼리 파라미터 `pick=1`로 전달된다.

### 교차 feature 경계

검색 결과는 `domain/spot`의 `TouristSpot`인데 지도가 그 타입을 import하면 경계가 무너진다
(CLAUDE.md §3). 처음에는 `dynamic`으로 필드를 읽어 피했는데, **그 선택이 런타임에 두 번
깨졌다** — `.name`이 확장 게터라 동적 호출에서 없다는 오류가 났고, 컴파일러도 테스트도
그걸 잡지 못했다.

타입을 피하려다 기능을 잃은 셈이라, 좌표·이름만 담는 값 객체를 `common/navigation/`에
두는 쪽으로 바꿨다(`PickedPlace`). 변환은 타입을 아는 검색 화면이 맡는다.

### 강조 표시

검색으로 찾은 마커는 **빨간 테두리**를 두르고(사용자 요청), 조회 결과에 밀려나지 않도록
고정한다. 새로 검색하면 이전 고정의 강조만 꺼지고 마커 자체는 남는다 — 지웠다 사라지면
화면이 깜빡인다.

## 5. 혼잡도 폴리곤

### 5.1 줌 게이트 (R25)

임계 줌 미만에서는 폴리곤을 그리지 않는다. 임계값은 `[TBD]`(spec §8 2번).

**표시하지 않을 때는 `seoulCongestion`을 호출하지도 않는다.** 이것이 일일 호출량을 지키는
실질적 장치다(spec §7.4). 게이트를 렌더링 단계에만 두고 조회는 계속하면 의미가 없다.

지도가 서울 밖이면 뷰포트에 걸치는 구역이 없어 호출이 0이 된다.

### 5.2 경계 캐싱 (R26)

`seoulCongestionAreas`는 정적이다. 앱 시작 시(또는 지도 첫 진입 시) 1회 조회해 캐시하고,
이후 실시간 응답과 구역 id로 조인한다.

- 캐시는 **메모리 + 로컬 영속** 양쪽을 고려한다. 121개 폴리곤은 매 실행마다 다시 받기엔
  크고, 앱 수명 내내 들고 있기엔 부담이 적다.
- **캐시 키에 활성 언어를 포함한다**(R31). `seoulCongestionAreas`가 이름을 활성 언어로
  내려주므로, 언어를 무시하고 캐싱하면 언어를 바꿔도 이전 언어 이름이 그대로 남는다.
  설정에서 언어를 변경하면 경계 캐시를 무효화하거나 언어별로 따로 보관한다.
  폴리곤 좌표는 언어와 무관하므로, 좌표와 이름을 분리해 좌표만 공유하는 방식도 가능하다.
- **혼잡도에는 있는데 경계 캐시에 없는 구역 id가 오면 그 구역만 건너뛴다**(R26). 오류로
  올리지 않는다. 서울시가 구역을 추가했는데 캐시가 낡은 경우가 여기 해당한다.
- 반대로 경계에만 있고 혼잡도에 없는 구역은 채색하지 않는다.

### 5.3 채색 (R24)

4단계를 서로 구분되는 색으로 칠한다.

**적록 대비에만 의존하지 않는다.** 흔한 신호등 배색(초록–노랑–빨강)은 적록색맹 사용자에게
1·4단계가 구분되지 않는다. 명도가 함께 변하는 순차형 스케일을 쓴다 — 4단계가 순서 있는
값이므로 순차형이 의미상으로도 맞다.

폴리곤 채우기는 반투명으로 두어 아래 지도와 마커가 보이게 한다.

## 6. 신선도·부재 표현

이 절의 규칙은 **사용자를 오해시키지 않는 것**이 목적이다. 전부 수용 기준이 걸려 있다.

### 6.1 구역 정보는 네 항목 (R27)

구역을 선택하면 아래 넷만 표시한다(spec §7.8). 항목을 늘리지 않는다.

```
┌──────────────────────────┐
│  강남 MICE 관광특구         │  name
│  ● 붐빔                   │  CongestionLevel (색 + 라벨)
│  3,000 – 3,500명           │  populationMin~Max
│  03:30 기준                │  observedAt
└──────────────────────────┘
```

데이터는 약 30분 지연되어 도착한다(spec §4.2). `observedAt`을 그대로 노출하고, "실시간"·"현재"
같은 표현으로 지금 시각을 암시하지 않는다.

단계는 **색과 라벨을 함께** 쓴다. 색만으로 표현하면 색각 이상 사용자가 구분할 수 없고,
폴리곤 채색(§5.3)과 같은 이유다.

상권은 `CommercialStatus.observedAt`이 따로 있고 **인구와 다른 시각**이다. 하나로 합쳐
표시하지 않는다.

**상권을 이 카드에 함께 넣는다**(사용자 결정, 2026-08-10). spec §7.8은 인구 관련 4항목만
확정했고 상권 포함 여부는 정하지 않았는데, 구역을 선택했을 때 상권을 볼 다른 자리가 없어
여기 넣는다. 다만 **구분선 아래 별도 섹션**으로 두어 4항목과 섞이지 않게 한다 — 기준 시각이
서로 다르므로(§4.3, 상권은 야간에 갱신이 멈춘다) 한 덩어리로 읽히면 인구의 신선도가 상권에도
있는 것처럼 보인다.

3상태는 눈에 보이게 다르게 그린다: 부재는 "정보 없음", 기본값은 단계를 흐리게 두고 "실측되지
않은 지역"을 덧붙이며, 실측만 자기 기준 시각을 함께 보여준다.

### 6.2 상권 3상태 (R28)

| 서버 응답 | 표시 |
|---|---|
| `commercial`이 부재 | "정보 없음" |
| `isDefaulted: true` | 실측과 구분되는 표현. 값을 신뢰 신호로 쓰지 않는다 |
| `isDefaulted: false` | 실측값으로 표시 |

121곳 중 82곳에만 데이터가 있고, 없는 구역은 업스트림이 `보통 시간대`로 채워 보낸다. 구분
없이 그리면 39곳의 가짜 "보통"이 실측과 섞인다.

### 6.3 레이어 독립 (R29)

`degraded`가 참이면 **혼잡도 레이어만** 안내로 대체한다. spot·문화행사 마커는 계속 표시하고
지도는 정상 조작 가능해야 한다. 전면 오류 화면으로 덮지 않는다.

`mapViewport`와 `seoulCongestion`이 별개 최상위 필드이므로, 각각의 로딩·오류 상태를 **별도
provider**로 둔다. 하나의 통합 상태로 묶으면 한쪽 실패가 다른 쪽을 가린다.

### 6.4 출처 표시 (R30)

공공누리 1유형은 출처 표시가 필수다. 혼잡도 레이어가 보이는 동안 "출처: 서울특별시 실시간
도시데이터"에 해당하는 표기를 노출한다. 접히거나 가려지는 위치에 두지 않는다.

**"보이는 동안"이 조건이다 — 상시 노출이 아니다.** 1차 구현에서 이것을 상수처럼 항상 띄웠다가
사용자 지적으로 고쳤다(2026-08-10). 혼잡도 데이터가 없는데도 전국 지도 위에 출처만 떠 있어
무엇의 출처인지 알 수 없었다. 표시 의무는 **그 데이터를 실제로 쓸 때** 생기는 것이라, 폴리곤이
하나도 없으면 노출하지 않는 편이 규정에도 맞고 화면도 정직하다.

판정은 `CongestionLayerState.showsAttribution` 하나가 쥔다. **범례도 같은 값을 본다** — 둘이
각자 조건을 따지면 색은 없는데 범례만 뜨는 조합이 생긴다.

같은 커밋에서 표기 위치도 하단 네비바 위로 올렸다. 셸이 `extendBody: true`라 body가 바 아래까지
그려지는데 `bottom: 8`이면 바에 가려, "가려지는 위치에 두지 않는다"를 어기고 있었다.

## 7. 다국어

UI는 영어 우선, EN/KO/JA/ZH(POL-022).

- 혼잡도 4단계와 상권 4단계는 **enum이므로 번역 대상이 아니다**(POL-023). 표시 문구를 별도
  번역 키로 둔다.
- **번역이 필요한 자유 텍스트가 없다.** 업스트림의 한국어 설명 문장(`AREA_CONGEST_MSG`)은
  계약에서 제외됐다(spec §7.8) — 4단계가 같은 내용을 이미 담고 있어 정보를 더하지 않으면서
  번역 불가 문제만 만들기 때문이다.
- 표시 항목이 전부 enum·숫자·시각이라 4개 언어 대응이 로케일 포맷팅만으로 끝난다. 인구
  범위의 천 단위 구분과 시각 표기는 로케일 규칙을 따른다.
- **구역명은 서버가 활성 언어로 내려준다**(spec §7.10, R31). `app_*.arb`에 121건을 넣지
  않는다 — 서울시가 구역을 추가하면 앱 재배포가 필요해진다.
- **`locale` 인자를 넘기지 않는다.** 활성 언어는 기존 방식대로 `Accept-Language` 헤더로
  전달된다 — 관광지 API 전체가 이 규약이며 지도만 다르게 하지 않는다. 언어 전환 시 헤더가
  바뀌므로 별도 인자 관리가 필요 없다.

### 7.1 기존 zh 번역과의 불일치

현재 `app_zh.arb`는 **간체(简体)**인데, 서버가 내려주는 구역명은 **번체(繁體)**다. 한 화면에
두 서체가 섞인다.

앱 UI 전체를 번체로 전환하는 작업은 지도와 무관하므로 **별도 spec에서 다룬다.** 본 spec은
구역명을 처음부터 번체로 만들어, 그 전환이 이뤄질 때 재작업이 없게 한다.

전환 전까지는 중국어 화면에서 UI는 간체, 구역명은 번체로 보인다. 의도된 과도기 상태다.

## 8. 테스트 — provider·도메인 모델만

위젯·통합 테스트는 범위 밖이다(플랫폼 방침).

| 단위 | 지는 기준 |
|---|---|
| 뷰포트 model | R20 — 확장 배율 계산, 포함 판정 |
| 유휴 판정 provider | R19 — 이동 중 미조회, 디바운스 후 1회, 재이동 시 취소 |
| 마커 상태 계산 | R21 — spot·행사 동반, 종류 구분 |
| 클러스터 탭 처리 | R22 — 줌 증가 |
| 잘림 안내 상태 | R23 |
| 채색 매핑 | R24 — 4단계가 서로 다른 색 |
| 줌 게이트 | R25 — 임계값 경계 |
| 경계 조인 | R26 — 캐시 재사용, 미매칭 구역 제외 |
| 경계 캐시 언어 키 | R31 — 언어 변경 시 이전 언어 이름이 남지 않는다 |
| 신선도 표시 문자열 | R27 — 기준 시각 포함, "지금" 미사용 |
| 상권 3상태 | R28 |
| 레이어 독립 상태 | R29 — 혼잡도 실패 시 마커 유지 |
| 출처 표기 상태 | R30 |

repository를 스텁으로 두고 provider를 검증한다. 순수 계산(뷰포트 확장, 포함 판정, 색 매핑,
표시 문자열)은 model 단위 테스트로 직접 검증한다.

**테스트하지 않는 것**: 실제 지도 SDK 렌더링, 네이티브 키 설정, 실 GraphQL 전송. 명시적으로
미검증으로 남긴다.

버린다(§3.3). 뷰포트를 빠르게 옮길 때 이전 응답이 현재 화면을 덮는 것을 막는다.

| 뷰포트 확장 · 포함 판정 | R20 |
| 채색 매핑 | R24 — 4색 상이, 명도 단조 감소로 색각과 무관하게 순서를 읽음 |
| 줌 게이트 | R25 — 임계값 경계 포함 |
| 경계 조인 | R26 — 미매칭 구역 제외, 입력 순서 유지 |
| 구역 선택 판정 | R27 — 폴리곤 내부/외부, 겹칠 때 결정적 |

| 잘림 · 실패 안내 | R23·R29 |

**검증하지 않은 것**: 실제 지도 SDK 렌더링, 네이티브 키 설정, 실 GraphQL 전송. 명시적으로
미검증으로 남긴다 — 실기기 육안 확인이 필요하다.

순수 계산을 먼저 두는 것은 미루기가 아니다. §8 테스트 표의 절반 이상(확장 배율, 포함 판정,
색 매핑, 줌 게이트, 표시 문자열, 상권 3상태)이 **repository 없이 검증되는 항목**이라,
서버가 오기 전에 확정해 둘 수 있는 부분이 실제로 크다.

## 10. 환경 변수

정의는 spec §12에 있다.

**새 변수를 만들지 않는다.** 지도 SDK는 카카오 로그인이 이미 쓰고 있는
`KAKAO_NATIVE_APP_KEY`를 그대로 쓴다 — 카카오는 로그인과 지도가 같은 네이티브 앱 키를
공유한다.

```
--dart-define=KAKAO_NATIVE_APP_KEY=...   # 기존 값 재사용
```

`lib/domain/auth/repository/sns_config.dart`가 이미 이 값을 읽고 있다. 지도 초기화도 같은
값을 참조하되, **auth 모듈에 의존하지 않도록** 공용 위치에서 읽는 형태를 검토한다 —
`map`이 `auth`를 import하면 도메인 경계가 무너진다.

### 네이티브 설정

- **Android** — 기존 `AndroidManifest.xml`에 카카오 로그인용 `meta-data`와
  `kakao{앱키}` 스킴이 **이미 등록돼 있다.** 지도 SDK가 요구하는 항목만 추가하고,
  중복 등록하지 않도록 기존 항목을 먼저 확인한다.
- **iOS** — `Info.plist`도 같은 방식으로 확인 후 추가한다.
- 키를 소스에 하드코딩하지 않는다. 현재 매니페스트에 앱 키가 스킴 문자열로 박혀 있는데,
  이는 카카오 SDK 규약상 불가피한 부분이라 그대로 두고 **새로 추가하는 값은 하드코딩하지
  않는다.**

`sns_initializer.dart`가 키가 비었을 때 SDK 초기화를 건너뛰고 로그로 알리는 방식을 쓴다.
지도도 같은 방침을 따라, 키가 없으면 지도 화면이 안내를 표시하고 앱 전체를 죽이지 않는다.

`[TBD]` 값은 실기기 측정이 정확하다. 정해지면 `[AMEND] SPEC-0014: ...`로 이슈에 회신한다.
