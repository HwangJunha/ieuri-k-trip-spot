# SPEC-0015 — 클라이언트 설계

요구사항·수용 기준·계약은 spec에 있다. 여기에는 클라이언트 쪽 설계 판단만 적는다.

관련 이슈: `HwangJunha/ieuri-k-trip-spot#44`
브랜치: `feature/SPEC-0015-region-recommendation`

---

## 1. 배치 — 기존 map 피처에 넣는다

`lib/domain/map/` 안에 둔다. 새 피처 디렉토리를 만들지 않는다.

추천의 귀결이 **지도 카메라 이동**이라 map과 분리하면 두 피처가 서로의 컨트롤러를 참조하게
된다. 지역 추천은 독립 기능이 아니라 지도의 진입 경로 중 하나다.

```
lib/domain/map/
  model/       region_recommendation.dart · region_score.dart
  provider/    region_recommendation_provider.dart
  repository/  기존 map_repository에 연산 추가
  view/        region_recommendation_screen.dart
  component/   region_card.dart · score_breakdown.dart
```

기존 `map_repository`에 연산을 더한다. 새 repository를 만들면 같은 GraphQL 엔드포인트에
대해 두 개가 생긴다.

## 2. 화면

### 2.1 목록

총점 순으로 지역 카드를 쌓는다. 카드 하나가 시군구 하나다.

카드에 들어가는 것:

| 요소 | 출처 |
|---|---|
| 지역명 | `name` (서버가 활성 언어로 제공) |
| 시도명 | `provinceName` — 같은 이름의 시군구를 구분한다 |
| 총점 | `totalScore` |
| 항목별 점수 | `scores` |
| 기준 시점 | `dataBasisAt` |

**시도명을 함께 보여주는 이유** — 같은 이름의 시군구가 실제로 여럿 있다(중구·남구·동구 등).
지역명만 있으면 어디인지 알 수 없다.

### 2.2 항목별 점수 표시 — 총점만 보여주지 않는다

R23. 총점만으로는 **왜 이 지역이 추천됐는지 알 수 없다.** "여기가 추천됐다"와 "덜 붐비고
가깝기 때문에 추천됐다"는 사용자에게 전혀 다른 정보다.

항목이 최대 5개이고 각각 0~100이라 막대 형태가 자연스럽다. 다만 **결측 항목을 0점 막대로
그리지 않는다** — 서버가 결측 항목을 목록에서 빼서 주므로(spec §7.5) 없는 항목은 자리를
비우거나 부재로 표기한다. 0으로 그리면 서버가 피한 왜곡을 화면이 되살린다.

**`scoreFactorCount`를 함께 쓴다.** 총점은 존재하는 항목만으로 계산되므로, 항목 3개로 나온
80점과 5개로 나온 80점은 근거의 두께가 다르다(서버 설계 §3.5). 이 값이 작을수록 근거가
얕다는 뜻이므로 신뢰도 표현에 쓴다.

숫자를 그대로 노출할 필요는 없다 — "일부 데이터 기준" 정도의 표현으로 충분하다. 다만
**항목 수 차이를 화면에서 완전히 감추지는 않는다.** 감추면 두 점수가 같은 근거에서 나온
것처럼 보인다.

### 2.3 "지금 한산함"으로 쓰지 않는다

R24. 이것이 이 화면에서 가장 틀리기 쉬운 지점이다.

서버가 주는 값은 **향후 예측(집중률)과 측정된 과거 데이터**에서 나온 점수다. 전국 실시간
혼잡 데이터는 존재하지 않는다(spec §3).

| 쓰지 않는 표현 | 쓰는 표현 |
|---|---|
| 지금 한산함 · 현재 여유 | 덜 붐빌 것으로 예상 |
| 실시간 | (기준 시점) 기준 |

`dataBasisAt`을 화면에 표시한다(POL-038). SPEC-0014의 혼잡도가 "N시 M분 기준"을 표시한 것과
같은 처리이며, 그쪽은 30분 지연, 이쪽은 예측이라는 차이만 있다.

## 3. 카메라 이동

지역을 선택하면 지도 화면으로 이동하고 `center`로 카메라를 옮긴다.

SPEC-0014가 이미 `CameraUpdate.newCenterPosition`을 쓰고 있다(`map_screen.dart`의 내 위치
이동·검색 결과 이동). **같은 경로를 재사용한다.**

### 3.1 줌 레벨 — 미결

spec §8 5번. 두 방식이 있다.

| 방식 | 판단 |
|---|---|
| 고정 줌 | 시군구 면적 편차가 커서(종로구 vs 홍천군) 어떤 곳은 넘치고 어떤 곳은 점처럼 보인다 |
| 폴리곤 bbox 기반 계산 | 지역마다 맞지만 서버가 bbox를 내려줘야 한다 |

현재 계약은 `center`만 준다. bbox 기반으로 가려면 계약에 bbox를 추가해야 하므로 **결정 전까지
고정 줌으로 두고, 실사용에서 편차가 문제되면 `[AMEND]`로 요청한다.**

서버는 이미 경계 폴리곤을 적재하므로 bbox 추가는 데이터 문제가 아니라 계약 문제다.

### 3.2 이동 후 조회는 기존 경로다

카메라가 옮겨지면 SPEC-0014의 뷰포트 조회가 유휴 판정 후 자동으로 실행된다(POL-037). **추천
화면이 spot을 직접 조회하지 않는다.**

시군구 면적이 서버의 뷰포트 면적 상한(`max-area-square-degrees` 기본 4.0)보다 훨씬 작아
기존 조회가 그대로 받는다(spec §7.2).

## 4. 위치 권한

### 4.1 없어도 동작한다

R27. 위치 권한이 없거나 거부되면 `origin` 없이 요청한다. 서버가 거리 항목을 빼고 나머지로
산출해 준다(R21).

**추천 자체를 막지 않는다.** 다섯 항목 중 넷은 위치와 무관하다.

### 4.2 거리순이 아님을 오해하게 두지 않는다

이것이 위치 관련 판단에서 중요한 부분이다.

거리는 **필터가 아니라 점수 항목**이다(spec §7.6). 반경으로 잘라내지 않으므로 목록에는
가까운 곳이 주로 오되 **조금 멀어도 다른 항목이 뚜렷하게 나은 곳이 섞인다.**

사용자가 이것을 거리순 목록으로 오해하면 "왜 더 가까운 데를 안 보여주지"로 읽힌다. 목록이
**종합 점수 순**임이 화면에서 드러나야 한다. 거리 점수를 항목별 표시에 포함하는 것이
1차적인 해소책이다.

위치 없이 받은 결과에서는 거리 항목이 부재로 표기된다(R27).

## 5. 상태와 실패

### 5.1 빈 결과는 정상이다

R15 · spec §7.8. 배치가 데이터를 충분히 쌓기 전에는 추천이 성립하지 않는다.

**빈 결과를 오류 화면으로 그리지 않는다.** "아직 추천할 데이터가 없다"는 안내가 맞다. 오류로
그리면 사용자가 재시도를 반복하고, 재시도로는 해결되지 않는다.

**빈 결과에도 두 상태가 있다**(R20 · 계약의 `dataBasisAt`).

| `dataBasisAt` | 뜻 | 안내 |
|---|---|---|
| null | 적재된 데이터가 아직 없다 | "데이터를 모으는 중" |
| 값 있음 | 데이터는 있으나 조건을 만족한 지역이 없다 | "조건에 맞는 지역이 없다" |

둘을 같은 문구로 뭉뚱그리면 사용자가 기다려야 하는 상황인지 조건을 바꿔야 하는 상황인지
알 수 없다.

### 5.2 재시도는 횟수로 제한한다

R28 · POL-040. 시간 기반이 아니라 횟수 상한이다. 응답 시간 목표(POL-029)에 근거가 없는 동안
시간 기반 수치는 근거 없는 값이 된다.

SPEC-0006이 같은 처리를 했고 그것이 POL-040의 출처다.

## 6. 생성 타입 누출 금지

POL-020. `graphql_codegen`이 만든 타입은 repository 밖으로 나가지 않는다. repository가
도메인 모델로 매핑한다.

특히 `RegionScoreFactor` enum은 **생성 enum을 그대로 provider·view로 넘기지 않는다.** 도메인
enum으로 옮긴다 — 서버가 항목을 추가하면 생성 타입이 바뀌는데, 그것이 화면 코드까지 번지면
계약 변경이 UI 변경으로 직결된다.

---

## 7. 테스트 — provider · 도메인 모델 계층만

위젯 테스트와 통합 테스트는 범위 밖이다(플랫폼 방침).

| 단위 | 지는 기준 |
|---|---|
| 추천 목록 상태 | R22 — 총점 순 유지 |
| 표시 모델 변환 | R23 — 항목별 점수 보존 |
| 기준 시점 포함 | R24 — `dataBasisAt`이 표시 모델에 포함 |
| 실시간 문구 부재 | R24 — 실시간을 뜻하는 문구가 없음 |
| 카메라 이동 요청 | R25 · R26 — 좌표와 줌이 함께 요청됨 |
| 위치 권한 부재 | R27 — 위치 없이 요청, 거리 항목 부재 표기 |
| 재시도 상한 | R28 — 상한 횟수를 넘지 않음 |
| 결측 항목 표시 | §2.2 — 0점 막대로 그리지 않음 |
| 산출 항목 수 반영 | R31 · §2.2 — `scoreFactorCount`가 표시 모델에 보존됨 |
| 빈 결과의 두 상태 | §5.1 — `dataBasisAt` 유무로 안내가 갈림 |

**인프라로만 관측 가능해 테스트하지 않는 것**: 실제 지도 SDK의 카메라 이동, 실 GraphQL 전송,
위치 권한 다이얼로그. 카메라 이동은 **컨트롤러에 전달되는 인자**를 검증하고 SDK 동작 자체는
신뢰한다 — SPEC-0014가 같은 방식을 썼다.

## 8. 남은 결정

spec §8의 미결 중 클라이언트 소관은 5번(줌 레벨 결정 방식)뿐이다. §3.1대로 고정 줌으로
시작하고, 편차가 실사용에서 문제되면 계약에 bbox 추가를 `[AMEND]`로 요청한다.

## 9. 구현 중 바뀐 것 (2026-08-11)

### 9.1 repository는 아직 서버에 연결되지 않았다

`fetchRecommendedRegions`는 인터페이스와 매핑 헬퍼까지만 있고 구현체는
`UnimplementedError`를 던진다.

작업 시점에 **GraphQL 서버가 떠 있지 않았고**(localhost:8888 응답 없음) introspection
스냅샷에도 `recommendedRegions`가 없었다. 계약 초안(`Specs/SPEC-0015/contract.graphql`)만
보고 연산을 쓰면 서버가 소유한 실제 스키마와 어긋난다(CLAUDE.md §13) — 과거
`signUp`/`login`을 지어냈다가 서버의 `registerEmailMember`/`loginEmail`과 달랐던 것이 같은
실패다. **추측하지 않고 비워 두는 쪽**을 골랐다.

연결할 때 할 일은 세 가지다: `map_operations.graphql`에 쿼리 추가 →
`map_schema.graphql`에 실제 SDL 반영 후 build_runner → `_query` 호출부 연결. 매핑 헬퍼
(`factorFrom` 등)는 계약 초안 기준으로 이미 작성돼 있다.

**그때까지 이 화면은 실행 시 항상 오류 상태로 그려진다.** 목록·빈 결과 경로는 서버가
배포된 뒤에야 실제로 도달한다.

### 9.2 재시도 상한을 목록 provider 밖으로 뺐다

§5.2의 "횟수 상한"은 그대로다. 다만 **횟수를 목록 provider 안에 두지 않는다** —
`regionRecommendationRetryCountProvider`가 따로 센다.

provider의 생명주기(autoDispose 폐기·재생성, 지연 빌드)에 횟수를 얹으면 "몇 번 조회했나"가
구독 상태에 따라 달라진다. 실제로 **재시도 한 번에 요청이 두 번 나가거나, 상한 3회를 넘겨
네 번째가 나가는 것**을 측정했다. 상한을 세도 서버가 받는 요청 수가 달라지면 R28은
무의미해진다.

횟수는 누른 사람이 세는 값이지 조회 상태의 일부가 아니다. 화면이 `canRetry`를 보고
`record()`한 뒤 `ref.invalidate(regionRecommendationsProvider)`로 다시 조회한다.
