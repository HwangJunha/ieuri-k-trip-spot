# SPEC-0017 — 피드와 다이렉트 메시지 (클라이언트 설계)

요구사항·수용 기준·계약은 원본 스펙에 있다. 이 문서는 **클라이언트 구현 결정만** 담으며 요구사항은
번호로만 참조한다.

## 구조

`lib/domain/feed/{component,model,provider,repository,view}` 를 신설한다. 커뮤니티(`lib/domain/community`)와
분리한다 — 피드와 커뮤니티는 제품상 격리된 개념이고, 한 디렉터리에 두면 화면·모델·provider가 서로
스며든다.

DM은 피드 하위에 둔다(`feed/view/conversation_*`). 진입점이 피드 작성자뿐이라 독립 도메인으로
세울 근거가 없다(R7).

생성된 GraphQL 타입은 **repository 밖으로 나가지 않는다**(POL-020). repository가 도메인 모델로
매핑한다.

## 설계 결정

### 1. 세그먼트 토글은 제스처 표면 밖에 둔다 (R5)

둘러보기 탭 상단에 추천↔피드 세그먼트 토글을 둔다. **토글은 제스처 표면 위 오버레이가 아니라 별도
헤더다.**

두 화면 모두 전면 제스처를 쓴다 — 추천은 스와이프 카드(SPEC-0002/0006), 피드는 세로 스크롤. 토글을
제스처 표면 위에 겹치면 토글 탭과 카드 드래그·스크롤 시작이 같은 영역에서 경합한다. 헤더로 분리하면
경합 자체가 생기지 않는다.

기존 스와이프 추천 화면은 **제거하지 않는다.** 토글의 한쪽으로 남는다(AC5-2). 각 화면의 상태는 토글
전환 후에도 유지하며, 한쪽의 실패가 다른 쪽을 막지 않는다(AC5-3).

### 2. 피드는 목록을 제공하지 않는다 (R4)

한 번에 한 건이 화면을 채우는 세로 전면 스크롤이다. 그리드·목록 뷰를 만들지 않는다 — 비범위이며,
목록이 없다는 것이 이 화면의 성격이다.

다음 페이지는 `pageInfo.hasNextPage`로 판정한다. **총 개수는 내려오지 않으므로** "N개 중 M번째" 같은
표현을 만들지 않는다. 서버가 주지 않는 값을 클라이언트가 추정하지 않는다.

프리페치는 현재 항목 기준 앞쪽 일부만 한다. 사진이 1~5장씩 붙는 화면이라 과도한 선반입은 메모리와
대역폭을 함께 소모한다.

### 3. 좋아요와 메시지 전송은 낙관적 업데이트 (R6·R9)

책임분리표에 따라 낙관적 업데이트와 롤백은 클라이언트 몫이다.

- 좋아요 — 즉시 반영하고, 실패 시 이전 상태로 되돌린다. 서버 연산이 멱등이므로 중복 탭이 수를
  어긋내지 않는다
- 메시지 — 전송 중 상태로 즉시 말풍선을 그리고, 실패 시 실패 표시와 재시도 수단을 남긴다.
  **조용히 사라지지 않는다**

재시도는 **횟수로 제한한다**(POL-040). 시간 기반 백오프 수치는 근거가 없다.

### 4. 작성 폼의 필수 조건은 제출 전에 막는다 (R1·R2)

spot 1곳과 사진 1장 이상이 갖춰지기 전에는 제출 버튼을 활성화하지 않는다. 서버가 같은 규칙을 다시
판정하지만(책임분리표: 데이터 무결성 검증은 서버, 클라이언트는 UX용 미러링), 제출 후 오류로
돌려보내는 것은 나쁜 경험이다.

spot 피커는 **기존 `searchSpots` 흐름을 재사용한다**(SPEC-0013). 커뮤니티 작성 화면이 이미 쓰고 있는
경로이며, 새로 만들면 검색 동작이 두 벌이 된다.

사진은 사전 서명 URL로 직접 PUT하고 확정 키만 제출한다(POL-042). 업로드 실패 시 어느 장에서 실패했는지
알 수 있어야 한다 — 5장 중 3장째 실패를 "업로드 실패"로 뭉뚱그리지 않는다.

### 5. 타이핑 표시는 반드시 자동으로 해제된다 (R10)

이것이 이 화면에서 가장 틀리기 쉬운 지점이다.

타이핑 이벤트는 **유실될 수 있다** — 전달 보장이 없고 재연결해도 재전송되지 않는다(계약에 명시).
"입력 중" 표시를 이벤트로만 켜고 끄면, 마지막 이벤트가 유실되는 순간 화면이 영원히 "입력 중"에
갇힌다.

따라서 표시는 **마지막 이벤트 수신 시각 기준 타임아웃으로 자동 해제한다**(AC10-4). 서버가 "멈췄다"는
이벤트를 보내주기를 기다리지 않는다. `TypingEvent.emittedAt`이 이 판단을 위해 존재한다.

입력 중일 때 `notifyTyping`을 보내되 **키 입력마다 보내지 않는다.** 일정 간격으로 throttle한다.

WebSocket 재연결은 클라이언트 책임이며, 시도 횟수를 상한으로 둔다(POL-040). 재연결 후 과거 타이핑
이벤트는 오지 않는다 — 정상이다.

### 6. DM 진입점은 피드에만 노출한다 (R7)

피드 작성자 프로필·피드 항목에서만 DM 진입점을 보인다. **커뮤니티 글 작성자에게는 노출하지 않는다.**

서버가 구조적으로 막고 있지만(입력이 `feedItemId`), 클라이언트가 진입점을 보여주고 서버가 거부하는
것은 사용자에게 고장으로 보인다. 보이지 않는 것이 맞다.

### 7. 대화 메시지는 로컬에 캐시한다 (R18)

**서버가 원본이고 로컬은 사본이다.** 로컬을 원본으로 두는 설계(카카오톡식)는 동기화·충돌·백업을
직접 만들어야 해서 이번 범위를 넘는다.

- 대화를 다시 열면 캐시된 메시지를 **즉시** 그리고, 서버 조회는 그 뒤에 얹는다. 빈 화면을 거치지
  않는다(AC18-1)
- 캐시가 비어 있어도 정상 동작한다(AC18-4). **캐시는 최적화이지 동작의 전제가 아니다**
- **서버의 6개월 보관 기간이 로컬 기록을 지우지 않는다**(AC18-3). 서버에서 사라진 과거 메시지가
  로컬에 남아 있으면 그대로 보여준다. 서버에 없다는 이유로 기기의 기록을 삭제하지 않는다

로컬 캐시 정리 정책은 이번 스펙에서 정하지 않는다 — 용량이 문제가 되면 그때 다룬다. 지금 근거 없는
상한을 박지 않는다(POL-044).

### 8. 차단·신고 UI는 기존 것을 쓴다 (R11·R12·R15)

피드 신고는 커뮤니티의 기존 시트를 재사용하고 대상 타입만 `FEED_ITEM`으로 넓힌다.

**DM 신고는 다르다.** 메시지 단위 다중 선택이 필요하다(R15) — 대화 화면에서 메시지 여러 건을 골라
한 번에 신고한다. 기존 단건 신고 시트로는 표현되지 않으므로 선택 모드를 별도로 둔다.

- 선택 0건이면 신고 버튼이 활성화되지 않는다(AC15-3을 UX에서 먼저 막는다)
- 자기 메시지는 선택 대상에서 제외한다(AC15-5)
- 한 대화 안에서만 선택 가능하므로 대화 혼재(AC15-4)는 화면 구조상 발생하지 않는다

**`ReportTargetType`을 default 없이 전수 분기하는 코드가 있으면 열거값 추가 시점에 깨진다.** 계약은
가산적이지만 생성 타입을 `switch`로 전수 처리한 곳은 클라이언트 책임이다. 신고 관련 분기를 점검하고
알 수 없는 값에 대한 기본 동작을 둔다.

차단 목록 진입점은 **설정에 있다**(SPEC-0011 선례). 피드 화면에 새로 만들지 않는다.

### 9. 다국어 (POL-022)

UI 문구는 영어 우선 EN/KO/JA/ZH다. spot 이름 등 데이터 고유명사는 서버가 내려준다(POL-039) —
클라이언트 번역 파일에 넣지 않는다.

상대 시간 표기("3분 전")는 클라이언트가 만든다. 서버는 ISO-8601만 준다.

## 테스트

CLAUDE.md 테스트 범위표에 따라 **provider/notifier와 도메인 모델 로직만** 대상이다. 위젯·통합
테스트는 요구하지 않는다.

| 단위 | 대상 요구사항 |
|---|---|
| 피드 작성 폼 상태 — spot·사진 충족 여부에 따른 제출 가능 판정 | R1·R2 |
| 좋아요 notifier — 낙관적 반영과 실패 시 롤백 | R6 — AC6-1 |
| 메시지 전송 notifier — 전송 중·실패 상태 전이, 재시도 횟수 상한 | R9, POL-040 |
| 타이핑 표시 notifier — **타임아웃 자동 해제** | R10 — AC10-4 |
| 피드 페이지네이션 provider — 커서 이어읽기, 소진 판정 | R4 — AC4-2, AC4-4 |
| 토글 상태 — 전환 후 양쪽 화면 상태 유지, 한쪽 실패 격리 | R5 — AC5-1~5-3 |
| repository 매핑 — 생성 타입 → 도메인 모델 | POL-020 |
| 로컬 캐시 — 캐시 우선 표시, 캐시 부재 시 서버 폴백, 서버 부재 메시지 유지 | R18 — AC18-1, AC18-3, AC18-4 |
| 신고 선택 상태 — 0건 시 비활성, 자기 메시지 제외 | R15 — AC15-3, AC15-5 |

타임아웃 자동 해제 테스트는 **가짜 시계로 검증한다.** 실제 시간을 기다리지 않는다.

WebSocket 연결·실제 구독 수신·이미지 업로드 전송은 테스트하지 않는다 — 인프라 경계이며 범위 밖이다.

## 구현 기록

### 서버 계약 확정으로 추가된 것 (2026-08-13)

서버 구현이 끝나 라이브 스키마로 대조했다. **이 문서의 기존 내용에 틀린 것은 없었고**,
서버가 구현 중 확정한 넷이 빠져 있어 아래를 더한다.

**1. 피드 인용은 대화가 아니라 메시지에 붙는다.** `Conversation.originFeedItem`은 **없다** —
인용은 `Message.feedItem`이다. 같은 상대와의 방은 하나인데 인용할 피드는 여러 개라, 방 상단에
고정하면 틀린 맥락이 뜬다. **말풍선마다** 그린다(인스타그램 스토리 답장과 같은 형태).
피드가 삭제되면 `feedItem`이 null이 되지만 **말풍선 자체는 보여야 한다** — 숨기면 대화 기록이
사라진다. 모델에서 `Conversation.originFeedItem`을 제거했다.

**2. DM 사진 전송이 있다.** `sendMessage(conversationId, body, feedItemId, photoKey)`.
업로드 경로는 **피드와 완전히 같다**(`createPostImageUploadUrls` → PUT → `confirmPostImageUploads`)
— DM 전용 업로드 뮤테이션은 없어서, repository가 커뮤니티 오퍼레이션을 그대로 재사용한다.

  **`body`가 `String!`이라 사진만 보낼 때도 빈 문자열을 넘긴다.** 생략하면 GraphQL 검증에서
  실패한다. 셋(`body`·`feedItemId`·`photoKey`)이 다 비면 서버가 거부하므로 그 조합만 클라이언트가
  먼저 막는다. 반대로 **빈 `body`를 "본문 없음"으로 보고 말풍선을 접으면 안 된다** — 첨부만
  보낸 메시지가 화면에서 사라진다.

**3. `newMessage` 구독이 있다 — 폴링을 만들지 않는다.** 대화 화면은 구독을 **둘** 연다
(`typingIndicator`·`newMessage`). 셋을 지킨다:
  - **전달 보장이 아니라 신호다.** 끊긴 동안의 메시지는 오지 않으므로 재연결 때마다
    `conversationMessages`로 공백을 메운다. 타이핑은 버려도 되지만 메시지는 안 된다
  - **자기 메시지도 에코된다**(다른 기기에서 보낸 경우). `Message.id`로 dedupe하지 않으면 내
    메시지가 두 번 뜬다. 에코가 전송 응답보다 **먼저** 올 수 있어, 그때는 낙관적 말풍선을
    걷어내고 에코를 남긴다
  - **구독 실패는 `errors[]`로 온다.** `FORBIDDEN`에는 재연결하지 않는다 — 재시도로 풀리지
    않고 상한까지 헛돈다

**4. `unreadCount`가 실제로 동작하고 읽음 처리 뮤테이션이 생겼다.**
`markConversationRead(conversationId, upToMessageId)`. **조회만으로는 읽음이 되지 않는다** —
목록 미리보기나 알림에서 스쳐 본 것이 읽음이 되면 사용자가 메시지를 놓치기 때문이다.

  호출 시점은 서버가 클라이언트에 위임했다. **이 앱은 대화 화면에 진입할 때 한 번 부르고,
  `upToMessageId`를 생략해 "모두 읽음"으로 보낸다** — 마지막 메시지 id를 몰라도 부를 수 있고,
  화면에 들어온 이상 그 대화는 읽은 것으로 보는 편이 사용자의 기대와 맞다. 멱등이라 중복
  호출이 안전하고, 페이로드가 잔여 수를 주므로 재조회하지 않는다.

**그 밖의 확정 사항:** 메시지 페이지 기본값은 **30**(피드·대화는 20), 상한 초과는 오류가 아니라
절삭, `ReportTargetType`에 `FEED_ITEM`이 추가됨(DM 신고는 이 열거형이 아니라 `reportMessages`),
WebSocket은 HTTP와 **같은 `/graphql` 경로**에 `graphql-transport-ws` 프로토콜이며 인증은
`connection_init` 페이로드의 `Authorization: Bearer <token>`(접두어 필수).

### 서버 미배포로 인한 단계 분리 (2026-08-12)

**서버의 SPEC-0017이 아직 배포되지 않았다.** 라이브 스키마에 `feed`·`feedItem`·`conversations`·
`conversationMessages`, 7개 뮤테이션, `Subscription` 루트가 모두 없고 `ReportTargetType`에도
`FEED_ITEM`이 없다. 계약서(`Specs/SPEC-0017/contract.graphql`)는 **제안이고 스키마는 서버가
소유하므로**(CLAUDE.md §13), 지금 오퍼레이션을 쓰면 검증을 통과하지 못해 codegen이 실패한다.

그래서 **서버에 의존하지 않는 층부터** 구현했다. `FeedRepository`는 인터페이스만 두고
`feedRepositoryProvider`가 `UnimplementedError`를 던진다 — 서버가 배포되면 구현체를 채우는
것으로 끝나고 provider·화면은 손대지 않는다. 테스트는 이 provider를 오버라이드한다.

**이 단계는 끝났다**(2026-08-13). 서버 배포 후 `.graphql` 오퍼레이션 + `feed_schema.graphql`,
`FeedRepositoryImpl`, WebSocket 전송을 모두 채웠고 `feedRepositoryProvider`가 실제 구현을
돌려준다. 예상대로 provider·모델은 거의 손대지 않았다 — 경계를 인터페이스로 끊어 둔 값이다.

**남은 일:** `view/`·`component/`(화면), ARB 4개 언어 문구.

### 결정 기록

- **업로드 프로토콜 모델을 `common/`으로 올렸다.** `composer_photo.dart`와
  `post_image_upload.dart`가 커뮤니티에만 있었는데 피드도 같은 사전 서명 URL 흐름을 쓴다
  (POL-042). 교차 기능 import는 금지이고(§3) 복제하면 같은 모양에 이름이 둘 생기므로
  `common/model/`로 옮겼다(§4). 기존 import는 모두 갱신했다
- **`ConversationController.build`는 동기다.** 캐시 읽기가 즉시 끝나므로 화면이 첫 프레임부터
  캐시된 대화를 그린다(AC18-1). 서버 조회는 화면이 `sync()`를 불러 그 위에 얹는다 — build를
  await로 막으면 캐시가 있어도 빈 화면이 한 번 지나간다. build 도중 상태를 바꾸는 것은
  Riverpod이 금지하므로 호출 시점을 화면이 갖는다
- **`TypingSignal`의 상태는 `DateTime?`이 아니라 epoch 마이크로초 정수다.** riverpod_generator가
  nullable 상태의 notifier를 만들지 못한다 — 표현이 아니라 도구의 제약이다
- **`FeedMutationResult.errorCode`는 열거형이 아니라 문자열이다.** 계약이 가산적이라 서버가 새
  코드를 더할 수 있고, 열거형으로 전수 분기하면 그 시점에 깨진다(설계 §8과 같은 이유).
  `ReportTargetType`을 전수 분기하는 곳은 현재 코드에 없음을 확인했다
