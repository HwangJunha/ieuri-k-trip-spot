# SPEC-0022 — 커뮤니티 글 작성 자동 저장 (클라이언트 설계)

요구사항과 수용 기준은 스펙에 있습니다. 이 문서는 이 레포에서의 설계만 다룹니다.

## 1. 무엇이 달라지는가

`PostComposer`는 지금 `autoDispose`이고, 그 선택은 의도된 것이었습니다 — 모델 파일에 "컴포저를 닫으면 초안이 사라지는 것이 맞다"고 적혀 있습니다. SPEC-0022가 그 판단을 철회하므로, **해당 주석과 그 전제를 함께 고칩니다.** 주석만 남으면 다음 사람이 상충하는 두 근거를 읽게 됩니다.

`autoDispose` 자체는 유지합니다. 초안이 살아남는 곳을 프로바이더의 수명이 아니라 **디스크**로 옮기는 것이 이 설계의 핵심입니다. 프로바이더를 `keepAlive`로 바꾸면 앱 종료를 견디지 못해 R3를 만족하지 못하고, 화면 밖에서 컴포저 상태가 계속 살아 있는 부작용만 생깁니다.

## 2. 저장 계층

초안 저장은 커뮤니티 도메인 밖에 둡니다. 사진 바이트를 파일로 쓰는 일은 커뮤니티 고유의 관심사가 아니고, `ComposerPhoto`가 이미 `common/model/`에 있어 피드 컴포저와 공유되던 전례를 따릅니다.

```
lib/common/storage/
  draft_store.dart          — 추상 포트. 저장·복원·삭제·TTL 판정
  draft_store_impl.dart     — 구현. shared_preferences + 앱 전용 디렉토리
```

**두 저장소를 나눠 씁니다.** 텍스트 계열(카테고리·장소·제목·본문·태그·사진 메타·저장 시각)은 `shared_preferences`에 JSON 한 덩어리로, 사진 바이트는 `path_provider`가 주는 앱 전용 디렉토리에 파일로 씁니다. 바이트를 JSON에 base64로 넣지 않는 이유는 사진 5장이면 최대 50MiB이고, `shared_preferences`는 그 크기를 담으라고 만든 물건이 아니기 때문입니다 — 로드가 동기적으로 일어나 앱 시작이 느려집니다.

`flutter_secure_storage`는 쓰지 않습니다. 토큰용이고(POL-008), 초안은 기기 소유자 본인의 작성 중 콘텐츠라 암호화 저장 대상이 아닙니다(스펙 §7 POL-012 판정). 앱 전용 디렉토리는 OS가 이미 다른 앱으로부터 격리하므로 R12는 그것으로 충족됩니다.

`path_provider`는 현재 `pubspec.yaml`에 없으므로 **추가가 필요합니다.** `shared_preferences`와 `image_picker`는 이미 있습니다.

## 3. 저장 형식

`PostDraft`를 그대로 직렬화하지 않고 저장 전용 모델을 둡니다. `PostDraft.photos`는 `ComposerPhoto` sealed 타입이고 `LocalPhoto`가 `Uint8List`를 들고 있어 그대로는 JSON이 되지 않습니다.

```
StoredDraft
  savedAt        DateTime      — TTL 판정 기준 (R8)
  category       String?       — TargetCategory의 식별자
  spotId         String?
  spotTitle      String?
  title          String
  body           String
  tags           List<String>
  photos         List<StoredPhoto>   — 순서가 표시 순서 (R3-4)

StoredPhoto  (sealed, ComposerPhoto와 1:1 대응)
  StoredRemotePhoto  objectKey
  StoredLocalPhoto   id · name · contentType · contentLength
```

구현에서 `StoredLocalPhoto`의 필드가 설계와 조금 달라졌습니다. `fileName`을 값으로
들고 있지 않고 **`id`에서 유도하는 계산 속성**으로 두었습니다 — 두 값을 함께 저장하면
어긋날 수 있고, 어차피 §4가 "파일 이름은 `LocalPhoto.id`에서 유도한다"고 정하고
있어서 저장할 이유가 없습니다. 유도할 때 파일 이름으로 쓸 수 없는 문자를 `_`로
바꿉니다 — 사진 선택기가 만든 id에 경로 구분자가 섞이면 앱 전용 디렉토리 밖을 가리킬
수 있습니다. 표시 이름(`name`)은 `LocalPhoto`에 있는 이름 그대로 함께 저장합니다 —
복원 후 업로드가 실패했을 때 사용자에게 보여줄 이름이 없으면 안 됩니다.

`StoredLocalPhoto`는 바이트를 담지 않고 **파일 이름만** 가집니다. 실제 바이트는 별도 파일입니다. 복원 시 파일을 읽어 `LocalPhoto`로 되돌립니다.

`contentLength`를 저장해 두고 복원 후 실제 읽은 바이트 길이와 **대조합니다.** 어긋나면 그 초안은 복원 불가로 처리합니다(R10). 이 값은 사전 서명에 들어가므로 1바이트만 달라도 스토리지가 403을 냅니다 — 등록 시점이 아니라 복원 시점에 잡아야 합니다.

복원 불가는 **`DraftStore`가 타입 있는 결과로 알립니다** — 예외를 던지거나 null을 반환하지 않고, "정상 · 형식 해석 불가 · 사진 파일 없음 · 길이 불일치"를 구분해 돌려줍니다. 파일 존재 여부는 파일 시스템의 사실이라 매핑 계층이 관찰할 수 없고, 포트가 알려 줘야 notifier가 스텁만으로 R10-2를 판정할 수 있습니다.

`category`는 `TargetCategory`의 식별자 문자열로 저장합니다. 서버 주도 목록이라 저장 당시의 카테고리가 나중에 사라질 수 있고, 그 경우 해당 값만 null로 복원한 뒤 사용자가 다시 고르게 합니다 — 초안 전체를 버리지 않습니다.

## 4. 저장 시점

`PostComposer`의 상태가 바뀔 때마다 디스크에 쓰면 타이핑 한 글자마다 파일 I/O가 일어납니다. **디바운스를 겁니다.**

- 상태 변경 후 **2초** 동안 추가 변경이 없으면 저장
- 컴포저 화면이 dispose될 때 즉시 저장 (디바운스 대기 중인 변경을 흘리지 않기 위해)
- 앱이 백그라운드로 갈 때 즉시 저장 (`AppLifecycleState.paused`) — OS가 이 뒤에 앱을 죽여도 마지막 상태가 남습니다

사진 바이트는 목록이 바뀔 때만 씁니다. 제목 한 글자 때문에 50MiB를 다시 쓰지 않도록, 텍스트 저장과 사진 저장을 분리합니다. 파일 이름은 `LocalPhoto.id`에서 유도해, 이미 쓰여 있는 사진은 다시 쓰지 않습니다.

빈 초안은 저장하지 않습니다(R1-3). 여섯 요소가 모두 비어 있으면 저장 대신 삭제를 호출합니다 — 그래야 "다 지웠는데도 이어쓰기를 묻는" 상태가 생기지 않습니다.

## 5. 복원 흐름

복원은 컴포저를 여는 시점에 한 번 판정합니다.

```
컴포저 진입 (신규 모드)
  └ 초안 있음?
      ├ 없음         → 빈 상태로 시작
      └ 있음
          ├ TTL 초과(30일)   → 삭제, 빈 상태로 시작        (R8)
          ├ 복원 불가        → 삭제, 빈 상태로 시작        (R10)
          └ 정상             → 이어쓰기 제안               (R5)
                                ├ 이어쓰기 → 상태 채움
                                └ 버리기   → 삭제, 빈 상태
```

수정 모드는 이 분기에 아예 들어오지 않습니다(R11). 컴포저가 이미 신규/수정을 구분하고 있으므로, 수정 모드에서는 저장도 복원도 호출하지 않습니다. 수정 모드 진입이 기존 초안을 지우지도 않습니다(R11-3).

이어쓰기 제안은 화면 진입 직후의 상태로 표현합니다. 다이얼로그를 띄우되, 판정이 끝났다는 사실을 컴포저 상태에 남겨 **복원 이후의 저장이 제안 상태를 되살리지 않게** 합니다(R5-4). 복원한 초안이 곧바로 다시 저장되므로, 이 표시가 없으면 "초안 있음" 조건이 계속 참이 됩니다.

**다이얼로그 밖을 눌러 닫으면 초안을 지우지 않습니다.** 구현하면서 정한 것으로,
이어쓰기·버리기 둘 다 고르지 않은 것이므로 아무 결정도 하지 않은 것으로 봅니다 —
실수로 닫았는데 글이 사라지면 이 기능의 취지가 무너집니다. 다만 판정이 끝났다는
표시는 남겨 이후의 저장이 제안을 되살리지 않게 합니다(R5-4). 초안은 그대로 있으므로
화면을 다시 열면 그때 다시 묻습니다.

TTL 판정은 복원 시점의 비교 한 번입니다. 별도 스케줄러나 백그라운드 정리 작업을 두지 않습니다 — 초안이 단건이라 덮어쓰기가 누적을 막고, 남는 경우는 등록 성공 후뿐이며 그건 R6이 삭제로 처리합니다.

## 6. 삭제 시점

초안 삭제는 항상 **텍스트와 사진 파일을 함께** 지웁니다. 한쪽만 지우면 고아 파일이 남거나 참조가 깨집니다.

| 계기 | 근거 |
|---|---|
| 글 등록 성공 | R6-1 |
| 사용자가 버리기 선택 | R6-3 |
| TTL 초과 확인 | R8-1 |
| 복원 불가 확인 | R10 |
| 새 초안 덮어쓰기 | R4-2 — 이전 초안의 사진 파일을 지웁니다 |

등록 **실패** 시에는 지우지 않습니다(R6-2). 업로드가 중간에 실패한 상황이 오히려 초안이 가장 필요한 순간입니다.

## 7. 실패 취급

자동 저장 실패는 삼킵니다(R9). 저장 공간 부족이나 파일 쓰기 실패가 작성을 막아서는 안 됩니다. `DraftStore`의 저장·삭제 경로는 예외를 밖으로 던지지 않고 실패를 기록만 합니다.

이것은 fail-closed를 요구하는 POL-008의 토큰 저장소와 정반대 방향이며, 의도적입니다. 토큰 저장 실패는 보안 사고로 이어지지만 초안 저장 실패의 최악은 사용자가 원래 겪던 상태 — 초안이 없는 것 — 로 돌아가는 것뿐입니다.

로그에는 본문·제목·태그 내용을 남기지 않습니다(POL-013). 실패 원인과 초안 존재 여부까지만 남깁니다.

삼키는 자리를 **포트와 notifier 두 곳에 둡니다.** `DraftStoreImpl`이 예외를 밖으로
내보내지 않는 것이 계약이지만, notifier도 저장·삭제 호출을 한 번 더 감쌉니다 —
삼키지 않는 구현이 끼어들어도 타이핑이 죽어서는 안 되고, 등록 성공 뒤의 초안 삭제가
실패했다고 이미 서버에 올라간 글이 실패로 뒤집혀서도 안 되기 때문입니다.

**복원** 실패는 조용히 빈 상태로 시작합니다(R10-3). "초안을 불러오지 못했습니다"는 사용자가 할 수 있는 일이 없는 오류이며, 글을 쓰려고 화면을 연 사람에게 처리할 수 없는 실패를 알리는 것은 방해입니다.

## 8. 단위 테스트가 붙는 단위

수용 기준은 아래 두 층에서 판정합니다. `DraftStore`를 포트로 두고 스텁으로 대체하므로 실제 파일 시스템이 필요 없습니다.

| 단위 | 커버하는 기준 |
|---|---|
| `PostComposer` (notifier) | R1, R4, R5, R6, R7, R9, R10-2, R10-3, R11 — 저장·삭제 호출 여부와 복원 후 상태 |
| `StoredDraft` ↔ `PostDraft` 매핑 | R2, R3, R10-1 — 직렬화 왕복, 순서 보존, `contentLength` 대조 |
| TTL 판정 함수 | R8 — 경계값(29일/31일) |

TTL 판정은 순수 함수로 분리해 `savedAt`과 기준 시각을 인자로 받게 합니다. `DateTime.now()`를 안에서 부르면 경계값 테스트가 불가능해집니다.

디바운스 타이머의 실제 시간 경과, 실제 파일 I/O, `AppLifecycleState` 전달은 **테스트하지 않습니다.** 각각 프레임워크와 OS의 동작이며, 애플리케이션 경계 위에서 관찰할 수 없습니다 — 스펙의 테스트 범위 밖입니다.

## 9. 건드리는 파일

| 파일 | 변경 |
|---|---|
| `lib/common/storage/draft_store.dart` | 신규 — 포트 |
| `lib/common/storage/draft_store_impl.dart` | 신규 — shared_preferences + 파일 |
| `lib/common/model/stored_draft.dart` | 신규 — 저장 전용 모델과 매핑 |
| `lib/domain/community/provider/post_composer_providers.dart` | 저장·복원·삭제 연결, 디바운스, `autoDispose` 근거 주석 수정 (§1) |
| `lib/domain/community/view/post_composer_screen.dart` | 이어쓰기 제안 UI, 백그라운드 전환 감지 |
| `pubspec.yaml` | `path_provider` 추가 |
| l10n 파일 | 이어쓰기·버리기 문구 4개 언어 (POL-022) |

`autoDispose` 근거 주석은 설계가 짚은 `post_draft.dart`가 아니라 **프로바이더**에
있었습니다(`PostComposer`의 문서 주석). 모델 쪽에는 그런 서술이 없어 고칠 것이
없었고, 프로바이더의 주석을 고쳤습니다.

테스트는 §8의 세 단위에 붙였습니다 — `test/common/model/stored_draft_test.dart`
(매핑·TTL), `test/domain/community/provider/post_composer_autosave_test.dart`
(저장·복원·삭제 호출), 그리고 기존 화면 테스트에 이어쓰기 제안 케이스를 더했습니다.
`DraftStore`를 스텁(`test/common/storage/fake_draft_store.dart`)으로 대체하므로 실제
파일 시스템이 필요 없습니다. 기존 컴포저 테스트는 새 공유 의존이 생겨 override가
필요해졌고, 그 뒷정리도 함께 했습니다(CLAUDE.md §8).
