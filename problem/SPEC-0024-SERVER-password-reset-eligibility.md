# SPEC-0024 · 서버 요청 — 탈퇴 차단(긴급) · 비밀번호 재설정 대상 제한 · 오류 코드

> 대상: `requestPasswordReset` / `resetPassword` / `withdrawMember`
> 확인 환경: `http://localhost:8888/graphql` (2026-08-17, SPEC-0024 서버 PR #89 반영본)

## 처리 결과 (2026-08-17, 서버 회신 반영 후 재검증)

| 항목 | 결과 |
|---|---|
| §0 탈퇴 FK 차단 | **서버 수정됨.** `deleteMember`가 FK 자식 5개 중 `password_reset`을 빠뜨리고 있었음. 나머지 4개는 원래 정리되고 있었고, 목록 누락 시 실패하는 테스트가 추가됨 |
| §1~§3 SNS 재설정 메일 | **제 오진.** 아래 정정 참고 |
| §4-2 판단 요청 | **(B) 현행 유지로 결정됨.** 인증 없이 부를 수 있는 오퍼레이션이라 코드로 알려 주면 주소만으로 "가입 여부 + 사용 SNS"를 캐낼 수 있다는 판단 |
| §4-3 비밀번호 사유 | **서버 수정됨.** `PASSWORD_POLICY_VIOLATION` 신설 + `field` 채움 |
| 부수: DB 예외 원문 노출 | **서버 수정됨.** 탈퇴만이 아니라 매핑되지 않은 모든 예외가 같은 상태였고, 체인 끝을 정제 핸들러로 교체해 `INTERNAL_ERROR`만 나감 |

### 정정 — §1~§3의 "SNS 회원에게 메일이 발송된다"는 **틀렸습니다**

서버 회신 후 같은 주소로 재검증했습니다.

```
# 카카오로 가입한 주소 (재검증)
resetPassword(code: "999999") → failureReason: "INVALID_OR_EXPIRED"
# 확실히 미가입인 주소 (대조군)
resetPassword(code: "999999") → failureReason: "INVALID_OR_EXPIRED"
```

둘이 **같습니다.** 어제 `CODE_MISMATCH`를 관찰한 것은 서버 팀 설명대로 그 주소에
`Provider.EMAIL` 계정이 함께 존재했기 때문이고(R5가 같은 주소의 복수 provider를
허용), 코드가 발급된 것은 SNS 계정이 아니라 그 EMAIL 계정이었습니다. 실제로
재검증 시점에는 같은 주소로 `registerEmailMember`가 성공했습니다 — 어제 있던 EMAIL
계정이 사라졌다는 뜻이고, 이것이 결과가 달라진 이유를 설명합니다.

**`failureReason`의 차이를 "코드 발급 여부"의 근거로 삼은 것이 오류였습니다.**
그 값은 어느 계정에 코드가 있는지까지 말해 주지 않는데, 조회 대상이 하나뿐이라고
가정했습니다. 서버는 `provider='EMAIL'`로만 조회하고 있었고 코드 경로는 정상이었습니다.

아래 §1~§3은 **잘못된 진단으로 남겨 둡니다** — 무엇을 어떻게 잘못 읽었는지가 다음
판단에 쓰이기 때문입니다.

## 0. 【긴급】 비밀번호 재설정을 요청한 회원은 탈퇴할 수 없습니다

**가장 시급한 항목이라 앞에 둡니다.** 비밀번호 재설정을 한 번이라도 요청한 계정은
`withdrawMember`가 DB 제약에 걸려 **영구히 탈퇴하지 못합니다.**

실기기에서 잡은 응답입니다(회원 id=48, 직전에 비밀번호 재설정을 요청한 계정).

```
withdrawMember → data: null
org.springframework.dao.DataIntegrityViolationException:
  could not execute statement
  [ERROR: update or delete on table "member" violates foreign key constraint
   "fk_pr_member" on table "password_reset"
   Detail: Key (id)=(48) is still referenced from table "password_reset".]
  [delete from auth.member where id=?]
```

`member` 삭제 시 `password_reset` 행이 함께 정리되지 않아 FK 제약이 삭제를
막습니다. 재설정을 요청한 적 없는 계정은 정상 탈퇴되기 때문에 그동안 드러나지
않았습니다.

**영향이 큽니다.** 탈퇴는 사용자가 자기 데이터를 지울 수 있는 유일한 경로이고,
막히면 계정을 버릴 수도 쓸 수도 없는 상태가 됩니다. SPEC-0024가 인증 화면의 탈출구로
탈퇴를 지정하고 있어서(설계 §3, 미인증 상태에서 열리는 두 경로 중 하나), 인증할 수
없는 주소로 가입한 회원이 여기 걸리면 앱에서 빠져나갈 방법이 사라집니다.

**요청.** `withdrawMember`가 `member`를 지우기 전에 `password_reset`을 함께
정리하거나, FK에 `ON DELETE CASCADE`를 걸어 주세요. 같은 형태의 참조가 다른
테이블(인증 코드·토큰 등)에도 있는지 함께 확인해 주시면 좋겠습니다 — 재설정만
문제일 이유가 없어 보입니다.

**부수 요청.** 이 실패가 DB 예외 원문 그대로 클라이언트까지 옵니다. 스택과 SQL,
테이블·제약 이름, 회원 id가 노출되므로(POL-013) 서버에서 잡아 일반 오류로 바꿔
주세요. 앱은 서버 message를 사용자에게 그대로 보여 주지 않지만, 응답에 실려 오는
것 자체가 문제입니다.

## 1. 무엇이 문제인가

비밀번호 재설정은 **자체 가입(`Provider.EMAIL`) 회원에게만** 성립해야 합니다. 지금은
두 부류가 그 경계를 넘습니다.

| 입력 | 현재 `requestPasswordReset` | 기대 |
|---|---|---|
| 가입되지 않은 이메일 | `success: true` | 메일 미발송 (지금도 그런 것으로 보임) |
| **SNS 회원의 이메일** | `success: true` + **메일 발송됨** | 발송하지 않음 |

`success: true`로 통일해 계정 존재 여부를 숨기는 설계 자체는 타당합니다. 문제는
**SNS 회원에게 실제로 코드가 발송된다**는 점입니다.

## 2. 발송된다고 판단한 근거

1단계는 두 경우가 구분되지 않지만, **2단계 응답이 갈립니다.**

```
# 미가입 이메일 + 임의 코드
resetPassword → success: false, failureReason: "INVALID_OR_EXPIRED"

# SNS 회원 이메일 + 임의 코드
resetPassword → success: false, failureReason: "CODE_MISMATCH"
```

`CODE_MISMATCH`는 **대조할 코드가 존재한다**는 뜻입니다. 미가입 쪽은 발급 자체가
없어 `INVALID_OR_EXPIRED`가 나옵니다. 즉 SNS 회원에게는 재설정 코드가 실제로
발급·발송되고 있습니다.

실사용에서도 확인했습니다 — 카카오로 가입한 계정의 주소로 재설정을 요청하니 앱에
"인증 코드를 보냈습니다"가 떴습니다.

## 3. 왜 고쳐야 하는가

SNS 회원에게는 **애초에 비밀번호가 없습니다.** 재설정이 성립할 수 없는 대상에게
코드를 보내면:

- 사용자는 오지 않을(혹은 와도 쓸 수 없는) 코드를 기다립니다.
- 코드를 넣어도 비밀번호가 설정될 수 없으니 끝까지 실패합니다.
- 주소를 아는 사람이 SNS 회원에게 메일을 계속 보내게 할 수 있습니다.

마지막 항목은 발송량이 요청자에 의해 좌우된다는 뜻이라, 계정 열거보다 실질적인
문제로 보입니다.

## 4. 요청 사항

### 4-1. SNS 회원에게는 발송하지 않는다 (필수)

`requestPasswordReset`이 대상 회원의 provider를 보고 `EMAIL`이 아니면 **메일을
발송하지 않습니다.** 응답은 지금처럼 `success: true`로 두어도 됩니다 — 계정 존재
여부를 숨기는 설계를 유지하면서 발송만 막으면 됩니다.

### 4-2. 앱이 사용자에게 설명할 수 있게 해 주세요 (판단 요청)

지금 구조에서는 앱이 "코드를 보냈습니다"라고 말할 수밖에 없는데, SNS 회원에게는
그것이 사실이 아닙니다. 사용자는 오지 않는 메일을 기다립니다.

두 가지 방향이 있고, **어느 쪽이든 서버 팀의 판단을 따르겠습니다.**

**(A) 오류 코드로 알려 주기.** `NOT_EMAIL_MEMBER`를 `userErrors`에 실어 주시면 앱이
"이 계정은 카카오/구글/애플로 가입되어 있습니다. 해당 방법으로 로그인해 주세요"라고
정확히 안내합니다.

- 장점: 사용자가 즉시 다음 행동을 압니다.
- 단점: **계정 존재 여부와 가입 수단이 노출됩니다.** 로그인 화면에서 SNS 버튼으로
  같은 사실을 어느 정도 알 수 있다는 점을 감안해도, 이건 보안 정책 판단이 필요한
  트레이드오프라 서버 팀이 결정해 주시는 게 맞다고 봅니다.

**(B) 현행 유지 + 앱이 문구를 중립적으로.** 서버는 그대로 두고, 앱이
"가입된 계정이라면 코드를 보냈습니다"처럼 단정하지 않게 바꿉니다.

- 장점: 보안 설계가 유지됩니다.
- 단점: SNS 회원은 여전히 **왜 코드가 안 오는지 모릅니다.**

> **앱은 (B)를 이미 적용해 두었습니다.** (A)로 가기로 하면 앱에서 코드 분기를
> 추가하는 것은 작은 작업입니다.

### 4-3. `INVALID_INPUT`의 사유를 나눠 주세요 (있으면 좋음)

`registerEmailMember`가 비밀번호 규칙 위반을 `INVALID_INPUT` 하나로 냅니다.

```
registerEmailMember(password: "123")
→ code: "INVALID_INPUT", message: "비밀번호는 8자 이상 100자 이하여야 합니다.", field: null
```

사유가 `message`에만 있어서 앱이 분기할 수 없습니다. 앱은 서버 `message`를 그대로
띄우지 않습니다 — 다국어 대응이 되지 않고, 서버 메시지에 내부 정보가 섞일 수 있기
때문입니다(POL-013). 그래서 지금은 "입력하신 정보가 올바르지 않습니다"라는 일반
안내만 보여 줍니다.

둘 중 하나면 앱이 정확히 안내할 수 있습니다.

- `field`에 `"password"`를 채워 주기 (가장 작은 변경)
- 또는 `PASSWORD_POLICY_VIOLATION` 같은 별도 코드

## 5. 앱이 이미 반영한 것

서버 변경 없이 처리한 부분입니다.

- `MEMBER_ALREADY_REGISTERED`, `INVALID_INPUT`, `ACCOUNT_INACTIVE`,
  `VERIFICATION_RATE_LIMITED`, `VERIFICATION_NOT_FOUND`를 문구로 매핑했습니다.
  이전에는 전부 "문제가 발생했습니다"로 떨어져 사용자가 원인을 알 수 없었습니다.
- 비밀번호 재설정 1단계 안내 문구를 단정형에서 조건형으로 바꿨습니다(4-2 B안).

## 6. 서버 회신 이후 앱이 반영한 것 (2026-08-17)

- **`PASSWORD_POLICY_VIOLATION`** 을 SDL·모델·문구에 추가했습니다. BREAKING이지만
  `INVALID_INPUT` 분기를 남겨 두어 어느 코드가 와도 안내가 나갑니다.
- **`field`로 입력칸을 특정합니다.** 서버가 `"input.password"`처럼 **경로**로 주므로
  마지막 마디만 비교하는 `AuthFailure.pointsAt()`을 두었습니다 — 경로를 그대로
  비교하면 영원히 일치하지 않아 오류가 어느 칸에도 붙지 않습니다. 가입 화면이 이제
  비밀번호·이메일 오류를 해당 칸 아래에 붙입니다.
- **message 매칭 폴백은 남겼습니다.** 서버가 예외를 정제하면서 실질적으로 걸리지
  않게 됐지만, 구버전 서버를 상대할 가능성이 있는 한 비용 없이 두는 편이 낫다고
  판단했습니다. 주석에 그 사정을 적었습니다.

## 7. 최종 재검증 (2026-08-18)

서버 재기동 후 **§0(탈퇴 FK)과 §1~§3(발송 대상)을 모두 실측으로 확정했습니다.**

### 탈퇴 FK — 수정 확인됨

비밀번호 재설정을 요청한 계정 2개를 만들어 탈퇴시켰고, 둘 다 성공했습니다.

```
requestPasswordReset(email) → success: true
loginEmail → accessToken
withdrawMember → { success: true, userErrors: [] }
```

이전에는 같은 순서에서 `fk_pr_member` 위반으로 실패했습니다. 해결됐습니다.

### 발송 대상 — 서버가 이미 올바릅니다

각 주소에 `Provider.EMAIL` 계정이 있는지를 `registerEmailMember`로 먼저 판별한 뒤
(성공 = 없음 / `MEMBER_ALREADY_REGISTERED` = 있음), 재설정 코드 발급 여부를
2단계 `failureReason`으로 확인했습니다.

| 주소 | EMAIL 계정 | 코드 발급 |
|---|---|---|
| 미가입 주소 | 없음 | **안 됨** (`INVALID_OR_EXPIRED`) |
| `tarotaws001@gmail.com` | 없음 | **안 됨** (`INVALID_OR_EXPIRED`) |
| `wnsgk7518@naver.com` | 있음 | 됨 (`CODE_MISMATCH`) |

**EMAIL 회원에게만 발급됩니다.** 미가입자·SNS 회원에게 메일이 나가는 낭비는
없습니다. 세 번째 줄이 `CODE_MISMATCH`인 것은 그 주소에 EMAIL 계정이 실제로
존재하기 때문이고(§처리 결과의 정정과 같은 원인), SNS 계정 때문이 아닙니다.

**남은 것은 서버 문제가 아니라 앱의 안내였습니다.** 서버가 계정 존재 여부를
숨기므로(§4-2 B안) 앱은 "코드를 보냈다"고 단정할 수 없는데, 사용자는 코드가 오지
않으면 이유를 알 수 없었습니다. 재설정 화면에 그 조건을 상시 안내로 넣었습니다 —
계정을 특정하지 않으면서 "SNS 가입 계정에는 발송되지 않는다"는 사실은 알립니다.

## 8. 【재요청】 §4-2 결정을 (A)로 바꿔 주시길 요청합니다

**이전에 (B)로 결정하신 것을 다시 논의하고 싶습니다.** 실기기에서 미가입 주소로
재설정을 시도해 보니, (B)의 비용이 제가 §4-2에서 적었던 것보다 훨씬 큽니다.

### 무엇이 문제인가

미가입자가 이메일을 넣으면 **코드 입력 화면으로 넘어갑니다.** 6칸 입력칸과
"메일로 보내 드린 6자리 코드를 입력해 주세요"라는 문구를 보게 됩니다.

사용자 입장에서 이건 **"내 계정이 있고 메일이 오는 중"이라는 확인**입니다.
실제로는 계정이 없어 메일이 오지 않는데, 사용자는 그 사실을 알 방법이 없어
스팸함을 뒤지고 재시도합니다. 가입한 적 없다는 것을 기억해 낼 때까지요.

**계정이 없는 사람은 애초에 이 화면에 들어오면 안 됩니다.**

### (B)가 지키려던 것과 실제로 지켜지는 것

(B)의 근거는 계정 열거 방지였습니다. 그런데 지금 상태에서도 **2단계로 넘어가면
`resetPassword`의 `failureReason`이 계정 유무를 알려 줍니다.**

```
# 미가입 → 발급된 코드가 없다
resetPassword(code: "999999") → failureReason: "INVALID_OR_EXPIRED"
# EMAIL 회원 → 대조할 코드가 있다
resetPassword(code: "999999") → failureReason: "CODE_MISMATCH"
```

이 차이는 인증 없이 두 번의 호출로 관찰됩니다. 즉 **(B)는 계정 열거를 막지 못하면서
정직한 사용자만 혼란스럽게 합니다.** 열거를 진짜로 막으려면 이 응답까지 통일해야
하는데, 그러면 코드 오타와 만료를 구분할 수 없어 정상 사용자 경험이 나빠집니다.

### 업계 사례

조사한 범위에서 확인된 것만 적습니다.

- **Instagram** — 미가입 주소에 "이메일 주소를 찾을 수 없음"을 안내합니다
  (공식 헬프 문서 존재: `help.instagram.com/372185676193504`).
- **Discord** — 재설정 시 "존재하지 않는 이메일"을 알린다는 사용자 보고가 있습니다.
- **OWASP** — 일관된 메시지를 권고합니다(§4-2에서 인용한 근거).
- **Troy Hunt(중간안)** — 화면에서는 숨기되, **미가입 주소에는 "계정이 없습니다"
  메일을 보냅니다.** 받은 사람만 진실을 알게 되어 열거를 막으면서 사용자에게는
  알립니다.

Tinder·Airbnb·Uber·Netflix 등은 **확인하지 못했습니다** — 추측으로 채우지 않겠습니다.

### 요청

**(A) — `requestPasswordReset`이 자격 없는 대상에 오류 코드를 주기.**

- 미가입 → `MEMBER_NOT_FOUND`
- SNS 회원 → `NOT_EMAIL_MEMBER`

앱은 이 코드를 받으면 **2단계로 넘어가지 않고** 이메일 칸에 "이 이메일로 가입된
계정이 없습니다. 카카오·구글·애플로 가입하셨다면 해당 방법으로 로그인해 주세요"를
붙입니다. 코드는 이미 매핑해 두었으니 서버가 주는 즉시 동작합니다.

**(A)가 부담스러우시면 Troy Hunt 안도 좋습니다** — 화면은 지금처럼 두고 미가입
주소에 "가입된 계정이 없습니다" 메일을 보내는 방식입니다. 사용자가 진실을 알게
되는 것이 핵심이라, 경로는 어느 쪽이든 괜찮습니다.

**어느 쪽도 어렵다면 알려 주세요.** 그때는 2단계 화면 문구를 더 강하게 조건부로
바꾸는 선에서 마무리하겠습니다(지금도 "SNS 가입 계정에는 발송되지 않습니다"를
안내하고 있습니다).

### 앱은 이미 준비돼 있습니다

`MEMBER_NOT_FOUND`·`NOT_EMAIL_MEMBER`를 받으면 1단계에 머무르며 이메일 칸에 안내를
붙이는 분기를 넣어 두었습니다. 서버가 지금처럼 `success: true`만 주는 동안에는 그
분기가 발화하지 않아 동작이 달라지지 않습니다.
