# SPEC-0024 — 클라이언트 설계

요구사항·수용 기준·계약은 위 스펙에 있습니다. 이 문서는 앱 쪽 설계 결정만 다룹니다.

## 1. 변경의 성격

세 갈래입니다.

| 갈래 | 변경 | 요구사항 |
|---|---|---|
| 가입 폼 | SNS 이메일 입력을 읽기 전용으로, provider 미제공 시에만 편집 가능 | R1 |
| 라우팅 | 인증 미완료 시 메인 진입 차단 | R10 |
| 인증 화면 | 단일 필드를 6칸 박스로, 주소 재입력 경로 추가 | R11, R7 |

이 중 **라우팅이 가장 침습적**입니다. 앱 전체의 진입 경로에 조건이 하나 더 붙습니다.

## 2. 가입 폼 (R1)

현재 SNS 가입 폼의 이메일 입력은 provider 값을 기본으로 채우고 편집을 허용합니다(POL-003 원문). 이것이 두 상태로 갈립니다.

| provider 이메일 | 입력 상태 | 초기값 |
|---|---|---|
| 있음 | 읽기 전용 | provider 값 |
| 없음 | 편집 가능 | 비어 있음 |

읽기 전용 표시는 비활성 필드로 보이게 하되, 값을 읽을 수 없을 만큼 흐리게 처리하지는 않습니다 — 사용자가 어느 주소로 가입하는지 확인할 수 있어야 합니다.

**편집을 허용하면 사용자가 속습니다.** 서버는 provider가 이메일을 준 경우 제출값을 무시하고 provider 응답값을 저장합니다(스펙 R12). 보안상 구멍은 없지만, 앱이 편집을 허용하면 사용자가 입력한 주소와 실제 가입된 주소가 달라집니다. 편집 차단은 보안이 아니라 **표시와 실제를 일치시키기 위한** 요구사항입니다.

## 3. 라우팅 (R10)

### 판정 지점

로그인 성공 직후와 앱 시작 시 세션 복원 직후, 두 곳에서 `me.emailVerified`를 확인합니다. 거짓이면 인증 화면으로, 참이면 메인으로 보냅니다.

R10-4가 세션 복원 경로를 명시적으로 요구합니다 — 미인증 상태로 앱을 종료했다가 재실행하면 저장된 토큰으로 세션이 복원되는데, 이때도 메인이 아니라 인증 화면으로 가야 합니다. 로그인 직후만 판정하면 이 경로가 뚫립니다.

### 차단의 형태

GoRouter의 redirect로 처리합니다. 인증 미완료 상태에서 메인 이하 경로로의 이동을 인증 화면으로 되돌립니다(R10-2). 화면을 띄운 뒤 가리는 방식은 한 프레임이라도 메인이 보이므로 쓰지 않습니다.

인증 화면에서 나갈 수 있는 곳은 세 곳뿐입니다 — 인증 성공 시 메인(R10-3), 로그아웃, 탈퇴. 뒤로가기로 메인에 도달할 수 없어야 합니다.

### 서버 게이트와의 관계

서버는 미인증 토큰의 비허용 오퍼레이션을 `EMAIL_NOT_VERIFIED` 최상위 오류로 거부합니다(스펙 R9). 앱의 라우팅 차단이 정상 동작하면 이 오류는 원칙적으로 발생하지 않습니다.

허용 목록에 **토큰 갱신과 로그아웃이 포함**되므로(R9), 인증 화면에 머무는 동안 accessToken이 만료돼도 세션이 유지되고 로그아웃도 가능합니다. 인증 화면이 5분 이상 열려 있어도 갱신 실패로 튕기지 않습니다.

그래도 **공통 오류 처리에서 이 코드를 잡아 인증 화면으로 보내는 경로를 둡니다.** 라우팅이 놓친 진입점이 있거나, 인증 상태가 서버에서 바뀐 경우의 안전망입니다. 이 처리는 화면별이 아니라 GraphQL 클라이언트의 공통 오류 지점에 둡니다.

### 인증 직후의 토큰

서버가 게이트 판정을 토큰 클레임으로 할 경우, 인증에 성공해도 기존 토큰이 만료될 때까지(최대 5분, POL-008) 게이트에 걸릴 수 있습니다. 서버 설계 문서가 인증 성공 시 토큰 재발급을 권하고 있습니다.

앱은 **인증 성공 응답을 받은 뒤 메인으로 이동하기 전에 세션을 갱신**하는 형태로 대비합니다. 서버가 재발급을 하지 않기로 하면 이 단계는 `me` 재조회로 축소됩니다. 어느 쪽이든 인증 성공 직후 서버 상태를 한 번 다시 읽는 것은 필요합니다 — R10-3의 판정 근거가 갱신되어야 하기 때문입니다.

## 4. 인증 화면

### 6칸 코드 입력 (R11)

단일 `TextField`를 6개의 개별 박스로 바꿉니다. 동작 요구사항은 네 가지입니다.

- 한 칸 입력 시 다음 칸으로 포커스 이동 (R11-2)
- 빈 칸에서 삭제 시 이전 칸으로 포커스 이동 (R11-3)
- 6자리 문자열 붙여넣기 시 여섯 칸이 순서대로 채워짐 (R11-4)
- 앞자리 0 보존 (R11-5)

**R11-5가 함정입니다.** 코드는 숫자가 아니라 6자리 문자열이며 앞자리 0이 의미를 가집니다(POL-004). 칸 값을 정수로 다루거나 여섯 칸을 합칠 때 수치 변환을 거치면 `012345`가 `12345`가 됩니다. 입력·결합·전송 전 구간에서 문자열로 유지합니다.

키보드는 숫자 전용으로 띄우되, 입력 처리 자체는 문자열입니다.

### 주소 재입력 (R7)

인증 화면에 인증 대상 주소를 정정하는 경로를 둡니다. 사용 대상은 두 부류입니다.

- 이메일 가입자 — 오타로 잘못된 주소를 넣은 경우
- provider가 이메일을 주지 않은 SNS 가입자 — 앱에서 직접 입력했으므로 오타 위험이 동일

**이메일 변경(`changeEmail`)과 다른 경로입니다.** 그쪽은 인증을 마친 회원이 설정 화면에서 쓰고 `Provider.EMAIL` 회원만 가능합니다. 이쪽은 인증 전 상태에서만 쓰고 가입 유형을 가리지 않습니다. 두 경로의 UI를 공유하지 않습니다.

재입력 실패 시 사용자가 분기해야 하는 코드는 두 개입니다 — `RESEND_COOLDOWN_ACTIVE`(60초 대기)와 `EMAIL_ALREADY_IN_USE`(같은 provider에 이미 존재). 각각 다른 안내가 필요합니다.

## 5. 설정 화면 (R6)

이메일 변경 진입점을 `me.canChangeEmail`로 분기합니다(R6-5). 거짓이면 진입점을 **숨깁니다** — 비활성 상태로 두면 왜 못 쓰는지 설명해야 하고, SNS 계정의 이메일이 provider 소유라는 사실은 설정 화면에서 설명할 만한 내용이 아닙니다.

provider 값을 받아 앱에서 `provider == EMAIL`을 판정하지 않습니다. 서버가 준 capability를 그대로 씁니다 — 규칙이 바뀌어도 앱을 고치지 않아도 됩니다.

## 6. 기존 동작의 파기

두 가지가 지금 동작과 달라집니다.

**로그인 실패를 인증 유도 신호로 쓰던 분기 제거.** 지금은 미인증 회원의 `loginEmail`이 `EMAIL_NOT_VERIFIED`로 실패하고, 앱이 그것을 받아 인증 화면으로 보냅니다. R8 이후 이 로그인은 **성공**합니다. 로그인 결과가 아니라 `me.emailVerified`로 판정해야 하며, 기존 분기를 남겨 두면 죽은 코드가 됩니다.

**SNS 회원의 이메일 변경 진입점 제거.** SPEC-0011 R8이 모든 회원에게 이메일 변경을 열었고 그에 맞춰 구현됐다면, 해당 진입점을 R6에 맞춰 닫습니다. `canChangeEmail` 분기가 이 역할을 합니다.

## 7. 단위 테스트가 짊어질 단위

이 프로젝트의 테스트 범위는 provider/notifier와 도메인 모델 로직입니다. 위젯·통합 테스트는 쓰지 않습니다.

**도메인 모델 / 순수 로직**

- 6칸 코드의 결합 — 앞자리 0 보존 (R11-5)
- 붙여넣기 문자열의 칸 분배 (R11-4)
- 포커스 이동 규칙 — 입력 시 전진, 빈 칸 삭제 시 후진 (R11-2, R11-3). 포커스 자체가 아니라 "다음에 어느 칸이 활성인가"를 반환하는 순수 함수로 분리해 시험합니다

**provider / notifier**

- 진입 경로 판정 — `emailVerified` 참/거짓에 따른 목적지 (R10-1, R10-3)
- 세션 복원 시의 같은 판정 (R10-4)
- 가입 폼 상태 — provider 이메일 유무에 따른 편집 가능 여부와 초기값 (R1-1, R1-2)
- 설정 화면의 이메일 변경 진입점 노출 여부 — `canChangeEmail` 분기 (R6-5)
- 주소 재입력의 오류 코드별 분기 — 쿨다운과 중복

**시험하지 않는 것.** GoRouter의 실제 redirect 동작(R10-2)은 라우터 런타임을 세워야 관찰됩니다. 판정 로직을 순수 함수로 분리해 그것을 시험하고, 라우터에 연결하는 부분은 시험하지 않습니다. 화면 렌더링(R11-1, R1-1의 시각적 상태)도 위젯 테스트 영역이므로 범위 밖입니다.

## 8. 구조

`lib/domain/auth/` 하위에 놓습니다. 인증 화면은 이미 존재하므로 신설이 아니라 개편입니다.

- 6칸 입력은 `component`의 재사용 가능한 위젯으로 — 코드 입력은 인증과 이메일 변경 확인 두 곳에서 쓰입니다
- 진입 경로 판정은 `provider`에 두고, 라우터가 그것을 읽습니다. 라우터가 직접 `me`를 조회하지 않습니다
- 서버 응답은 `repository`에서 도메인 모델로 변환합니다. graphql_codegen 생성 타입이 provider·view로 넘어가지 않습니다 (POL-020)
- 인증 화면과 주소 재입력의 문구는 EN/KO/JA/ZH 네 언어 (POL-022)

## 9. 최종 구현 상태 (2026-08-17 · 서버 PR #89 반영 후)

서버 PR ieuri-server#89가 올라와 §10에서 **차단으로 적었던 R7·R6이 열렸습니다.**
아래 표가 최종 상태이며, §10은 서버 이전 시점의 기록으로 남깁니다.

| 항목 | 상태 |
|---|---|
| `loginEmail`의 `EMAIL_NOT_VERIFIED` 분기 제거 | 해당 분기가 애초에 없었음(§10) |
| 세션 복원 시 `me.emailVerified` 판정 | 1차에 완료 |
| 최상위 오류 5종 공통 처리 | 추가 |
| `INVALID_TOKEN` / `TOKEN_REUSE_DETECTED` 분리 | 추가 |
| SNS 폼 provider 이메일 읽기 전용 | 이미 구현돼 있었음 |
| `verificationId` null이면 인증 화면 건너뛰기 | 이미 그렇게 동작(주석만 갱신) |
| 설정 이메일 변경을 `canChangeEmail`로 제어 | 추가 |
| `retargetEmailVerification` 화면 | 추가 |
| 재발송/주소정정 60초 공유 타이머 | 추가 |
| `codeValue` enum 분기 + `code` 폴백 | 추가 |
| `failureReason`을 `userErrors`와 구분 | 추가 |
| 6칸 입력, 앞자리 0 보존 | 1차에 완료 |

### 최상위 오류를 정본 `code`로 판별합니다

서버가 `extensions.code`에 5종을 실어 주므로, 그동안 임시방편이던 **message 문자열
매칭을 대체**했습니다(`auth_error_classifier.dart`). 판별 순서는 `code` → `errorType`
→ message 폴백입니다.

폴백을 지우지 않은 이유는 아직 코드가 붙지 않은 경로가 남아서입니다 — 미인증 상태의
`retargetEmailVerification` 호출은 지금도 `errorType: INTERNAL`에 예외 클래스명만
담겨 옵니다(라이브 확인).

**`INVALID_TOKEN`과 `TOKEN_REUSE_DETECTED`를 나눴습니다.** 전자는 갱신 대상
(`unauthenticated`), 후자는 갱신해도 회복되지 않으므로 별도 분류입니다. 갱신 링크는
`unauthenticated`에만 반응하므로 재사용 감지가 자동으로 갱신에서 제외됩니다 —
뭉개 두면 회복 불가능한 상태에서 갱신을 반복하게 됩니다. 사용자 문구도 이때만
"다시 로그인해 주세요"로 다릅니다.

### 코드 검증 실패는 `AuthFailure`와 다른 타입입니다

`verifyEmail`이 `success: true, verified: false`로 오는 경우를 `VerificationFailure`로
따로 던집니다. 이전 구현은 이 경우를 전부 `unknown`으로 뭉개 사용자에게 "알 수 없는
오류"만 보여 줬습니다 — 만료(재발송 필요)와 오타(다시 입력)는 사용자가 해야 할 행동이
다릅니다.

### 쿨다운은 하나의 타이머입니다

`ResendCooldown`(순수 모델)이 재발송과 주소 정정을 함께 셉니다. 서버가 두
오퍼레이션에 하나의 타이머를 쓰므로 앱이 따로 세면 한쪽이 열려 보이는데 누르면
실패합니다. 서버가 `RESEND_COOLDOWN_ACTIVE`로 막으면 그때 앱 타이머도 다시 세워
어긋남을 흡수합니다.

### §10에 적은 "게이트 진입 시 재발송 불가"가 해소됐습니다

세션 복원 경로(R10-4)로 도착하면 `verificationId`가 없어 재발송을 부를 수 없다는
문제를, `retargetEmailVerification`이 해결합니다 — 이쪽은 **토큰만으로** 새 코드를
받아 내므로 핸들이 필요 없습니다. 그 상태에서 재발송 버튼은 여전히 숨기고 주소 정정만
남깁니다.

### 미검증 항목

- **`EMAIL_NOT_VERIFIED` 안전망은 형태만 검증했습니다.** 분류기 단위 테스트로 코드
  판별은 확인했지만, 실제로 미인증 토큰을 들고 비허용 오퍼레이션을 호출해 훅이 도는
  것까지는 확인하지 못했습니다 — 미인증 계정의 유효 토큰이 필요합니다. 라우팅 게이트가
  정상이면 발화하지 않는 안전망이라는 점을 감안해 이 상태로 둡니다.
- **`codeValue`(enum)의 실제 직렬화 형태**는 단위 테스트의 캔드 응답으로만 확인했습니다.
  생성 타입의 `toJson()`이 enum을 이름 문자열로 낸다는 전제에 기대고 있으며, 살아 있는
  오류 응답으로는 확인하지 못했습니다. 다만 `code`(문자열) 폴백이 항상 있어 이 전제가
  틀려도 분기는 유지됩니다.
- 인증 성공 직후 토큰 재발급 여부는 여전히 확인하지 못했고, `refreshMe()`로 두었습니다(§10).

> 어떤 계약이 언제 없었는지가 이후 판단의 근거가 되기 때문입니다.

라이브 서버(`http://localhost:8888/graphql`)에 직접 쏴서 확인한 계약을 기준으로,
요구사항이 **구현된 것과 서버를 기다리는 것으로 갈렸습니다.**

| 요구사항 | 상태 | 근거 |
|---|---|---|
| R1 SNS 이메일 읽기 전용 | 이미 구현돼 있었음 | `sns_sign_up_screen.dart` — provider 이메일이 있으면 `enabled: false` |
| R10 인증 게이트 라우팅 | 구현 | `me.emailVerified` 사용 가능 |
| R11 6칸 코드 입력 | 구현 | 서버 계약과 무관한 순수 UI |
| R7 주소 재입력 | **차단** | `ResendVerificationInput`에 `email` 인자 없음 |
| R6 `canChangeEmail` 분기 | **차단** | `Me`에 `canChangeEmail` 필드 없음 |

차단된 둘은 서버가 먼저 나와야 합니다. 없는 필드에 맞춰 미리 짜 두면 codegen은
통과하지만 런타임에 전부 실패합니다(CLAUDE.md §13이 경고하는 그 상황).

확인 명령과 응답:

- `me { canChangeEmail }` → `Field 'canChangeEmail' in type 'Me' is undefined`
  (`FIELD_NOT_FOUND`)
- `resendVerification(input: {verificationId, email})` → `The variables input
  contains a field name 'email' that is not defined for input object type
  'ResendVerificationInput'`
- `me { emailVerified }` → `UNAUTHENTICATED`만 반환 = **형태는 통과**. R10의 판정
  근거는 유효합니다.

전체 오퍼레이션 문서 스윕(§13) 결과 불일치 0건이며, `.graphql`을 고치지 않았으므로
codegen은 돌리지 않았습니다.

### 스펙 §6이 지목한 "파기 대상"은 실재하지 않았습니다

- **로그인 실패를 인증 유도로 쓰던 분기** — `login_screen.dart`에 그런 분기가 애초에
  없습니다. `AuthFailureKind`를 참조하지 않고 실패를 배너로만 그립니다. 지울 죽은
  코드가 없습니다.
- **SNS 회원의 이메일 변경 진입점** — 설정 홈에는 없고
  `profile_edit_screen.dart:151`에 조건 없이 열려 있습니다. 닫으려면
  `canChangeEmail`이 필요하므로 R6과 함께 막혀 있습니다.

### 게이트 진입 시 재발송이 불가능합니다 (서버 공백)

R10-4 경로(미인증 세션으로 앱 재시작)로 인증 화면에 도착하면 `verificationId`가
없습니다. `me`가 그 값을 주지 않고, `resendVerification`은 그것을 **필수**로
요구합니다. 즉 **이 경로의 사용자는 코드를 다시 받을 수단이 없습니다.**

앱은 이 상태에서 재발송 버튼을 **숨깁니다** — 없는 기능을 버튼으로 보여 주면 눌렀을
때 실패합니다. 대신 로그아웃 출구를 두어 갇히지 않게 했습니다.

해소하려면 서버가 둘 중 하나를 주면 됩니다: `me`에 진행 중인 `verificationId`를
싣거나, 이메일만으로 재발송하는 오퍼레이션을 열거나. R7의 주소 재입력이 들어오면
후자로 함께 풀립니다.

### 게이트 판정 순서

언어 → 인증 → **이메일 인증** → 온보딩 → 약관 → 목적지.

이메일 인증을 온보딩보다 **앞**에 뒀습니다. 서버가 미인증 토큰의 비허용 오퍼레이션을
거부하므로(R9), 온보딩을 먼저 태우면 그 안의 서버 호출이 실패합니다.

인증 미완 상태에서 열리는 경로는 인증 화면과 **탈퇴 화면뿐**입니다. 약관 게이트가
설정 계열 전체를 여는 것과 다릅니다 — 미인증 토큰으로는 프로필 조회가 거부되므로
설정을 열어 줘도 오류 화면만 보게 됩니다.

### 미검증 항목

- **`EMAIL_NOT_VERIFIED` 공통 오류 처리(설계 §3)는 넣지 않았습니다.** 서버의 R9
  게이트가 아직 없어 이 코드를 실제로 받아 본 적이 없고, 오류 코드 문자열도 확정되지
  않았습니다(`UserError.code`는 스키마상 자유 문자열). 추측한 문자열로 안전망을 짜면
  동작 여부를 확인할 수 없는 코드가 남습니다. 서버 게이트가 들어온 뒤 실제 응답을
  보고 `auth_error_classifier.dart`에 추가합니다.
- **인증 성공 직후 토큰 재발급(설계 §3)** — 서버가 재발급을 하는지 확인하지 못해
  `refreshMe()`(= `me` 재조회)로 구현했습니다. 설계가 "어느 쪽이든 서버 상태를 한 번
  다시 읽는 것은 필요하다"고 한 최소선은 충족합니다.
- GoRouter의 실제 리다이렉트 동작은 설계 §7대로 시험 범위 밖이며, 판정 순수 함수
  (`resolveGate`)만 표로 검증했습니다.
