# SPEC-0026 · 서버 요청 — 질문 작성 자격 게이팅 제거 · 「내 질문」 조회 신설

> 대상: `createSpotQuestion` / `createSpotAnswer` / `createSpotAnswerReply`(R3·R4·R5 판정),
> 신규 `myQuestions` · 관련 수용 기준: AC-3.2·AC-3.3·AC-3.6·AC-4.2
> 확인 환경: `http://localhost:8888/graphql` (2026-08-18 라이브 introspection)
> 근거: `feature/SPEC-0026-spot-qa` 구현 후 사용성 점검 · **상태: 요청 중**

> **이 문서는 작업 중 기록이다.** 정책으로 승격할 사안이 정리되면 그때
> `ieuri-recorder`로 올린다(CLAUDE.md §10).

두 건입니다. **①은 규칙을 없애 달라는 것이고, ②는 조회를 만들어 달라는 것**입니다.
둘은 원인이 다르지만 증상이 같습니다 — 질문을 올린 사람이 답을 못 받습니다.

## ① 좋아요 기반 작성 자격 게이팅을 없애 주세요

### 무엇을 바꿔야 하는가

R3·R4·R5를 삭제하고, `createSpotQuestion`·`createSpotAnswer`·`createSpotAnswerReply`에서
`NOT_ELIGIBLE_TO_ASK` / `NOT_ELIGIBLE_TO_ANSWER` 판정을 제거해 주세요.

**로그인한 회원이면 반응 상태와 무관하게 질문·답변·답글을 쓸 수 있어야 합니다.**
`LIKE`·`DISLIKE`·반응 없음 셋 다 허용입니다.

영향받는 수용 기준: AC-3.2, AC-3.3, AC-4.2가 삭제됩니다. AC-3.6(비활성 + 좋아요 안내)도
게이팅이 사라지면 존재 이유가 없어집니다. AC-3.4·AC-3.5(본문 길이·공백 검증)는 그대로
유지해 주세요 — 그건 자격이 아니라 입력 검증입니다.

`SpotDetail.viewerReaction`은 **남겨 주세요.** 자격 판정에는 안 쓰지만 상세 화면이 내
반응 상태를 표시하는 데 이미 쓰고 있고, 이 필드가 없으면 "이미 좋아요한 장소를 다시
열었을 때 반응 없음으로 시작하는" 기존 버그가 되살아납니다.

### 왜 필요한가 — 질문할 이유와 좋아요할 이유가 반대다

스펙 26행은 이 기능을 "장소를 좋아요한 사람들끼리 묻고 답하는 경로"로 정의했습니다.
답하는 쪽에는 맞는 말입니다. **묻는 쪽에는 맞지 않습니다.**

「지금 여기 어때?」는 **가기 전에** 묻는 질문입니다. 지금 붐비는지, 주차가 되는지,
비 와도 볼 만한지 — 아직 가 보지 않았고 좋아할지도 모르는 상태에서 나오는 질문입니다.
반면 좋아요는 "여기 가고 싶다/좋았다"는 이미 기운 판단입니다.

그래서 게이팅은 **질문이 가장 필요한 사람을 정확히 막습니다.** 판단이 선 사람만 물을 수
있고, 판단하려고 묻는 사람은 못 씁니다. 이 기능의 이름 자체가 그 모순을 드러냅니다.

DISLIKE도 마찬가지입니다. 한 번 실망한 사람이 "그때 공사 중이었는데 지금은 끝났나요?"를
묻지 못합니다. 부정적 반응은 오히려 확인하고 싶은 게 많다는 신호입니다.

### 모집단 문제 — 스펙이 이미 인정하고 있습니다

스펙 225~226행:

> **임계값을 장소 규모에 맞춰 조정하지 않는다.** 이 기능은 그 장소를 좋아요한 회원만
> 참여하므로 커뮤니티 글보다 모집단이 작고, 좋아요 인원이 5명 미만인 장소에서는 자동
> 숨김이 사실상 동작하지 않는다.

그리고 68행은 실시간 채팅방을 제외한 이유로 "좋아요한 사용자만 쓰는 구조에서 초기 동시
접속자가 사실상 없어 빈 방 문제가 치명적"이라고 적었습니다.

**같은 진단이 질문/답변에도 그대로 적용됩니다.** 비동기라서 혼자여도 성립한다는 것은
맞지만, 그건 "질문이 오래 남는다"는 뜻이지 "답이 온다"는 뜻이 아닙니다. 질문 하나에
답이 달리려면 그 장소를 좋아요한 사람이 **여러 명** 있고 그중 누군가 다시 들어와야
합니다. 좋아요 5명 미만인 장소가 대부분인 초기에는 질문이 그냥 방치됩니다.

게이팅을 풀면 답할 수 있는 모집단이 "좋아요한 회원"에서 "그 장소를 아는 회원"으로
넓어집니다. 가 본 적 있지만 좋아요를 누르지 않은 사람이 훨씬 많습니다.

### 악용 우려에 대해

게이팅의 원래 목적이 스팸 억제였다면, 그 목적은 이미 다른 장치가 담당합니다.
R11의 신고 누적 자동 숨김(POL-041 3항), R12의 차단 반영, 그리고 SPEC-0024의 이메일
인증 게이트가 그것입니다. 로그인 + 이메일 인증을 통과한 회원으로 한정하는 것으로
충분하며, 좋아요는 스팸과 상관관계가 약합니다 — 스패머는 좋아요를 누르면 그만입니다.

**좋아요는 자격이 아니라 클릭 한 번입니다.** 진입 장벽으로는 약하고, 정상 사용자에게는
불필요한 마찰입니다.

### 클라이언트가 지금 어떻게 대응하고 있는가

게이팅을 전제로 만든 코드가 이미 있습니다. 계약이 바뀌면 다음이 정리됩니다.

- `spot_qa_eligibility.dart` — 자격 판정 함수 전체 삭제
- 진입점의 조건부 노출 → 항상 노출
- `NOT_ELIGIBLE_TO_ASK/ANSWER` 분기와 안내 문구 4개 로케일 → 삭제

**계약이 바뀔 때까지는 클라이언트가 오류 코드 처리를 유지합니다.** 서버가 아직
게이팅을 강제하는데 클라이언트가 진입점을 열어 두면, 사용자가 다 쓰고 나서 거절당하기
때문입니다. 이 요구가 받아들여지는 시점에 함께 걷어내겠습니다.

## ② 「내가 쓴 질문」 조회를 만들어 주세요

### 무엇을 만들어야 하는가

```graphql
extend type Query {
  """
  호출자가 작성한 질문 목록. 최신순.
  숨겨진 질문도 작성자 본인에게는 보인다(hidden=true로).
  인증 필수 — 비인증이면 UNAUTHENTICATED.
  """
  myQuestions(first: Int = 20, after: String): SpotQuestionConnection!  # NEW
}
```

`SpotQuestionConnection`은 이미 있으니 그대로 재사용하면 됩니다. `SpotQuestion.spot`이
non-null이라 어느 장소의 질문인지도 함께 옵니다 — 목록에서 장소명을 보여주는 데 필요한
값이 이미 노드 안에 있습니다.

`myPosts`가 정확히 같은 모양으로 이미 있으므로(라이브 확인) 그 구현을 그대로 따르면
됩니다.

### 왜 필요한가 — 지금은 답을 받을 방법이 없습니다

**현재 구조에서 질문자가 답변을 확인하는 유일한 경로는 이렇습니다.**

> 어느 장소에 질문했는지 스스로 기억 → 그 장소를 검색하거나 지도에서 찾음 →
> 장소 상세 진입 → 질문 목록 → 목록에서 내 질문을 눈으로 찾음 → 열어서 답변 확인

기억에 의존하는 단계가 맨 앞에 있습니다. 사흘 전 스와이프하다 지나친 장소 이름을
기억해야 답을 볼 수 있습니다. **사실상 못 봅니다.**

라이브 스키마를 확인한 결과 다음이 전부 없습니다.

| 조회 | 상태 |
|---|---|
| `myQuestions` / `mySpotQuestions` | `FieldUndefined` |
| `myAnswers` | `FieldUndefined` |
| `spotQuestions(authorId:)` / `(mine:)` 인자 | `UnknownArgument` |
| `notifications` / `unreadNotificationCount` | `FieldUndefined` |
| `spotQuestion(id:)` 단건 조회 | `FieldUndefined` |

**즉 서버 데이터만으로는 "내가 어느 장소에 질문했는지"를 알아낼 수단이 아예 없습니다.**
클라이언트가 작성 시점에 로컬로 기록해 두지 않으면 영구히 유실됩니다.

### 알림이 제외된 것과 겹칩니다

스펙 "제외"에 "질문 푸시 알림 및 답변 대상자 타겟팅"이 있습니다. 알림을 안 만드는 것은
이번 범위로 이해합니다. **다만 알림도 없고 내 질문 목록도 없으면 답변이 달렸다는 사실을
알 경로가 0이 됩니다.** 둘 중 하나는 있어야 기능이 성립합니다.

`myQuestions`는 푸시 인프라 없이 조회 하나로 해결되므로 훨씬 싼 선택입니다. 답변 수는
`SpotQuestion.answerCount`로 이미 내려오니, 클라이언트가 마지막으로 본 수와 비교해
"새 답변" 배지를 스스로 만들 수 있습니다.

### 함께 검토해 주시면 좋을 것 (선택)

`spotQuestion(id: ID!): SpotQuestion` 단건 조회도 없습니다. 지금은 목록 provider가 유일한
출처라, 딥링크나 앱 재시작으로 뒤쪽 페이지의 질문에 직접 들어오면 열리지 않습니다.
①·②만큼 급하지는 않지만(정상 진입 경로에서는 도달하지 않습니다) 알림이나 공유 링크를
나중에 붙이면 반드시 필요해집니다.

## 클라이언트가 그동안 하는 것

②가 구현되기 전까지 **로컬 기록으로 버팁니다.** 질문 작성 성공 시 `catalogId`·`questionId`·
작성 시각·마지막으로 본 `answerCount`를 로컬에 쌓고, 「내 질문」 화면이 그 id들로 각
장소의 질문 목록을 조회해 되짚습니다. `recent_searches_store`와 같은 패턴입니다.

**이것은 임시방편이며 한계가 분명합니다.**

- 기기를 바꾸거나 앱을 지우면 기록이 사라집니다 — 질문은 서버에 남는데 주인이 못 찾습니다
- 같은 계정을 두 기기에서 쓰면 각 기기가 서로 다른 목록을 보여줍니다
- 장소당 한 번씩 조회하므로 질문이 여러 장소에 흩어지면 왕복이 늘어납니다

`myQuestions`가 생기면 이 로컬 저장소는 **삭제합니다.** 서버가 정답을 주는데 클라이언트가
따로 기록을 쥐고 있으면 둘이 어긋나는 순간 어느 쪽이 맞는지 판단할 근거가 없습니다.
