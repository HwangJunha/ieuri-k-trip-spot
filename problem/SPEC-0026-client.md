# SPEC-0026 장소 질문/답변 — 클라이언트 설계

요구사항·수용 기준·계약 초안은 스펙에 있다. 이 문서는 이 repo의 설계 결정만 다룬다.

관련 이슈: `#61`. 브랜치: `feature/SPEC-0026-spot-qa`.

## feature 배치

`lib/domain/spot_qa/`로 새 feature를 만든다. 기존 `spot`이나 `community`에 넣지 않는다.

- `spot`은 TourAPI 기반 장소 조회·스와이프를 다룬다. 질문/답변은 회원 생성 콘텐츠라 성격이 다르다
- `community`는 전역 게시판이다. 질문은 장소 상세에 종속되며 목록의 위치가 다르다
- `dm`과도 분리한다 — 질문/답변에서 DM으로 나가지만, 그 반대 방향 의존은 없다

```
lib/domain/spot_qa/
  component/   질문 카드 · 답변 타일 · 답글 타일 · 사진 첨부 피커 · 자격 안내 배너
  model/       SpotQuestion · SpotAnswer · SpotAnswerReply · SpotQaOrigin
  provider/    질문 목록 · 질문 상세 · 작성 · 사진 업로드
  repository/  spot_qa_repository
  view/        질문 목록 화면 · 질문 상세 화면 · 작성 화면
```

생성된 GraphQL 타입은 `repository/`를 넘지 않는다(POL-020). repository가 `model/`의 도메인
모델로 매핑한다.

## 진입점 (「지금 여기 어때?」)

장소 상세 화면(`lib/domain/spot/view/spot_detail_view.dart`)에 버튼을 놓는다. 이 화면은
SPEC-0025의 범위 밖이므로 레이아웃 충돌이 없다 — SPEC-0025는 스와이프 카드 화면을 다룬다.

버튼은 두 곳으로 간다. **질문이 있으면 질문 목록**, 없으면 바로 작성으로 보낸다. 빈 목록을
보여주고 다시 한 번 누르게 하는 것은 이 기능의 진입 장벽을 불필요하게 높인다.

**좋아요 직후에 이어서 질문할 수는 없다 — 기존 동작과의 충돌을 그대로 둔다.**
`spot_detail_view.dart`의 `_react()`는 반응 성공 시 카드를 스와이프 스택에서 소비하고
화면을 pop 한다(SPEC-0006 R11·R12, AC-38·AC-39). 따라서 "여기서 좋아요를 누르면 그 자리에서
진입점이 나타난다"는 흐름은 성립하지 않는다. 자격을 갖춘 사용자는 이미 좋아요한 장소를
다시 열었을 때(검색·좋아요 목록·지도·딥링크) 진입점을 본다.

이 pop을 질문 작성 유도를 위해 바꾸지 않는다. SPEC-0006의 수용 기준이 걸려 있어 이번 스펙이
단독으로 뒤집을 수 있는 동작이 아니다. 좋아요 직후 유도가 필요하다는 결론이 나면 별도 스펙에서
두 스펙을 함께 다뤄야 한다.

## 작성 자격 — 게이팅을 없앤다 (R3, R4, R5 폐지 요청)

**결정(2026-08-18, 사용자): 좋아요 여부와 무관하게 누구나 질문·답변할 수 있다.**
`LIKE`·`DISLIKE`·반응 없음 셋 다 허용이며, 진입점은 항상 보인다.

**왜 바꿨나 — 질문할 이유와 좋아요할 이유가 반대다.** 「지금 여기 어때?」는 **가기 전에**
묻는 질문이다. 지금 붐비는지, 주차가 되는지 — 아직 가 보지 않았고 좋아할지도 모르는
상태에서 나온다. 반면 좋아요는 이미 기운 판단이다. 게이팅은 **질문이 가장 필요한 사람을
정확히 막았다.** DISLIKE도 같다: 한 번 실망한 사람이 "그때 공사 중이었는데 지금은
끝났나요?"를 묻지 못했다.

모집단 문제도 겹친다. 스펙 스스로 좋아요 5명 미만인 장소가 흔하다고 적어 두었는데
(R11 임계값 논의), 그런 장소에서는 질문을 올려도 답할 사람이 없다. 게이팅을 풀면 답변
모집단이 「좋아요한 회원」에서 「그 장소를 아는 회원」으로 넓어진다.

**서버도 게이팅을 걷어냈다(2026-08-18).** 요청이 반영되어 R3·R4·R5와 AC-3.2·AC-3.3·
AC-4.2·AC-3.6이 스펙에서 빠졌고, `NOT_ELIGIBLE_TO_ASK` / `NOT_ELIGIBLE_TO_ANSWER`를
더 이상 내보내지 않는다. 클라이언트도 그에 맞춰 **정리를 끝냈다**:

- `spot_qa_eligibility.dart`(자격 판정)와 `spot_qa_eligibility_banner.dart`(안내 배너) 삭제
- `SpotQaComposerState.notEligible` · `SpotQaMutationResult.notEligible` 삭제
- 자격 안내 문구 2종을 4개 로케일에서 제거
- 작성 화면·인라인 컴포저의 자격 분기 삭제 — 이제 거절 사유를 가리지 않고 같은 안내를 띄운다

**AC-3.6("비활성 + 좋아요 안내")은 규칙째로 사라졌다.** 자격이라는 개념이 없어졌으니
비활성으로 보일 대상도 없다. 진입점은 항상 활성이다.

서버가 보내지 않는 코드를 검사하는 죽은 가지는 남기지 않았다 — 나중에 읽는 사람에게
그 규칙이 아직 있다고 알리기 때문이다.

**거절 시 입력 내용을 유실하지 않는 규칙은 그대로다.** 자격이 아니어도 본문 검증 같은
다른 거절이 남아 있고, 어느 쪽이든 화면을 닫지 않고 안내만 띄운다.

`SpotDetail.viewerReaction`은 남긴다. 자격 판정에는 안 쓰지만 상세가 내 반응 상태를
표시하는 데 쓰며, 이 필드가 없으면 좋아요 수 델타가 어긋나는 기존 버그가 되살아난다.

## 내 질문 (스펙 밖 — 사용성 보강)

**질문을 올린 사람이 답변을 받아 볼 공간이 없었다.** 스펙이 화면을 목록·상세·작성 3개로
잡고 알림을 「제외」에 넣은 결과, 답을 보려면 어느 장소에 질문했는지 스스로 기억해
그 장소를 다시 찾아 들어가야 했다. 사실상 못 본다.

**서버가 `spotQuestions(mine: true)`로 답했다(2026-08-18).** 요청은 `myQuestions`라는
새 루트였는데, 서버는 루트를 나누지 않고 기존 조회에 필터를 얹었다 — 루트가 둘이면
정렬·커서·차단 규칙이 두 벌이 되어 갈라지기 때문이다. 클라이언트도 매핑 코드 한 벌을
그대로 쓰므로 이쪽이 낫다.

그래서 **한때 로컬에 질문 목록을 쌓던 임시 저장소는 삭제했다.** 서버가 정답을 주는데
클라이언트가 따로 기록을 쥐면 어긋날 때 판단 근거가 없다. 그 결과 **기기를 바꿔도, 앱을
지웠다 깔아도 내 질문이 그대로 보인다** — 로컬 방식의 가장 큰 구멍이 그것이었다.

`mine: true`는 **인증이 필수**다. 비로그인이면 최상위 `errors`로 실패하며, 화면은 이를
빈 목록으로 접지 않는다 — 조용히 비우면 "쓴 적 없음"으로 오해되는데 실제로는
"로그인하면 보인다"이기 때문이다.

**로컬에 남은 것은 「마지막에 본 답변 수」 하나뿐이다**(`SeenAnswerCountsStore`).
서버에 읽음 지점이 없어 `answerCount`가 누적값으로만 오고, 그래서 "어디까지 봤는지"를
서버가 모른다. 이 값이 비어도 목록은 정상이고 배지만 안 뜬다 — **목록의 정확성을
로컬 상태에 걸지 않는다.** 서버가 질문별 읽음 지점을 갖게 되면 이것도 걷어낸다.

진입점은 두 곳이다: 마이페이지(못 본 개수 배지 포함)와 질문 목록 화면 상단.

목록 줄에는 **장소 썸네일**을 붙인다. 이 목록은 장소를 가로지르므로 어느 장소에
물었는지가 가장 먼저 구분돼야 하고, 그건 글자보다 이미지가 빠르다. 썸네일은 이미
`spotQuestions`가 `PostSpot.thumbnailImageUrl`로 내려주고 있어 추가 조회가 없다.

## 채팅 진입 (기존 결함 수습)

대화 목록 화면과 라우트는 있는데 **거기로 가는 버튼이 앱 어디에도 없었다**(`origin/dev`
부터 그런 상태였다 — SPEC-0021로 피드가 걷히며 진입 경로가 사라졌다). 질문/답변에서
DM을 시작하게 만들어 놓고 그 대화를 다시 찾을 길이 없으면 반쪽이라, 마이페이지에
「메시지」 진입을 추가했다.

## 진입점·작성 화면 디자인 (2026-08-18, 벤치마크 반영)

「비어 보인다」는 지적을 받고 실서비스를 조사해 고쳤다.

**진입점은 한 줄짜리 행이다.** 아이콘 · 「지금 여기 어때?」 · 질문 수 · 화살표. 예전에는
큰 버튼과 텍스트 버튼이 세로로 쌓여 두 칸을 먹으면서 정보를 주지 않았다. **질문 수를
함께 보이면 줄 자체가 들어갈 이유가 된다** — "3개 있네"와 "아직 없네"는 다음 행동이
다르다. 조회 전에는 둘째 줄을 비운다(0개라고 단정했다가 뒤집히면 잘못 알려준 것이다).

아이콘은 겹친 말풍선(`forum`)을 유지한다. **말풍선 개수가 의미를 가른다** — 겹친 2개는
여러 사람의 스레드, 단일 버블은 1:1 대화다. 이 앱에는 이미 DM이 있어 단일 버블 계열은
그쪽과 헷갈린다. 물음표가 든 `contact_support`는 전 세계적으로 "고객센터" 관용이라 뺐다.

**「내 질문」은 상세가 아니라 질문 목록 화면 상단과 마이페이지에 둔다.** 상세는 *이
장소*를 보는 화면이고 내 질문은 장소를 가로지르는 목록이라 성격이 다르다.

**작성 화면에 세 가지를 넣었다.**

1. **장소 헤더** — 어디에 묻는지 한 줄. 장소명이 비면(딥링크) 줄째로 생략한다.
2. **예시 질문 칩 4개** — 혼잡·운영·주차·우천. 본문이 비었을 때만 나오고 쓰기 시작하면
   사라진다. 탭하면 완성된 질문이 입력창에 들어가고 **커서가 끝에 놓인다** — 곧바로
   제출하지 않는다. 빈 화면에서 문장을 짓는 것보다 있는 문장을 고치는 편이 쉽다.
3. **구체적인 플레이스홀더** — "질문을 입력하세요" 같은 동어반복 대신 실제 예시.

칩의 근거는 **작성률이 아니라 cold start**다. 신규 장소는 질문이 0개라 무엇을 물어도
되는지 알 수 없고, 빈 입력창은 "무엇이든 쓰세요"가 아니라 "뭘 써야 할지 모르겠다"로
읽힌다. 부수 효과가 더 중요한데 **답변 가능한 질문으로 수렴시킨다** — 혼잡·주차·날씨는
가 본 사람이면 바로 답할 수 있다. 답 없는 질문이 쌓이면 기능이 죽는다(구글 지도가
커뮤니티 Q&A를 접은 이유가 그것이다).

**칩 라벨은 주제어, 채워지는 것은 문장이다.** 처음엔 문장을 그대로 칩에 넣었는데 렌더해
보니 하나가 한 줄씩 차지해 화면 아래 1/3을 먹었다. 라벨을 주제어로 줄이니 두 줄에
들어간다. 4개 언어의 길이가 제각각이라 가로 스크롤 한 줄이 아니라 `Wrap`을 쓴다.

**칩은 카테고리가 아니다.** 고르면 입력창을 채우고 사라질 뿐 질문에 꼬리표로 남지
않는다 — 서버 계약에 그런 개념이 없고, 분류로 승격시키면 없는 필드를 만들게 된다.

넣지 않은 것: 제목 필드(필드가 늘수록 이탈이 는다 — 본문 하나라는 강점을 지킨다),
카테고리 선택, 상단 가이드 문구 블록, 상시 카운터(90%부터만 노출), 사진 아이콘(서버
미구현이라 비활성 아이콘조차 두지 않는다 — 되는 줄 알고 누른다).

## 질문 목록 화면 (R1, R2, R16)

- 정렬은 서버가 고정한다(미해결 우선, 그 안에서 최신순). **정렬 UI를 두지 않는다** — 두면
  계약에 없는 인자를 요구하게 된다
- 미해결과 해결을 시각적으로 구분한다. **강조가 뒤집혀 있다** — 미해결이 강조색
  배지로 뜨고 해결됨은 낮은 명도의 아이콘 + 글자다. 이 기능은 답이 달려야 성립하는데,
  답을 기다리는 질문이 해결된 것과 같은 톤이면 어느 것이 도움을 기다리는지 알 수 없다
- 해결됨도 숨기지 않는다 — 지난 질문의 답변도 다음 방문자에게 정보다
- 배지는 `SpotQaResolutionBadge` 하나로 목록·상세·「내 질문」이 함께 쓴다. 세 곳이
  제각기 그리면 한쪽만 고쳐질 때 조용히 어긋난다
- **배지는 오른쪽 끝에 붙인다.** 본문 아래 왼쪽은 읽는 눈이 먼저 닿는 자리라 본문의
  일부처럼 읽힌다
- 커서 기반 무한 스크롤. 기본 20건씩
- 로그인하지 않아도 읽을 수 있다(AC-1.4). 읽기 화면에서 인증을 요구하지 않는다

## 질문 상세 화면 (R7)

질문 본문 + 답변 목록 + 답변별 답글. 답글은 답변에 종속되어 표시된다.

**질문 본문의 출처가 둘이다.** 목록에서 들어온 보통의 경우에는 목록 provider가 이미
받아 둔 항목을 쓴다 — 해결 표시의 낙관적 갱신을 그 컨트롤러가 쥐고 있어 즉시 반영된다.
목록에 없으면 `spotQuestions(ids: [...])`로 직접 조회한다(딥링크·알림 진입, 아직 받지
못한 페이지).

서버는 여기서도 `spotQuestion(id:)` 루트를 만들지 않고 `ids` 필터를 택했다(2026-08-18).
같은 이유다 — 루트를 나누면 규칙이 두 벌이 된다.

**빈 결과는 오류가 아니다.** 차단·숨김·삭제로 가려진 id는 결과에서 빠지도록 서버가
정해 두었고 그 구분은 클라이언트에 오지 않는다 — "없거나 볼 수 없음"을 하나로 다루며
재시도를 권하지 않는다. 반면 전송 실패는 재시도가 의미 있어 버튼을 준다. 두 경우를
화면이 구분한다.

**`ids: []`는 "결과 없음"이지 "전체"가 아니다.** repository가 빈 목록이면 서버를 부르지
않고 곧장 빈 결과를 돌려준다 — 결과는 같지만 왕복 한 번을 아낀다.

**답글에는 답글 액션을 노출하지 않는다**(AC-7.3의 클라이언트 측 표현). 계약의
`SpotAnswerReply`에 `replies` 필드가 없으므로 타입 수준에서도 불가능하다.

**해결 표시는 상단바 ⋮ 메뉴에 있고 토글이다.** 처음에는 본문 아래 왼쪽에 두었는데,
바로 위 「해결됨」 배지와 자리도 아이콘(`check_circle_outline`)도 같아 **버튼이 아니라
상태 표시로 읽혔다** — 아직 해결하지 않은 질문인데 이미 해결된 것처럼 보였다.

⋮로 옮기면서 신고도 같은 메뉴에 넣었다. 둘은 서로 배타적이라(내 질문이면 해결 토글,
남의 질문이면 신고) 각각 아이콘을 두면 자리만 차지한다.

**되돌릴 수 있다**(2026-08-18 서버가 `resolveSpotQuestion`에 `resolved` 인자를 필수로
추가했다). 메뉴 라벨은 「해결」/「미해결」 두 단어다 — 상태는 배지가 이미 보여주므로
액션이 그것을 다시 설명할 필요가 없다. 확인 다이얼로그는 없앴다 —
되돌릴 수 없던 시절에는 한 번 물었지만, 지금은 잘못 눌러도 한 번 더 누르면 그만이라
그 물음이 사용자를 붙잡을 뿐이다.

이 인자를 놓쳐 한동안 **서버에서 반드시 실패하는 뮤테이션을 들고 있었다.** 라이브 스윕이
`variables: {}`로 보내 필수 인자 누락이 `coerced Null`(무시하도록 정해 둔 잡음)로 묻혔기
때문이다. CLAUDE.md §13에 그 한계와 보완 절차를 적어 두었다.

**당겨서 새로고침이 있다.** 답변이 달렸는지 보러 다시 들어오는 화면이라 갱신 수단이
필요하다. 질문과 답변을 **함께** 다시 받는다 — 답변만 받으면 해결 여부·답변 수 같은
질문 쪽 값이 낡은 채로 남는다. 질문의 출처가 둘이라(목록 캐시 또는 `ids` 조회) 양쪽을
다 무효화한다.

답변 목록은 커서 페이지네이션, 답글은 답변에 딸려 한 번에 내려온다.

## 사진 첨부 (R9) — 커뮤니티 업로드를 그대로 쓴다

**전용 뮤테이션은 만들지 않기로 서버가 정했다(2026-08-18).** 계약 초안의
`createSpotQaImageUploadUrls` 3종 대신 커뮤니티의 `createPostImageUploadUrls` /
`confirmPostImageUploads` / `deletePostImage`를 그대로 쓴다.

근거는 오브젝트 키 형식이다. `{상태}/community/{memberId}/{uuid}`라서 검증이 **회원
소유 기준**이고 질문 id가 키에 들어가지 않는다 — 질문/답변 사진도 같은 흐름을 그대로
통과한다. 전용 경로를 만들면 같은 로직의 복사본이 되고 고를 이유 없는 선택지만 는다.
DM도 같은 판단으로 커뮤니티 업로드를 재사용하고 있다(POL-042).

흐름은 커뮤니티 글과 동일하다: presigned URL 발급 → R2 직접 PUT → confirm → 확정된
키를 `createSpotQuestion(input: { photoKeys: [...] })`에 전달. 최대 5장.

**실패 코드가 커뮤니티와 통일돼 있다** — `OBJECT_KEY_NOT_FOUND`가 아니라
`PHOTO_NOT_UPLOADED`다. 확정되지 않은 임시 키(`pending/...`)를 작성에 넘겼을 때 온다.

**업로드는 제출 시점이다.** 고르는 즉시 올리면 질문을 쓰지 않고 나간 사용자의 사진이
스토리지에 고아로 남고, 붙였다 뺐다를 반복하면 그만큼 쌓인다 — 실제 저장 비용이다.
그래서 컴포저는 아직 올리지 않은 장(`LocalPhoto`)을 그대로 들고 있다가 「올리기」에서
한 번에 올린다(커뮤니티와 같은 판단).

**부분 성공이 정상이다.** 1단계 발급은 전부 아니면 전무지만(빈 목록이 곧 "전부 거부"),
3단계 확정은 장별로 갈린다. 통과한 장은 상태에서 같은 자리의 `RemotePhoto`로 바뀌므로
**제출이 거부돼 다시 눌러도 이미 올라간 장을 또 올리지 않는다.** 실패한 장수는 안내로
알리되 **질문 자체는 올라간다** — 사진 한 장 때문에 사용자가 쓴 글을 통째로 버리게
하지 않는다.

크기 상한(10 MiB)은 고른 직후에 거른다. 발급이 하나만 어긋나도 전부 거부되므로, 큰 장
하나가 나머지를 같이 죽이지 않게 미리 빼고 걸러진 장수를 알린다.

작성을 취소하면 이미 확정한 키를 `deletePostImage`로 정리한다. 다만 **정리를 기다리지
않고 닫는다** — 화면을 떠나는 길을 네트워크에 묶을 이유가 없고, 실패해 남은 오브젝트는
서버 lifecycle의 몫이다.

**답변·답글에는 사진을 붙이지 않았다.** 계약상 `createSpotAnswer`도 `photoKeys`를
받지만, 답변 컴포저는 목록 하단의 좁은 한 줄이라 첨부 줄을 넣을 자리가 없다. 스펙의
"최대 5장"도 질문을 기준으로 쓰여 있다. 필요해지면 인라인 컴포저를 펼치는 형태로
바꿔야 하며 그건 별도 설계다.

업로드 실패는 장별로 갈린다. 일부만 성공한 경우 성공한 것은 유지하고 실패한 것만 재시도할
수 있어야 한다 — 전부 다시 올리게 하지 않는다.

작성을 취소하면 이미 확정한 키를 `deleteSpotQaImage`로 정리한다. 정리하지 않으면 서버에
고아 파일이 남는다.

## DM 연결 (R13, R14)

답변·답글의 작성자에게 DM을 시작하는 액션을 둔다. `startConversation`에 `sourceAnswerId`를
함께 보낸다.

대화 화면(`lib/domain/dm/`)에서 `Conversation.spotQaOrigin`이 있으면 상단에 맥락 카드를
표시한다 — 장소명과 질문 발췌. 카드를 누르면 그 장소 상세로 간다(`catalogId`가 스냅샷에
있으므로 항상 유효하다).

**출처가 없는 대화도 정상 동작해야 한다.** 기존 DM은 전부 `spotQaOrigin`이 null이며,
맥락 카드 없이 지금과 같이 표시된다. 이 필드를 non-null로 가정하는 코드를 쓰면 기존 대화가
깨진다.

### 인용은 대화가 아니라 메시지에 붙는다 (2026-08-18, 서버 변경 · breaking)

**서버가 인용을 메시지 단위로 옮겼다.** `StartConversationInput.sourceAnswerId`와
`Conversation.spotQaOrigin`이 사라지고 `SendMessageInput.sourceAnswerId`와
`Message.spotQaOrigin`이 생겼다.

이전에는 대화당 인용이 하나뿐이었고 최초 시작 시점에 고정됐다. 그래서 A 질문으로
대화를 튼 뒤 B 질문에서 같은 사람에게 말을 걸면 상단 카드가 계속 A를 가리켰다 —
사용자는 B를 보고 왔는데 화면은 A를 말했다. 그때는 평문을 입력창에 채워
("'릴랙스워크' 질문 관련해서 문의드려요") 우회했는데, 이제 계약이 제대로 지원한다.

**바뀐 것:**

- **상단 고정 카드가 없다.** 인용이 말풍선 안으로 들어갔다 — 인스타 스토리 답장과
  같은 모양이다. 카드 하나로는 두 번째 인용을 표현할 수 없었고, 갈아끼우면 첫 인용이
  사라졌다(Airbnb 헤더가 그 방식이고 그래서 욕먹는다)
- **평문 조립을 걷어냈다.** 문장을 지어 보내는 대신 `sourceAnswerId`를 넘긴다
- **몇 번이든 인용할 수 있고 앞선 인용은 그대로 남는다**

**DM 진입은 대화를 연 뒤 인용을 첫 메시지로 보낸다.** 본문 없이 인용만 보낸다
(`body: ''`) — 사용자가 아직 할 말을 쓰지 않았는데 문장을 지어 보내는 것은 월권이다.
인용만 먼저 놓고 무슨 말을 할지는 사용자가 정한다.

**낙관적 말풍선에 스냅샷을 지어 넣지 않는다.** 스냅샷의 출처는 서버이고, 여기서
만들어 두면 서버가 인용을 만들지 못했을 때(답변 삭제) 없는 인용이 잠깐 보인다.
대신 `sourceAnswerId`를 전송 경로에 직접 실어 보낸다 — 스냅샷에서 되짚게 했더니
낙관 스냅샷이 없어 인용이 서버에 전달되지 않았다(테스트가 잡았다).

**인용을 만들지 못해도 메시지는 간다.** 답변이 삭제됐거나 작성자가 대화 상대가
아니면 서버가 조용히 무시하고 일반 메시지로 보낸다 — 거절이 아니므로 화면은
`Message.spotQaOrigin`이 null인 경우를 정상으로 다룬다.

**인용도 「내용」이다.** `Message.hasContent`가 인용을 포함해야 본문 없이 인용만 보낸
메시지가 "내용 없음"으로 그려지지 않는다.

## 신고·차단 (R11, R12)

- 질문·답변·답글에 신고 액션. 기존 `reportContent`를 그대로 쓰며 대상 타입만 새 값
  (`SPOT_QUESTION` / `SPOT_ANSWER` / `SPOT_ANSWER_REPLY`)을 넘긴다
- 신고 사유는 고정 4종(POL-041 2항). 자유 입력을 받지 않는다
- 차단 관계 콘텐츠는 서버가 목록에서 제외한다. **클라이언트가 별도로 거르지 않는다** —
  이중 필터링은 서버 규칙이 바뀔 때 어긋난다

## 본문 길이 (미검증)

상한 500자를 `String.length`(UTF-16 코드 단위)로 센다. 제출 가능 판정과 화면의 카운터가
같은 기준을 쓰므로 "카운터는 초과인데 버튼은 활성" 같은 어긋남은 없다.

**서버가 무엇으로 세는지는 확인하지 못했다.** 인증 없이 보낸 요청은 길이 검증에
닿기 전에 끊겨(`INTERNAL_ERROR`) 이모지로 재 볼 수 없었다. 코드포인트로 센다면
이모지가 많은 본문에서 클라이언트가 먼저 막는 쪽으로 어긋난다 — 데이터가 잘리는 방향은
아니라 그대로 두되, 로그인 상태로 확인할 기회가 생기면 맞춘다.

## 상태 관리

Riverpod codegen. 목록은 페이지네이션 상태를 가지는 notifier, 작성은 폼 상태 notifier로 나눈다.

**낙관적 업데이트를 적용하는 것**: 질문 해결 표시. 되돌리기가 없고 실패 확률이 낮다.

**적용하지 않는 것**: 질문·답변·답글 작성. 서버가 자격을 판정하므로 낙관적으로 목록에 넣으면
거부 시 롤백이 필요한데, 그 사이 사용자가 자기 글을 본 상태가 된다. 작성은 서버 응답을
기다린 뒤 목록을 갱신한다.

## 구현하며 갈린 것 (2026-08-18)

- **신고가 community repository에 있다.** `reportContent`는 커뮤니티 소유라 spot_qa가
  신고하려면 커뮤니티의 provider까지 끌어다 쓴다(§3의 기능 간 의존). `dm`이 이미 같은
  방식으로 커뮤니티 신고 시트를 쓰는 선례가 있어 그대로 따랐다. 신고를 `common/`으로
  올리는 것이 정리 방향이지만 이번 스펙의 범위를 넘어선다.
- **작성 라우트는 질문 목록의 자식이 아니라 최상위다.** 자식으로 두면 GoRouter가 부모를
  함께 쌓아 장소 상세에서 곧장 작성으로 갔을 때 뒤에 빈 목록이 깔린다 — 「빈 목록을
  거치지 않는다」가 그 자리에서 깨진다. 질문 상세만 자식으로 남겨 뒤로 가기가 목록이
  되게 했다.
- **질문·답변 삭제 UI를 만들지 않았다.** 모델에 `ownedByViewer`가 있고 서버에 삭제
  뮤테이션도 있으나 R1~R16이 삭제 화면을 요구하지 않는다. repository까지는 열어 두었으니
  필요해지면 커뮤니티의 삭제 확인 패턴을 그대로 얹으면 된다.

## 답변을 받아 볼 자리 — 「내 질문」 (2026-08-18 사용자 지적)

**"질문을 올렸는데 답변을 받아 볼 공간이 없다."** 서버에 `myQuestions`도 알림도 없어서
(라이브 확인 완료) 질문을 올린 사용자가 답을 확인할 경로가 앱에 전혀 없었다.

**클라이언트가 로컬로 기록한다.** 작성이 성공하면 `catalogId`·`questionId`·장소명·작성
시각을 SharedPreferences에 적어 두고(`MyQuestionRef`, 상한 50건), 「내 질문」 화면이 그
기록의 `catalogId`로 각 장소의 질문 목록을 조회해 내 질문을 되짚는다. 장소당 한 번만
조회하며, 한 장소가 실패해도 나머지는 그대로 보여준다.

한계를 화면에 적는다 — **이 기기에만 저장된다**(`spotQaLocalOnlyNotice`). 기기를 바꾸거나
앱을 지우면 사라지고, 같은 계정을 두 기기에서 쓰면 각자 다른 목록을 본다. `myQuestions`가
계약에 생기면 저장소와 이 화면의 되짚기를 **삭제한다**.

**「새 답변 N개」 배지가 이 화면의 존재 이유다.** 알림이 없으므로 마지막으로 열어 본
답변 수(`seenAnswerCount`)와 지금 서버 값의 차이가 "답이 달렸다"를 알리는 유일한 신호다.
질문 상세를 열면 그 시점의 답변 수를 기록해 배지를 끈다.

**서버에서 못 찾은 질문도 목록에서 지우지 않는다.** 삭제·숨김·페이지 밖 중 어느 것인지
클라이언트가 구분할 수 없고, 조회 실패를 삭제로 해석하면 일시적인 네트워크 오류에 내
기록이 사라진다. 본문 자리에 안내만 띄운다.

### 진입점 세 곳

- **설정(마이페이지)** — "내 질문"(못 본 답변이 있으면 개수 배지), "메시지". 대화 목록
  화면은 예전부터 있었으나 **앱 어디에도 진입점이 없었다**(origin/dev부터) — 질문/답변에서
  시작한 DM을 다시 열 자리가 필요해 여기 뚫었다
- **장소 상세** — 기존 「지금 여기 어때?」(OutlinedButton) 아래에 「내 질문」 TextButton.
  주-보조를 시각적으로 구분한다. 여기서 물었으니 여기서 답을 확인하러 돌아온다
- 라우트는 `/my/questions`로 **최상위**다. 설정 아래에 두면(내가 쓴 글과 달리) 장소
  상세에서 열었을 때 뒤로 가기가 설정 홈으로 빠진다

### 갈린 것

- **장소명은 작성 화면에 쿼리 파라미터(`?spot=`)로 넘긴다.** 작성 화면이 `domain/spot`의
  상세 provider를 watch하면 기능 간 의존이 생긴다(§3). 장소 상세의 `?thumb=`와 같은
  성격의 **표시용 힌트**이며, 딥링크로 들어와 비어 있어도 작성은 정상 동작하고 목록이
  서버 조회로 장소명을 채운다 — 장소명 때문에 작성이 실패하는 경로가 없다
- **「내 질문」 행(`MyQuestionsEntryTile`)은 `spot_qa`가 소유한다.** 배지가 spot_qa의
  provider를 보기 때문이며, 설정은 자리만 내준다(설정→auth와 같은 방식의 진입점 의존)
- **좋아요 게이팅 폐지에 맞춰 기존 테스트를 고쳤다.** `canWriteSpotQa`·인자를 받던
  `showSpotQaEntry`가 사라져 해당 테스트 4건이 컴파일되지 않았다 — 노출은 항상 참이라는
  단일 테스트로 대체했다. **서버 거부 분기(`NOT_ELIGIBLE_TO_*`)는 그대로 둔다**
- **`MyQuestionRef`의 시각 비교를 순간 기준으로 바꿨다.** `encode`는 UTC로 쓰고
  `decode`는 로컬로 읽는데 `DateTime.==`가 UTC 플래그까지 보는 탓에, 저장했다 읽은 값이
  원본과 다르다고 나왔다(왕복 테스트로 드러남)

## 테스트가 실릴 단위

provider/notifier와 도메인 모델 로직의 단위 테스트만 작성한다. 위젯·통합 테스트는 범위 밖이다.

- 질문 목록 notifier — 페이지 누적, 커서 진행, 빈 목록
- 작성 notifier — 서버 거부 시 입력 보존, 사진 키 누적, 취소 시 정리 호출
- 해결 표시 notifier — 낙관적 반영과 실패 시 롤백
- 모델 매핑 — GraphQL 응답 → 도메인 모델, `spotQaOrigin` null 처리
- 자격 판정 표시 로직 — `viewerReaction`이 null / LIKE / DISLIKE일 때의 진입점 노출 여부

repository는 스텁한다. 실제 GraphQL 전송을 세우지 않는다.
