# SPEC-0027 — 장소 상세 미니 지도 (클라이언트)

요구사항·수용 기준·계약은 spec에 있습니다. 이 문서는 이 리포에 한정된 설계 판단만 담습니다.

## 착수 전 확인 — 소형 지도가 되는가

**이것을 가장 먼저 하십시오.** 나머지 설계는 전부 이 확인에 걸려 있습니다.

`kakao_map_sdk`로 비전체화면 지도를 그린 사례가 이 앱에 아직 없습니다. 현재 유일한 `KakaoMap` 사용처는 전체화면 지도 화면이고, 그것은 `Scaffold` 본문 전체를 차지하며 스크롤되지 않습니다. 미니 지도는 정반대 조건입니다 — **`SingleChildScrollView` 안의 고정 높이 박스**이고, 사용자가 스크롤하면 화면 밖으로 나갔다 들어옵니다.

네이티브 뷰를 Flutter 위젯 트리에 끼워 넣는 구조(플랫폼 뷰)에서 이 조건은 흔한 문제 지점입니다. 확인할 것:

1. 스크롤 뷰 안에서 지도가 정상 렌더링되는가
2. 스크롤이 지도 위에서 지도에 먹히지 않고 부모 스크롤로 전달되는가 — **이것이 가장 위험합니다.** 지도가 세로 드래그를 자기 팬 제스처로 삼키면 사용자가 지도 위에서 화면을 스크롤할 수 없습니다
3. 화면 밖으로 나갔다 돌아올 때 지도가 유지되는가, 재초기화되는가
4. 상세 화면을 열고 닫기를 반복할 때 네이티브 리소스가 누수되지 않는가

2번이 해결되지 않으면 지도 영역을 사용자가 팬할 수 없게 고정하는 것(제스처를 지도에 주지 않고 탭만 받는 것)이 대안입니다. 이 경우에도 R10·R11의 줌·내 위치 컨트롤은 카메라를 프로그램으로 움직이므로 그대로 성립하며, spec의 어떤 요구사항도 팬 제스처를 요구하지 않습니다.

**전부 막히면 임의로 우회하지 말고 `[AMEND]`로 보고하십시오.** 정적 지도 이미지로 대체하는 것 같은 판단은 spec 개정 사항입니다.

## 교차 feature 의존 — 공용화가 선행 작업이다

필요한 것들이 전부 `lib/domain/map/` 아래에 있습니다.

| 필요한 것 | 현재 위치 | 성격 |
|---|---|---|
| 줌 컨트롤 | `lib/domain/map/component/` | 순수 표현. 콜백만 받음 |
| 내 위치 버튼 | `lib/domain/map/component/` | 순수 표현. 콜백과 진행 상태만 받음 |
| 오버레이 그리기 (핀·내 위치 점) | `lib/domain/map/component/` | SDK 컨트롤러를 생성자로 받는 재사용 가능 클래스 |
| 실시간 좌표 provider | `lib/common/location/` | **이미 common에 있음. 이동 불필요** |
| 하버사인 거리 계산 | `lib/common/model/` | **이미 common에 있음. 이동 불필요** |
| 거리 표기 포맷 | `lib/common/model/` | **이미 common에 있음. 이동 불필요** |

`lib/domain/spot/`에서 `lib/domain/map/`을 직접 import하면 교차 feature 의존 금지에 걸립니다. 앞의 세 개를 `lib/common/`으로 올립니다.

**승격은 이동이지 재작성이 아닙니다.** 세 컴포넌트 모두 이미 map 화면의 상태에 결합되어 있지 않고 콜백과 값만 받습니다 — 즉 이미 공용 컴포넌트의 모양을 하고 있으며, 위치만 잘못 있습니다. 승격 후 전체 지도 화면의 동작이 달라지면 그것은 승격을 잘못한 것입니다.

거리 계산·표기가 이미 `common`에 있다는 사실이 R8(표기 일관성)을 거의 공짜로 만들어 줍니다. **새 포맷 함수를 만들지 마십시오.** 기존 것을 그대로 호출하면 AC R8-3("스와이프 카드의 표기 결과와 문자열로 같다")이 구조적으로 보장됩니다.

## 상태 소유

지도 섹션의 상태를 상세 화면 컨트롤러에 섞지 않고 **별도 provider**로 둡니다.

이유는 생명주기가 다르기 때문입니다. 상세 본문은 한 번 받으면 끝이지만, 지도 상태는 사용자 위치 스트림에 따라 계속 갱신됩니다. 둘을 한 상태에 두면 위치가 5m 움직일 때마다 상세 본문 전체를 들고 있는 상태 객체가 새로 만들어지고, 갤러리·소개·연락처를 그리는 위젯이 전부 다시 빌드됩니다.

지도 섹션 상태가 들고 있어야 하는 것:

- spot 좌표 (상세 응답에서, 고정)
- 사용자 좌표 (스트림에서, 갱신됨) — **없을 수 있음**
- 계산된 거리 — 두 좌표가 다 있을 때만
- 카메라 상태 (중심·배율)
- 지도 사용 가능 여부 (SDK 초기화 실패 판정)

사용자 좌표를 **nullable로 두는 것이 이 설계의 핵심**입니다. R9·R14가 요구하는 축소 동작이 여기서 나옵니다 — 좌표가 null이면 거리도 null이고, 내 위치 표시도 목록에 들어가지 않습니다. 실패를 별도 플래그로 표현하지 마십시오. `hasLocationError` 같은 것을 따로 두면 "좌표는 null인데 에러 플래그는 false"인 상태가 생기고, 그 조합에서 화면이 무엇을 그려야 하는지 아무도 모릅니다.

위치 실패 사유(권한 거부 / 서비스 꺼짐 / 조회 실패)는 **구분하지 않습니다.** R14가 세 경우에 같은 결과를 요구하고 AC R14-1/2/3이 그것을 명시합니다. 전체 지도 화면의 기존 내 위치 버튼도 사유를 구분하지 않고 같은 안내를 냅니다.

## 위치 조회 — 어느 provider를 쓰는가

`common/location`에 두 가지가 있습니다.

- 1회 조회 provider — 값이 고정됨. 스와이프 세션이 이것을 씁니다
- 실시간 스트림 provider — autoDispose. 구독자가 없으면 GPS 스트림이 종료됩니다

**미니 지도는 1회 조회를 씁니다.**

상세 화면은 사용자가 잠깐 머무는 화면이고, 여기서 알고 싶은 것은 "지금 여기서 저기까지 얼마나 머냐"입니다. 걸어 다니면서 거리 배지가 실시간으로 줄어드는 것은 이 화면이 답하는 질문이 아니고, 그 대가로 GPS 스트림을 켜 두는 것은 배터리를 씁니다.

R11(내 위치 바로가기)이 실시간성을 요구하는 것처럼 보이지만 아닙니다 — 그 버튼은 **카메라를 옮기는 것**이지 위치를 갱신하는 것이 아닙니다. 다만 최초 조회가 실패했을 때 이 버튼이 재시도 경로가 되어야 합니다(R11의 "실패를 알리고"는 재시도했으나 또 실패한 경우입니다). 자동 재시도는 두지 않습니다 — POL-040에 따라, 그리고 사용자가 명시적으로 누르는 것이 더 정직합니다.

## 카메라 맞춤 (R5)

두 좌표를 담는 영역 계산은 **순수 함수로 분리하십시오.** SDK 호출과 섞지 마십시오. AC R5-1~4가 전부 이 함수에 대한 테스트이고, SDK가 관여하면 단위 테스트로 판정할 수 없게 됩니다.

함수가 다뤄야 하는 경계:

- 두 좌표가 같은 지점 → 영역 크기가 0이 되면 안 됨 (AC R5-3). SDK에 넘기면 배율이 무한대로 튑니다
- 여백 → 두 점이 화면 가장자리에 붙지 않도록 (AC R5-2). 핀 아이콘 자체가 좌표 위쪽으로 그려지므로 여백 없이는 위쪽 핀의 머리가 잘립니다
- 거리가 멀어지면 배율이 단조 감소 (AC R5-4)

여백 값과 최소 영역 크기는 spec이 수치를 정하지 않았습니다. 구현 재량이되, **상수로 박지 말고 이름 있는 값으로 빼십시오**(POL-044의 계열). 실기기에서 조정하게 됩니다.

### SDK 함정 — 배율을 함께 넘길 것

전체 지도 화면에 이미 기록된 함정이 있습니다: 카메라 중심만 바꾸는 API에 배율을 명시하지 않으면 기본값이 네이티브까지 전달되어 **전국 축소로 튑니다.**

R11(내 위치 이동)이 정확히 이 API를 씁니다. AC R11-3("배율을 기본값으로 되돌리지 않는다")이 이 함정을 잡기 위한 기준입니다. 현재 배율을 읽어 함께 넘기십시오.

## 지도를 그릴 수 없을 때 (R15)

SDK 키 부재·초기화 실패는 지도 섹션만의 문제이고 상세 화면 전체의 문제가 아닙니다. AC R15-2가 이것을 명시합니다 — 소개·운영 정보·연락처는 그대로 나와야 합니다.

전체 지도 화면은 화면 전체를 안내 문구로 대체하지만, 여기서는 **섹션 하나만 대체**합니다. 기존 안내 문구 키를 재사용하되, 전체 화면용 문구가 섹션 크기에 맞지 않으면 새 키를 만드십시오(4개 언어 전부).

## 전체 지도로의 이동 (R13)

지도 영역 탭 → 전체 지도 경로. 다만 **컨트롤 탭이 이동을 일으키면 안 됩니다**(AC R13-2/3). 줌 버튼을 누를 때마다 화면이 전환되면 지도가 쓸모없어집니다.

컨트롤을 지도 위에 겹쳐 놓되 탭 처리는 컨트롤이 먼저 소비하도록 계층을 구성하십시오. 컨트롤이 지도 영역 밖에 있으면 이 문제 자체가 없어지지만, 그 배치가 섹션 높이를 키웁니다 — 겹침을 권합니다.

전체 지도로 이동할 때 **해당 spot을 중심에 두고 열지, 그냥 열지**는 spec이 정하지 않았습니다. 중심에 두는 편이 자연스럽지만 전체 지도 화면의 초기 카메라 로직과 충돌할 수 있습니다. 간단하면 중심에 두고, 기존 로직을 건드려야 하면 그냥 여십시오 — 후자를 택했다면 이슈 완료 코멘트에 적으십시오.

## 문자열 (POL-022)

거리 표기는 기존 키를 재사용합니다. 새로 필요할 수 있는 것:

- 지도 섹션 제목 (둘 것인지부터 판단 — 다른 섹션은 제목이 있지만 지도는 자명합니다. 제목 없이 지도만 두는 쪽을 권합니다)
- 지도 섹션용 SDK 불가 안내 (기존 키로 충분하면 추가하지 않음)

**추가하는 키는 4개 언어에 함께 넣습니다.** 한국어 파일이 템플릿이고 설명은 한국어로 씁니다.

## 테스트

Riverpod notifier와 순수 함수 단위 테스트만입니다. 위젯·통합 테스트는 비범위입니다.

| 단위 | 테스트 |
|---|---|
| 지도 섹션 상태 provider | AC R3, R4, R6, R7, R9, R14 전부. 사용자 좌표 유무에 따른 상태 조합이 핵심 |
| 카메라 영역 계산 (순수 함수) | AC R5-1~4 |
| 상세 화면 섹션 구성 | AC R2-1~3, R15-1~2 |
| 거리 표기 | AC R8-1~3. 기존 포맷 함수를 재사용하면 대부분 이미 통과 |
| 컨트롤 동작 | AC R10, R11, R12, R13 |

지도 SDK에 실제로 무엇이 그려지는지는 테스트 대상이 아닙니다. 판정하는 것은 **어떤 핀 목록과 어떤 카메라 값을 계산해 SDK에 넘기는가**까지입니다.

`SpotDetail` 도메인 모델에 좌표가 더해지므로 repository 매핑 테스트가 있다면 함께 갱신하십시오. 생성 타입이 repository 밖으로 나가지 않아야 합니다(POL-020) — 좌표는 기존 `Coordinates` 값 객체로 매핑합니다.

## 하지 않는 것

- 길찾기, 외부 지도 앱 연동
- 두 점을 잇는 경로선
- 주변 spot 표시, 클러스터링, 혼잡도 폴리곤
- 줌·내 위치 외의 컨트롤 (R12가 이것을 요구사항으로 못박았습니다)
- 카메라의 사용자 위치 자동 추적
- 사용자 위치를 서버로 전송 (POL-045 — 이 화면은 위치를 기기 밖으로 내보내지 않습니다)

## 중단 기록 (2026-08-19) — 쿼터 구조 때문에 보류한다

**구현은 완료했으나 되돌렸다.** 기능이 동작하지 않아서가 아니라, 이 화면이 카카오
지도 쿼터를 감당할 수 없는 방식으로 쓰기 때문이다.

### 무엇이 문제인가

카카오는 **"지도를 로딩하는 호출"을 1건으로 센다.** 화면 이동·확대/축소·마커 추가는
세지 않는다(카카오 직원 답변, devtalk 149529·150594). 일간 무료 30만건이다.

미니 지도는 상세 화면에 있고, 상세는 이 앱의 **주된 탐색 행위**다. 그래서 호출량이
이렇게 곱해진다:

```
지도 로드 = DAU × 1인당 상세 열람 횟수
```

전체 지도 탭은 사용자당 몇 번이지만 상세는 수십 번이다. DAU 6,000명이 각 50개를 보면
정확히 30만건이다. 게다가 **곱해지는 두 항이 모두 성장과 함께 늘어난다** — 사용자가
늘고, 앱이 재밌어질수록 1인당 열람도 는다. 초과분은 건당 과금이라 조용히 샌다.

기능 자체의 결함이 아니라 **배치의 문제**다. 같은 지도를 전체 지도 탭에 두면 아무
문제가 없다.

### 시도한 해법과 결과

업계 표준은 두 가지다(구글 Maps Platform 최적화 가이드).

**1. 정적 지도 이미지로 대체 — 불가**

구글·맵박스는 `https://.../staticmap?center=…&markers=…` 형태의 이미지 URL을 준다.
캐시가 들어 같은 장소를 100번 열어도 사실상 1건이다.

**카카오는 이미지 URL을 제공하지 않는다.** `kakao.maps.StaticMap`은 div에 렌더링하는
JavaScript SDK 전용이라, Flutter 네이티브 앱에서 쓰려면 WebView에 지도를 로드해야
하고 그러면 피하려던 로드가 그대로 일어난다.

**2. 인스턴스 재사용 — 이 SDK에서는 불가 (2회 실측 실패)**

지도 하나를 앱에 상주시키고 화면들이 빌려 쓰는 구조를 만들었다. Flutter가
`GlobalKey`가 붙은 위젯은 트리를 옮겨도 파괴하지 않는다는 문서 근거를 썼다
(`platform_view.dart:68`).

1차: 상세 3회 진입 → 로드 3건. 실패.
2차: 프레임 동기화를 고침 → 여전히 3건. 실패.

**원인은 SDK 구조다.** 네이티브 뷰를 실제로 쥔 `PlatformViewLink`/`UiKitView`는
`_KakaoMapState.build()`가 매번 새로 반환하고 **키가 없다**. 우리가 붙일 수 있는
`GlobalKey`는 한 단계 바깥의 `KakaoMap`이라 정작 필요한 지점에 닿지 않는다. 트리
위치가 바뀌면 키 없는 자식은 매칭되지 않고 파괴 후 재생성된다.

→ **SDK를 수정하지 않는 한 위젯 바깥에서 인스턴스를 재사용할 방법이 없다.**

Flutter 이슈 #64080(2020~)이 같은 문제이고 아직 미해결이다. 프레임워크 차원의
해법이 없다는 뜻이다.

### 남은 길

**상세 화면을 파괴하지 않는 것**뿐이다. 상세가 최상위 push 라우트라 닫힐 때 화면이
통째로 사라지고 지도도 함께 죽는다. 상세를 Discover 화면 안의 **인라인 시트**로
만들면 화면이 파괴되지 않으니 지도가 살아 있다 — 프레임 타이밍이나 SDK 내부 구조에
기대지 않고 "위젯이 트리에 남아 있다"는 사실에만 의존한다.

다만 이것은 **네비게이션 구조 개편**이라 SPEC-0027의 범위를 넘는다. 진입 경로가 7곳
이고(Discover·홈 추천·홈 인기·Happening Now·지도 마커·검색·좋아요 목록), 반응 후 pop
계약(R11·R12)과 QA 라우트도 함께 검토해야 한다. 별도 스펙으로 다룰 일이다.

**지연 로딩(보일 때만 로드)은 채택하지 않았다.** 호출을 절반쯤 줄이지만 곱셈 구조가
그대로 남아 근본 해결이 아니다(사용자 결정).

### 남긴 것

- **`SpotDetail.mapX/mapY`** — SDL·쿼리·도메인 모델·repository 매핑. 서버에 이미
  non-null로 있던 것을 클라이언트가 안 받고 있었다. 지금 쓰는 화면은 없지만 서버가
  주는 값을 도메인까지 싣는 것은 그 자체로 옳고, 다시 붙일 때 서버 확인과 codegen을
  되풀이할 이유가 없다.
- **`MapLoadCounter`** — 걷어냈다. 다시 시도할 때 `onMapReady`에 한 줄 붙이면 된다
  (커밋 094ebbb 참조). 콘솔 사용량은 반영이 늦어 개발 중 판정에 못 쓴다.

### 걷어낸 것

`SpotMiniMap`, `MiniMapOverlay`, `MiniMapState`, `fitCamera`, `MiniMapController`,
그리고 상세 화면 통합·l10n 키·테스트. 구현은 커밋 `e6573a5`에 남아 있으므로 인라인
시트가 정해지면 거기서 되살린다 — 카메라 계산과 상태 설계는 배치와 무관하게 그대로
쓸 수 있다.

`MapZoomControls`·`MyLocationButton`의 `common/widget` 승격도 함께 되돌렸다.
쓰는 곳이 전체 지도 하나로 돌아갔기 때문이다.

### 다음에 이 문서를 읽는 사람에게

**"미니 지도를 다시 붙이자"는 판단은 배치 문제를 먼저 풀고 와야 한다.** 지도를 상세에
두는 이상 로드는 열람 횟수만큼 일어나고, 그것을 막을 방법이 이 SDK에는 없다. 인라인
시트든 다른 것이든, 상세 화면이 파괴되지 않는 구조가 선행 조건이다.
