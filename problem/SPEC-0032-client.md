# SPEC-0032 — 클라이언트 설계

요구사항·수용 기준·계약은 spec에 있다. 이 문서는 **k-trip-spot 안에서의 설계 판단만** 다룬다.

관련 이슈: `HwangJunha/ieuri-k-trip-spot#75` · 브랜치 `feature/SPEC-0032-auth-recovery-and-retry-caps` (`dev`에서 분기)

---

## 1. 먼저 — 무엇이 이미 맞게 되어 있는가

**HTTP 토큰 갱신 경로 자체는 손대지 않는다.** 조사 결과 아래가 모두 올바르게 구현되어 있다.

| 장치 | 위치 | 역할 |
|---|---|---|
| 요청별 `retried` 플래그 | `graphql_client.dart` `_RefreshLink` | 요청당 갱신 1회 |
| `_inFlight` 단일 비행 | 같은 파일 `_refreshOnce` | 동시 401 N건 → 갱신 1회 |
| `TokenRefreshBridge.suppressed` | 같은 파일 | 실패 후 연쇄 재발화 차단 |
| 갱신 후 `AuthLink` 재읽기 | 링크 순서 | 재생 시 새 토큰 자동 반영 |

리프레시 토큰이 서버에서 일회성으로 회전되므로 단일 비행은 **필수**다. 이것이 이미 있다는 것은
중요하다 — **이 spec은 갱신을 고치는 것이 아니라 갱신 바깥을 고친다.**

무한 호출 버그도 `RetryLink`나 수동 재시도 루프 때문이 아니다. 그런 것은 없다. **웹소켓 하나와
Riverpod 기본값이 원인이다.**

## 2. 인증 실패 판정의 단일화 (R10·R18)

### 2.1 현재 구조

판정이 **두 계층에서 따로** 일어난다.

| 계층 | 판정 방식 | 인식하는 코드 |
|---|---|---|
| 링크 (`_RefreshLink`) | `auth_error_classifier.dart` — 3단계 (code → errorType → 메시지) | `UNAUTHENTICATED` `INVALID_TOKEN` `TOKEN_REUSE_DETECTED` `EMAIL_NOT_VERIFIED` `FORBIDDEN` |
| 저장소 9종 | 각자 문자열 리터럴 | 대부분 `UNAUTHENTICATED`만 |

`AuthRepositoryImpl`만 분류기를 쓰고 나머지 8종은 쓰지 않는다.

### 2.2 무엇이 깨지는가

**`INVALID_TOKEN`을 매칭하는 저장소가 0개다.** 링크는 이 코드로 갱신하는데, 갱신이 억제된 상태에서
이 코드가 저장소에 도달하면 **네트워크 오류로 분류된다.** 결과가 셋이다.

1. 사용자에게 "네트워크 오류"로 보인다 — 실제로는 재로그인이 필요하다
2. 재시도 예산을 소모한다 (`retry_counting.dart`가 `unauthenticated`만 면제한다)
3. 재시도 지연을 거친다 — 재시도로 해결되지 않는 실패인데

`map`·`national_map`·`event` 3개 도메인은 더 나쁘다. **실패 모델에 인증 갈래 자체가 없다.**
`MapFailure`는 `String? code`를 그대로 들고 있고 `NationalMapFailure`는 `isUnauthenticated` 게터가
있으나 아무도 분기하지 않는다.

### 2.3 설계

**모든 저장소가 `auth_error_classifier`를 거친다.** 새 분류기를 만들지 않는다 — 3단계 판정이 이미
견고하고 서버가 내는 코드를 전부 안다.

- 저장소별 `fromQueryErrorCode`의 인증 갈래를 분류기 호출로 대체한다.
- 도메인 고유 코드(`SPOT_NOT_FOUND` 등)는 그대로 저장소가 판정한다. **분류기는 인증만 본다.**
- `map`·`national_map`·`event`의 실패 모델에 **인증 갈래를 추가한다** (R18). 없는 것을 매칭할 수는
  없다.

**신규 코드 2종을 분류기에 추가한다** (계약 §3).

| 코드 | 분류 | 처리 |
|---|---|---|
| `AUTH_STORE_UNAVAILABLE` | 재시도 가능 | 세션 유지, 상한 내 재시도 |
| `SUBSCRIPTION_UNAUTHENTICATED` | **영구** | 재연결 금지, 갱신 후 재구독 |

`SUBSCRIPTION_UNAUTHENTICATED`을 영구로 두는 것이 R15의 핵심이다. 소켓 신원은 `connection_init`에
고정되어 **재연결해도 결과가 같다.** 지금 `UNAUTHENTICATED`이 영구가 아니라서 무한 재연결이 돈다.

> 이 슬라이스는 서버보다 먼저 나간다. 아직 오지 않는 코드를 미리 인식해 두는 것이며, **그것이
> 서버 배포의 파괴를 흡수하는 방법이다.**

## 3. 세션 종료 판정의 기본값 뒤집기 (R11·R12)

### 3.1 현재 구조가 왜 잠기는가

`_refreshSession`이 **세션을 끝내는 경우를 열거하고 나머지를 전부 유지**한다 —
`refreshRejected` · `tokenReuseDetected` · `accountInactive`만 종료, 그 외는 `RefreshUnavailable`.

`AuthFailure.fromCode`는 모르는 코드에 `unknown`을 반환한다. 둘을 합치면:

**서버가 클라이언트가 모르는 인증 코드를 내면 → `unknown` → `RefreshUnavailable` → 갱신 억제 +
토큰 유지 + 세션 유지 → 사용자가 아무것도 못 하는 상태로 고정된다.**

빠져나올 방법은 `retryRefresh()`뿐인데 **호출부가 없다.** 앱 재시작이 유일한 복구다.

이것이 사용자가 보고한 "로그아웃일 때 재로그인이 안 된다"의 실체다. 로그아웃 화면으로 가지도
못하고 갱신도 안 되는 중간 상태다.

### 3.2 설계

**열거를 반대로 한다.** 세션을 유지할 조건을 열거하고 나머지는 종료한다.

| 판정 | 조건 | 결과 |
|---|---|---|
| 유지 | 네트워크 오류 · `AUTH_STORE_UNAVAILABLE` · 타임아웃 — **재시도 가능함이 확인된 경우** | 화면 유지 + 재시도 수단 |
| 종료 | 그 외 전부 (모르는 코드 포함) | 로그인 화면 |

**모르는 코드에서 로그인 화면으로 보내는 것이 안전한 기본값이다.** 재로그인은 사용자가 아는 동작이고,
잠긴 세션은 아무도 모르는 상태다. 잘못 보내도 사용자는 다시 로그인하면 되지만, 잘못 잠그면 앱을
지우는 수밖에 없다.

**억제 해제 경로를 UI에 노출한다** (R12). `retryRefresh()`가 호출부 없이 존재하는 현 상태를 고친다.
세션 유지 판정이 난 화면(위 표 첫 행)에 재시도 수단을 둔다.

라우팅은 기존 경로를 쓴다 — `signOut()` → 상태 변경 → `app_router`의 리스너 → `resolveGate`
리다이렉트. 이 경로는 정상 동작하므로 **판정만 바꾸면 라우팅은 따라온다.**

## 4. 소켓 재연결 (R13)

`resetSocketConnection()`이 존재하고 문서 주석까지 있으나 **호출부가 없다.**

소켓 신원은 `connection_init`의 `initialPayload`에 고정되어 HTTP 갱신으로 바뀌지 않는다. 갱신
성공 후에도 소켓은 낡은 신원을 유지하고, 서버가 새 `subscribe`를 거부할 때까지 그 상태다 —
그리고 그 거부가 §5의 무한 재연결로 이어진다.

**갱신 성공 지점에서 부른다.** `AuthController._refreshAccessToken`이 `RefreshSucceeded`를 받아
토큰을 저장하는 자리가 유일하게 "새 신원이 확정된" 지점이다.

주의: 소켓 클라이언트는 `keepAlive` 싱글턴이고 auth와 별개 provider다. 갱신 경로가 소켓 provider를
직접 참조하면 순환이 생길 수 있다 — `locale_invalidation.dart`가 이중 등록으로 `CircularDependencyError`를
겪은 선례가 있다. **직접 참조보다 상태 관찰이 안전하다.** 구현 시 판단한다.

## 5. 재시도 상한 (R14·R15·R16·R17)

### 5.1 웹소켓 — 유일한 진짜 무한 루프

```
autoReconnect: true
delayBetweenReconnectionAttempts: 5초
inactivityTimeout: null
```

**상한이 없다.** `subscriptionReconnectAttempts = 5`가 선언되어 있고 주석이 "상한은 클라이언트가
센다"라고 적고 있으나 **읽는 코드가 없다.** 세는 주체가 없다.

여기에 `ConversationController.onError`가 겹친다 — `DmFailure.permanent`(즉 `FORBIDDEN`)일 때만
구독을 닫고, 그 외에는 `sync()`를 부르고 재연결에 맡긴다. `UNAUTHENTICATED`은 `permanent`가
아니므로:

**5초마다 재연결 + 매 사이클 `sync()` HTTP 질의 → 영원히.** 이것이 보고된 무한 호출이다.

**설계**: 재연결 시도를 클라이언트가 직접 센다. 상한 도달 시 `autoReconnect`에 맡기지 않고 구독을
닫는다. 성공적으로 연결되면 카운터를 리셋한다. **선언된 상수를 실제로 쓰는 것이 최소 요건이다.**

`SUBSCRIPTION_UNAUTHENTICATED`은 카운터를 태우지 않고 **즉시 종료**한다 (R15) — 재연결로 해결되지
않으므로 5회를 세는 것 자체가 낭비다. 갱신 후 재구독 경로로 보낸다.

### 5.2 HTTP — 상한은 있으나 구멍이 있다

명시된 정책은 전부 1회 + `RetryBudget` 2회로 잘 잡혀 있다. 문제는 **정책이 없는 provider가 약
40개**라는 것이다. Riverpod 3의 기본값은 **10회 지수 백오프**이며, 코드 주석이 이미 이를 알고 있다.

무한은 아니지만 POL-040 위반이고, 인증 실패에 10회를 태우는 것은 실패당 10배의 트래픽이다.
`map`·`national_map`·`event`가 특히 그렇다 — 인증 개념도 재시도 정책도 없어 **인증 실패에 10회
재시도가 그대로 나간다.**

**설계**: 전역 기본 상한을 명시적으로 정하고 도메인별 정책이 없는 곳에 적용한다 (R17).
Riverpod 기본값에 의존하지 않는다 — 라이브러리 기본값은 우리 정책이 아니다.

POL-040에 따라 **횟수로** 표현한다. 지연·백오프 값은 근거가 없으므로 새로 만들지 않는다 — 기존
400ms 고정을 따르되, 이 수치를 늘리거나 지수화하지 않는다.

### 5.3 재시도하지 않을 실패 (R15)

`retry_counting.dart`가 현재 `unauthenticated`만 면제한다. 아래를 **전부 면제**한다 — 예산을
소모하지 않고 즉시 해당 처리로 보낸다.

- `UNAUTHENTICATED` → 갱신 경로
- `INVALID_TOKEN` · `TOKEN_REUSE_DETECTED` → 세션 종료
- `SUBSCRIPTION_UNAUTHENTICATED` → 재구독 경로
- `FORBIDDEN` · `EMAIL_NOT_VERIFIED` · 입력 오류 · 미존재 자원 → 해당 화면 처리

`AUTH_STORE_UNAVAILABLE`은 **면제하지 않는다** — 진짜 재시도 대상이다.

### 5.4 상한 소진의 가시성 (R16)

조용히 멈추면 사용자는 앱이 멈춘 것으로 인식하고, 그 상태에서 할 수 있는 것이 앱 재시작뿐이 된다 —
§3이 고치는 것과 같은 실패 양상이다.

상한이 소진된 화면은 실패 상태와 재시도 수단을 함께 노출한다. 구독 끊김은 별도 표시가 필요하다 —
데이터가 틀린 것이 아니라 **갱신이 멈춘 것**이라 화면만으로는 구별되지 않는다.

문구는 EN 우선 EN/KO/JA/ZH (POL-022). 문구 자체는 클라이언트가 가진다 (POL-016).

## 6. 위치 취급 — 클라이언트는 바뀌지 않는다

위치 감사 기록(R19~R22)은 **전적으로 서버 작업이다.** 클라이언트는 지금처럼 좌표를 보내고, 기록
여부를 알지도 못한다.

**클라이언트에 위치 관련 변경이 없다.** `location_service.dart`에 geolocator 호출이 전부 모여 있고
권한 요청도 한 곳이며, 폴링 타이머도 없다 — 이미 올바르다. 건드리지 않는다.

**주의**: 감사 기록이 생긴다고 해서 클라이언트가 좌표를 더 보내거나 정밀도를 올리지 않는다.
POL-045의 "필요 이상의 정밀도를 요구하지 않는다"가 그대로 적용된다.

## 6-b. 닉네임 (R32·R33)

**클라이언트는 제거만 한다.** 닉네임 결정은 전적으로 서버 작업이며(R29·R30), 클라이언트가 닉네임을
보내지 않는다 — 계약에 인자가 추가되지 않는다.

### 6-b.1 카카오 닉네임은 이미 받고 있고, 그대로 둔다

`sns_authenticator.dart`가 `UserApi.instance.me()`로 카카오 닉네임을 받아 `SnsCredential.nickname`에
담고 있다. **이 값은 가입 화면 프리필용이며 서버로 보내지 않는다.** 지금 동작이 맞고, 바꾸지 않는다.

서버는 별도로 `id_token` 클레임에서 닉네임을 읽는다. **두 값이 다를 수 있고, 서버 값이 정본이다.**
가입 후 화면에 보이는 닉네임이 프리필과 다를 수 있으나 이는 의도된 동작이다.

> 프리필 값을 서버로 보내 일치시키고 싶은 유혹이 있지만, 그러면 임의 값을 넣을 수 있게 되어
> "provider가 준 값을 쓴다"는 요구가 무너진다. 보내지 않는다.

### 6-b.2 제거 대상 (R32)

중복이 허용되면 아래가 전부 도달 불가능한 코드가 된다.

| 대상 | 위치 |
|---|---|
| `nicknameAlreadyTakenCode` 상수 | `profile_edit_controller.dart` |
| `nicknameTaken` 상태 플래그와 `hasFieldError` 합성 | 같은 파일 |
| 중복 에러 분기 | 같은 파일 |
| 화면의 중복 문구 표시 | `profile_edit_screen.dart` |
| `profileEditNicknameTaken` 문구 | ARB 4개 언어 + 생성 파일 |
| 코드젠 enum의 `NICKNAME_ALREADY_TAKEN` | 재생성으로 사라진다 |

**형식 검증은 남긴다.** 길이 검사와 `INVALID_NICKNAME` 분기는 중복과 무관하다.

> **부수 발견 — 최소 길이 불일치.** 서버는 2자 미만을 거부하는데 클라이언트 검증은 빈 값과 최대
> 길이만 본다. 1자 닉네임이 제출되면 서버가 형식 오류로 거절한다. **이 spec의 범위 밖**이며
> 고치려면 별도 이슈로 낸다 — 중복 허용과 무관하고, 지금 함께 건드리면 R32의 리뷰 범위가 흐려진다.

### 6-b.3 화면 (R33)

**게시글·댓글·DM·관계 목록은 바꾸지 않는다.** 이미 회원 식별자를 함께 받고 있고, 탈퇴 회원이 이미
모두 같은 문구로 표시되고 있어 동일 표시가 새로운 조건이 아니다.

동명이인 구별 UI를 지금 만들지 않는다 — 실사용 데이터 없이 만들면 근거 없는 설계가 된다.

## 7. 테스트가 실릴 단위

**provider/notifier와 도메인 모델 로직만 테스트한다. 위젯·통합 테스트는 쓰지 않는다.**

| 요구 | 단위 |
|---|---|
| R10·R18 | 분류기 — 코드별 판정. 저장소별 인증 갈래 매핑 |
| R11 | 갱신 실패 → 세션 종료/유지 판정 (모르는 코드 포함) |
| R12 | 억제 해제 → 갱신 재시도 |
| R14 | 재연결 카운터 — 상한 도달 시 중단, 성공 시 리셋 |
| R15 | 코드별 재시도 예산 소모 여부 |

**인프라로만 관측되는 것.** 실제 웹소켓 재연결 동작(R13·R14의 전송 계층)은 소켓 서버가 있어야
드러난다. **카운터와 판정 로직을 전송에서 분리해 순수하게 테스트하고, 전송 결합은 검증하지
않는다.** 통합 테스트 계획을 지어내지 않는다.

기존 `retry_budget` 테스트가 있으므로 그 형태를 따른다.

## 8. 이 문서가 여는 것

| 슬라이스 | 완료 시 열리는 것 |
|---|---|
| 1 (코드 매칭·재시도 상한) | **무한 호출이 이 시점에 멈춘다.** 서버가 새 코드를 내도 안전해져 서버 슬라이스 2가 배포 가능해진다 |
| 3 (복구 경로) | 재로그인 흐름이 끝에서 끝까지 닫힌다. **사용자가 겪던 재로그인 버그가 이 시점에 해소된다.** 그리고 서버 슬라이스 4(실시간 세션)가 배포 가능해진다 |

**슬라이스 3이 서버 슬라이스 4의 선행 조건이다.** R13(갱신 후 소켓 재연결)이 없으면 갱신에
성공해도 소켓이 낡은 신원을 유지하고, 서버가 R7로 그 연결을 거부하기 시작하는 순간 재구독이
영영 실패한다. 슬라이스 1만으로는 부족하다 — 재연결은 멈추지만 구독이 복구되지 않는다.

**슬라이스 1이 서버보다 먼저 나가야 한다.** 서버가 먼저 나가면 `VIEWER_AWARE` 9종이
`UNAUTHENTICATED`를 내기 시작하는데, 구버전 앱은 그 연산들에서 조용히 비로그인 데이터를 받고
있었으므로 화면이 비는 대신 **에러를 보게 된다.**

> 미출시 상태라 실사용자 영향은 없다(spec §9.0). 순서는 개발 환경의 혼선을 막기 위해 지킨다.

**슬라이스 6(닉네임)만 순서가 반대다 — 서버가 먼저다.** 클라이언트가 먼저 중복 분기를 지우면
아직 서버가 내는 `NICKNAME_ALREADY_TAKEN`을 처리하지 못한다. 반대는 안전하다: 서버가 더 이상
방출하지 않는 코드를 클라이언트가 잠시 더 인식하고 있어도 도달하는 응답이 없다.

파괴의 방향이 달라서다 — 슬라이스 1은 **서버가 새로 내는 에러**, 슬라이스 6은 **서버가 더 이상
내지 않는 에러**다.

## B. 스와이프 — 원인을 두 번 짚었다

처음에는 애니메이션 부재로 봤고(맞다, `AnimationController`가 없었다), 넣은 뒤에도
끊겨서 다시 봤다. **진짜 원인은 리빌드 범위였다** — 매 프레임 `setState`를 부르면
사진·텍스트·오버레이를 포함한 카드 스택 전체가 60fps로 다시 빌드된다.

변위를 `ValueNotifier`로 옮기고 `ValueListenableBuilder`의 `child`로 카드를 고정해,
프레임마다 다시 그리는 것을 `Transform` 하나로 좁혔다. 손 떼는 속도를 스프링백과
날아가기에 실어 손가락과 카드가 이어지게 했다.

**상하 확정은 걷어냈다**(사용자 결정). 아래로 밀면 패스가 되는 것이 직관과 어긋난다 —
좋아요는 오른쪽, 패스는 왼쪽이라는 관례가 굳어 있다. 카드는 여전히 손가락을 따라
위아래로도 움직이지만 판정은 가로 변위만 본다.

이 과정에서 **dispose 크래시**를 발견해 함께 고쳤다. 컨트롤러가 `late final`이라
카드를 한 번도 밀지 않은 화면에서는 `dispose()`가 첫 접근이 되고, 이미 비활성화된
트리에서 `createTicker`가 조상을 찾다 터진다 — Discover 탭을 지나가기만 해도 났다.

## C. 약관 — 웹뷰로 전문을 띄운다

가입 동의 화면이 `"Full terms text coming soon."`을 그대로 띄우고 있었다. 개인정보를
수집하는 앱이 약관 본문 없이 동의를 받는 셈이라 심사에서 그대로 반려된다.

**주소는 `TermsCode.documentUrl`이 단일 출처다**(`common/model/terms_code.dart`) —
가입 폼(auth)과 약관 관리(settings) 둘 다 쓰므로 `common/`에 둔다(§4).

| 항목 | 주소 |
|---|---|
| 서비스 이용약관 | `https://www.ieuri.co.kr/terms` |
| 개인정보 처리방침 | `https://www.ieuri.co.kr/privacy` |
| 위치기반서비스 이용약관 | `https://www.ieuri.co.kr/location-terms` |

마케팅 수신 동의는 `null`이다 — 별도 문서가 없고 서비스 약관에 포함된다.

**본문을 앱에 넣지 않는 이유**: 약관은 앱 배포와 무관하게 개정되고 개정본이 즉시
효력을 갖는다. 번들에 박으면 심사를 통과한 구버전 앱이 낡은 약관을 계속 보여 준다.

**외부 브라우저가 아닌 웹뷰인 이유**: 가입 도중 앱을 나갔다 오면 입력하던 폼이 날아갈
수 있다. 심사자도 같은 경로를 밟는다. 대신 앱바에 "브라우저로 열기"를 둬 막다른 길이
되지 않게 했다.

노출 지점은 둘이다 — **가입 동의 체크리스트**의 각 항목 옆 "보기", **설정 → 약관 관리**의
각 행에 문서 아이콘. 동의한 뒤에도 상시 열람할 수 있어야 한다.

`webview_flutter: ^4.14.1`을 추가했다. Android 디버그 빌드로 실제 컴파일을 확인했고,
세 주소 모두 HTTP 200에 서버 렌더 본문임을 확인했다(개인정보 처리방침 15개 조항).

## D. 권한 사유 문구

**iOS**(`Info.plist`) — Apple은 "무슨 데이터를, 어느 기능에, 왜"가 없으면 반려한다.
막연한 문구를 구체적으로 다시 썼다.

- `NSLocationWhenInUseUsageDescription` — 주변 관광지 표시·거리순 정렬·실시간 혼잡도.
  **없으면 어떤 곳이 가까운지 알 수 없다**는 점과, 백그라운드 추적을 하지 않는다는 점을 명시.
- `NSPhotoLibraryUsageDescription` — 사진의 위치 태그로 방문 지역을 채우고 글·프로필에
  첨부. 기기에서 읽고 **첨부를 고를 때만 업로드**된다는 점을 명시.

`NSPhotoLibraryAddUsageDescription`과 `NSUserTrackingUsageDescription`은 **넣었다가
뺐다** — 코드를 확인하니 이미지 저장 기능도 광고 추적도 없다. 쓰지 않는 권한을 선언하면
그 자체가 심사 질의 대상이 된다.

카메라 권한은 없다 — `image_picker`를 `ImageSource.gallery`로만 쓴다(확인함).

**Android**(`AndroidManifest.xml`) — 매니페스트 주석이 이미 각 권한의 근거를 적고 있어
문구 수정은 없다. 다만 **`READ_MEDIA_IMAGES`는 Play 선언 심사 대상**이다(아래 §E).

## G. 사진 접근 — 두 경로를 구분해야 한다

사용자 질문(2026-08-24)으로 정리한다. 이 앱이 사진에 닿는 경로는 **둘이고 요건이
서로 다르다.**

| 경로 | 쓰는 것 | 권한 | 어디에 |
|---|---|---|---|
| 사진 **첨부** | `image_picker` | **필요 없음** | 커뮤니티 글, 프로필 사진 |
| 전국 지도 **EXIF 스캔** | `photo_manager` | `READ_MEDIA_IMAGES` + `ACCESS_MEDIA_LOCATION` | 방문 지역 자동 채우기 |

**첨부는 권한이 필요 없다.** `image_picker`는 Android 13+에서 시스템 Photo Picker를
띄우고, 사용자가 고른 사진의 URI만 앱에 넘어온다 — 앱이 권한을 받을 일이 없다.
[공식 문서](https://developer.android.com/training/data-storage/shared/photopicker)가
명시한다: *"Android 13+ devices: No READ_MEDIA_IMAGES or READ_MEDIA_VIDEO needed."*

**전국 지도가 권한을 요구하는 쪽이다.** 사진첩 전체를 프로그램으로 훑어야 하고,
무엇보다 **Photo Picker는 반환 이미지에서 GPS를 지운다** — 피커로는 이 기능이
원천적으로 불가능하다. 매니페스트 주석(`AndroidManifest.xml:7-15`)이 이미 같은
근거를 적고 있다.

### 좌표가 기기 밖으로 나가지 않는다 (신청 문구의 근거)

`photo_scan_controller.dart:214-224`에서 확인했다. 흐름은 이렇다.

```
사진 EXIF 좌표 → CoordinateReduction.reduce(격자 축약)
              → resolver.districtAt(p)  ← 기기 안에서 행정구역 코드로 변환
              → 서버에는 지역 코드만 전송
```

원본 좌표도 사진 자체도 서버로 가지 않는다. Play 선언 양식과 데이터 보안 섹션에
이 사실을 그대로 적을 수 있다.

   > 이미지에서 위치 정보를 제거하므로 이 기능을 구현할 수 없습니다. 사진은 기기
   > 내에서만 읽고 좌표는 지역 판별에만 사용하며, 사진 자체를 업로드하거나 좌표를
   > 저장하지 않습니다.

3. **첨부 기능은 언급하지 않는다.** 이미 피커를 쓰므로 이 신청과 무관하고,
   "첨부에도 필요하다"고 쓰면 *"그건 피커로 되잖아요"* 로 반려된다.
4. 데이터 보안 섹션의 사진 항목과 답변이 어긋나지 않는지 확인한다.

## H. 출시 전 점검 — 전수 확인 (2026-08-24)

사용자 질문("이제 출시할 때 걸리는 게 없나, 권한은 다 적었나, iOS 추가분은 없나")에
따라 코드와 설정을 전수로 훑은 결과다.

### H.1 권한 — 코드와 선언이 정확히 일치한다

`Permission.*` 호출을 전부 뽑아 선언과 대조했다. **빠진 것도, 남는 것도 없다.**

| 코드가 요청 | iOS 선언 | Android 선언 |
|---|---|---|
| `locationWhenInUse` | `NSLocationWhenInUseUsageDescription` ✅ | `ACCESS_FINE/COARSE_LOCATION` ✅ |
| `photos` | `NSPhotoLibraryUsageDescription` ✅ | `READ_MEDIA_IMAGES` + `ACCESS_MEDIA_LOCATION` ✅ |
| `notification` | **불필요**(런타임 전용, plist 키 없음) | `POST_NOTIFICATIONS` ✅ |

- 카메라·마이크·연락처·백그라운드 위치는 **코드에 없고 선언도 없다** — 일치.
- `NSLocationAlways*` 계열 0건. 백그라운드 위치를 안 쓰므로 올바르다.
- `NSPhotoLibraryAddUsageDescription`·`NSUserTrackingUsageDescription`은 §D에서
  넣었다 뺐다 — 이미지 저장도 광고 추적도 없다.

### H.2 iOS에서 추가로 손댄 것

**`ITSAppUsesNonExemptEncryption = false`를 넣었다.** 이 키가 없으면 App Store
Connect가 **업로드할 때마다** 수출 규정(암호화) 질문을 되묻는다. 이 앱은 HTTPS만
쓰고 자체 암호화를 구현하지 않아 면제 대상이다. `plutil -lint` 통과 확인.

ATS(`NSAppTransportSecurity`) 예외는 **없다** — 기본값(HTTPS 강제)이 그대로라 정상이다.
약관 3종이 모두 https이므로 웹뷰도 걸리지 않는다(`terms_code_test.dart`가 스킴을 검사).

### H.3 Android 릴리스 서명 — 하드 블로커였다

`buildTypes.release`가 **디버그 키로 서명**하고 있었다(Flutter 기본 TODO가 그대로).
Play는 디버그 서명 산출물을 거부하므로 이대로는 업로드 자체가 불가능하다.

`key.properties`(gitignore됨)에서 키를 읽고, **없으면 디버그 키로 물러나며 그 사실을
빌드 로그에 남기도록** 했다 — `google-services.json`을 다루는 기존 판단과 같은 결이다.
빌드를 막으면 `flutter run --release`로 성능을 재는 흔한 작업까지 키스토어를 요구하게 된다.

`android/key.properties.example`에 생성 방법을 적어 뒀다. **키스토어는 사용자가 만들고
보관해야 한다** — 잃어버리면 같은 패키지명으로 갱신할 수 없다.

`./gradlew :app:signingReport`로 현재 release가 debug 키를 쓰는 것을 확인했고,
릴리스 APK 빌드(227.9MB)가 성공하는 것도 확인했다.

### H.4 출시 전 남은 것 — 코드가 아닌 항목

| # | 항목 | 누가 |
|---|---|---|
| 1 | **업로드 키스토어 생성 + `key.properties` 작성** | 사용자. §H.3, `key.properties.example` |

## I. iOS 권한 문구 현지화 (2026-08-24)

사용자 질문("iOS는 영어로만 적어야 하나")으로 확인한 결과, **아니다** —
`InfoPlist.strings`로 언어별 번역이 가능하고, 기기 언어에 맞는 문장이 OS 권한
팝업에 뜬다([Apple 문서](https://developer.apple.com/documentation/bundleresources/information-property-list/nslocationwheninuseusagedescription)).

### 무엇이 빠져 있었나

`ios/Runner/ko.lproj/InfoPlist.strings`가 **이미 있었지만 위치 문구 하나뿐**이었다.
사진 문구가 없어 한국어 기기에서도 사진 팝업만 영어로 떴다. `ja`/`zh`는 디렉토리
자체가 없었는데, 앱은 그 두 언어를 지원한다(`supportedLocales`).

### 처리

- `ko`에 `NSPhotoLibraryUsageDescription`과 `CFBundleDisplayName` 추가
- `ja.lproj`·`zh.lproj` 신규 작성(위치·사진·앱 이름)
- **Xcode 프로젝트에 등록**했다 — 파일만 만들면 번들에 안 들어간다.
  `project.pbxproj`의 `PBXFileReference`·`PBXVariantGroup.children`·`knownRegions`
  세 곳을 모두 손봐야 한다.

`Info.plist`의 영어 원문은 그대로 둔다 — 위 세 언어가 아닌 기기의 폴백이다.

### 검증

`plutil -lint` 4개 파일 통과, `flutter build ios --debug` 성공, **빌드 산출물의
`Runner.app/{ko,ja,zh}.lproj/InfoPlist.strings`에 번역이 실제로 들어간 것까지 확인**했다.

### Android에는 이런 필드가 없다

같은 질문의 나머지 절반이다. Android 매니페스트에는 iOS의 `UsageDescription`에
해당하는 필드가 **없다**(`android:description`은 커스텀 권한을 *정의*할 때 쓰는
것이라 무관하다). OS 권한 팝업 문구는 안드로이드가 자체 문구로 띄우며 앱이 바꿀 수
없고, 사유 설명은 **앱이 팝업 전에 직접 보여 주는 화면**으로 한다 — 이 저장소는
`PermissionRationaleSheet`가 그 역할이고 4개 언어 ARB로 이미 관리된다.

### Info.plist의 주석

`plutil -convert json`으로 확인했다 — 주석은 파싱 시점에 사라져 값으로 새어 들어가지
않는다(키 26개, 주석 유입 0건). OS도 심사자도 보지 않으므로 남겨 둔다. 이 저장소는
다른 키(OAuth 클라이언트 id, URL 스킴, FCM)에도 같은 방식으로 근거를 적고 있다.

## J. 로깅 통일 (2026-08-24)

사용자 지적: 서버의 logback처럼 `log.info`/`log.warn`/`log.error`를 쓰고 싶었는데,
AI가 `if (kDebugMode)` 조건문으로 감싸는 형태로 만들어 놨다 — 그걸 걷어낸다.

### 무엇이 문제였나

로그 호출마다 `if (kDebugMode) { debugPrint('[Tag] ...'); }`를 손으로 둘렀다.
문제가 셋이다 — 조건이 호출부에 흩어져 빠뜨리기 쉽고, 태그를 문자열로 매번 다시
적어 표기가 갈리며, **수준 개념이 없어 "이건 경고인가 오류인가"가 코드에 남지 않는다.**
게다가 `debugPrint`(39곳)와 `developer.log`(27곳) 두 가지가 섞여 있었다.

### `package:logger`를 쓴다 — 직접 만들지 않는다

처음에는 `AppLog`라는 래퍼를 손으로 만들었다. 사용자 지적으로 걷어냈다 —
**수준 체계와 필터는 이미 검증된 라이브러리에 있고, 그것을 흉내 내는 코드를
저장소가 떠안을 이유가 없다.**

`lib/common/log/app_log.dart`는 이제 팩토리 하나와 필터·프린터만 남는다.

```dart
static final Logger _log = appLogger('MapSdkInitializer');
_log.e('지도 SDK 초기화 실패', error: error, stackTrace: stackTrace);
```

메서드는 라이브러리 관례를 따른다 — `t`/`d`/`i`/`w`/`e`/`f`.
후보 비교: `logging`(dart.dev 공식, 이미 전이 의존성)은 `severe`/`warning`/`fine`이라
log4j 이름과 더 멀고, `logger`(좋아요 1위)가 `w`/`e`로 짧다. 이름이 한 글자인 대신
수준 경계가 명확하고 필터가 교체 가능해 이쪽을 골랐다.

**릴리스는 `warn` 이상만 남긴다**(`_releaseMinimum`). `info`까지 내보내면 정상 흐름이
전부 기기 로그(안드로이드 logcat)에 쌓여 다른 앱이 읽을 수 있고, 정작 필요한 오류가
그 안에 묻힌다.

### 결과

28개 파일이 `appLogger`를 쓴다. `if (kDebugMode)`·`debugPrint`·`developer.log`
호출부는 **전부 0건**이고, 손으로 만들었던 `AppLog` 클래스와 `LogLevel` enum도
**0건**이다.

**필터를 손대지 않는다.** 한때 "릴리스에서도 warning은 남겨야 실기기 장애를 본다"며
커스텀 필터를 넣었는데, 사용자 지적으로 걷어냈다 — **로그는 개발용이고 사용자 기기에
남길 것이 아니다.** 라이브러리 기본값(`DevelopmentFilter`)이 릴리스에서 전부 끄는 것이
맞고, 그 판단을 우리가 뒤집을 이유가 없었다.

그 필터 하나 때문에 `kDebugMode`가 로거 안에 남고 `--dart-define=LOG_LEVEL`까지 붙을
뻔했다. 걷어내니 **`lib/` 전체에서 `kDebugMode`가 0건**이 됐다(GraphQL 마스킹 통로는
보안 목적이라 별개). 수준 조절이 필요하면 `Logger.level`을 바꾼다.

출력은 `[이름] 메시지` 한 줄이다. `PrettyPrinter`의 박스·이모지는 여러 줄로 늘어나
실기기 로그에서 다른 로그와 뒤섞인다.

### 판단한 것

- **POL-013 마스킹을 살렸다.** provider 계층은 대부분 `'... failed: ${error.runtimeType}'`
  처럼 타입만 남기고 있었고, "서버 message는 PII를 담을 수 있다"는 근거가 주석에 적혀
  있었다. `AppLog`는 받은 값을 마스킹하지 않으므로 **이 21곳은 `error` 객체를 넘기지
  않는다.** SDK 실패·로컬 정리처럼 서버 메시지가 없는 곳만 인자로 넘긴다.
- **`kDebugMode`가 로그 이상을 뜻하던 2곳은 조건을 분리했다.** `map_repository_impl`의
  경계 매핑 누락과 `map_screen`의 혼잡도 조인 실패는 데이터가 조용히 사라지는 신호라
  로그 조건을 걷어냈다. 다만 **릴리스에서는 이 로그도 나오지 않는다**(위 필터 방침) —
  §E의 "지도 무음 실패"는 여전히 열린 항목이고, 그것을 실기기에서 보려면 로그가 아니라
  크래시 리포팅/애널리틱스가 필요하다.
- `draft_store_impl`은 같은 파일에 `_log()` 헬퍼 메서드가 이미 있어 필드명을 `_logger`로
  했다.

`graphql_debug_log.dart`는 **건드리지 않았다** — 본문 마스킹과 디버그 전용 처리를 함께
맡는 별도 통로이고, 일반 로거로 합치면 §7 보안 규칙이 깨진다.

`test/common/log/app_log_test.dart` 5개 추가(수준 순서·관례 값·조건 없는 호출·const 생성).

## K. 체감 성능과 로딩 표시 (2026-08-25)

사용자 지적: "행동 하나하나가 좀 느리고 뭔가 끊기는 느낌이다. 특히 발견에서
그렇고 새로고침도 그렇다. skeletonizer로 시머 효과를 내면 좋겠다."

### K.1 먼저 — 스와이프 제스처는 이미 고쳐져 있었다

§B에서 리빌드 범위를 좁힌 것(`ValueNotifier` + `ValueListenableBuilder`의
`child`)이 그대로 살아 있고 올바르다. **남은 문제는 전부 이미지 디코딩과
래스터**였다.

### K.2 원본 해상도로 디코딩하고 있었다

`Image.network`의 `width`/`height`는 **배치 제약이지 디코딩 제약이 아니다.**
그 둘만 주면 서버가 준 원본 그대로 디코딩해 래스터 캐시에 올린다. 관광 API
사진은 2000~4000px라 3000×2000 한 장이 RGBA로 **24MB**고, Flutter 기본 이미지
캐시 100MB에는 **네 장이면 찬다** — 다섯 번째가 들어올 때마다 앞의 것이
밀려나고, 되돌아오면 다시 디코딩한다.

호출부 15곳 중 `cacheWidth`를 지정한 곳이 **하나도 없었다.** 손으로 적게 두면
반드시 빠뜨리므로 `common/widget/network_photo.dart`로 규칙을 모았다.

발견 탭이 특히 나빴다. 카드 스택이 두 장을 동시에 물고 있고, 탭 셸이
`StatefulShellRoute.indexedStack`이라 **다른 탭에 가 있어도 그 두 장이
메모리에 남는다.**

### K.3 진짜 렉의 원인은 블러 배경이었다

`contain`으로 그릴 때 남는 여백을 같은 사진의 블러본으로 채우는데(§4.7),
이것이 **같은 사진을 원본 크기로 한 번 더 디코딩**한 뒤 전체화면에 sigma 20을
걸고 있었다. 게다가 이 위젯이 드래그하는 `Transform` 안에 있어 **매 프레임 다시
래스터화**된다 — `ValueListenableBuilder`의 `child` 최적화는 위젯 *빌드*를
막지만 *래스터*는 막지 못한다.

`contain`은 저작권 미지정의 **기본값**이라 대부분의 카드에 걸린다.

셋을 고쳤다.
- 어차피 뭉갤 그림이므로 **40px로 디코딩**한다. 축소한 만큼 sigma도 낮춰야
  한다 — sigma는 픽셀 단위라 40px 그림에 20을 걸면 통째로 단색이 된다.
- `RepaintBoundary`로 레이어를 굳힌다. 이후 프레임은 그 레이어를 옮기기만 한다.
- 스와이프 카드와 상세 갤러리에 **같은 코드가 복제**돼 있어 한쪽만 고칠
  뻔했다. `component/blur_backdrop.dart`로 합쳤다.

카드 두 장에도 `RepaintBoundary`를 둘렀다. 저장소 전체에 이 위젯이 **0건**이었다.

### K.4 그 밖의 리빌드 범위

- `MediaQuery.of` → `viewPaddingOf`. 실제로 읽는 것은 `viewPadding` 하나인데
  통짜로 구독해 키보드·글자 크기·밝기 변화에도 카드 스택이 다시 빌드됐다.
- 카테고리 바를 `DiscoverSwipeView.build` 밖으로 뺐다. 인라인이라 권한 상태나
  카드 큐가 바뀔 때마다 칩 열 개가 통째로 다시 만들어졌다.
- `ListView(children:)` → `ListView.builder`. 통짜 목록은 화면 밖 칩까지 매
  빌드마다 즉시 만든다.
- `availableSpotCategoriesProvider`를 `AsyncValue` 통째로 watch하면서 `.value`만
  읽고 있었다 — `select`로 좁혔다.

### K.5 프리캐시 — 그리고 그 과정에서 발견한 버그

스택은 두 장만 붙여 놓으므로 **세 번째 카드는 요청조차 나가 있지 않다.** 한
장을 넘기면 그때부터 받기 시작해, 느린 연결에서는 회색 플레이스홀더가 먼저
보인다. 큐가 밀릴 때 다음 사진을 미리 받는다.

이때 **`NetworkPhoto`가 배치용 `width`를 디코딩 힌트로 쓰고 있던 것을
발견했다.** 스와이프 카드가 넘기는 값이 정확히 `double.infinity`고,
`(infinity * dpr).round()`는 터진다. 배치 폭은 디코딩 힌트가 될 수 없다.

계산을 `decodeWidthFor`로 빼 위젯과 프리캐시가 **같은 값**을 쓰게 했다. 이미지
캐시는 (URL, 디코딩 크기)로 키를 잡으므로 폭이 다르면 미리 받아 둔 것을 못 쓰고
두 벌이 메모리에 남는다. `Image.network`의 `cacheWidth`도 내부적으로
`ResizeImage`를 만들어([공식 문서](https://api.flutter.dev/flutter/widgets/Image/Image.network.html))
형태가 일치한다.

### K.6 스켈레톤 — 미뤄 뒀던 결정이었다

`skeletonizer ^2.1.3`(Dart ≥3.7 / Flutter ≥3.32, 의존성은 flutter SDK 하나).

**이 저장소는 이미 전 화면 일괄 도입을 전제해 두고 있었다.**
`region_recommendation_screen.dart`의 주석이 *"이 화면만 스켈레톤을 두면 로딩
모양이 화면마다 달라진다"*며 중앙 스피너를 쓰고 있었고, 설계 문서 여러 곳이
스켈레톤을 예정해 두고 "앱 전체 로딩 패턴 통일은 별도 결정"으로 남겨 뒀다.

핵심은 **뼈대를 손으로 그리지 않는다**는 것이다. 실제 카드에 더미 모델을 넣어
그린 뒤 시머로 덮으므로, 카드 디자인이 바뀌면 뼈대가 저절로 따라간다.

| 위젯 | 자리 |
|---|---|
| `common/widget/app_skeleton.dart` | 효과·색·모서리의 단일 진입점 |
| `common/widget/skeleton_list.dart` | 목록 초기 로딩 |

**`PaginationListView`는 공통 진입점이 아니다.** 거기 스피너는 하단 더보기
전용이고, 초기 로딩은 호출부의 `when(loading:)`이 그린다 — 그 위젯은 `data:`
갈래에서야 트리에 들어온다. 그래서 `SkeletonList`가 따로 필요했다.

적용: 홈 3섹션(`HomeSection` 한 곳), 좋아요, 커뮤니티, 숨긴 글, 차단 목록,
대화 목록, 내 글, 장소 Q&A, 내 질문, 겹친 칸, 알림 설정, 장소 검색.
댓글·답변·알림 설정은 **`SkeletonList`가 아니라 `AppSkeleton`**이다 — 바깥
`PaginationListView`/`ListView`의 한 칸으로 들어가는 자리라 목록을 중첩하면
스크롤이 겹친다.

**더미의 이미지 URL은 빈 문자열이다.** `SpotThumbnail`이 `http`로 시작하지 않는
값을 색블록으로 폴백하므로 뼈대가 실패할 요청을 쏘지 않는다. 날짜는 고정값이다
— `DateTime.now()`를 쓰면 상대시각이 프레임마다 달라져 뼈대가 깜빡인다.

**다크 모드에서 시머가 뒤집힐 뻔했다.** 이 앱의 라이트 스킴은 손으로 지정한
값이라 `surfaceContainerHighest`가 `surfaceContainerLow`보다 **어둡고**, 시드에서
파생되는 다크 스킴은 반대다. 색 이름만 믿으면 한쪽 모드에서 시머가 어두운 쪽으로
흘러 얼룩처럼 보인다 — 두 색을 밝기로 정렬해 쓴다.

### K.7 손대지 않은 것과 그 이유

- **버튼 안 스피너 17곳.** 제출 중 표시라 스켈레톤 대상이 아니다.
- **하단 더보기 스피너.** 이미 읽고 있는 콘텐츠 아래 한 줄이라 레이아웃 예고가
  이미 충족돼 있고, 뼈대로 바꾸면 진짜 항목과 헷갈려 탭 오작동을 부른다.
- **전체 화면 사진 뷰어.** `InteractiveViewer`가 확대를 허용하므로 디코딩을
  줄이면 확대했을 때 뭉개진다.
- **장소 상세 로딩.** 목록에서 넘어온 썸네일로 갤러리 자리를 이미 채우고 있어
  스켈레톤의 이점이 작고, 그 정교한 처리를 건드릴 위험이 더 크다.
- **발견 탭 초기 로딩.** 전체화면 카드 한 장을 뼈대로 그리면 "카드가 떴는데
  사진만 안 나온 것"으로 오인되고, 문구("주변을 찾는 중")가 실제 정보를 담는다.
- **DM 대화 화면.** 그 화면 주석이 이미 "캐시가 있으면 로딩이 거의 안 보인다"며
  스켈레톤을 두지 않기로 판단해 뒀다.
- **지도 도형 로딩.** 목록이 아니라 벡터 지도라 뼈대의 대상이 아니다.
- **설정·인증 폼의 `ListView(children:)`.** 항목이 고정 소수라 `builder`로 바꿀
  실익이 없다.

### K.8 확인한 것 / 확인하지 못한 것

**측정이 아니라 코드로 확인한 것.** Riverpod 3.0.3 소스에서
`skipLoadingOnRefresh`가 기본 `true`이고 `ref.invalidate`에도 적용됨을 확인했다 —
**당겨서 새로고침할 때 기존 목록은 이미 유지되고 있다.** 새로고침이 화면을
비운다는 의심은 틀렸다. 다만 `skipLoadingOnReload`는 기본 `false`라 `ref.watch`로
인한 재조회(카테고리 전환 등)는 로딩으로 떨어지는데, 그건 실제로 다른 데이터라
로딩 표시가 맞다 — 이제 그 자리가 스켈레톤이다.

**확인하지 못한 것 — 사용자 몫이다.**
- **끊김이 실제로 줄었는지는 실기기에서만 알 수 있다.** 프로파일링을 돌리지
  않았고, 위의 근거는 전부 코드와 문서에서 온 것이다.
- 시머의 속도(1200ms)와 대비가 눈에 편한지.
- 블러 배경을 40px로 줄인 것이 원본과 구분되는지. 계산상 겉보기 흐림은 같지만
  실제로 본 것은 아니다.
- 로딩→데이터 전환에서 화면이 튀지 않는지. 스피너가 차지하던 세로 여백이
  실제 행 높이로 바뀐 자리가 있다(답변 목록·알림 설정).

**GraphQL 계약은 건드리지 않았다** — `.graphql` 오퍼레이션 변경이 없어 §13
스윕이 필요 없다. 이번 작업은 전부 표시 계층이다.

## L. 안드로이드만 초기 구동이 느렸다 (2026-08-25)

사용자 실기기 확인: "아이폰은 최적화 잘 된 것 같은데, 안드로이드는 되긴 하지만
시간이 좀 지나야 된다. **처음에는 좀 버벅거림이 있다.**" (테스트 기기 Android 12+)

§K가 렌더링·디코딩을 고쳤다면 이번은 **부팅 경로**다.

### L.1 주범은 폰트였다 — 그리고 안드로이드에서만 비용이 된다

선언된 폰트가 **40개 198.5MB**였고, 코드가 실제로 쓰는 웨이트는 다섯이다 —
`w500`(2곳)·`w600`(20곳)·`w700`(21곳)·`w800`(1곳)·`bold`(1곳), 나머지는 본문
기본값 400. **Thin·ExtraLight·Light·Black은 한 번도 쓰이지 않았다.**

**왜 안드로이드만인가.** APK 안의 압축 방식을 직접 검사했다.

```
12190608  Stored   lib/arm64-v8a/libapp.so        ← 무압축 → mmap 가능
 6185868  Defl:N   NotoSansKR-Regular.ttf         ← deflate
10559284  Defl:N   NotoSansSC-Regular.ttf         ← deflate
```

Android `AssetManager`는 **압축된 asset을 mmap하지 못해, 쓸 때마다 통째로 메모리에
푼다.** SC-Regular 한 종을 처음 쓰면 10.1MB를 zlib으로 풀고 그것을 힙에 올린 뒤
FreeType이 파싱한다. iOS는 같은 파일이 `.app` 안에 압축 없이 들어가 mmap되므로
실제로 읽히는 것은 글리프가 있는 페이지뿐이다.

**같은 코드, 같은 폰트인데 비용이 구조적으로 다르다.**

"처음에만"도 정확히 설명된다. 폴백 체인이 KR→JP→SC라(`app_theme.dart`) 한국어
기기는 스플래시 첫 프레임부터 CJK를 건드리고, 한 번 로드되면 엔진이 typeface를
캐시해 이후로는 공짜다.

**안 쓰는 4웨이트만 지웠다**(사용자 결정) — CJK 84.7MB + 라틴 2.4MB = 약 87MB.
화면에 보이는 굵기가 하나도 바뀌지 않는다. 이탤릭은 남긴다(`area_info_card`·
`message_bubble`이 실제로 쓴다).

### L.2 지도 SDK가 첫 프레임을 막고 있었다

`KakaoMapSdk.initialize`는 네이티브 인증이라 **네트워크를 탈 수 있는데**(그 파일의
catch 주석이 이미 "네트워크가 없으면 여기로 온다"고 적고 있었다), `main`이 이것을
`await` 하고 있었다. 지도는 5개 탭 중 하나인데 **홈·발견을 보려는 사람까지
스플래시에 묶였다.**

`main`은 `start()`로 발사만 하고, 지도 화면이 `ready()`를 기다린다. `isReady`만
보게 두면 "초기화 중"을 "키 없음"으로 오인해 안내 문구가 스쳤다 지도로 바뀐다 —
그래서 화면에 `FutureBuilder`를 둔다.

`main`의 병렬화(`.wait`) 자체는 이미 올발랐다. 고친 것은 **무엇을 기다리는가**다.

### L.3 콜드 GPS가 홈 세 섹션을 함께 묶고 있었다

`getCurrentPosition`은 **새 fix를 기다린다.** 홈의 세 섹션이 모두 같은 좌표
provider를 await 하므로, 그동안 화면이 통째로 뼈대다.

`getLastKnownPosition`은 즉시 돌아온다(없으면 null — 공식 문서 확인). 반경 기반
추천에 몇십 미터 오차는 무의미하다. 캐시가 없으면 새로 잡되 **10초 시한**을 건다.

**지도의 실시간 점은 영향받지 않는다** — `watchCoordinates`는 `currentCoordinates`를
권한 확인용으로만 부르고 반환값을 버린다.

이 항목은 안드로이드 전용 문제는 아니다. GPS 하드웨어 편차가 커 더 자주 드러날 뿐이다.

### L.4 원인이 아니었던 것 — 짚어 둔다

**Impeller·셰이더 워밍업은 원인이 아니다.** 처음에 의심했으나:

- Flutter 3.44에는 `--bundle-sksl-path`가 **아예 없다**(기능 제거됨). "SkSL이
  없어서 느리다"는 이 버전에서 성립하지 않는 진단이다.
- Impeller는 Flutter 3.27부터 Android API 29+ 기본 활성이고 셰이더를 빌드 타임에
  미리 컴파일한다([공식 문서](https://docs.flutter.dev/perf/impeller)).
  사용자 테스트 기기가 Android 12+라 OpenGL 폴백 경로에 해당하지 않는다.

**이미지 캐시 100MB 기본값도 주범이 아니다.** 오히려 "오래 쓸수록 나빠지는" 쪽이라
증상과 방향이 반대다. §K의 `cacheWidth` 규칙이 이미 올바른 대응이다.

### L.5 손대지 않은 것

**`flutter_secure_storage`의 Android Keystore.** 조사에서 2순위로 지목됐다 —
`AndroidOptions`가 지정돼 있지 않고, 하드웨어 Keystore 키 생성은 첫 1회가 비싸며
(iOS Keychain은 사실상 공짜), 라우터가 앱 시작 즉시 토큰을 읽어 반드시 발생한다.

**그러나 고치지 않았다.** 9.x의 `encryptedSharedPreferences` 기본값과 기존 저장
데이터의 마이그레이션 영향을 공식 문서에서 확인하지 못했다(pub.dev가 11.0.0 기준
문서를 서빙한다). **토큰이 날아가면 전 사용자가 로그아웃되는 영역**이라, 근거 없이
건드리지 않는다. 필요하면 별도 이슈로 낸다.

**minify/shrink, fat APK(3 ABI).** `isMinifyEnabled`가 꺼져 있고 릴리스 APK가
3개 ABI를 전부 담고 있다. 앱 크기와 dex 로딩에 영향은 있으나 **"워밍업 후
개선"과는 무관**해 이번 증상의 원인이 아니다. 켜려면 `proguard-rules.pro`의
카카오 지도 keep 규칙을 연결해야 하므로 출시 직전에 따로 다룬다.

### L.6 확인하지 못한 것

**실기기 측정을 하지 않았다.** 위 판단은 전부 코드·빌드 산출물·공식 문서에서 온
것이다. 폰트 항목은 APK 압축 방식이라는 직접 증거가 있지만, **실제로 몇 ms가
줄었는지는 재보지 않았다.**

사용자 확인이 필요하다.
- 안드로이드 콜드 스타트가 실제로 빨라졌는지 (`adb shell am start -W`로 `TotalTime` 비교)
- 폰트를 지운 뒤 **글자 굵기가 달라 보이는 곳이 없는지** — 코드상 안 쓰는 웨이트만
  지웠으나 눈으로 확인한 것은 아니다
- 지도 탭 첫 진입에서 스피너가 오래 돌지 않는지 (초기화를 뒤로 미뤘으므로 그 대기가
  이제 지도 화면에 보인다)

## M. 실기기 피드백 반영 (2026-08-25)

사용자가 실기기 영상을 세 번 보내 준 것을 근거로 고쳤다. **코드만 보고는 못 찾았을
것들**이라 그 경위를 남긴다.

### M.1 "어둡다" — 내가 만든 부작용이었다

§K에서 블러 필터를 걷어낸 뒤 화면이 칙칙해졌다. 배경에 `black26`을 `darken`으로
얹고 있었는데 **강한 가우시안이 그 어두움까지 뭉개 놔서 티가 안 났던 것**이다.
필터가 사라지자 어두움만 선명하게 남았다.

`ColorFiltered`를 없애고, 덩달아 도드라진 카테고리 바 스크림도 `Colors.black`
(완전 불투명) → `black87`로 낮췄다. **스크림 자체는 걷어내지 않는다** — 상태바
시계와 칩 라벨 가독성을 위한 것이고 그 근거가 실기기 확인으로 남아 있다(부록 §B 무렵).

### M.2 "지도 스와이프가 뻑뻑하다" — 지도가 아니라 발견 탭이었다

영상을 보고서야 알았다. 나는 지도로 읽고 지도만 고쳤다(그 작업도 유효하지만 헛다리다).

프레임에서 두 가지가 드러났다.
- 모든 카드가 "공공누리 제3유형"이라 **거의 전부가 `contain` → 블러 배경 경로**를 탄다.
- 카드가 겹치는 구간에서 **전체화면 블러가 동시에 두 장** 살아 있다.

그리고 §K의 조치가 왜 부족했는지도 드러났다 — **디코딩을 줄여도 `ImageFiltered`는
출력 크기(전체화면)에서 돈다.** `RepaintBoundary`도 부모 `Transform`이 움직이면
필터 레이어를 다시 합성하므로 약을 못 쓴다.

필터를 아예 뺐다. 40px로 디코딩한 그림을 전체화면으로 늘리면 **그 자체가 이미
뭉개진 그림**이라 확대 보간이 블러를 대신한다.

### M.3 지도 진입 크래시 — 이것도 내가 만들었다

§L에서 SDK 초기화 대기를 붙이며 `build`를 `FutureBuilder`로 감쌌는데, 그러면
`ref.watch`·`ref.listen`이 **빌드 콜백 안**으로 들어가 Riverpod 단언에 걸린다.

대기를 `initState`로 옮기고 플래그로 표시한다. **`build`를 감싸는 방식 자체가
틀렸다** — ConsumerWidget에서는 `ref.*`가 build 본문에 있어야 한다.

### M.4 아이콘 — 한반도 실루엣으로

기존 핀+하트는 위치 기반 앱에서 가장 흔한 조합이고 **한국 여행 앱이라는 정체성이
없었다.** 앱 안에서는 이미 `KoreaIcon`(Natural Earth 1:110m)을 전국 지도 탭에
쓰고 있었는데 런처 아이콘만 그걸 안 썼다.

같은 도형을 런처 아이콘으로 올리고 서울 자리에 하트 핀을 얹었다. iOS 15종 +
Android 5종 재생성, 전량 크기 검증·iOS 알파 없음 확인.

**Android 어댑티브 아이콘은 없다** — `mipmap-anydpi-v26/`가 없어 Android 8+
런처에서 아이콘이 축소돼 시스템 배경 위에 놓인다. 별도 작업으로 남긴다.

### M.5 하단 탭 "내 활동" 아이콘 — 두 번째 교체

북마크 → 사람 → **하트**. 북마크는 저장해 둔 것만 있는 보관함처럼 읽혔고
(2026-08-24), 사람은 프로필·계정으로 읽혀 설정과 헷갈렸다(2026-08-25) — 설정은
홈 앱바에 따로 있다.

하트는 이 탭의 주역인 좋아요와 **스와이프 오른쪽**이 이미 쓰는 기호라, 기호가
이어져 "내가 하트한 것들이 여기 모인다"가 곧바로 읽힌다.

### M.6 전국 지도 아이콘이 늦게 뜬다

§L에서 SVG 161장을 8장씩 나눠 싣게 했더니 스파이크는 사라졌지만 **묶음이 20개라
회색 지도가 오래 보였다.**

- 동시 수를 8 → 16으로. 묶음이 절반이 되고, 요즘 기기 코어 수를 생각하면 여전히
  한꺼번에 터뜨리는 것과는 거리가 멀다.
- **방문한 칸을 먼저 싣는다.** 방문 칸은 보통 몇 개~몇십 개라 첫 묶음 한두 번이면
  끝나고, 컬러가 먼저 뜨면 "내가 채운 지도"가 즉시 읽힌다. 무채색 칸은 뒤따라
  채워져도 티가 덜 난다.

### M.7 온보딩 — 디자인만 받아 두었다

현재 온보딩 3장이 실제 5탭과 어긋난다(전국 지도가 없고, "내 활동"이 좋아요+커뮤니티인
것도 반영되지 않았다). Stitch에 5탭 구조로 5장을 받아 `docs/design/SPEC-0032-onboarding.md`에
정리했다.

**구현은 하지 않았다** — 문구 5장 분량을 4개 언어 ARB에 새로 넣는 일이고, 일러스트를
어떻게 할지도 미정이다. 별도 작업으로 남긴다.
