# SPEC-0036 — 지도 영역 기준 추천 조회 요청

**대상 operation**: `mapViewport` (또는 이를 대체할 새 operation)
**검증 환경**: 미검증 — 라이브 서버(`http://localhost:8888/graphql`)가 내려가 있고 목 안내도
아직 없다(2026-09-18 기준)
**상태: 요청 중**

관련: `ieuri-server#136` · `k-trip-spot#110` · `Specs/SPEC-0036/spec.md` 미결 **T3·T5**

---

## 요청하는 것

지도 탭이 **보고 있는 영역 안의 장소를 추천 순서로** 받을 수 있어야 한다(FR-001·FR-002).
현재 계약으로는 불가능하다.

| operation | 영역을 받는가 | 추천 순서인가 |
|---|---|---|
| `mapViewport(bbox, zoom, categories)` | 예 (사각형) | **아니오** — 관련도 순, 늘 같은 순서 |
| `recommendedSpots(latitude, longitude, radiusMeters, ...)` | **아니오** (중심점·반경) | 예 |

이 차이가 미결 T3이며, 스펙은 해소 방법을 두 저장소 공동 결정으로 남겼다.

## 이 저장소의 제안

**`mapViewport`가 추천 순서로 정렬해 주는 쪽**을 제안한다. 새 operation을 만드는 것보다
변경 면적이 작고, 지도 화면이 이미 bbox를 쥐고 있어 클라이언트 쪽 변환이 필요 없다.

```graphql
mapViewport(
  bbox: MapBoundsInput!
  zoom: Int!
  categories: [String!]
): MapViewportResult!
```

- `spots` 배열이 **추천 점수 내림차순**으로 온다. 점수 계수는 SPEC-0035가 정한 것을 쓴다
- 거리 감쇠의 기준점은 **bbox의 중심**이 자연스럽다 — 화면 한복판이 사용자가 보고 있는 곳이다
- 인자는 그대로 두는 것이 좋다. 클라이언트가 이미 보낸다

### 대안: `recommendedSpots`에 영역 인자를 더한다

`latitude`/`longitude`/`radiusMeters` 대신 `bbox`를 받는 변형. 지도가 사각형이라
중심점·반경으로 옮기면 모서리가 잘리거나(내접원) 화면 밖이 섞인다(외접원) — 어느 쪽이든
FR-002의 「보고 있는 영역」과 어긋난다. 서버가 이쪽을 택한다면 클라이언트는 맞출 수 있다.

## 함께 필요한 것 — 소진을 판정할 수단

**이것이 이 문서에서 가장 중요한 항목이다.** FR-008(후보가 소진되면 더 보기 수단이
사라진다)과 FR-009(가짜 소진 금지)를 동시에 지키려면, **「영역 안에 아직 안 준 장소가
남았는가」를 서버가 알려 줘야 한다.**

클라이언트가 자체적으로 판정할 수 없는 이유:

- 「제외한 뒤 새 장소가 0개」로 판정하면 **FR-009가 금지한 가짜 소진**이다. SPEC-0035에서
  실제로 터졌다(열 장 만에 소진 화면)
- 현재의 `truncated`로는 대신할 수 없다. 이 저장소 코드의 기록에 따르면 **도심에서는
  `truncated`가 거의 항상 참**이다(`map_screen.dart` 잘림 안내 주석, 2026-08-10 사용자
  결정의 근거). 그러면 소진이 사실상 영원히 판정되지 않아 FR-008이 死문이 된다

제안: 응답에 **영역 안 전체 후보 수** 또는 **더 남았는지의 불리언**을 둔다.

```graphql
type MapViewportResult {
  spots: [MapSpot!]!
  events: [CulturalEvent!]!
  truncated: Boolean!
  # 이 영역 안에서 조건에 맞는 장소의 총 수. 클라이언트가 이미 표시한 수와 비교해
  # 「더 볼 것이 있는가」를 판정한다.
  totalInBounds: Int!
}
```

`truncated`와 다른 값이다 — `truncated`는 「이번 응답이 잘렸는가」이고, 이것은 「영역 안에
전부 몇 개인가」다.

## 클라이언트가 이미 정한 것 (서버가 알아야 하는 것)

- **「이미 본 장소」는 클라이언트가 들고 있다.** 세션 단위 집합이며 앱을 끄면 사라진다.
  서버에 제외 목록을 보내지 않고, 서버가 세션을 기억할 필요도 없다
- **한 번에 10개씩 누적한다.** 서버에 페이지·커서를 요구하지 않는다 — 영역 안 후보를
  점수순으로 받아 클라이언트가 안 본 것부터 고른다
- 따라서 **오프셋·커서 인자는 필요 없다**(POL-037과도 일치)

## 미결 T5에 대하여

「한 번에 점수를 계산하는 후보 수」는 서버가 정한다. 클라이언트 입장에서 중요한 것은 그
값이 **영역 안 후보 수보다 작으면 가짜 소진이 생긴다**는 점뿐이다 — 위의 `totalInBounds`가
점수 계산 상한이 아니라 **영역 안 실제 총 수**여야 하는 이유이기도 하다.
