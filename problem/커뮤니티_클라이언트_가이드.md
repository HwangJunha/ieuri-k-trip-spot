# 커뮤니티(SPEC-0010) — 클라이언트 구현 가이드

서버 구현이 끝났다. 이 문서는 앱(ieuri-k-trip-spot#32)이 붙일 때 필요한 계약과 제약을 담는다.
스펙 원문은 `Specs/SPEC-0010/spec.md`, 서버 설계는 `problem/SPEC-0010-server.md`에 있다.

**계약이 스펙 초안(`contract.graphql`)과 다른 곳이 몇 군데 있다.** §1에 먼저 정리했으니
초안을 보고 작업을 시작했다면 그 부분부터 확인할 것.

---

## 1. 스펙 초안과 달라진 점 (먼저 읽을 것)

초안대로 만들면 컴파일이 안 되거나 런타임에 빈 화면이 나오는 항목이다. 근거는 이슈 #45에 있다.

| 초안 | 최종 | 이유 |
|---|---|---|
| `spotPosts(spotId:)` | `targetPosts(targetType:, targetId:)` | 커뮤니티는 관광지 전용이 아니라 플랫폼이다. 상품 등이 붙을 자리를 미리 열었다 |
| `Post.spot: PostSpot!` | `Post.target: PostTarget!` | 위와 같음. `PostTarget.type`이 종류를 알려 준다 |
| `CreatePostInput.spotId` | `targetType` + `targetId` | 위와 같음 |
| (없음) | `confirmPostImageUpload` 뮤테이션 | 업로드 검증·이동 단계가 초안에 없었다. **사진 흐름이 3단계가 된다** |
| (없음) | `CreatePostImageUploadUrlInput.contentLength` | 크기를 서명에 넣어야 위조·초과 업로드를 막는다 |
| `CreatePostPayload.post` | `postId` 추가, `post`는 **항상 null** | 지연 필드 때문에 생성 응답에서 조립할 수 없다 |
| `TOPIC_REQUIRED` 에러 | 발생하지 않음 | `topic`이 non-null이라 GraphQL이 먼저 거부한다 |
| (없음) | `discoveryTiles`에 `filterTargetType` | 타일이 대상 종류로도 필터할 수 있다 |

**지금은 `PostTargetType`에 `SPOT` 하나뿐이다.** 관광지 화면에서는 `targetType: SPOT`을 상수로
넘기면 되고, `PostTarget.id`는 기존 `spot.id`와 같은 값이라 상세 화면 이동은 그대로 동작한다.
다만 **enum을 하드코딩하지 말고 값으로 다룰 것** — 값이 늘어난다.

## 3. 사진 업로드 — 4단계, 순서를 지킬 것

**서버는 이미지 바이트를 받지 않는다.** 앱이 R2로 직접 PUT한다. 이 경로만 GraphQL 예외다.

```
1. createPostImageUploadUrl(contentType, contentLength)
      → uploadUrl, objectKey("pending/..."), expiresAt
2. 그 uploadUrl로 R2에 직접 PUT           ← GraphQL 아님. 순수 HTTP PUT
3. confirmPostImageUpload(objectKey)
      → objectKey("images/...")            ← 최종 키. 이걸 써야 한다
4. createPost(photoKeys: [최종 키들])
```

### 반드시 지켜야 하는 것

**(1) PUT 요청의 `Content-Type`·`Content-Length`가 1단계에서 선언한 값과 정확히 같아야 한다.**
두 값이 서명에 포함되어 있어서, 다르면 R2가 `403 SignatureDoesNotMatch`로 거부한다.
서버를 거치지 않으므로 이 실패는 앱에서만 보인다.

```
PUT {uploadUrl}
Content-Type: image/jpeg        ← 1단계에 넘긴 값과 동일
Content-Length: 184320          ← 1단계에 넘긴 값과 동일 (실제 바이트 수)
<binary>
```

**(2) 3단계를 건너뛰면 안 된다.** 1단계가 준 `pending/...` 키를 `createPost`에 그대로 넘기면
`PHOTO_NOT_UPLOADED`로 거부된다. 반드시 3단계가 돌려준 `images/...` 키를 쓸 것.

**(3) 5분 안에 2단계를 끝낼 것.** `expiresAt` 이후의 PUT은 거부된다. 대용량이거나 네트워크가
느리면 만료되므로, 실패 시 1단계부터 다시 한다(키가 새로 발급된다).

**(4) 사진마다 1~3단계를 각각 돈다.** URL 하나는 키 하나에만 유효하다. 5장이면 15번 호출한다.

### 제약

| 항목 | 값 | 위반 시 |
|---|---|---|
| 형식 | `image/jpeg`, `image/png`, `image/webp` | `UNSUPPORTED_CONTENT_TYPE` |
| 크기 | 최대 10 MiB (10485760 바이트) | `UNSUPPORTED_CONTENT_TYPE` |
| 개수 | 글당 최대 5장 | `TOO_MANY_PHOTOS` |
| 만료 | 발급 후 5분 | R2가 403 |

3단계에서 서버가 **실제 크기와 매직바이트**를 다시 본다. 확장자만 바꾼 파일은 여기서 걸린다.

### 조회

`Post.photoKeys`는 **키 배열이지 URL이 아니다.** 앱이 CDN 베이스와 조합한다.

```
https://cdn.ieuri.co.kr/{photoKey}
```

베이스 URL은 앱 설정에 둘 것. 서버는 이 값을 내려주지 않는다 — 그래야 CDN이 바뀌어도
서버 배포 없이 앱만 고치면 된다.

> 개발 환경 시드 데이터의 사진 키는 실제 오브젝트가 없어 **404가 정상**이다.
> 키 배열과 순서만 확인하는 용도다.

## 4. 지연 필드 — 필요한 것만 요청할 것

`Post.target` / `Post.author` / `Post.comments`는 **요청할 때만 서버가 조회한다.**
`{ id body }`만 물으면 추가 I/O가 0이고, `target`을 넣으면 관광지 조회가 붙는다.

```graphql
# 목록 카드 — 필요한 것만
{ id body topic createdAt likeCount commentCount likedByViewer ownedByViewer hidden
  target { type id title thumbnailImageUrl }
  author { id nickname profileImageUrl } }

# 상세에서만 댓글을 붙인다
{ ...위 필드
  comments(first: 20) {
    edges { cursor node { id body createdAt ownedByViewer hidden author { id nickname } } }
    pageInfo { hasNextPage endCursor }
  } }
```

**목록에서 `comments`를 요청하지 말 것.** 20건짜리 피드에 댓글 쿼리가 20번 붙는다.
댓글 수는 `commentCount`로 충분하다.

## 5. 페이지네이션 — 커서 기반

```graphql
edges { cursor node { ... } }
pageInfo { hasNextPage hasPreviousPage startCursor endCursor }
```

- 다음 페이지: `after: pageInfo.endCursor`, `hasNextPage: false`면 끝
- `first` 기본 20 / **상한 50** — 초과해도 오류가 아니라 50으로 잘린다
- `totalCount`는 **없다.** 전체 개수를 표시하는 UI는 만들 수 없다
- **`hasPreviousPage`를 믿지 말 것.** 앞으로만 가는 피드라 `after`를 넘겼는지만 반영한다.
  이전 페이지 UI가 필요하면 앱이 스택으로 관리할 것
- 커서는 불투명 문자열이다. 파싱하거나 만들어 내면 `INVALID_INPUT`

## 6. 모더레이션 — 화면에서 놓치기 쉬운 부분

### 차단은 양방향이다

내가 차단한 사람 **그리고 나를 차단한 사람**의 글·댓글이 모든 피드에서 사라진다.
서버가 걸러서 내려주므로 앱이 필터링할 것은 없다. 다만 두 가지를 유의:

- **`blockedUsers`에는 내가 건 차단만 나온다.** 나를 차단한 사람은 목록에 없다 —
  남이 건 차단은 내가 풀 수 없기 때문이다. "왜 안 보이는데 목록에 없지"는 정상이다.
- 차단 직후 피드를 새로 고치면 그 사람 글이 사라진다. 캐시를 쓴다면 무효화할 것.

### 숨김 글은 작성자에게만 보인다

서로 다른 5명이 신고하면 자동 숨김된다. 그 글은 **작성자 본인에게만** `hidden: true`로
계속 보인다. 남에게는 애초에 목록에 들어오지 않는다.

→ **`hidden: true`인 글을 받으면 "신고 누적으로 숨겨졌다"는 배지를 보여줄 것.**
작성자는 자기 글이 왜 반응이 없는지 알 수 없으면 서버 장애로 오해한다.

### 댓글 수는 모두에게 같다

`commentCount`는 숨겨진 댓글을 제외한 수이며, **차단은 반영하지 않는다.**
내가 차단한 사람의 댓글은 목록에서 빠지지만 숫자에는 남는다 — 즉 `commentCount: 4`인데
목록에 3건만 올 수 있다. **이것은 버그가 아니다.** 숫자는 모두에게 같아야 하기 때문이다.

→ 댓글 수와 목록 길이가 다르다고 오류 처리하지 말 것.

### 단건 조회도 같은 규칙이다

`post(id:)`는 차단·숨김이면 **오류가 아니라 `null`**을 준다. 딥링크로 들어온 경우이므로
"삭제되었거나 볼 수 없는 글입니다" 정도의 안내로 처리할 것. `errors[]`를 기대하면 안 된다.

## 7. 에러 처리

### 두 갈래다

**(1) 최상위 `errors[]` — 인증 실패만**

```json
{ "errors": [{ "message": "인증이 필요합니다." }], "data": { "createPost": null } }
```

`UNAUTHENTICATED`는 **`userErrors`에 담기지 않는다.** 토큰 자동 갱신은 최상위 `errors[]`를
보는 링크 계층에서 일어나야 한다(SPEC-0005와 동일).

**(2) payload의 `userErrors[]` — 나머지 전부**

```json
{ "data": { "createPost": {
    "success": false,
    "userErrors": [{ "code": "POST_BODY_REQUIRED", "message": "본문을 입력해 주세요.", "field": null }],
    "postId": null } } }
```

**HTTP는 실패해도 200이다.** `success`와 `userErrors`로만 판정할 것.

### 코드 목록 (16종)

| 코드 | 발생 | 화면 처리 |
|---|---|---|
| `POST_BODY_REQUIRED` | 본문이 비었거나 공백뿐 | 입력 필드 |
| `POST_BODY_LENGTH_INVALID` | 본문 500자 초과 | 입력 필드 |
| `SPOT_NOT_FOUND` | 대상이 없음 | 토스트 |
| `TOO_MANY_PHOTOS` | 사진 6장 이상 | 선택 단계에서 미리 막을 것 |
| `PHOTO_NOT_UPLOADED` | 미확인·타인·위조 키 | 사진 재업로드 유도 |
| `UNSUPPORTED_CONTENT_TYPE` | 미지원 형식·크기 초과 | 선택 단계에서 미리 막을 것 |
| `NOT_POST_OWNER` | 남의 글 삭제 시도 | 토스트 (버튼을 숨기면 안 뜬다) |
| `NOT_COMMENT_OWNER` | 남의 댓글 삭제 시도 | 위와 같음 |
| `POST_NOT_FOUND` | 이미 삭제된 글 | 목록 새로고침 |
| `COMMENT_NOT_FOUND` | 이미 삭제된 댓글 | 목록 새로고침 |
| `COMMENT_BODY_REQUIRED` | 댓글이 비었거나 공백뿐 | 입력 필드 |
| `COMMENT_BODY_LENGTH_INVALID` | 댓글 500자 초과 | 입력 필드 |
| `CANNOT_BLOCK_SELF` | 자기 차단 | UI에서 미리 막을 것 |
| `MEMBER_NOT_FOUND` | 없는 회원 | 토스트 |
| `ALREADY_REPORTED` | 같은 대상 재신고 | "이미 신고했습니다" |
| `REPORT_DETAIL_REQUIRED` | `OTHER`인데 상세 없음 | 입력 필드 |
| `INVALID_INPUT` | 형식 위반 (잘못된 커서 등) | 토스트 |

**`PHOTO_NOT_UPLOADED`는 세 원인이 한 코드다** — 미업로드·타인 키·위조 키를 구분해 주지
않는다(키 존재 여부를 캐낼 수 있어서다). 앱도 구분해 안내할 수 없다.

## 8. 멱등 동작 — 오류가 아닌 것들

아래는 `success: true`로 돌아온다. 실패로 처리하지 말 것.

- 이미 좋아요한 글에 `likePost` → `likeCount` 변화 없음
- 좋아요하지 않은 글에 `unlikePost` → 0 아래로 안 내려감
- 이미 차단한 사람에게 `blockUser`
- 차단하지 않은 사람에게 `unblockUser`

**낙관적 업데이트를 쓴다면 응답의 `likeCount`로 되맞출 것.** 서버 값이 정본이다.

## 9. 신고

```graphql
reportContent(input: {
  targetType: POST | COMMENT | MEMBER
  targetId: ID!
  reason: SPAM | ABUSE | INAPPROPRIATE_CONTENT | OTHER
  detail: String     # reason이 OTHER면 필수
})
```

- `OTHER`인데 `detail`이 비면 `REPORT_DETAIL_REQUIRED`. **입력 폼에서 미리 막을 것**
- 같은 대상 재신고는 `ALREADY_REPORTED`. 신고 후 버튼을 비활성화하는 편이 낫다
- **`MEMBER` 신고는 기록만 된다.** 5명이 신고해도 그 사람의 글이 사라지지 않는다.
  "신고가 접수되었습니다" 이상을 약속하지 말 것 — 자동 조치는 글·댓글에만 있다

## 10. 다국어

- **주제 태그(`PostTopic`)와 대상 종류(`PostTargetType`)는 앱이 매핑한다.**
  서버가 표시 문자열을 내려주지 않는다. `SpotCategory`와 같은 방식(POL-023)
  - `QUESTION` 질문 / `TIP` 팁 / `REVIEW` 후기 / `COMPANION` 동행 / `PHOTO` 사진
- **탐색 타일의 `title`은 서버가 문자열로 내려준다.** 운영자가 시즌마다 쓰는 자유 문구라
  매핑할 enum이 없다. 앱은 그대로 표시할 것
- 타일은 `Accept-Language` 헤더로 언어를 고른다. **해당 언어의 타일이 없으면 빈 목록이며
  다른 언어로 대체되지 않는다** — 타일 영역이 비는 경우를 레이아웃에서 허용할 것

## 11. 글 작성 후 화면 갱신

`createPost`는 **`postId`만 준다. `post`는 항상 null이다.**

```graphql
mutation { createPost(input: {...}) { success userErrors { code message } postId } }
```

작성 직후 상세로 이동한다면 `post(id: $postId)`를 한 번 더 조회할 것.
피드로 돌아간다면 목록을 새로 고치면 된다. `createComment`도 `commentId`만 준다.

이유: `Post.target`·`author`가 지연 필드라 생성 응답에서 채우려면 앱이 요청하지도 않은
다른 도메인 조회를 매번 왕복해야 한다.

## 12. 본문 길이와 이모지 — 주의

본문은 **500자**인데, 서버는 **코드포인트**로 센다. 이모지에서 앱과 어긋날 수 있다:

| 입력 | 사용자가 보는 글자 | 서버 계산 |
|---|---|---|
| `🥲` | 1 | 1 |
| `🇰🇷` (국기) | 1 | 2 |
| `👨‍👩‍👧‍👦` (ZWJ 결합) | 1 | 7 |

앱이 `String.length`(UTF-16)나 grapheme 단위로 세면 서버와 다른 숫자가 나오고,
"499자인데 거부됨" 같은 상황이 생긴다.

**권장:** 입력 카운터를 **코드포인트 기준**으로 맞출 것.
- Dart/Flutter: `body.runes.length`
- JS: `[...body].length`

이 기준을 앱과 통일할지는 아직 확정되지 않았다([TBD]). 다르게 가려면 서버 쪽 판정도
같이 바꿔야 하므로 알려줄 것.

## 13. 미인증 사용자

읽기 4종(`targetPosts`·`nearbyPosts`·`post`·`discoveryTiles`)은 **로그인 없이 된다.**
쓰기와 `blockedUsers`는 전부 `UNAUTHENTICATED`.

- 미인증에게 `likedByViewer`는 null이 아니라 **`false`**
- 미인증에게 `ownedByViewer`도 **`false`**
- 미인증은 차단 관계가 없으므로 숨김 글만 빠지고 나머지는 다 보인다

→ 비로그인으로 피드를 보여주고, 상호작용 시점에 로그인을 유도하는 흐름이 가능하다.

## 14. 지역 피드 주의

```graphql
nearbyPosts(latitude: 37.5665, longitude: 126.9780, radiusMeters: 5000)
```

- `radiusMeters` 기본 20000 / **상한 100000** — 초과해도 오류가 아니라 잘린다
- **반경 안의 대상 수에 상한(2000)이 있다.** 반경이 매우 넓으면 결과가 부분집합일 수 있다.
  "반경 100km 전체"를 보장하지 않으므로 그런 UI 문구는 피할 것
- 위치를 가진 대상만 결과에 든다. 지금은 관광지뿐이라 문제가 없지만, 좌표 없는 종류가
  생기면 그 글은 지역 피드에 나타나지 않는다

## 15. 아직 없는 것

- **알림 없음.** 내 글에 댓글·좋아요가 달려도 푸시가 없다(비범위)
- **글 수정 없음.** 삭제 후 재작성으로 갈음
- **대댓글 없음.** 1단계 댓글만. `Comment`에 부모 필드가 아예 없다
- **검색 없음.** 태그 필터와 탐색 타일로 갈음
- **탐색 타일 어드민 없음.** 운영자가 DB에 직접 넣어야 채워진다.
  당분간 비어 있을 수 있으니 **빈 목록을 정상으로 처리할 것**
- 고아 오브젝트(업로드했는데 글을 안 쓴 경우) 정리 없음 — R2 lifecycle로 처리할 사안

## 16. 개발 환경 확인용 데이터

`R__seed_community.sql`이 더미 데이터를 넣는다(로컬·개발 전용). **회원 20번이 주인공**이다.

| 회원 | 20번으로 로그인해 조회했을 때 |
|---|---|
| 20 | 본인 글 4건, `ownedByViewer: true` |
| 19 | 글 2건·댓글 1건이 **안 보여야** 함 (20이 차단) |
| 18 | 글 1건·댓글 1건이 **안 보여야** 함 (18이 20을 차단 — 양방향 확인) |
| 17 | 숨김 글 1건 안 보임 + 정상 글 1건은 보임 |
| 12·14·15·16 | 글 5건 정상 표시 |

- 20번으로 조회 시 **14건 중 10건**이 보이면 정상
  (제외 4건 = 19번 글 2건 + 18번 글 1건 + 17번의 숨김 글 1건)
- `nearbyPosts(37.5665, 126.9780, 5000)` — 서울 시청 기준. 해운대 글(331km)은 빠져야 함
- 경복궁 글은 `commentCount: 4`인데 20번에게는 댓글 **3건**만 온다(19번 것이 차단됨).
  §6에서 설명한 정상 동작이다
- 사진 키는 실제 오브젝트가 없어 CDN에서 404다. 키·순서 확인용

## 17. 시작 순서 제안

1. **읽기부터.** `targetPosts`로 spot 상세에 피드를 붙인다. 미인증으로도 되므로 로그인 흐름과
   분리해서 만들 수 있다
2. **커서 페이징**을 붙이고 `hasNextPage`로 무한 스크롤을 확정한다
3. **상호작용**(좋아요·댓글). 멱등이라 낙관적 업데이트가 쉽다
4. **글 작성 — 사진 없이 먼저.** `createPost`에 `photoKeys: []`를 넘기면 된다
5. **사진 업로드**를 마지막에. 3단계 흐름이라 가장 손이 많이 간다
6. 차단·신고·탐색 타일

§1의 차이점과 §3의 업로드 순서, §6의 모더레이션 세 가지가 이 기능에서 가장 자주 어긋나는
지점이다. 막히면 이슈 #45나 PR #46에 남겨 줄 것.
